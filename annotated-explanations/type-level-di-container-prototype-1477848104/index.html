본문으로 건너뛰기

타입 수준 DI 컨테이너를 읽기 위한 하스켈 타입 프로그래밍 해설

원문: Mark Seemann, Type-level DI Container prototype

검토일: 2026-09-20

EPUB 다운로드

이 문서에서 설명하는 내용

Mark Seemann의 원문은 실무에 쓸 의존성 주입(Dependency Injection, DI) 프레임워크를 권하는 글이 아닙니다. 저자 스스로 “상당히 쓸모없는 하스켈 연습”이라고 부르는 실험을 통해, 서로 다른 타입의 값을 한 컨테이너에 담으면서도 다음 두 규칙을 컴파일 시점에 표현합니다.

  • 같은 타입은 한 번만 등록할 수 있습니다.
  • 등록되지 않은 타입은 꺼낼 수 없습니다.

이 구현을 읽기 어려운 이유는 값 수준 코드와 타입 수준 코드가 짧은 구문 안에서 평행하게 움직이기 때문입니다. 특히 kind, 승격된 목록(promoted list), type family, first-class-families의 Exp와 Eval, 사용자 정의 타입 오류, visible type application, Proxy, unsafeCoerce가 한꺼번에 등장합니다.

먼저 이 개념들의 관계를 설명한 뒤, 하이라이트를 원문 순서대로 하나씩 풀이하겠습니다. 원문의 구현은 흥미로운 프로토타입이지만, unsafeCoerce의 안전성을 컴파일러가 직접 증명하는 구조는 아니라는 점도 함께 살펴보겠습니다.

먼저 알아야 할 공통 개념

값, 타입, kind는 서로 다른 층에 있습니다

하스켈에서 값은 타입으로 분류됩니다. 예를 들어 값 "hello"의 타입은 String입니다. 이와 비슷하게 타입 수준의 항은 kind로 분류됩니다. 일반적인 값의 타입인 String, Bool, IO () 등은 보통 Type이라는 kind에 속합니다.

"hello" :: String
String  :: Type

첫 줄의 ::는 값 "hello"의 타입이 String임을 나타냅니다. 둘째 줄의 ::는 타입 String의 kind가 Type임을 나타냅니다. 즉 ::의 기본 뜻은 “왼쪽 항의 분류가 오른쪽이다”이며, 어느 층에서 쓰였는지에 따라 오른쪽이 타입일 수도 있고 kind일 수도 있습니다. GHC의 Kind Signatures 안내서는 (t :: k) 형태를 명시적 kind annotation으로 설명합니다.

원문의 k는 목록이 아니라 kind 변수입니다. PolyKinds 확장을 사용하므로 k를 특정 kind로 고정하지 않고 일반화할 수 있습니다. 반면 [k]는 “원소의 kind가 k인 타입 수준 목록의 kind”이고, ts :: [k]에서 실제 목록은 ts입니다. GHC의 PolyKinds 안내서는 이런 kind 변수의 일반화를 설명합니다.

t  :: k
ts :: [k]

DataKinds는 값 생성자를 타입 수준으로 올립니다

보통 목록에는 빈 목록 생성자 []와 cons 생성자 (:)가 있습니다. DataKinds 확장은 이런 데이터 생성자를 타입 수준으로 승격합니다. 승격된 생성자를 분명히 표시할 때 앞에 작은따옴표를 붙입니다.

  • '[]는 타입 수준의 빈 목록입니다.
  • '[A, B]는 타입 수준 목록 리터럴입니다.
  • A ': As는 타입 수준 목록 As의 앞에 A를 붙입니다.

원문의 컨테이너 타입에는 값이 아니라 등록된 서비스의 타입 목록이 들어갑니다. 예를 들어 Container '[String, Bool]은 String과 Bool이 등록되었다는 정보를 타입에 기록합니다. GHC의 DataKinds 안내서는 '[], 승격된 목록 리터럴, ': 문법을 공식적으로 설명합니다.

컨테이너는 같은 등록 정보를 두 가지 표현으로 유지합니다

원문의 핵심은 런타임 표현과 컴파일 시점 표현을 같은 순서로 유지하는 것입니다.

data Reg where
  Reg :: a -> Reg

data Container (ts :: [k]) where
  UnsafeContainer :: [Reg] -> Container ts

런타임에는 서로 다른 타입의 값을 [Reg]에 담습니다. Reg 생성자의 타입 변수 a는 결과 타입 Reg에 나타나지 않으므로 existentially hidden, 즉 존재적으로 숨겨집니다. Reg x를 꺼낸 코드에서는 x가 어떤 구체 타입인지 알 수 없습니다. GHC의 Existential Quantification 안내서는 패턴 매칭으로 얻는 숨겨진 타입을 임의의 구체 타입과 동일하다고 가정할 수 없음을 설명합니다.

컴파일 시점에는 Container ts의 ts가 같은 등록들의 타입을 같은 순서로 기록합니다. 공개 API인 nil과 insert는 런타임 목록과 타입 수준 목록의 머리에 항상 대응하는 항목을 함께 추가합니다.

런타임:     Reg x : xs
타입 수준:  t ': ts

이 평행 관계는 get이 올바른 위치를 찾고 unsafeCoerce를 제한적으로 사용하는 근거입니다. 그러나 GHC가 [Reg]의 내용과 ts의 대응을 자동으로 증명하는 것은 아닙니다. 숨겨진 UnsafeContainer 생성자와 nil·insert 구현이 불변식(invariant)을 지킨다는 수동 논증에 의존합니다.

first-class-families는 타입 수준 계산을 표현과 평가로 나눕니다

일반적인 type family는 완전히 적용되어야 계산할 수 있기 때문에 값 수준 함수처럼 부분 적용하고 합성하기 어렵습니다. first-class-families 라이브러리는 계산을 나타내는 표현 Exp a와 그 표현을 실제 결과로 축약하는 Eval을 사용해 이 제약을 우회합니다.

type Exp a = a -> Type
type family Eval (e :: Exp a) :: a

이 구조에서 Filter, Null, TyEq 등은 즉시 최종 결과를 내는 값 수준 함수가 아니라 Exp ... kind의 타입 수준 계산 표현을 만듭니다. Eval이 그 표현을 평가합니다. 이 정의는 first-class-families 0.8.2.0의 고정된 소스인 Fcf.Core에서 확인할 수 있습니다.

원문의 중복 검사식은 다음 순서로 읽을 수 있습니다.

type UniqueType (t :: k) (ts :: [k]) = Null =<< Filter (TyEq t) ts
  1. TyEq t는 목록의 각 원소가 t와 같은 타입인지 검사하는 predicate를 만듭니다.
  2. Filter (TyEq t) ts는 ts에서 t와 같은 원소만 남기는 계산을 만듭니다.
  3. =<<는 오른쪽 계산을 평가한 결과를 왼쪽의 Null에 넘깁니다.
  4. 같은 타입이 하나도 없어서 필터 결과가 비어 있으면 Null의 결과는 'True입니다.

여기서 비교하는 것은 서비스 값이나 함수 구현의 동일성이 아니라 타입의 동일성입니다. 서로 다른 두 함수라도 타입이 같으면 이 컨테이너에서는 같은 등록 종류로 취급됩니다.

타입 수준 결과는 제약과 런타임 값으로 각각 연결됩니다

등록 경로에서는 Eval (UniqueType t ts)가 계산한 타입 수준 Boolean을 RequireUniqueType이 Constraint로 바꿉니다. 결과가 'True이면 빈 제약 ()로 통과시키고, 'False이면 TypeError를 발생시킵니다.

조회 경로에서는 FindIndex가 계산한 타입 수준 자연수 Nat을 KnownNat, Proxy, natVal이 런타임 정수로 가져옵니다. 이때 @ 문법으로 어떤 타입 수준 자연수를 반영할지 지정합니다.

따라서 전체 흐름은 다음과 같습니다.

등록: 타입 목록 검색 → Bool → Constraint 또는 TypeError
조회: 타입 목록 검색 → Nat → KnownNat/natVal → 런타임 목록 인덱스

하이라이트와 메모별 해설

t :: k에서 k와 ::는 무엇인가요?

하이라이트: t :: k

원문 문맥:

type UniqueType (t :: k) (ts :: [k]) = Null =<< Filter (TyEq t) ts

사용자 메모: Is k a list? If not, what’s :: ?

k는 목록이 아니라 kind 변수입니다. t :: k는 “타입 수준 항 t의 kind가 k이다”라는 kind annotation입니다. 같은 선언의 ts :: [k]에서 목록인 것은 ts이며, [k]는 그 목록의 kind입니다. 즉 원소 t와 목록 ts의 관계는 다음처럼 대응합니다.

t  :: k      -- 원소 하나
ts :: [k]    -- 같은 kind의 원소들로 이루어진 타입 수준 목록

::는 값 수준에서는 “이 값의 타입”, 타입 수준에서는 “이 타입 수준 항의 kind”를 표시합니다. 이 위치에서는 후자입니다. PolyKinds 때문에 k는 Type 하나에 고정되지 않고 일반화됩니다.

Filter는 무엇을 걸러 내나요?

하이라이트: Filter

원문 문맥:

type UniqueType (t :: k) (ts :: [k]) = Null =<< Filter (TyEq t) ts

Filter는 first-class-families가 제공하는 타입 수준 목록 계산입니다. 이 코드의 Filter (TyEq t) ts는 타입 목록 ts에서 t와 같은 타입만 남깁니다.

예를 들어 설명을 위해 ts가 '[String, Bool, String]이고 t가 String이라고 하면, 필터 결과는 개념적으로 '[String, String]입니다. t가 Int라면 결과는 '[]입니다. 이 결과가 비었는지를 Null이 검사하므로, 빈 결과만 “새 타입을 넣어도 된다”는 'True가 됩니다.

Filter의 결과는 즉시 목록 자체가 아니라 Exp [k] 형태의 계산 표현입니다. 그래서 뒤에서 =<<나 Eval을 통해 평가해야 합니다. 정확한 kind와 재귀 정의는 라이브러리의 Fcf.Data.List에서 확인할 수 있습니다.

TyEq는 값이 아니라 타입을 비교합니다

하이라이트: TyEq

원문 문맥:

type UniqueType (t :: k) (ts :: [k]) = Null =<< Filter (TyEq t) ts

TyEq는 타입 수준 equality predicate입니다. TyEq t를 Filter에 넘기면, 목록의 각 타입이 t와 같은지 'True 또는 'False로 판정하는 조건이 됩니다.

중요한 점은 TyEq가 런타임 서비스 값의 identity나 함수 본문의 동일성을 검사하지 않는다는 것입니다. 타입이 LocalTime -> IO [Reservation]인 서로 다른 함수 두 개를 등록해도 둘째 등록은 거절됩니다. 같은 표현 타입을 서로 다른 역할로 각각 등록해야 한다면 newtype 등으로 타입을 구분하거나, 여러 값을 하나의 목록 타입으로 묶어 등록해야 합니다. TyEq의 정의는 라이브러리의 Fcf.Utils에서 확인할 수 있습니다.

=<<는 타입 수준 계산을 오른쪽에서 왼쪽으로 연결합니다

하이라이트: =<<

원문 문맥:

type UniqueType (t :: k) (ts :: [k]) = Null =<< Filter (TyEq t) ts

여기의 =<<는 값 수준 Control.Monad.=<<가 아니라 first-class-families의 타입 연산자입니다. 역할은 비슷합니다. 오른쪽 계산을 먼저 평가하고 그 결과를 왼쪽 계산에 입력합니다.

data (=<<) :: (a -> Exp b) -> Exp a -> Exp b
type instance Eval (k =<< e) = Eval (k (Eval e))

따라서 원문의 식은 개념적으로 “Filter (TyEq t) ts를 평가한 목록을 Null에 넘겨, 그 목록이 비었는지 계산한다”라고 읽습니다. 정확한 정의는 라이브러리의 Fcf.Combinators에 있습니다.

Constraint는 계산 결과를 함수의 전제 조건으로 만듭니다

하이라이트: Constraint

원문 문맥:

type family RequireUniqueType (result :: Bool) (t :: k) :: Constraint where

Constraint는 값 타입이 아니라 제약의 kind입니다. RequireUniqueType ... :: Constraint는 이 type family의 결과를 함수 시그니처의 => 왼쪽에 놓을 수 있다는 뜻입니다. Constraint의 공식 정의와 용도는 Data.Kind에 설명되어 있습니다.

이 family는 'True일 때 ()를 돌려주는데, 여기의 ()는 값 수준 unit 값이 아니라 충족할 조건이 없는 빈 constraint tuple입니다. 'False일 때는 TypeError를 돌려주어 타입 검사를 실패시킵니다. 즉 타입 수준 Boolean을 “통과” 또는 “컴파일 오류”라는 API 규칙으로 바꾸는 경계입니다.

:<>:는 타입 오류 메시지 조각을 이어 붙입니다

하이라이트: :<>:

원문 문맥:

      'Text "Attempting to add the type " ':<>:
      'ShowType t ':<>:
      'Text " to the container, but this container already contains that type.")

:<>:는 ErrorMessage 두 개를 같은 줄에서 연결하는 승격된 생성자입니다. 값 수준 문자열의 (++)나 일반적인 (<>)가 아닙니다. 이 코드에서는 고정된 앞 문장, 실제 타입 표기, 고정된 뒷 문장을 하나의 컴파일 오류로 조립합니다.

줄바꿈을 만드는 별도 생성자 :$$:도 있지만 원문에서는 사용하지 않습니다. TypeError, ErrorMessage, :<>:의 공식 타입은 GHC.TypeLits에서 확인할 수 있습니다.

ShowType은 Show 인스턴스를 요구하지 않습니다

하이라이트: ShowType

원문 문맥:

      'ShowType t ':<>:

'ShowType t는 컴파일러가 타입 t를 오류 메시지 안에 타입 표기로 렌더링하게 하는 ErrorMessage 생성자입니다. 값에 show를 호출하는 것이 아니며, Show t 제약도 필요하지 않습니다.

예를 들어 중복된 타입이 LocalTime -> IO [Reservation]이라면 그 타입 표기가 오류 메시지 가운데에 들어갑니다. 앞뒤의 'Text는 고정 문자열을 만들고, ':<>:가 세 조각을 연결합니다. 이 생성자의 정의도 GHC.TypeLits에 있습니다.

일반 type과 type family는 어떤 차이가 있나요?

하이라이트: type family

원문 문맥:

type family RequireUniqueType (result :: Bool) (t :: k) :: Constraint where

앞에서 본 UniqueType은 일반 type synonym입니다.

type UniqueType (t :: k) (ts :: [k]) = Null =<< Filter (TyEq t) ts

이 선언은 오른쪽의 타입 수준 계산 표현에 이름을 붙입니다. 반면 RequireUniqueType은 입력 모양에 따라 서로 다른 식으로 축약되는 closed type family입니다.

RequireUniqueType  'True t = ()
RequireUniqueType 'False t = TypeError (...)

closed type family는 관련 식을 하나의 where 절에 모으며, GHC는 겹칠 수 있는 식을 위에서 아래 순서로 고려합니다. 원문에서는 가능한 Boolean 두 경우를 모두 다뤄 중복 검사 결과를 제약으로 바꿉니다. 자세한 축약 규칙은 GHC의 Type Families 안내서에서 확인할 수 있습니다.

RequireUniqueType의 k도 목록이 아닙니다

하이라이트: k

원문 문맥:

type family RequireUniqueType (result :: Bool) (t :: k) :: Constraint where

여기의 k도 앞의 t :: k에서와 같은 kind 변수입니다. 오류 메시지에 표시할 대상 t가 어떤 kind에 속하는지를 나타냅니다. k 자체가 목록이라는 뜻은 없습니다.

이 선언에는 ts :: [k]가 없으므로 목록을 직접 다루지도 않습니다. UniqueType이 계산한 Boolean과 검사 대상 t만 받아, 그 타입을 오류 메시지에 넣을지 결정합니다. PolyKinds 덕분에 이 family도 Type에 속한 타입만으로 불필요하게 제한되지 않습니다.

Eval은 조립된 타입 수준 계산을 실제 결과로 축약합니다

하이라이트: Eval

원문 문맥:

insert :: RequireUniqueType (Eval (UniqueType t ts)) t
       => t -> Container ts -> Container (t ': ts)

UniqueType t ts는 최종 Boolean 자체가 아니라 Exp Bool kind의 계산 표현입니다. Eval은 그 표현을 실제 'True 또는 'False로 축약합니다. 그 결과를 RequireUniqueType에 넘겨 insert가 허용되는지 결정합니다.

같은 Eval은 조회 경로에서도 사용됩니다.

type IsMember t ts = KnownNat (Eval (FindElem t ts))

여기서는 FindElem t ts라는 계산 표현을 실제 타입 수준 자연수로 축약합니다. 즉 Eval은 특정 중복 검사 전용 함수가 아니라 first-class-families 표현 전반의 평가기인 open type family입니다. 정확한 정의는 Fcf.Core에 있습니다.

':는 타입 수준 목록의 앞에 새 타입을 붙입니다

하이라이트: ':

원문 문맥:

       => t -> Container ts -> Container (t ': ts)

':는 승격된 목록 cons 생성자입니다. insert의 반환 타입 Container (t ': ts)는 기존 등록 타입 목록 ts의 앞에 새 타입 t가 추가되었음을 뜻합니다.

함수 본문에서도 같은 방향으로 런타임 목록을 갱신합니다.

insert x (UnsafeContainer xs) = UnsafeContainer (Reg x : xs)

타입 수준에서는 t ': ts, 런타임에서는 Reg x : xs가 됩니다. 두 목록의 순서가 함께 유지되기 때문에 나중에 타입 수준에서 계산한 인덱스로 런타임 값을 찾을 수 있습니다. 이 대응이 깨지면 마지막의 unsafeCoerce를 정당화할 근거도 깨집니다.

'[는 값이 아니라 타입들의 목록을 시작합니다

하이라이트: '[

원문 문맥:

container :: Container '[LocalTime -> IO [Reservation], Reservation -> IO ()]

바깥의 '[...]는 DataKinds로 승격된 타입 수준 목록 리터럴입니다. 이 목록의 원소는 서비스 값이 아니라 다음 두 타입입니다.

  • LocalTime -> IO [Reservation]
  • Reservation -> IO ()

첫 번째 원소 안의 [Reservation]은 평범한 값 목록 타입입니다. 따라서 한 줄 안에 서로 다른 층의 목록이 함께 있습니다.

'[ ... ]        등록된 서비스 타입들의 타입 수준 목록
[Reservation]   Reservation 값들의 평범한 목록 타입

앞의 작은따옴표가 이 차이를 눈에 보이게 합니다. 관련 승격 규칙은 GHC의 DataKinds 안내서에 설명되어 있습니다.

@는 값 인자가 아니라 타입 인자를 명시합니다

하이라이트: @

원문 문맥:

findElem = fromIntegral . natVal $ Proxy @(Eval (FindElem t ts))

@는 visible type application 문법입니다. 보통 컴파일러가 추론할 타입 인자를 소스 코드에서 직접 지정합니다. 여기서는 Proxy의 phantom type parameter가 Eval (FindElem t ts)임을 지정합니다.

같은 원리는 다음 호출에도 쓰입니다.

get (UnsafeContainer xs) = unReg $ xs !! findElem @t @ts

findElem의 결과는 단지 Int이므로, 결과만 봐서는 어떤 t와 ts의 인덱스를 계산해야 하는지 알 수 없습니다. @t @ts가 findElem :: forall t ts. ...의 타입 인자를 순서대로 명시합니다. 명시적 forall과 visible type application의 관계는 GHC의 Type Applications 안내서에 설명되어 있습니다.

Proxy는 자연수를 저장하지 않고 타입 자리만 제공합니다

하이라이트: Proxy

원문 문맥:

findElem = fromIntegral . natVal $ Proxy @(Eval (FindElem t ts))

Proxy (t :: k)는 실제 데이터를 담지 않고 phantom type parameter t만 갖는 타입입니다. natVal은 KnownNat n 제약 아래에서 proxy n 형태의 값을 받으므로, 실제 n 타입의 값을 만들지 않고도 “어느 타입 수준 자연수 n을 런타임 정수로 가져올 것인가”를 지정해야 합니다. 그 자리를 Proxy @n이 제공합니다.

Proxy 자체가 인덱스를 계산하거나 저장하지는 않습니다. FindElem과 Eval이 타입 수준 인덱스를 계산하고, KnownNat 인스턴스가 그 자연수의 런타임 표현을 제공하며, natVal이 값을 꺼냅니다. Proxy의 데이터 없는 정의는 Data.Proxy, KnownNat과 natVal의 관계는 GHC.TypeLits에서 확인할 수 있습니다.

unsafeCoerce의 안전성은 모듈 불변식에 달려 있습니다

하이라이트: unsafeCoerce

원문 문맥:

get (UnsafeContainer xs) = unReg $ xs !! findElem @t @ts
  where unReg (Reg x) = unsafeCoerce x

Reg x를 패턴 매칭하면 x의 구체 타입은 존재적으로 숨겨져 있습니다. get이 약속한 반환 타입 t와 그 숨겨진 타입이 같다는 사실을 GHC가 이 패턴만으로 알아낼 수 없으므로, 원문은 unsafeCoerce x로 타입 검사기를 우회합니다.

이 함수가 본질적으로 안전한 것은 아닙니다. unsafeCoerce :: a -> b는 임의 타입 사이의 변환을 허용하며, 실제 표현의 동등성을 다른 논리로 보장하지 못하면 결과는 정의되지 않을 수 있습니다. 공식 Unsafe.Coerce 문서도 안전한 사용에는 별도의 동등성 근거가 필요하다고 설명합니다.

이 프로토타입이 의존하는 불변식은 다음과 같습니다.

  1. 런타임 [Reg]와 타입 수준 ts의 길이가 같습니다.
  2. 같은 인덱스의 Reg 내부 값과 ts 원소의 실제 타입이 같습니다.
  3. 공개 insert로 만든 ts에는 같은 타입이 두 번 나타나지 않습니다.

nil이 빈 두 표현을 함께 만들고, insert가 양쪽 머리에 같은 등록을 함께 추가하며, UnsafeContainer 생성자를 외부에 공개하지 않기 때문에 정상적인 공개 API 사용은 이 불변식을 보존합니다. IsMember는 요청 타입의 인덱스가 존재하도록 제한하므로 !!의 범위 밖 접근도 막으려 합니다.

하지만 구현을 수정하면서 두 목록의 순서가 달라지거나 숨겨진 생성자를 잘못 사용하면, 컴파일러가 이를 막아 주지 못합니다. 따라서 정확한 평가는 “외부에는 타입 안전한 API를 제공하기 위해, 모듈 내부의 작은 unsafe core가 수동으로 유지되는 불변식에 의존한다”입니다.

원문의 설계를 한 흐름으로 다시 보기

등록할 때는 새 타입이 기존 타입 목록에 없는지 계산합니다.

TyEq로 같은 타입 판정
→ Filter로 같은 타입만 남김
→ Null로 결과가 비었는지 판정
→ Eval로 Bool 계산
→ RequireUniqueType으로 Constraint 또는 TypeError 생성

등록이 성공하면 값 수준 목록과 타입 수준 목록의 앞에 같은 등록을 추가합니다.

Reg x : xs
t ': ts

조회할 때는 요청 타입의 위치를 타입 수준에서 찾고 그 자연수를 런타임으로 가져옵니다.

FindIndex로 위치 계산
→ FromMaybe로 Nat 추출
→ Eval로 계산 완료
→ KnownNat와 Proxy, natVal로 런타임 Int 획득
→ 같은 위치의 Reg 조회
→ 불변식을 근거로 unsafeCoerce

이 설계가 보장하는 고유성은 “같은 서비스 객체를 두 번 넣지 않는다”가 아니라 “같은 타입을 두 번 넣지 않는다”입니다. 또한 Container '[String, Bool, String]이라는 타입 표기 자체가 문법적으로 금지되는 것은 아닙니다. 숨겨진 생성자와 공개 nil·insert를 정상적으로 사용해서는 그런 컨테이너 값을 만들 수 없다는 API 수준의 보장입니다.

정리

원문의 컨테이너는 런타임의 이질적 값 목록 [Reg]과 컴파일 시점의 타입 목록 ts를 같은 순서로 유지합니다. DataKinds와 PolyKinds가 타입 목록의 표현을 가능하게 하고, first-class-families의 Filter, TyEq, =<<, Eval이 중복 검사와 인덱스 검색을 조립합니다. Constraint, TypeError, ShowType, :<>:는 그 계산 결과를 읽기 쉬운 컴파일 오류로 바꿉니다. @, Proxy, KnownNat, natVal은 타입 수준 인덱스를 런타임 목록 조회에 연결합니다.

가장 중요한 주의점은 unsafeCoerce입니다. 이 구현의 안전성은 unsafeCoerce 자체나 자동 증명에서 나오지 않고, 숨겨진 생성자와 공개 API가 두 표현의 길이·순서·타입 대응을 계속 보존한다는 모듈 불변식에서 나옵니다. 따라서 이 코드는 타입 수준 프로그래밍의 여러 기법을 한데 보여 주는 좋은 학습용 프로토타입이지만, unsafe 경계를 포함한 내부 구현을 바꿀 때는 그 불변식을 다시 증명해야 합니다.
