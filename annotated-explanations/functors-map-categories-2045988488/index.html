Haskell의 종류(kind)로 범주 읽기: Cat k, (:~:), Refl 해설

해설 대상 원문: Iceland_jack, “Functors map categories”

검토일: 2026-11-17

이 해설의 EPUB 전자책 판: EPUB 파일 내려받기

이 문서에서 설명하는 내용

원문은 Reddit 사용자 Iceland_jack이 2023년 10월 27일 r/haskell에 올린 글 「Functors map categories」입니다. 글의 중심 주장은 "함자(functor)를 쓴다는 것은 범주(category)를 대응시키는 것"이라는 관점입니다. 저자는 타입 생성자의 인자마다, 그리고 결과마다 범주를 하나씩 짝지을 수 있다고 봅니다. 그리고 fmap, contramap, bimap, dimap 같은 사상 함수의 타입을 보면 각 인자가 어떤 범주로 바뀌는지 읽을 수 있다고 설명합니다. 함자 법칙(functor laws)도 "함자는 범주의 구조, 곧 항등 사상 id와 합성 (.)을 보존한다"는 사실에서 나온다고 말합니다.

남겨 주신 메모 다섯 개는 모두 글 앞부분의 세 지점에 모여 있습니다.

  • 함자 F의 원천 범주로 나열된 (->), (:~:) @Type, (<-)가 무엇인지에 관한 질문입니다.
  • Cat의 정의 두 줄(type Cat :: Type -> Type, type Cat k = k -> k -> Type)에 관한 질문 세 개입니다.
  • 동등성 타입 (:~:)의 생성자 Refl에 관한 질문입니다.

독자 이해에 관한 추정: Cat을 "종류"라고 부르신 점, type Cat k = …가 귀납적 정의인지 물으신 점, 두 인자의 종류가 왜 같아야 하는지 물으신 점을 보면, (1) 종류와 타입의 관계, (2) 타입 동의어(type synonym)라는 장치, (3) Haskell에서 범주를 "두 인자를 받는 타입 생성자"로 표현하는 관례가 아직 익숙하지 않으신 것으로 보입니다. 또 Refl이 "where 절 안에서 정의되었다"는 표현은 GADT 문법의 where를 함수의 지역 정의용 where로 읽으셨을 가능성을 보여 줍니다. 반면 (Type->Type) -> Type -> Type처럼 괄호를 정확히 친 종류를 직접 쓰신 것을 보면, 화살표로 된 종류를 읽고 쓰는 일 자체에는 익숙하신 것으로 추정합니다.

그래서 이 문서는 먼저 공통 개념 다섯 가지를 설명하고, 그다음 원문에 나오는 순서대로 각 하이라이트와 메모에 답합니다.

먼저 알아야 할 공통 개념

종류(kind)는 타입의 타입입니다

값에 타입이 있듯이 타입에도 "타입"이 있으며, 이것을 종류(kind)라고 부릅니다. 값을 가질 수 있는 보통의 타입은 종류 Type을 가집니다. Data.Kind 문서는 Type을 "들림(lifted) 값을 가지는 타입들의 종류(The kind of types with lifted values)"라고 설명하고 Int :: Type을 예로 듭니다. GHC에는 값이 있어도 종류가 Type이 아닌 비들림(unlifted) 타입도 있지만, 이 글을 읽는 데에는 필요하지 않으므로 이 문서에서는 다루지 않습니다(base Data.Kind 문서).

타입 수준의 대상 종류 읽는 법
Int, Bool, [Int] Type 값을 가지는 보통의 타입입니다.
Maybe, [] Type -> Type 타입 하나를 받아 타입을 만듭니다.
(->), Either Type -> Type -> Type 타입 둘을 받아 타입을 만듭니다.

GHCi에서 종류를 출력하면 Type 대신 *가 보이기도 합니다. *는 Type의 옛 표기입니다.

중요한 점이 하나 더 있습니다. 현대 GHC에서는 타입과 종류가 같은 세계에 있습니다. GHC 사용자 안내서는 "GHC 안에서는 타입과 종류를 구별하지 않는다"고 하고, Type의 타입은 그냥 Type이라고 설명합니다(GHC 사용자 안내서, 종류 다형성 개요). 따라서 Type -> Type -> Type이라는 종류도 그 자체로 종류 Type을 가지는 하나의 타입 수준 표현입니다. 이 사실이 뒤에서 Cat :: Type -> Type을 읽을 때 핵심이 됩니다.

DataKinds 확장을 켜면 보통의 자료형도 종류로 쓸 수 있습니다. GHC는 모든 자료형을 종류로, 그 값 생성자를 타입 생성자로 승격합니다(GHC 사용자 안내서, DataKinds). 그래서 Bool은 'False와 'True라는 두 타입을 가진 종류가 되고, 타입 수준 자연수의 종류 Nat에는 0, 1, 36 같은 리터럴 타입이 속합니다. 원문 뒷부분의 Cat Nat, Cat Bool은 이런 종류를 가리킵니다.

독립 종류 시그니처와 타입 동의어

원문의 Cat 정의는 서로 다른 두 선언으로 되어 있습니다.

type Cat :: Type -> Type
type Cat k = k -> k -> Type

첫 줄은 독립 종류 시그니처(standalone kind signature)입니다. 함수 정의 위에 f :: Int -> Int라는 타입 시그니처를 따로 쓰듯이, 타입 수준 선언 위에 그 종류를 따로 적는 문법입니다. GHC 8.10.1에서 StandaloneKindSignatures 확장으로 도입되었고 GHC2021 언어 판에 포함되어 있습니다(GHC 사용자 안내서, StandaloneKindSignatures). 이 시그니처는 선택 사항입니다. GHC 9.10.3에서 시그니처를 빼고 둘째 줄만 선언해도 GHC가 같은 종류 Type -> Type을 추론하는 것을 확인했습니다. 따라서 첫 줄은 문서화와 검사를 위한 것입니다.

둘째 줄은 매개변수가 하나인 타입 동의어(type synonym)입니다. Haskell 2010 보고서는 타입 동의어를 "편리하지만 순전히 구문적인 장치"라고 정의합니다. 또한 대수적 자료형이 중간에 끼지 않는 한 재귀할 수 없고, 부분 적용할 수 없다고 규정합니다(Haskell 2010 보고서 4.2.2절). 즉 Cat X라고 쓰면 컴파일러는 이를 곧바로 X -> X -> Type으로 바꿔 쓴다고 생각하시면 됩니다. Cat은 Maybe처럼 새 타입을 만드는 타입 생성자가 아니라 긴 표현의 약어입니다.

Haskell에서 범주는 "두 인자를 받는 타입 생성자"로 표현합니다

수학에서 범주는 대상(object)들과 대상 사이의 사상(morphism)들로 이루어집니다. 두 대상 x, y의 쌍마다 x에서 y로 가는 사상의 모임이 있고, 각 대상에는 항등 사상이 있으며, 이어지는 사상은 합성할 수 있습니다. 합성은 결합 법칙과 단위 법칙을 만족해야 합니다(nLab, category; Bartosz Milewski, 「Category: The Essence of Composition」).

Haskell은 이 구조를 다음과 같이 옮깁니다. 범주 하나를 타입 생성자 cat 하나로 나타내고, cat a b를 "대상 a에서 대상 b로 가는 사상들의 타입"으로 읽습니다. 표준 라이브러리 Control.Category의 클래스가 정확히 이 모양입니다(base Control.Category 문서).

class Category (cat :: k -> k -> Type) where
  id  :: cat a a
  (.) :: cat b c -> cat a b -> cat a c

위 코드는 문서에 나온 클래스 선언과 두 메서드의 타입을 간략히 옮겨 적은 것입니다. 문서에는 각 메서드의 forall과 종류 주석이 더 자세히 적혀 있습니다. 여기서 대응 관계는 다음과 같습니다.

범주론의 개념 Haskell에서의 표현
대상 종류 k를 가지는 타입들
x에서 y로 가는 사상들의 모임 타입 cat x y, 그 값 하나하나가 사상입니다.
항등 사상 id :: cat a a
합성 (.) :: cat b c -> cat a b -> cat a c

원문의 type Cat k = k -> k -> Type은 바로 이 cat의 종류 k -> k -> Type에 이름을 붙인 것입니다. 그래서 "X :: Cat k"는 "X는 대상의 종류가 k인 범주를 나타내는 타입 생성자"라고 읽으면 됩니다. base에 이미 있는 Category 인스턴스로는 함수 (->), 뒤집힌 함수 Op, 동등성 (:~:), Kleisli m 등이 있습니다(같은 문서의 인스턴스 목록).

교육적 단순화: 이 문서는 (->)를 "Haskell 타입을 대상으로, 함수를 사상으로 하는 범주"라고 부릅니다. 무한 루프나 undefined 같은 값까지 엄밀히 따지면 세부 사항이 더 복잡하지만, 원문과 메모를 이해하는 데에는 이 모델로 충분합니다.

함자는 대상과 사상을 함께 옮기며, 원문은 인자마다 범주를 하나씩 둡니다

범주론에서 함자는 범주 사이의 대응입니다. 함자는 대상을 대상으로, 사상을 사상으로 옮기며 항등 사상과 합성을 보존합니다. Haskell의 Functor에서는 타입 생성자가 대상(타입)을 옮기고 fmap이 사상(함수)을 옮깁니다(Bartosz Milewski, 「Functors」).

원문은 이 그림을 인자가 여럿인 타입 생성자로 넓힙니다. 원문 해석으로 정리하면 읽는 방법은 다음과 같습니다.

  • 타입 생성자 F의 인자 하나하나는 "대상"입니다.
  • 각 인자 자리마다 "그 인자를 어떤 종류의 사상으로 바꿀 수 있는가"를 정하는 범주가 하나 있습니다. 이것이 원천 범주(source category)입니다.
  • 결과 자리에도 범주가 하나 있습니다. 이것이 목표 범주(target category)입니다.
  • 사상 함수 mapF는 인자마다 해당 범주의 사상을 하나씩 받아서 목표 범주의 사상 하나를 돌려줍니다.

예를 들어 보통의 fmap :: (a -> a') -> (f a -> f a')은 인자 자리의 범주가 (->), 결과 자리의 범주도 (->)인 경우입니다. 원문은 이를 FunctorOf (->) (->) f라고 표기합니다. FunOf, FunctorOf, BifunctorOf, Nat 같은 이름은 저자가 이 글과 예전 글에서 쓰는 표기법이며 base에 들어 있는 정의가 아닙니다.

GADT 문법과 타입 동등성 (:~:)

data T a where로 시작해서 생성자마다 타입 시그니처를 적는 선언은 GADT 문법(GADT syntax)입니다. GHC 사용자 안내서의 해당 절 제목도 "명시적인 생성자 시그니처로 자료형 선언하기(Declaring data types with explicit constructor signatures)"입니다. 안내서는 data T a where 머리의 타입 변수는 생성자 시그니처 안에서 유효 범위가 없고, 각 생성자의 시그니처는 서로 독립적이며 평소처럼 암묵적으로 전칭 한정된다고 말합니다(GHC 사용자 안내서, GADT 문법). 여기의 where는 생성자 목록을 여는 키워드일 뿐이며, 함수 정의 뒤에 지역 정의를 붙이는 where와는 이름만 같습니다.

생성자마다 결과 타입을 따로 정할 수 있는 자료형을 GADT(generalised algebraic data type)라고 부릅니다. 안내서는 "GADT의 핵심은 패턴 매칭이 타입 정제(type refinement)를 일으킨다는 점"이라고 요약합니다(GHC 사용자 안내서, GADTs). 어떤 생성자와 일치했는지 알게 되면 그 분기 안에서 컴파일러가 타입에 관한 추가 사실을 알게 된다는 뜻입니다.

이 성질을 이용하는 가장 유명한 GADT가 타입 동등성 (:~:)입니다. base의 Data.Type.Equality 모듈이 이를 "명제적 동등성(propositional equality)"이라는 이름으로 제공합니다. 문서에 따르면 a :~: b 타입에 종료하는 값이 있으면 a와 b는 같은 타입입니다. 그리고 Refl 생성자로 패턴 매칭하면 그 본문 안에서 컴파일러가 a ~ b를 압니다(base Data.Type.Equality 문서). 여기서 a ~ b는 "a와 b가 같은 타입이다"라는 타입 동등성 제약(equality constraint)입니다. 또 data a :~: b처럼 연산자 기호로 된 타입 이름을 중위로 선언하고 쓰려면 TypeOperators 확장이 필요합니다(GHC 사용자 안내서, TypeOperators). 원문은 이 정의를 Cat k 시그니처와 함께 다시 적어 보여 줍니다.

하이라이트와 메모별 해설

(->), (:~:) @Type, (<-)는 각각 어떤 범주인가요

하이라이트: (->), (:~:) @Type, (<-)

원문 문맥:

The functor F maps three source categories (->), (:~:) @Type, (<-) to a target category (->) using the mapping function mapF:

사용자 메모: “What do these represent?”

이 세 표현은 함자 F의 세 인자 각각에 배정된 원천 범주입니다. 각 범주는 앞에서 설명한 관례대로 "사상들의 타입을 만드는 두 인자 타입 생성자"로 적혀 있습니다. 바로 아래에 나오는 원문의 mapF 타입을 함께 보면 의미가 분명해집니다.

mapF :: (a -> a') -> (b :~: b') -> (c <- c') -> (F a b c -> F a' b' c')

mapF의 첫째, 둘째, 셋째 인자의 타입이 각각 (->) a a', (:~:) b b', (<-) c c'입니다. 즉 세 범주에서 사상을 하나씩 받습니다. 결과 F a b c -> F a' b' c'은 목표 범주 (->)의 사상, 곧 보통의 함수입니다. 이를 표로 정리하면 다음과 같습니다.

자리 범주 mapF가 받는 사상 의미
첫째 인자 a (->) a -> a' 보통의 함수로 바꿉니다. 공변(covariant) 자리입니다.
둘째 인자 b (:~:) @Type b :~: b' b와 b'가 같은 타입이라는 증거만 받습니다. 사실상 바꿀 수 없는 자리입니다.
셋째 인자 c (<-) c <- c', 즉 c' -> c 방향의 함수 화살표를 거꾸로 받습니다. 반변(contravariant) 자리입니다.
결과 (->) F a b c -> F a' b' c' 결과는 보통의 함수로 나옵니다.

세 범주를 하나씩 보겠습니다.

먼저 (->)는 Haskell 타입을 대상으로, 함수를 사상으로 하는 범주입니다. base에 Category (->) 인스턴스가 있으며 id는 항등 함수, (.)는 함수 합성입니다(base Control.Category 문서). 첫째 인자를 이 범주로 옮긴다는 것은 fmap처럼 a -> a' 함수 하나로 a 자리를 바꿀 수 있다는 뜻입니다.

다음으로 (:~:) @Type은 동등성 범주입니다. 대상은 타입이고, a에서 b로 가는 사상은 a :~: b의 값입니다. 그런데 이 타입의 유일한 생성자 Refl :: a :~: a는 양쪽이 같을 때만 만들 수 있습니다. 따라서 이 범주에는 각 대상의 항등 사상만 있습니다. 이런 범주를 이산 범주(discrete category)라고 부릅니다(nLab, discrete category). base에도 Category (:~:) 인스턴스가 있습니다. 둘째 인자가 이 범주에 배정되었다는 것은 원문 해석으로 "mapF는 둘째 인자를 실제로는 바꾸지 못하고, 같은 타입에서 같은 타입으로만 옮긴다"는 뜻입니다.

뒤에 붙은 @Type은 가시적 종류 적용(visible kind application)입니다. (:~:)는 종류 다형적이어서 원문 표기로 Cat k, 곧 어떤 종류 k에 대해서든 쓸 수 있습니다. @Type은 그 k를 Type으로 고정합니다. F의 둘째 인자가 종류 Type이므로 그 자리의 범주도 Cat Type이어야 하기 때문입니다.

마지막으로 (<-)는 (->)의 반대 범주(opposite category)입니다. 대상은 같고 화살표 방향만 뒤집힌 범주로, 반대 범주의 x에서 y로 가는 사상은 원래 범주의 y에서 x로 가는 사상과 같습니다(nLab, opposite category). 그래서 c <- c'는 c' -> c 방향의 함수를 뜻합니다. 반변 함자는 반대 범주에서 출발하는 보통의 함자라는 설명도 같은 생각입니다(Bartosz Milewski, 「Functoriality」). 원문 뒷부분의 contramap :: (a <- a') -> (c a -> c a')이 이 표기를 씁니다. base의 contramap :: (a' -> a) -> f a -> f a'과 같은 내용입니다.

정리하면, 이 목록은 "F의 첫째 인자는 함수로, 둘째 인자는 동등성으로만, 셋째 인자는 거꾸로 된 함수로 바꿀 수 있다"는 정보를 범주의 이름으로 적은 것입니다. 원문의 F는 설명을 위해 가정한 임의의 타입 생성자이며 구체적인 정의가 없습니다. 그래서 세 범주가 실제로 어떻게 쓰이는지 보이기 위해 구체적인 F를 하나 만들어 보겠습니다. 이 문서가 새로 만든 예제이며 원문 코드가 아닙니다. GHC 9.10.3에서 module … where 아래에 두고 -Wall로 검사했을 때 경고 없이 통과했습니다. (<-)는 실제 코드로 쓸 수 없으므로 셋째 인자는 c' -> c로 적었습니다.

{-# LANGUAGE GADTs, TypeOperators #-}
import Data.Type.Equality ((:~:) (..))

data F a b c = F a (b -> b) (c -> Int)

mapF :: (a -> a') -> (b :~: b') -> (c' -> c) -> (F a b c -> F a' b' c')
mapF f Refl g (F x h k) = F (f x) h (k . g)

세 자리를 하나씩 보면 다음과 같습니다.

  • 첫째 인자 a는 값 x :: a로 들어 있습니다. 그래서 f :: a -> a'를 그대로 적용해 f x :: a'를 만들 수 있습니다. 이것이 (->) 범주의 사상입니다.
  • 둘째 인자 b는 b -> b 안에서 입력과 출력 양쪽에 나옵니다. 따라서 보통의 함수 하나로는 이 자리를 바꿀 수 없습니다. 대신 Refl로 패턴 매칭하면 그 분기에서 b와 b'가 같아지므로 h를 그대로 돌려줄 수 있습니다. 이것이 (:~:) 범주의 사상입니다.
  • 셋째 인자 c는 c -> Int의 입력 자리에 있습니다. 그래서 g :: c' -> c를 앞에 합성해 k . g :: c' -> Int를 만듭니다. 화살표를 거꾸로 받는 (<-) 범주의 사상입니다.
  • 결과 F a b c -> F a' b' c'은 보통의 함수, 곧 목표 범주 (->)의 사상입니다.

참고: 실제 코드로 옮길 때의 세부 사항. GHC 사용자 안내서는 타입 적용 문법을 종류 변수에도 쓸 수 있으나, 사용자가 명시한(specified) 변수에만 적용할 수 있고 추론된(inferred) 변수에는 적용할 수 없다고 설명합니다(GHC 사용자 안내서, TypeApplications). 이 문서를 위해 GHC 9.10.3과 base 4.20에서 확인한 결과, 원문처럼 type (:~:) :: Cat k 시그니처로 직접 정의한 동등성 타입에는 @Type을 적용할 수 있었습니다. 그러나 base의 Data.Type.Equality.(:~:)에 @Type을 적용하면 오류가 났습니다. base 쪽 종류 변수가 추론된 변수(forall {k}.)로 표시되기 때문입니다. base의 것을 쓸 때에는 (:~:) :: Cat Type처럼 종류 주석을 붙이면 됩니다. 이후 버전의 동작은 확인하지 않았습니다. 또 <-는 Haskell 2010의 예약 연산자이므로(Haskell 2010 보고서 2.4절) type a <- b = b -> a라고 선언하면 GHC 9.10.3은 구문 오류를 냅니다. base에서 (<-)와 같은 역할을 하는 타입은 Data.Functor.Contravariant의 newtype Op a b = Op { getOp :: b -> a }입니다. 문서는 이를 "뒤집힌 함수 화살표(dual function arrows)"라고 부르고 Category Op 인스턴스를 제공합니다(base Data.Functor.Contravariant 문서).

Cat은 종류인가요: type Cat :: Type -> Type 읽기

하이라이트: type Cat :: Type -> Type

원문 문맥:

For the following categories

type Cat :: Type -> Type
type Cat k = k -> k -> Type

(->)  :: Cat Type
(<-)  :: Cat Type
(:~:) :: Cat k

사용자 메모: “Is it correct to say that Cat is a kind that maps from Type to Type?”

절반은 맞고 절반은 바로잡아야 합니다. "Type에서 Type으로 간다"는 부분은 맞지만, "Cat이 종류다"라는 부분은 정확하지 않습니다.

이 줄은 독립 종류 시그니처이므로 "Cat의 종류는 Type -> Type이다"라는 뜻입니다. f :: Int -> Int가 "f는 Int -> Int라는 타입이다"가 아니라 "f는 Int -> Int라는 타입을 가진 함수다"라는 뜻인 것과 같습니다. 따라서 더 정확한 표현은 다음과 같습니다.

Cat은 인자 하나를 받는 타입 수준의 함수(타입 동의어)이며, 그 자신의 종류가 Type -> Type입니다.

그렇다면 Cat은 실제로 무엇을 무엇으로 보낼까요. 둘째 줄 type Cat k = k -> k -> Type을 보면 인자 k도 종류이고 결과 k -> k -> Type도 종류입니다. 그러므로 Cat은 종류 하나를 받아서 종류 하나를 돌려주는 함수입니다. 대상의 종류 k를 받아서 "그런 대상을 가지는 범주의 종류"를 돌려줍니다.

그런데 왜 종류에서 종류로 가는 함수의 종류가 Type -> Type으로 적힐까요. 앞에서 설명했듯 GHC에서는 Type :: Type이므로 Type, Type -> Type, Nat, Bool 같은 종류도 모두 종류 Type을 가지는 타입 수준 표현이기 때문입니다. 이 문서를 위해 GHC 9.10.3의 GHCi에서 확인한 결과는 다음과 같습니다. *는 Type의 옛 표기입니다.

Cat :: * -> *
Cat Type :: *
= * -> * -> *
Cat (Type -> Type) :: *
= (* -> *) -> (* -> *) -> *

Maybe :: Type -> Type과 비교하면 차이가 잘 보입니다. 두 이름의 종류는 똑같이 Type -> Type입니다. 하지만 Maybe Int는 값이 있는 보통의 타입입니다. 반면 Cat Type은 Type -> Type -> Type이라는 종류이며, 그 안에 직접 값이 들어 있지 않습니다. Cat Type에 속하는 것은 (->)나 Op 같은 타입 생성자입니다. 종류만 보아서는 두 경우가 구별되지 않는데, 이것이 "타입과 종류를 구별하지 않는다"는 설계의 결과입니다.

원문 문맥의 아래 세 줄도 같은 방식으로 읽으면 됩니다. (->) :: Cat Type은 "(->)의 종류는 Cat Type, 곧 Type -> Type -> Type이다"라는 뜻입니다. 따라서 (->)는 대상이 종류 Type인 범주입니다. 원문 해석으로 보면 이 세 줄은 선언이 아니라 "이런 것들이 범주의 예"라는 설명용 목록입니다. (<-)는 앞 절에서 말했듯 실제 코드로 선언할 수 없고, (:~:) :: Cat k의 k는 "어떤 종류든"을 뜻합니다.

마지막으로 Cat은 타입 동의어이므로 항상 인자를 채워 Cat Type, Cat k처럼 써야 합니다. 인자 없이 Cat만 단독으로 쓰면 GHC가 오류를 냅니다.

type Cat k는 귀납적 정의인가요

하이라이트: type Cat k

원문 문맥:

type Cat k = k -> k -> Type

사용자 메모: “Is this an inductive definition? Can you show me some examples?”

선택하신 부분은 위 줄에서 등호 앞의 왼쪽, 곧 정의되는 이름과 매개변수입니다. 결론부터 말하면 귀납적 정의가 아닙니다. 귀납적(재귀적) 정의는 정의하는 이름이 정의의 오른쪽에 다시 나타나야 합니다. 그런데 type Cat k = k -> k -> Type의 오른쪽에는 Cat이 없습니다. 왼쪽과 오른쪽에 함께 나오는 k는 단순한 매개변수입니다. 값 수준의 pair x = (x, x)에서 x가 양쪽에 나오는 것과 같습니다. 그래서 Cat을 어디에 쓰든 한 번 펼치면 끝납니다.

Cat Type           =  Type -> Type -> Type
Cat Bool           =  Bool -> Bool -> Type
Cat (Type -> Type) =  (Type -> Type) -> (Type -> Type) -> Type

또 Haskell은 타입 동의어의 재귀를 허용하지 않습니다. 앞에서 인용한 Haskell 2010 보고서 4.2.2절의 규정대로입니다. 예를 들어 이 문서에서 시험용으로 만든 다음 선언은 GHC 9.10.3에서 "타입 동의어 선언에 순환이 있다(Cycle in type synonym declarations)"는 오류로 거부됩니다.

-- 이 문서가 만든 예제입니다. 컴파일되지 않습니다.
type Loop :: Type -> Type
type Loop k = Loop k -> Type

원문에서 진짜 귀납적 정의를 찾으면, 자기 자신을 다시 언급하는 data/newtype 선언이 있습니다. 예를 들어 newtype Fix f where의 생성자 In :: f (Fix f) -> Fix f는 Fix f를 다시 사용하고, Vec의 생성자 (:>) :: a -> Vec n a -> Vec (1 + n) a는 더 짧은 Vec n a로 긴 벡터를 만듭니다. 이것들은 자료형이므로 재귀가 허용됩니다.

메모의 "예시"가 귀납적 정의의 예를 뜻했을 수도 있으므로, 가장 간단한 귀납적 정의와 Cat을 나란히 놓아 보겠습니다. 첫 줄은 이 문서가 만든 예제이며 GHC 9.10.3에서 경고 없이 통과했습니다. 둘째 줄은 원문의 정의입니다.

data List a = Nil | Cons a (List a)   -- 귀납적: 오른쪽에 List가 다시 나옵니다.
type Cat k = k -> k -> Type           -- 귀납적이지 않음: 오른쪽에 Cat이 없습니다.

List는 Nil에서 출발해 Cons를 한 번씩 더 붙여 가며 값을 쌓아 올립니다. 이것이 귀납적 정의의 전형적인 모양입니다. 반면 Cat k는 한 번 펼치면 끝나는 약어입니다.

"귀납"이라는 말이 떠오른 이유로 짐작되는 부분도 하나 있습니다. 원문 토론에서 저자는 "커리된 함수의 귀납적 성질(the inductive nature of curried functions)"을 언급합니다. 저자는 인자가 여럿인 함자를 Nat으로 한 겹씩 감싸서 만듭니다. 예를 들어 TrifunctorOf src1 src2 src3 tgt = FunctorOf src1 (Nat src2 (Nat src3 tgt))처럼 정의합니다. 원문 해석으로 보면, 이 귀납은 인자 목록 A -> B -> C -> Res를 앞에서부터 하나씩 처리하는 구조에 관한 것이며 Cat의 정의에 관한 것이 아닙니다. 메모가 그 토론을 염두에 두었는지는 알 수 없습니다.

Cat k의 예시는 대상의 종류별로 정리하면 다음과 같습니다. 표의 Op, Kleisli Maybe, (:~:)는 base에 있는 타입입니다. 표의 (:~:)는 종류 다형적이므로 각 행의 종류로 맞춰 씁니다. 원문의 정의라면 (:~:) @Type, (:~:) @Nat처럼 쓰고, base의 것이라면 앞의 참고 단락에서 설명했듯 (:~:) :: Cat Type처럼 종류 주석으로 고정합니다. (~>), (<->), Fun, (<=), Divides, (-?>)는 원문과 토론에 나오는 저자의 표기 또는 자체 정의입니다.

Cat k의 k 펼친 종류 이 종류를 가지는 범주의 예 사상의 의미
Type Type -> Type -> Type (->), Op(원문의 (<-)), (:~:), Kleisli Maybe, 원문의 (<->)와 Fun 함수, 뒤집힌 함수, 동등성 증거, a -> Maybe b 꼴의 함수, 동형 사상 쌍, 정해진 함수만 허용하는 사상
Type -> Type (Type -> Type) -> (Type -> Type) -> Type 원문의 (~>), (:~:) 자연 변환 forall x. f x -> f' x, 타입 생성자 사이의 동등성
Nat Nat -> Nat -> Type (:~:), 토론의 Divides, 원문의 (-?>) 자연수 사이의 동등성, "n이 n'을 나눈다"는 증거, 원문에서 정의하지 않은 길이 사상
Bool Bool -> Bool -> Type 원문의 (<=), (>=) False ≤ True 순서 관계의 증거

아래 코드는 이 표의 일부를 실제로 선언해 본 것입니다. 이 문서가 새로 만든 예제이며 원문 코드가 아닙니다. GHC 9.10.3에서 -Wall로 경고 없이 타입 검사를 통과했습니다. 원문의 (<=) :: Cat Bool은 표준 연산자 이름과 겹치므로, 같은 생각을 LeBool이라는 이름으로 옮겼습니다.

{-# LANGUAGE StandaloneKindSignatures, PolyKinds, DataKinds, GADTs, TypeOperators, RankNTypes #-}
module CatExamples where

import Control.Arrow (Kleisli)
import Data.Functor.Contravariant (Op (..))
import Data.Kind (Type)
import Data.Type.Equality ((:~:) (..))
import GHC.TypeNats (Nat)

type Cat :: Type -> Type
type Cat k = k -> k -> Type

-- Cat Type = Type -> Type -> Type
type Fn :: Cat Type
type Fn = (->)

type Opposite :: Cat Type
type Opposite = Op

type EqType :: Cat Type
type EqType = (:~:)

type KleisliMaybe :: Cat Type
type KleisliMaybe = Kleisli Maybe

-- Cat (Type -> Type) = (Type -> Type) -> (Type -> Type) -> Type
type (~>) :: Cat (Type -> Type)
data f ~> g where
  NT :: (forall x. f x -> g x) -> (f ~> g)

-- Cat Nat = Nat -> Nat -> Type
type EqNat :: Cat Nat
type EqNat = (:~:)

-- Cat Bool = Bool -> Bool -> Type
type LeBool :: Cat Bool
data LeBool a b where
  LeRefl    :: LeBool a a
  FalseTrue :: LeBool 'False 'True

LeBool은 Bool을 대상으로 하는 작은 범주입니다. 대상은 'False와 'True 두 개입니다. 각 대상에서 자기 자신으로 가는 항등 사상 LeRefl이 있고, 'False에서 'True로 가는 사상 FalseTrue가 하나 더 있습니다. 거짓 ≤ 참이라는 순서를 화살표로 그린 셈입니다. 이렇게 Cat k의 예를 만드는 일은 항상 "대상의 종류 k를 정하고, 대상 사이에 어떤 사상을 둘지 정하는 일"입니다.

두 인자는 꼭 같은 종류여야 하나요: k -> k -> Type

하이라이트: k -> k -> Type

원문 문맥:

type Cat k = k -> k -> Type

사용자 메모: “Must the two input be the same kind? Why can't it be (Type->Type) -> Type -> Type?”

선택하신 부분은 위 줄에서 등호 뒤의 오른쪽, 곧 Cat k가 펼쳐지는 종류입니다. 범주를 나타내려면 두 인자는 같은 종류여야 합니다. 이유는 두 가지이며, 하나는 정의에서, 다른 하나는 연산에서 나옵니다.

첫째, 정의상 그렇습니다. 범주에서 사상의 모임은 한 범주에 속한 두 대상의 쌍마다 정해집니다(nLab, category). cat a b의 a와 b는 같은 범주의 대상이고, 이 범주의 대상은 모두 종류 k의 타입입니다. 그러니 두 자리 모두 k가 됩니다.

둘째, id와 (.)가 그것을 강제합니다. Control.Category의 두 메서드를 다시 보겠습니다.

id  :: cat a a
(.) :: cat b c -> cat a b -> cat a c

id :: cat a a는 같은 a를 첫째 자리와 둘째 자리에 동시에 넣습니다. 첫째 자리의 종류가 j이고 둘째 자리의 종류가 k라면 a는 j이면서 k여야 하므로 j와 k는 같아야 합니다. 합성도 마찬가지입니다. b가 cat a b에서는 둘째 자리에, cat b c에서는 첫째 자리에 들어갑니다. 그래서 Control.Category는 클래스의 종류를 cat :: k -> k -> Type으로 고정합니다(base Control.Category 문서). base에는 종류가 서로 다른 두 타입을 비교하는 이종 동등성 (:~~:) :: k1 -> k2 -> Type도 있습니다. 하지만 그 Category 인스턴스는 두 종류가 같은 경우인 (:~~:) :: k -> k -> Type에만 주어집니다(같은 문서의 인스턴스 목록; base Data.Type.Equality 문서).

이제 (Type->Type) -> Type -> Type이 왜 안 되는지 보겠습니다. 먼저 바로잡을 점은, 이 종류 자체는 문법적으로 완전히 올바른 종류라는 것입니다. 이 종류를 가지는 타입 생성자도 실제로 많습니다. 예를 들어 MaybeT :: (Type -> Type) -> Type -> Type가 있고, IdentityT, Data.Monoid의 Ap와 Alt도 종류 다형적인 (k -> Type) -> k -> Type에서 k = Type으로 놓으면 이 종류가 됩니다(GHC 9.10.3의 GHCi에서 확인했습니다). 다만 이것은 범주의 종류는 아닙니다. 메모의 의도에 따라 두 가지로 읽을 수 있으므로 둘 다 답하겠습니다.

해석 1: "한쪽은 Type -> Type, 다른 쪽은 Type인 대상 사이의 사상"을 원하신 경우. 이는 j -> k -> Type에서 j = Type -> Type, k = Type으로 놓은 모양입니다. 이 경우 첫째 자리의 대상은 타입 생성자이고 둘째 자리의 대상은 보통의 타입입니다. 그러면 id :: cat a a를 쓸 수 없습니다. a가 타입 생성자이면서 보통의 타입일 수는 없기 때문입니다. 합성 역시 한 사상의 끝을 다음 사상의 시작에 이을 수 없습니다. 이 문서가 시험한 결과도 같습니다. 종류가 (Type -> Type) -> Type -> Type인 newtype Wrap f a = Wrap (f a)에 Category 인스턴스를 선언하면, GHC 9.10.3은 종류가 맞지 않는다는 오류를 냅니다. (이 Wrap은 이 문서가 만든 예제입니다.)

범주론에도 서로 다른 두 범주의 대상 사이를 잇는 화살표라는 개념은 있습니다. 이것을 이종 사상(heteromorphism)이라고 부르며, 보통 프로펑터(profunctor) 𝒞^op × 𝒟 → Set으로 다룹니다(nLab, heteromorphism). 하지만 이런 화살표는 같은 모임 안에서 자기들끼리 이어 붙일 수 없으므로 그 자체로 하나의 범주를 이루지 않습니다. 이 단락은 배경 지식이며 원문이 다루는 내용은 아닙니다.

해석 2: 원문의 Fix 절처럼 "인자가 Type -> Type일 때의 범주"를 생각하신 경우. 원문은 Fix :: (Type -> Type) -> Type의 인자를 옮기기 위해 (~>) :: Cat (Type -> Type)을 씁니다. 그런데 이 종류를 펼치면 메모의 종류가 아니라 다음과 같습니다.

Cat (Type -> Type)  =  (Type -> Type) -> (Type -> Type) -> Type
메모의 종류         =  (Type -> Type) -> Type -> Type

차이는 둘째 자리에 있습니다. Cat (Type -> Type)에서는 첫째와 둘째 자리가 모두 Type -> Type이지만, 메모의 종류에서는 둘째 자리가 Type입니다. (~>)의 사상 f ~> f'은 타입 생성자 f에서 타입 생성자 f'으로 가는 자연 변환이며, 양 끝이 모두 Type -> Type입니다. GHC 9.10.3에서도 두 종류가 서로 다르게 계산되는 것을 확인했습니다.

서로 다른 종류가 만나는 곳은 범주가 아니라 함자입니다. 원문 뒷부분의 시그니처를 보면 이 점이 드러납니다.

type FunctorOf :: Cat s -> Cat t -> (s -> t) -> Constraint

여기서 원천 범주 Cat s와 목표 범주 Cat t는 대상의 종류가 서로 달라도 됩니다. 예를 들어 원문의 mapFix는 FunctorOf (~>) (->) Fix의 사상 함수입니다. 이 함자는 대상의 종류가 Type -> Type인 범주 (~>)에서 대상의 종류가 Type인 범주 (->)로 갑니다. 다만 각 범주 안에서는 사상의 양 끝이 같은 종류입니다. 원문 해석으로 확장하면, 메모의 종류 (Type->Type) -> Type -> Type을 가진 MaybeT 같은 타입 생성자는 범주가 아니라 함자로 옮겨질 대상입니다. 원문의 표기를 빌리면 첫째 인자에는 (~>), 둘째 인자와 결과에는 (->)를 배정하는 식으로 생각할 수 있습니다. 이 배정은 원문에 나오지 않으며, 원문의 FunOf가 실제 코드로 정의되어 있지 않아 컴파일러로 확인하지도 않았습니다.

Refl은 무엇이고, 정말 쓰이지 않나요

하이라이트:

data a :~: b where
  Refl :: a :~: a

원문 문맥:

type (:~:) :: Cat k
data a :~: b where
  Refl :: a :~: a

mapFCong :: (a :~: a') -> (b :~: b') -> (c :~: c') -> (F a b c :~: F a' b' c')
mapFCong Refl Refl Refl = Refl

사용자 메모: “What is Refl? Is it correct to say that Refl it’s defined within where clause but not used anywhere?”

메모의 두 전제는 모두 바로잡아야 합니다.

첫째, 이 where는 지역 정의를 담는 where 절이 아닙니다. 공통 개념에서 설명한 GADT 문법의 where이며, "이제부터 이 타입의 생성자 목록을 적는다"는 뜻입니다. 따라서 Refl은 어떤 함수 안에 숨은 지역 정의가 아니라 (:~:) 타입의 데이터 생성자(data constructor)입니다. Haskell 98 문법으로 data Maybe a = Nothing | Just a를 쓰면 Nothing과 Just가 생성자가 되는 것과 같은 위치입니다. 다만 생성자의 전체 타입을 직접 적는다는 점이 다릅니다. 데이터 생성자는 최상위 이름이므로 선언한 모듈 전체에서 쓸 수 있고, 모듈이 내보내면 그 모듈을 가져오는 다른 모듈에서도 쓸 수 있습니다.

둘째, Refl은 바로 아래 mapFCong 정의에서 네 번 쓰입니다. mapFCong Refl Refl Refl = Refl에서 왼쪽의 세 Refl은 인자를 패턴 매칭하는 패턴이고, 오른쪽의 Refl은 결과로 돌려주는 값입니다.

이제 Refl이 무엇인지 보겠습니다. data a :~: b where는 두 타입 인자 a, b를 받는 타입 연산자 (:~:)를 선언합니다. 이렇게 중위 타입 이름을 쓰려면 공통 개념에서 말한 TypeOperators 확장이 필요합니다. 그리고 생성자는 Refl :: a :~: a 하나뿐입니다. GADT 문법에서는 머리의 변수 a, b가 생성자 시그니처 안에서 유효 범위가 없으므로, Refl의 a는 "아무 타입 a"라는 새 변수입니다(GHC 사용자 안내서, GADT 문법). 따라서 이 시그니처는 다음을 뜻합니다.

어떤 타입 a에 대해서든 a :~: a 타입의 값 Refl을 만들 수 있습니다. 그러나 양쪽이 다른 a :~: b 타입의 값을 만드는 생성자는 없습니다.

그래서 Refl :: Int :~: Int는 타입 검사를 통과하지만 Refl :: Int :~: Bool은 "Int와 Bool을 일치시킬 수 없다"는 오류가 납니다(GHC 9.10.3에서 확인했습니다). 결국 a :~: b 타입의 값이 있다는 것은 "a와 b가 같은 타입이다"라는 증거가 있다는 뜻입니다. base 문서도 같은 내용을 설명합니다(base Data.Type.Equality 문서). 이름 Refl은 동등성의 반사성(reflexivity), 곧 "모든 것은 자기 자신과 같다"에서 왔다고 흔히 설명합니다. 다만 이 어원을 명시한 공식 문서는 이번에 확인하지 못했습니다.

이 증거는 패턴 매칭할 때 쓸모가 생깁니다. Refl과 일치했다면 그 값은 a :~: a 꼴로 만들어졌을 수밖에 없으므로, 컴파일러는 그 분기 안에서 a와 b가 같은 타입이라는 사실을 사용합니다. 이것이 앞에서 말한 타입 정제입니다. 다음은 이 문서가 만든 예제입니다. GHC 9.10.3에서 경고 없이 통과했으며, base의 castWith와 같은 일을 합니다.

coerceVia :: (a :~: b) -> a -> b
coerceVia Refl x = x

x의 타입은 a인데 반환 타입은 b입니다. 보통이라면 타입 오류이지만, Refl로 패턴 매칭한 덕분에 그 분기에서는 a와 b가 같은 타입이므로 통과합니다.

원문의 mapFCong도 같은 원리로 읽으면 됩니다. 세 인자에서 Refl을 꺼내면 그 분기 안에서 a와 a', b와 b', c와 c'가 각각 같아집니다. 그러면 F a b c와 F a' b' c'도 같은 타입이므로 결과로 Refl을 돌려줄 수 있습니다. 이름의 Cong은 원문 해석상 합동(congruence), 곧 "같은 것을 넣으면 같은 것이 나온다"는 성질을 가리키는 것으로 보입니다.

이 코드가 원문에서 맡는 역할도 짚어 두겠습니다. (:~:)는 그 자체로 범주입니다. base에 Category (:~:) 인스턴스가 있으며, 원문 해석으로 보면 항등 사상은 Refl이고 합성은 동등성의 추이성("a = b이고 b = c이면 a = c")에 해당합니다. 앞 절에서 본 것처럼 이 범주에는 항등 사상만 있으므로 이산 범주입니다. 원문이 말하는 "요령(trick)"은 다음과 같습니다. 모든 인자와 결과에 이 동등성 범주를 배정하면, 어떤 타입 생성자든 아무 조건 없이 함자가 됩니다. 같은 인자를 넣으면 같은 결과가 나온다는 사실만 있으면 되고, mapFCong이 바로 그 사실의 증명입니다. 원문 표기로 FunOf (:~:) (:~:) ..라고 적은 것이 이것입니다. 원문은 타입 생성자를 예로 들지만 주장 자체는 더 넓습니다. 원문은 "어떤 함수든(any function)" 이런 개념적 인스턴스를 가진다고 말하고, 뒤에서 "모든 함수는 어떤 식으로든 함자"라고 일반화합니다. 그리고 원문의 F에서 둘째 인자에 (:~:) @Type이 배정된 것도, 그 인자에 대해서는 이 최소한의 함자성만 주장한다는 뜻으로 읽을 수 있습니다.

덧붙이면, 원문의 이 선언은 base의 Data.Type.Equality.(:~:)와 같은 것을 type (:~:) :: Cat k 시그니처와 함께 다시 적은 것입니다. 실제 코드에서는 직접 정의하지 않고 base의 것을 가져다 쓰면 됩니다.

정리

  • 원문은 타입 생성자의 인자와 결과마다 범주를 하나씩 배정하고, 사상 함수의 타입으로 그 배정을 읽는 관점을 제시합니다. (->), (:~:) @Type, (<-)는 F의 세 인자에 배정된 원천 범주이며, 각각 함수, 동등성 증거, 거꾸로 된 함수로 인자를 바꾼다는 뜻입니다.
  • Haskell에서 범주는 cat :: k -> k -> Type인 타입 생성자로 표현하고, cat a b를 a에서 b로 가는 사상들의 타입으로 읽습니다. Cat k는 이 종류의 약어입니다.
  • Cat 자체는 종류가 아니라, 종류 k를 받아 종류 k -> k -> Type을 돌려주는 타입 동의어입니다. Type :: Type이므로 그 종류가 Type -> Type으로 적힙니다.
  • type Cat k = …는 재귀하지 않는 타입 동의어이므로 귀납적 정의가 아니며, Haskell은 타입 동의어의 재귀를 금지합니다.
  • 범주 안의 두 인자는 같은 종류여야 합니다. 사상은 한 범주의 두 대상 사이에 있고, id와 (.)가 같은 변수를 두 자리에 넣기 때문입니다. (Type->Type) -> Type -> Type은 올바른 종류이지만 범주의 종류가 아니며, 서로 다른 종류는 범주가 아니라 함자 FunctorOf :: Cat s -> Cat t -> (s -> t) -> Constraint 수준에서 만납니다.
  • Refl은 GADT로 선언된 (:~:)의 유일한 데이터 생성자입니다. 이 값은 두 타입이 같다는 증거이며, 원문의 mapFCong에서 패턴과 결과로 네 번 쓰입니다.
