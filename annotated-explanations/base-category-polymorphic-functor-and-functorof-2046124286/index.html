이 문서에서 설명하는 내용

원문은 Haskell의 Functor를 단순히 Type -> Type인 타입 생성자에만 적용하지 않고, 서로 다른 객체 kind와 서로 다른 화살표를 가진 범주 사이에도 적용할 수 있도록 일반화하자고 제안합니다. 핵심 발상은 기존 fmap 타입에 두 번 나타나는 함수 화살표 (->)를 Dom f와 Cod f라는 연관 타입으로 바꾸는 것입니다.

fmap :: Dom f a b -> Cod f (f a) (f b)

이 제안을 이해하려면 세 층위를 구분해야 합니다.

  • Type, Constraint, Type -> Type 같은 표현은 타입과 제약의 kind를 설명합니다.
  • Cat i는 객체 kind가 i일 때 사상 타입 생성자가 가져야 할 모양을 설명합니다.
  • Category cat은 그 사상 생성자에 항등 사상과 합성이 있다는 구조와 법칙을 요구합니다.

원문의 코드는 완성된 라이브러리 설계라기보다 탐색 중인 제안입니다. 기존 Functor의 형태를 복원하는 부분은 설명할 수 있지만, <$, 고차 kind의 기본 화살표, 자동 인스턴스에 필요한 제약은 미완성으로 남아 있습니다. 현재 base도 여전히 Functor (f :: Type -> Type)를 사용하므로, 이 제안은 기존 클래스를 대체하는 설계로 채택되지 않았습니다.

먼저 알아야 할 공통 개념

Kind는 타입의 타입입니다

값에 타입이 있듯이 타입과 타입 생성자에는 kind가 있습니다. 다음 예에서 왼쪽 항목이 오른쪽 kind를 가집니다.

Int       :: Type
Maybe     :: Type -> Type
Either    :: Type -> Type -> Type
Functor   :: (Type -> Type) -> Constraint

Type은 일반적인 값 타입을 분류하는 kind입니다. Constraint는 타입 검사기가 요구하는 제약을 분류하는 kind입니다. 따라서 Functor Maybe는 런타임 값을 담는 타입이 아니라, Maybe에 Functor 인스턴스가 있어야 한다는 조건입니다. 이 구분은 Data.Kind와 GHC의 Constraint kind 설명에서 확인할 수 있습니다.

화살표는 오른쪽으로 결합합니다.

Type -> Type -> Type
= Type -> (Type -> Type)

따라서 두 인자를 받는 Either에 첫 인자만 주면 Either e :: Type -> Type이 됩니다. 기존 Functor가 다인자 타입 생성자의 마지막 인자를 사상시키는 이유도 이 부분 적용 뒤의 kind가 Type -> Type이기 때문입니다.

객체, 사상, Cat, Category

범주(category)는 객체와 객체 사이의 사상(morphism), 항등 사상, 사상 합성으로 이루어진 구조입니다. Haskell에서는 객체를 어떤 kind의 타입으로, 사상을 두 객체를 받아 값 타입을 만드는 타입 생성자로 표현할 수 있습니다.

원문이 바탕으로 삼은 Edward Kmett의 코드에는 다음 별칭이 있습니다.

type Cat i = i -> i -> Type

따라서 Cat Type은 Type인 객체 두 개를 받아 그 사이의 사상 타입을 만드는 형태입니다. 보통 함수 화살표는 다음 형태를 가집니다.

(->) :: Type -> Type -> Type

즉 (->) :: Cat Type이라고 읽을 수 있습니다. 그러나 이 kind만 안다고 해서 항등 사상과 합성이 생기지는 않습니다. Control.Category.Category는 cat :: k -> k -> Type인 사상 생성자에 id와 (.)를 제공하고 범주 법칙을 요구하는 클래스입니다.

요약하면 Cat i는 사상 생성자의 입력과 출력 형태이고, Category cat은 특정 cat이 범주로 작동하는 데 필요한 연산과 법칙입니다. 원문이 링크한 Kmett의 Category는 base의 클래스보다 더 많은 구조를 포함합니다. 원문은 어느 정의 전체를 전제하는지 명확히 고정하지 않으므로, 두 클래스의 세부 구조가 같다고 단정하면 안 됩니다.

기존 Functor는 Hask의 Endofunctor입니다

일반적인 범주론의 functor는 원천 범주의 객체와 사상을 목표 범주의 객체와 사상으로 보내며, 항등과 합성을 보존합니다. 기존 Haskell Functor는 다음과 같습니다.

class Functor f where
  fmap :: (a -> b) -> f a -> f b

객체를 Haskell 타입으로 보고 사상을 Haskell 함수로 보는 범주를 관용적으로 Hask라고 부릅니다. 위 타입에서 f :: Type -> Type은 객체를 Hask에서 Hask로 보내고, fmap은 함수 a -> b를 함수 f a -> f b로 보냅니다. 원천과 목표가 같은 범주이므로 endofunctor라고 부릅니다.

이 설명은 실용적인 교육적 단순화입니다. Haskell에는 비종료와 seq가 있으므로 Hask를 집합과 전함수의 범주와 완전히 같다고 말하려면 별도의 의미론적 주의가 필요합니다.

원문의 범주 다형적 Functor

원문의 중심 정의는 다음과 같습니다.

type Functor :: (from -> to) -> Constraint

class (Category (Dom f), Category (Cod f)) => Functor (f :: from -> to) where
 type Dom f :: Cat from
 type Cod f :: Cat to
 fmap :: Dom f a b -> Cod f (f a) (f b)

여기서 역할은 다음과 같습니다.

  • f :: from -> to는 원천 객체를 목표 객체로 보냅니다.
  • Dom f :: Cat from은 원천 객체 사이의 사상 생성자입니다.
  • Cod f :: Cat to는 목표 객체 사이의 사상 생성자입니다.
  • fmap은 Dom f a b라는 원천 사상을 Cod f (f a) (f b)라는 목표 사상으로 보냅니다.

기존 Functor는 from ~ Type, to ~ Type, Dom f ~ (->), Cod f ~ (->)인 특수 사례가 됩니다. 원문의 FunctorOf는 이 두 화살표를 제약식에 드러내기 위한 이름입니다.

class (Functor f, dom ~ Dom f, cod ~ Cod f) => FunctorOf dom cod f
instance (Functor f, dom ~ Dom f, cod ~ Cod f) => FunctorOf dom cod f

이 정의는 새로운 fmap 구현을 만들지 않습니다. FunctorOf dom cod f는 Functor f이면서 Dom f가 dom이고 Cod f가 cod라는 조건을 한 번에 표현합니다.

하이라이트와 메모별 해설

type instance는 열린 타입 패밀리의 식을 추가합니다

하이라이트: type instance

원문 문맥:

type (-->) :: Cat ob

type family   (-->)
type instance (-->) @Type = (->)

type family는 타입 수준 함수를 선언합니다. 열린 타입 패밀리(open type family)는 선언과 별도의 위치에서 입력별 식을 추가할 수 있습니다. type instance는 그 식 하나를 정의하는 문법입니다.

위 코드는 먼저 (-->)라는 타입 패밀리를 선언하고, 객체 kind가 Type인 경우에는 결과를 함수 화살표 (->)로 정합니다.

(-->) @Type  ==>  (->)

여기서 type instance는 클래스 인스턴스나 값 수준 함수 정의가 아닙니다. 타입 검사 중에 타입 식을 환원하는 규칙입니다. 열린 타입 패밀리와 그 인스턴스 문법은 GHC User’s Guide의 Type families 절에 설명되어 있습니다.

또한 이 식은 모든 객체 kind에 대한 포괄 기본값이 아닙니다. 원문이 실제로 제시한 식은 Type에 대해서만 환원됩니다. 예를 들어 (-->) @(Type -> Type)에는 별도의 식이 필요합니다.

숨은 kind 인자를 지정하는 @Type

하이라이트: @Type

원문 문맥:

type instance (-->) @Type = (->)

@Type은 가시적 타입 적용(visible type application)을 kind 인자에 사용한 표현입니다. read @Int가 추론될 타입 인자를 Int로 지정하듯이, (-->) @Type은 (-->)의 숨은 객체 kind 인자를 Type으로 지정합니다.

type family (-->)의 선언 arity는 0이지만, standalone kind signature의 Cat ob 때문에 숨은 객체 kind 인자 ob를 받습니다. @Type은 바로 그 숨은 인자를 지정합니다.

첫 선언을 풀어 생각하면 (-->)에는 다음과 같은 kind 매개변수가 숨어 있습니다.

(-->) :: forall ob. Cat ob

그러므로 (-->) @Type은 Cat Type, 즉 Type -> Type -> Type 형태의 사상 생성자를 선택합니다. 그 결과를 (->)로 정의한 것이 해당 type instance입니다. 관련 문법은 GHC의 Visible type application 설명과 kind 다형성 및 standalone kind signature 설명에서 확인할 수 있습니다.

기본 Dom과 Cod가 기존 fmap을 복원하는 과정

하이라이트: With default definitions Dom f = (-->) and Cod f = (-->) this works as a drop-in replacement for old Functor.

원문 문맥:

With default definitions Dom f = (-->) and Cod f = (-->) this works as a drop-in replacement for old Functor. Except for ..

사용자 메모: How does it work?

원문의 주장은 연관 타입 기본값과 열린 타입 패밀리 환원을 결합한다는 뜻입니다. 클래스에 다음 기본 식이 있다고 가정합니다.

type Dom f = (-->)
type Cod f = (-->)

기존 타입 생성자 f :: Type -> Type에 대한 환원 과정은 다음과 같습니다.

  1. f의 입력과 출력 객체 kind는 모두 Type입니다.
  2. 인스턴스가 Dom f와 Cod f를 별도로 정의하지 않으면 연관 타입 기본값이 사용됩니다.
  3. 두 기본값의 숨은 객체 kind는 문맥에 따라 Type으로 정해집니다.
  4. (-->) @Type은 type instance (-->) @Type = (->)에 따라 (->)로 환원됩니다.
  5. 일반화된 fmap은 기존 타입으로 특수화됩니다.
fmap :: Dom f a b -> Cod f (f a) (f b)
     :: (a -> b)   -> (f a -> f b)

따라서 다음과 같은 기존 인스턴스의 소스 형태를 유지할 수 있다는 주장입니다.

instance Functor [] where
  fmap = map

연관 타입의 기본 식과 생략 시의 선택 규칙은 GHC의 Associated type synonym defaults 설명에서 확인할 수 있습니다.

다만 “drop-in replacement”는 제한적인 표현입니다. 바로 다음 절의 <$ 기본 구현은 일반 범주에서 성립하지 않으며, 핵심 클래스를 교체하면 라이브러리 호환성, 타입 추론, 오류 메시지에도 영향을 줍니다. 수집된 두 댓글도 기존 클래스를 교체하기보다 별도 CategoricalFunctor 계열 클래스를 두는 방안을 선호합니다. 따라서 위 환원은 기존 fmap 타입을 복원하는 방법이지, 생태계 전체가 변경 없이 호환된다는 증명은 아닙니다.

FunctorOf (->) (->)는 Hask에서 Hask로 가는 경우를 명시합니다

하이라이트: a functor from Hask to Hask (FunctorOf (->) (->))

원문 문맥:

A very useful 'notation' for thinking about functors, we can express that our old functor is actually a functor from Hask to Hask (FunctorOf (->) (->)) aka an EndoFunctorOf (->):

FunctorOf (->) (->) f는 대략 다음 세 조건을 묶은 제약입니다.

Functor f
Dom f ~ (->)
Cod f ~ (->)

즉 f가 functor이며, 입력 사상과 출력 사상이 모두 Haskell 함수라는 뜻입니다. FunctorOf는 별도의 사상 연산을 추가하지 않고, f에 이미 연결된 Dom과 Cod를 사람이 읽기 쉬운 제약 형태로 노출합니다.

EndoFunctorOf cat = FunctorOf cat cat은 원천과 목표가 같은 경우에 붙인 별칭입니다. 그러므로 기존 Functor를 EndoFunctorOf (->)로 표현할 수 있다는 것이 원문의 요지입니다.

~는 컴파일 시간의 타입 동등성 제약입니다

하이라이트: ~

원문 문맥:

class    (Functor f, dom ~ Dom f, cod ~ Cod f) => FunctorOf dom cod f

이 항목의 ~는 dom ~ Dom f에 나타나는 타입 동등성 제약입니다. 양쪽 타입이 같아야 해당 제약이 만족됩니다.

dom ~ Dom f
cod ~ Cod f

따라서 호출자가 FunctorOf dom cod f를 요구하면 dom과 cod를 임의로 고를 수 없습니다. 각각 f의 연관 타입인 Dom f, Cod f와 같아야 합니다. (~) :: forall k. k -> k -> Constraint이므로 비교하는 양쪽은 같은 kind여야 합니다. 자세한 의미는 GHC의 Equality constraints 설명에서 확인할 수 있습니다.

비슷해 보이는 기호는 구분해야 합니다.

  • a ~ b는 타입 검사기가 해결하는 동등성 제약입니다.
  • a :~: b는 Refl을 패턴 매치할 수 있는 값 수준 증거 타입입니다. Data.Type.Equality에 정의되어 있습니다.
  • f ~> g는 이 원문에서 자연 변환을 나타내려는 사용자 정의 연산자로 해석됩니다.

요구 조건의 kind인 Constraint

하이라이트: Constraint

원문 문맥:

type FunctorOf :: Cat from -> Cat to -> (from->to) -> Constraint

이 standalone kind signature는 FunctorOf가 두 사상 생성자와 객체 매핑 f를 받은 뒤 Constraint를 만든다고 말합니다.

FunctorOf dom cod f :: Constraint

따라서 FunctorOf dom cod f는 Int나 Maybe String처럼 값을 분류하는 타입이 아닙니다. 함수의 context나 인스턴스 선언에서 타입 검사기가 만족시켜야 할 조건입니다.

example :: FunctorOf dom cod f => ...

Type과 Constraint의 차이는 Data.Kind와 GHC의 Constraint kind 설명에서 확인할 수 있습니다.

Cat은 사상 생성자의 모양이고 Category는 구조와 법칙입니다

하이라이트: Cat

원문 문맥:

type FunctorOf :: Cat from -> Cat to -> (from->to) -> Constraint

사용자 메모: How is this different from Category?

Cat과 Category는 서로 다른 층위에 있습니다. 원문이 참조한 코드에서 Cat은 다음 타입 별칭입니다.

type Cat i = i -> i -> Type

Cat i는 객체 kind i에 속한 객체 두 개를 받아 사상 타입을 만드는 타입 생성자의 모양입니다. 예를 들어 (->) :: Cat Type입니다.

반면 Category cat은 특정 사상 생성자 cat이 다음 연산을 제공하고 범주 법칙을 만족해야 한다는 클래스 제약입니다.

id  :: cat a a
(.) :: cat b c -> cat a b -> cat a c

따라서 차이는 다음처럼 정리할 수 있습니다.

Cat i       : “사상 생성자가 어떤 kind를 가져야 하는가?”
Category c  : “이 사상 생성자에 항등과 합성의 범주 구조가 있는가?”

c :: Cat i라고 안다고 해서 Category c가 자동으로 성립하지는 않습니다. Category c 인스턴스가 별도로 있어야 합니다. 현재 base의 정의와 법칙은 Control.Category에서 확인할 수 있고, 원문이 직접 참조한 Cat 별칭은 Edward Kmett의 Categories.hs에 있습니다.

const가 임의의 원천 범주에서는 사상이 아닙니다

하이라이트: const

원문 문맥:

(<$) = fmap . const

기존 Functor에서 타입은 다음과 같습니다.

const :: a -> b -> a
(<$)  :: Functor f => a -> f b -> f a

값 x :: a를 고정하면 const x :: b -> a가 됩니다. 기존 fmap은 (b -> a)를 입력으로 받을 수 있으므로 다음 합성이 성립합니다.

fmap . const

그러나 범주 다형적 Functor의 fmap은 (b -> a)가 아니라 다음 사상을 요구합니다.

fmap :: Dom f b a -> Cod f (f b) (f a)

const x는 항상 Haskell 함수, 즉 (->) 범주의 사상입니다. Dom f가 (->)가 아닌 범주라면 const x를 fmap에 전달할 수 없습니다.

더 근본적으로 임의의 범주에는 “입력을 버리고 지정한 값으로 보내는 사상”이 자동으로 존재하지 않습니다. 그런 연산을 일반화하려면 terminal object나 Cartesian 구조처럼 더 강한 범주 구조가 필요할 수 있습니다. 그래서 원문은 <$를 별도 클래스로 분리할지, 더 강한 제약 아래에서만 제공할지 결정하지 못했다고 말합니다. 어느 한 해결책이 이 글에서 확정된 것은 아닙니다. 현재 타입은 Data.Function.const와 Data.Functor에서 확인할 수 있습니다.

Profunctor는 두 인자의 반대 변성을 함께 다룹니다

하이라이트: Profunctor

원문 문맥:

We have Functor, Bifunctor and Contravariant. We are aching for Profunctor to be added to base.

Profunctor p는 보통 p :: Type -> Type -> Type인 타입 생성자의 첫 인자를 반변적으로, 둘째 인자를 공변적으로 사상시킵니다.

dimap :: (a -> b) -> (c -> d) -> p b c -> p a d

첫 함수의 방향을 보면 입력이 a -> b인데 p의 첫 자리는 b에서 a로 바뀝니다. 둘째 자리는 c -> d와 같은 방향으로 바뀝니다. Data.Profunctor가 이 인터페이스를 정의합니다.

원문이 Functor, Bifunctor, Contravariant, Profunctor를 함께 언급한 이유는 변성의 조합마다 별도 클래스가 생기는 상황을 문제로 보기 때문입니다. 범주와 화살표를 매개변수화한 하나의 Functor 개념으로 더 많은 경우를 표현하려는 것이 제안의 동기입니다.

다만 원문이 말한 당시의 “Profunctor를 base에 추가하려는 움직임”의 규모나 공식 상태는 제공된 자료만으로 확정할 수 없습니다. 현재도 Profunctor는 profunctors라는 별도 패키지에 있습니다.

Cofree::TT->TT는 자연 변환을 자연 변환으로 올리는 예입니다

하이라이트: Cofree::TT->TT

원문 문맥:

Instead of hoistCofree for Cofree::TT->TT we use the same abstraction:

원문은 T, TT, (~>)를 직접 정의하지 않습니다. 문맥상 다음 축약으로 읽는 것이 일관됩니다.

T  = Type
TT = Type -> Type

그러면 Cofree의 kind는 다음과 같습니다.

Cofree :: (Type -> Type) -> Type -> Type

화살표가 오른쪽으로 결합하므로 이를 다음처럼 읽을 수 있습니다.

Cofree :: TT -> TT

또한 원문을 해석하기 위한 의사 표기로 f ~> g를 다음처럼 읽을 수 있습니다.

f ~> g  =  모든 x에 대한 함수 f x -> g x

이는 원문에 실제 선언된 독립적인 Haskell 코드가 아니라 자연 변환의 의미를 간단히 나타낸 표기입니다.

공식 free 패키지의 hoistCofree는 개략적으로 다음 타입을 가집니다.

hoistCofree
  :: Functor f
  => (forall x. f x -> g x)
  -> Cofree f a
  -> Cofree g a

첫 인자를 f ~> g로 보면 결과도 모든 a에 대해 Cofree f a -> Cofree g a이므로 Cofree f ~> Cofree g입니다. 원문은 이 전용 함수의 작동을 다음 하나의 일반화된 functor 제약으로 표현하고 싶어 합니다.

FunctorOf (~>) (~>) Cofree

즉 원천 사상도 자연 변환이고 목표 사상도 자연 변환인 functor라는 뜻입니다. 실제 타입과 설명은 Control.Comonad.Cofree에서 확인할 수 있습니다.

이 해석은 문맥상 가장 자연스럽지만, 원문에 T, TT, (~>)의 정의가 없다는 점은 남습니다. 특히 목표 범주가 comonad 구조까지 보존하는지와 단순히 Haskell 타입에서 자연 변환으로 보이는지는 구분해야 합니다.

원문의 바로 앞 Fix 예도 같은 패턴의 companion 사례입니다. Fix는 자연 변환을 Haskell 함수로 보내는 경우이며, 뒤의 “제안의 장점과 남은 설계 문제” 절에서 함께 설명합니다.

다섯 튜플 인스턴스는 각 부분 적용 단계의 다음 인자를 사상시킵니다

하이라이트:

instance Functor @T @TTTTT  (,,,,)
instance Functor @T @TTTT  ((,,,,) a)
instance Functor @T @TTT   ((,,,,) a b)
instance Functor @T @TT    ((,,,,) a b c)
instance Functor @T @T     ((,,,,) a b c d)

원문 문맥:

It allows us to define functoriality in any arguments

It's possible we can get them automatically from a single Functor (,,,,) instance with a clever definition of

(,,,,)는 다섯 타입 인자를 받아 5-튜플 타입을 만드는 생성자입니다. 원문의 축약을 다음처럼 해석할 수 있습니다.

T      = Type
TT     = Type -> Type
TTT    = Type -> Type -> Type
TTTT   = Type -> Type -> Type -> Type
TTTTT  = Type -> Type -> Type -> Type -> Type

각 줄의 의도는 다음과 같습니다.

인스턴스 머리 이미 고정한 인자 다음에 사상시키려는 인자 객체 매핑의 개략 kind
(,,,,) 없음 첫째 T -> TTTTT
((,,,,) a) 첫째 둘째 T -> TTTT
((,,,,) a b) 첫째와 둘째 셋째 T -> TTT
((,,,,) a b c) 첫째부터 셋째 넷째 T -> TT
((,,,,) a b c d) 첫째부터 넷째 다섯째 T -> T

현재 base의 Functor는 Type -> Type만 받으므로 마지막 행만 직접 표현할 수 있습니다. Data.Functor도 다인자 생성자에서 마지막 타입 인자를 바꾸는 동작으로 설명합니다. 두 인자를 함께 공변적으로 다루려면 별도 Bifunctor를 사용합니다.

원문의 일반화는 from과 to를 kind 다형적으로 만들어 각 부분 적용 단계에 같은 Functor 클래스 이름을 사용하려는 것입니다. 이 목록은 한 번의 fmap으로 다섯 필드를 동시에 바꾼다는 뜻이 아닙니다. 각 줄은 서로 다른 부분 적용 상태에서 “다음 인자”를 바꾸는 functor 구조입니다.

여기에는 중요한 미완성 부분도 있습니다. 첫 줄의 목표 객체 kind는 TTTTT이므로 기본 화살표를 쓰려면 (-->) @TTTTT가 환원되어야 합니다. 그러나 원문이 실제로 정의한 식은 다음 하나뿐입니다.

type instance (-->) @Type = (->)

따라서 고차 kind에 대한 추가 화살표 식이나 각 인스턴스의 명시적인 Cod 정의가 필요합니다. 원문이 참조한 Edward Kmett의 Categories.hs는 비슷한 경우에 Nat (->) (->) 같은 자연 변환 범주를 사용합니다. 제시된 다섯 줄만으로 완성된 컴파일 가능 설계가 되지는 않습니다.

마지막 ..는 생략된 제약을 나타내는 Placeholder입니다

하이라이트: ..

원문 문맥:

instance (Functor f, ..) => Functor (f a)

이 위치의 ..는 유효한 일반 인스턴스 context 문법이 아닙니다. 저자가 아직 적지 않은 추가 제약을 표시한 의사 코드의 placeholder로 읽어야 합니다.

앞선 튜플 예를 하나의 Functor (,,,,) 인스턴스에서 자동으로 유도하려면 f와 f a의 kind 관계, 원천과 목표 화살표, 자연 변환 구조, 인스턴스 중복 가능성 등을 정해야 합니다. 원문은 “clever definition”이 가능할 수 있다고 제안할 뿐, 그 제약을 완성하지 않았습니다.

따라서 이 줄을 그대로 컴파일 가능한 Haskell 코드로 사용하면 안 됩니다. 원문 본문의 문장 부호로 쓰인 다른 ..가 아니라, 마지막 코드 블록의 (Functor f, ..) 안에 있는 생략 기호라는 점도 문맥으로 구분해야 합니다.

제안의 장점과 남은 설계 문제

이 제안의 장점은 Fix, Cofree, GADT, 타입 동등성 사상처럼 기존 Type -> Type과 (->)에 맞지 않는 사례를 “다른 클래스의 특수 연산”이 아니라 동일한 functor 개념으로 표현할 가능성을 연다는 점입니다. 예를 들어 Fix :: (Type -> Type) -> Type은 자연 변환을 Haskell 함수로 보내는 다음 형태로 해석할 수 있습니다.

FunctorOf (~>) (->) Fix

Data.Fix의 hoistFix는 이러한 해석을 뒷받침하는 구체적인 연산입니다.

반면 제안에는 적어도 다음 문제가 남습니다.

  • <$처럼 (->)의 특별한 구조에 의존하는 메서드를 일반 Functor에 그대로 둘 수 없습니다.
  • (-->) @Type = (->)만으로는 Type -> Type 같은 고차 객체 kind의 기본 사상을 정할 수 없습니다.
  • Functor (f a)를 자동 유도하는 인스턴스의 정확한 제약과 충돌 조건이 제시되지 않았습니다.
  • 기존 핵심 클래스를 교체하면 타입이 맞는 일부 소스 코드 외에도 라이브러리 생태계, 오류 메시지, 학습 난이도에 변화가 생깁니다.

수집된 두 댓글은 이 이유로 기존 Functor를 교체하기보다 별도의 CategoricalFunctor를 두고 기존 Functor마다 일반화된 인스턴스를 제공하는 접근을 제안합니다. 다만 원문에는 전체 29개 토론 중 두 댓글만 수집되어 있으므로, 이를 당시 커뮤니티 전체의 합의로 일반화하면 안 됩니다.

정리

원문의 핵심은 Functor를 “Haskell 함수를 Haskell 함수로 올리는 클래스”에서 “선택한 원천 범주의 사상을 선택한 목표 범주의 사상으로 보내는 클래스”로 일반화하는 것입니다. Dom f와 Cod f가 그 두 사상 생성자를 선택하고, FunctorOf dom cod f가 선택 결과를 제약에 명시합니다.

type instance (-->) @Type = (->)와 연관 타입 기본값을 함께 사용하면 f :: Type -> Type인 기존 functor의 fmap :: (a -> b) -> f a -> f b를 복원할 수 있습니다. 그러나 이 환원만으로 완전한 호환성이 보장되지는 않습니다. <$의 const, 고차 kind의 화살표, 튜플 인스턴스 자동 유도에는 추가 설계가 필요합니다.

따라서 이 글은 완성된 대체안이라기보다 중요한 설계 질문을 드러내는 제안으로 읽는 편이 정확합니다. 어떤 타입 생성자가 기존 Functor가 될 수 없을 때 “functor가 아니다”라고 끝내지 않고, 객체와 사상으로 어떤 범주를 선택해야 하는지를 먼저 묻게 한다는 점이 가장 큰 개념적 가치입니다.
