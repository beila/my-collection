Distributors 해설 3/8: 토큰 (Tokens)

해설 대상 원문: Eitan Chatav, “Distributors — Unifying Parsers, Printers & Grammars”

검토일: 2026-11-21

이 쪽은 여덟 쪽 시리즈의 세 번째 쪽이며, 원문의 "Tokens" 절을 다룹니다. 2쪽에서 프린터-파서(printer-parser)의 타입 틀인 Parsor와 Printor를 세웠으니, 이제 그 틀 안에서 실제로 토큰(token) 하나를 읽고 쓰는 가장 작은 부품 anyToken을 만듭니다. 이 절은 코드는 짧지만 처음 보는 하스켈 문법이 한꺼번에 나옵니다. 다중 매개변수 타입 클래스(multi-parameter type class), 함수적 종속성(functional dependency), GADT(generalized algebraic data type) 문법, 그리고 lens 라이브러리의 Cons와 Prism입니다. 이 쪽은 이것들을 하나씩 처음부터 설명한 뒤 원문 코드를 읽습니다.

2쪽에서 가져올 것

  • 프로펑터(profunctor) p a b는 "a를 받아 b를 내는 것"이고, dimap으로 입력 쪽과 출력 쪽에 함수를 붙일 수 있습니다.
  • Parsor s f a b는 스트림(stream) s를 읽어 결과 b와 남은 스트림을 컨테이너 f에 담아 돌려주며, a는 쓰지 않습니다. Printor s f a b는 값 a를 받아 자기 함수(endofunction) s -> s를 f에 담아 돌려주며, b는 쓰지 않습니다.
  • 결과 컨테이너 f에 Applicative만 요구하면 실패할 수 없으므로 망라적(exhaustive)이고, Alternative를 요구하면 empty로 실패할 수 있으므로 부분적(partial)입니다. pure, empty, <|>의 뜻은 1쪽에서 작은 파서 예제와 함께 설명했습니다.

왜 기본 부품이 필요한가

원문은 이렇게 시작합니다.

Combinators are great for generating new printer-parsers from existing ones, but if we want to generate examples we need an interface which generates basic printer-parsers from scratch.

조합자(combinator)는 이미 있는 프린터-파서를 조합해 새 프린터-파서를 만듭니다. 그러나 조합할 재료가 하나도 없으면 아무것도 만들 수 없습니다. 1쪽의 파서 예제에서 item, charP, digitP가 했던 역할, 즉 "실제로 글자 하나를 읽는 부품"이 필요합니다. 이 글은 그런 부품을 단 하나만 둡니다. 스트림의 맨 앞 토큰 하나를 다루는 anyToken입니다. 이후의 token, satisfy, tokens, 그리고 7쪽의 문법 전체가 이 하나의 부품에서 출발합니다.

필요한 문법 1: 다중 매개변수 타입 클래스

보통의 타입 클래스는 타입 하나에 관한 성질을 말합니다. Show a는 "타입 a는 문자열로 보일 수 있다"는 뜻입니다. 다중 매개변수 타입 클래스(multi-parameter type class)는 여러 타입 사이의 관계를 말합니다. 다음은 원문 코드가 아니라 작은 예시입니다. 이 쪽의 예시는 모두 원문과 필요한 라이브러리 정의를 최소한으로 다시 만든 코드로 GHC 9.10.3에서 실행한 결과입니다.

class Convert a b where
  convert :: a -> b

instance Convert Int String where
  convert = show

Convert a b는 "a를 b로 바꿀 수 있다"는 두 타입 사이의 관계이고, 인스턴스 하나는 "Int와 String 사이에 이 관계가 있다"는 사실 하나입니다.

>>> convert (42 :: Int) :: String
"42"

여기서 결과 타입 표시 :: String을 빼면 GHC는 어느 b를 쓸지 정하지 못합니다. Int에서 다른 타입으로 가는 인스턴스가 나중에 더 추가될 수도 있기 때문입니다. 다중 매개변수 클래스는 표현력이 크지만 이런 모호성(ambiguity) 문제를 자주 일으킵니다. 이 기능은 MultiParamTypeClasses 확장이며, GHC 9.2부터 기본 언어 판인 GHC2021에 들어 있습니다.

필요한 문법 2: 함수적 종속성

함수적 종속성(functional dependency)은 이 모호성을 줄이는 장치입니다. 클래스 머리 뒤에 세로 막대 |를 쓰고 a -> b 꼴의 규칙을 적습니다.

class Convert a b | a -> b where
  convert :: a -> b

여기서 a -> b는 함수 타입이 아닙니다. "a가 정해지면 b가 하나로 정해진다"는 규칙입니다. GHC 사용자 안내서는 이 표기가 "a 매개변수가 b 매개변수를 유일하게 결정한다(uniquely determines)"는 뜻이라고 설명합니다(GHC 사용자 안내서: Functional dependencies). 이 규칙에서 두 가지가 따라 나옵니다.

  1. 추론: 사용하는 곳에서 a만 알려져 있어도, GHC는 a에 맞는 인스턴스 머리를 보고 빠진 b를 채워 넣습니다. 이 추론은 인스턴스 머리가 b를 직접 적고 있을 때 확실하게 동작합니다. 아래 Tokenized에서 이 조건이 중요해집니다.
  2. 일관성: a는 같고 b만 다른 두 인스턴스를 만들 수 없습니다. 만들면 컴파일 오류입니다.

규칙은 쉼표로 여러 개 쓸 수 있고, 왼쪽에 매개변수를 여러 개 둘 수도 있습니다(s b -> t는 "s와 b가 함께 정해지면 t가 정해진다"는 뜻입니다). 이 기능은 FunctionalDependencies 확장이며, GHC2021에 들어 있지 않으므로 따로 켜야 합니다.

필요한 문법 3: FlexibleInstances와 FlexibleContexts

하스켈 98 표준은 인스턴스 머리를 엄격하게 제한합니다. 인스턴스 머리는 T a1 ... an처럼 타입 생성자에 서로 다른 타입 변수만 적용한 꼴이어야 합니다. 이 쪽의 코드는 이 제한을 여러 번 넘습니다. instance Tokenized a b (Identical a b)는 a와 b를 두 번씩 쓰고, instance ... => Tokenized c c (Printor s f)는 c를 두 번 씁니다. 5쪽의 IsString (Parsor s f () ())처럼 구체 타입 ()를 넣는 경우도 있습니다. 이런 인스턴스를 허용하는 확장이 FlexibleInstances입니다. 마찬가지로 제약에 구체 타입을 쓰는 Tokenized Char Char p나 Cons s s Char Char 같은 꼴을 허용하는 확장이 FlexibleContexts입니다. 두 확장은 GHC2021에 들어 있으므로 최근 GHC에서는 보통 따로 켤 필요가 없습니다. 위의 instance Convert Int String도 사실 이 확장 덕분에 가능합니다.

코드 읽기: Tokenized 클래스와 Identical

원문은 기본 부품을 위한 인터페이스를 다음과 같이 정의합니다.

class Tokenized a b p | p -> a, p -> b where
  anyToken :: p a b

data Identical a b s t where
  Identical :: Identical a b a b
instance Tokenized a b (Identical a b) where
  anyToken = Identical

원문은 바로 이어서 "Tokenized 인터페이스는 너무 추상적이어서 이름이 없었다면 동기를 알기 어려웠을 것"이라고 말합니다. 실제로 클래스의 메서드는 anyToken :: p a b 하나뿐입니다. "p에는 a에서 b로 가는 기본 값 anyToken이 있다"는 것 외에는 아무것도 말하지 않습니다. 이름이 의도를 알려 줍니다. anyToken은 "스트림 맨 앞의 토큰 아무것이나 하나"를 다루는 부품이어야 합니다.

p가 토큰 타입을 정합니다

하이라이트: Tokenized a b p | p -> a, p -> b

원문 문맥:

For that purpose, we define the Tokenized interface.

class Tokenized a b p | p -> a, p -> b where
  anyToken :: p a b

세 매개변수의 역할. Tokenized a b p는 세 타입 사이의 관계입니다.

  • p는 프린터-파서의 타입입니다. 예를 들어 Parsor String []나 Printor String []입니다. 매개변수 두 개를 더 받아 p a b가 되는 타입 생성자입니다.
  • a는 프린터 쪽에서 받는 토큰의 타입입니다.
  • b는 파서 쪽에서 내는 토큰의 타입입니다.

문자열 스트림에서는 a와 b가 모두 Char입니다. 두 자리가 따로 있는 이유는 아래 Identical과 4쪽의 타입을 바꾸는 옵틱(optic) 때문이며, 스트림 인스턴스는 항상 같은 타입(c c)을 씁니다.

| p -> a, p -> b의 뜻. "p가 정해지면 a가 정해지고, p가 정해지면 b가 정해진다"는 두 개의 함수적 종속성입니다. 프린터-파서의 타입만 알면 그것이 다루는 토큰 타입이 결정된다는 말이며, 직관적으로도 자연스럽습니다. String을 읽는 파서의 토큰은 당연히 Char입니다.

이 규칙은 무엇을 하려는 것일까요. 2쪽에서 보았듯이 Parsor는 왼쪽 매개변수 a를 쓰지 않습니다. 원문 예제의 다음 식을 생각해 보십시오.

runParsor anyToken "xyz" :: [(Char,String)]

이 식에서 GHC가 알 수 있는 것은 p가 Parsor String []이고 결과 토큰 b가 Char라는 사실뿐입니다. a는 식 어디에도 나타나지 않습니다. p -> a 규칙의 의도는, 이렇게 p만 알려진 상황에서 GHC가 인스턴스를 보고 빠진 a를 채워 넣게 하는 것입니다. 즉 함수적 종속성은 유령(phantom) 쪽 매개변수를 p로부터 정하려는 장치입니다.

이 장치가 실제로 동작하는지는 인스턴스 머리의 모양에 달려 있습니다.

  • 머리가 토큰 타입을 직접 적는 경우: 위 코드 블록의 instance Tokenized a b (Identical a b)처럼 p 자리(Identical a b)에 a와 b가 그대로 들어 있으면, p를 아는 순간 a와 b가 정해집니다. 원문 코드가 아닌 작은 실험으로 확인해 보면, p가 Identical Char Bool로 알려진 자리에 타입 표시 없이 anyToken을 넣어도 GHC가 나머지 두 자리를 Char와 Bool로 채웁니다.
  • 원문의 스트림 인스턴스: 아래에서 읽을 instance (..., Cons s s c c) => Tokenized c c (Parsor s f)에서는 p 자리(Parsor s f)에 c가 없고, c는 인스턴스 문맥의 Cons s s c c에서만 정해집니다. 이 경우 GHC는 두 규칙 p -> a와 p -> b를 따로따로 적용하면서 c를 규칙마다 새 변수로 둡니다. 그래서 b가 Char라는 정보가 a에까지 전해지지 않습니다.

원문 코드에 관한 짧은 주의. 원문은 literate Haskell이 아니어서, 코드가 그대로 컴파일된다는 보장은 없습니다(8쪽 참고). 바로 위의 이유로, 원문의 인스턴스 머리를 그대로 옮겨 최소한으로 다시 만든 코드를 GHC 9.10.3에서 실행하면 예제 runParsor anyToken "xyz" :: [(Char,String)]는 a가 모호하다는 오류를 냅니다. anyToken :: Parsor String [] Char Char처럼 두 자리를 모두 적으면 문제없이 동작합니다. 뒤에 나오는 token, satisfy, posDecInt 같은 예제는 시그니처가 두 자리를 고정하므로 영향을 받지 않습니다. 참고로 현재 distributors 패키지는 이 클래스를 class Categorized token => Tokenized token p | p -> token 꼴로 바꾸었으며, 이것은 원문의 코드와 다른 이후의 설계입니다.

Identical: GADT 문법으로 쓴 타입 동치 증거

Identical을 읽으려면 GADT 문법을 알아야 합니다.

GADT 문법 처음부터

일반화 대수적 자료형(generalized algebraic data type, GADT) 문법은 생성자마다 타입 시그니처를 직접 쓰는 자료형 선언 방식입니다. 익숙한 Maybe를 GADT 문법으로 쓰면 다음과 같습니다.

data Maybe a where
  Nothing :: Maybe a
  Just    :: a -> Maybe a

data ... where 다음 줄마다 "생성자 이름 :: 생성자의 타입"을 씁니다. Just :: a -> Maybe a는 "Just는 a를 받아 Maybe a를 만드는 생성자"라는 뜻입니다. 여기까지는 보통의 선언과 같은 내용을 다르게 적었을 뿐입니다.

GADT의 진짜 힘은 생성자의 결과 타입을 구체적으로 정할 수 있다는 데 있습니다. 다음은 원문 코드가 아닌 고전적인 예시입니다.

data Expr a where
  IntE  :: Int -> Expr Int
  BoolE :: Bool -> Expr Bool
  If    :: Expr Bool -> Expr a -> Expr a -> Expr a

evalE :: Expr a -> a
evalE (IntE n)   = n
evalE (BoolE b)  = b
evalE (If c x y) = if evalE c then evalE x else evalE y

IntE로 만든 값은 반드시 Expr Int이고, BoolE로 만든 값은 반드시 Expr Bool입니다. 그래서 evalE의 IntE n 갈래에서 GHC는 "여기서 a는 Int"라는 사실을 압니다. 결과 타입이 a인데 n :: Int를 돌려줘도 되는 이유입니다. 이렇게 패턴 매칭이 타입 정보를 늘려 주는 성질이 GADT의 핵심입니다.

>>> evalE (If (BoolE True) (IntE 1) (IntE 2))
1

GADT의 이런 타입 정제(type refinement)는 보통 GADTs 확장을 켜고 씁니다.

Identical 읽기

하이라이트:

where
  Identical :: Identical a b a b

원문 문맥:

data Identical a b s t where
  Identical :: Identical a b a b
instance Tokenized a b (Identical a b) where
  anyToken = Identical

하이라이트는 data Identical a b s t 줄 끝의 where부터 생성자 시그니처까지입니다. 처음 보면 Identical :: Identical a b a b가 같은 이름을 되풀이하는 순환 정의처럼 보이지만, 앞의 Identical은 생성자 이름이고 뒤의 Identical a b a b는 타입입니다. 타입과 생성자가 같은 이름을 쓰는 것은 newtype Parsor = Parsor ...에서도 본 관례입니다.

타입이 말하는 것. data Identical a b s t는 매개변수가 네 개인 타입입니다. 그런데 유일한 생성자 Identical의 타입은 Identical a b a b입니다. 세 번째 자리가 첫 번째와 같고(s가 a), 네 번째 자리가 두 번째와 같습니다(t가 b). 따라서 Identical a b s t 타입의 값은 s가 a와 같고 t가 b와 같을 때에만 존재할 수 있습니다. 그 값을 가지고 있다는 사실 자체가 두 타입이 같다는 증거입니다. 이런 타입을 타입 동치 증거(type equality witness)라고 부릅니다. base의 Data.Type.Equality에 있는 Refl :: a :~: a가 같은 생각을 한 쌍의 타입에 적용한 것이고, lens 라이브러리의 Control.Lens.Equality 모듈에도 "(s ~ a, b ~ t)가 성립한다는 증거"라는 설명과 함께 같은 이름의 타입이 있습니다(lens 문서: Control.Lens.Equality). 원문은 lens의 이 타입을 언급하지 않습니다.

패턴 매칭으로 증거를 쓰는 모습. 위의 evalE처럼, Identical을 패턴 매칭하면 GHC는 그 갈래에서 s와 a가 같다는 것을 압니다. 다음은 원문 코드가 아닌 작은 예시입니다.

castWith :: Identical a b s t -> s -> a
castWith Identical x = x

x의 타입은 s인데 결과 타입은 a입니다. 보통이라면 타입 오류지만, Identical과 매칭된 갈래에서는 s와 a가 같으므로 컴파일됩니다.

>>> castWith (Identical :: Identical Int Bool Int Bool) 5
5

Tokenized 인스턴스. instance Tokenized a b (Identical a b) where anyToken = Identical에서 p는 Identical a b입니다. 그러면 anyToken :: p a b는 Identical a b a b가 되고, 이것은 정확히 생성자 Identical의 타입입니다. 함수적 종속성 p -> a, p -> b도 자연스럽게 맞습니다. p = Identical a b를 보면 a와 b가 바로 보입니다.

이것이 왜 쓸모 있을까요. Identical은 아무것도 파싱하지도, 출력하지도 않습니다. 그저 "여기에 토큰 하나가 온다"는 표시입니다. 이 표시는 나중에 어떤 Tokenized 인스턴스로든 해석할 수 있습니다. 다음은 원문 코드가 아닌 예시입니다.

fromIdentical :: Tokenized a b p => Identical a b s t -> p s t
fromIdentical Identical = anyToken

Identical과 매칭된 갈래에서 s는 a, t는 b이므로 anyToken :: p a b를 p s t 자리에 돌려줄 수 있습니다.

>>> runParsor (fromIdentical (anyToken :: Identical Char Char Char Char) :: Parsor String [] Char Char) "hi"
[('h',"i")]

즉 Identical은 가장 헐벗은 Tokenized이며, "토큰 하나"를 데이터로 적어 둔 것입니다. 8쪽의 열린 질문 "Identical Char Char에서 출발하는 자유(free) Grammatical 디스트리뷰터(distributor)"는 바로 이 생각을 문법 전체로 넓히자는 제안입니다. 한 가지 덧붙이면, Identical은 Profunctor가 아니며 그럴 필요도 없습니다. Tokenized 클래스에는 상위 클래스가 없기 때문입니다.

lens 라이브러리 입문

원문은 이어서 lens 라이브러리의 Cons 클래스를 가져옵니다. 이 클래스의 메서드 타입에는 Prism이 나오므로, lens를 처음 쓰는 독자를 위해 필요한 만큼만 처음부터 설명하겠습니다. 4쪽은 이 개념들의 내부 구조를 자세히 다룹니다.

lens는 무엇을 하는 라이브러리인가

lens는 Edward Kmett가 만든 하스켈 라이브러리이며, 자료 구조의 일부를 읽고 고치고 맞추어 보는 일을 일급 값(first-class value)으로 다루게 해 줍니다. 이런 값을 통틀어 옵틱(optic)이라고 부릅니다. 이 글에서 lens는 Cons, Prism, Iso, 그리고 7쪽의 makePrisms를 제공합니다.

렌즈: 정확히 한 부분에 초점 맞추기

렌즈(lens)는 구조 안의 정확히 한 부분을 가리킵니다. _1은 쌍의 첫 원소를 가리키는 렌즈입니다. 렌즈로 할 수 있는 기본 동작은 세 가지입니다.

  • view l s: s에서 l이 가리키는 부분을 읽습니다.
  • over l f s: 그 부분에 함수 f를 적용한 새 구조를 만듭니다.
  • set l x s: 그 부분을 값 x로 바꾼 새 구조를 만듭니다.

다음은 원문 코드가 아닌 예시입니다. 실제 lens 라이브러리 대신 lens의 정의를 따라 필요한 부분만 다시 만든 코드로 실행했으며, 결과는 lens 문서가 설명하는 동작과 같습니다.

>>> view _1 (1,'x')
1
>>> over _1 (+1) (1,'x')
(2,'x')
>>> set _1 0 (1,'x')
(0,'x')

프리즘: 여러 경우 중 한 경우에 맞추기

프리즘(prism)은 합 타입(sum type)의 한 생성자를 가리킵니다. 렌즈와 달리 그 경우가 아닐 수 있으므로 "맞으면 꺼내고, 아니면 실패"합니다. 프리즘에는 두 방향이 있습니다.

  • preview p s: s가 그 경우이면 Just로 내용을 꺼내고, 아니면 Nothing을 돌려줍니다. 이것이 맞추기(match) 방향입니다.
  • review p x: 내용 x로 그 경우의 값을 만듭니다(build).

_Just는 Maybe의 Just 경우를 가리키는 프리즘입니다.

>>> preview _Just (Just 3)
Just 3
>>> preview _Just Nothing
Nothing
>>> review _Just 3
Just 3

프리즘은 결국 "맞추는 함수"와 "만드는 함수"의 쌍이라고 생각하면 됩니다. 이것이 정확히 파서와 프린터의 관계와 닮았다는 점이 이 글의 핵심 착안 중 하나입니다. 파서는 텍스트에서 값을 맞추어 꺼내고, 프린터는 값에서 텍스트를 만듭니다.

타입 Prism s t a b 읽기

lens의 옵틱 타입은 Prism s t a b처럼 매개변수 네 개를 받습니다. s는 바깥 구조, a는 그 안에서 맞춘 부분입니다. t와 b는 "부분을 b로 바꾸면 바깥 구조가 t가 된다"는 타입 변경을 위한 자리입니다. 타입을 바꾸지 않는 단순한 경우에는 Prism' s a = Prism s s a a라고 씁니다. 예를 들어 _Just :: Prism' (Maybe Int) Int처럼 쓸 수 있습니다. 이 네 글자 약속은 2쪽에서 본 dimap의 s, t, a, b와 같습니다.

Cons 클래스: (:) 패턴의 일반화

원문은 anyToken의 의도를 다음과 같이 설명합니다. s가 String이라면 anyToken은 "cons" 패턴 (:)에 해당하며, 출력할 때는 Char 하나를 String 맨 앞에 붙이고(cons), 파싱할 때는 맨 앞에서 떼어 냅니다(uncons). 그리고 lens 라이브러리의 Cons 인터페이스가 (:) 패턴을 일반화하므로 스트림 타입에 대해 다형적인 상태를 유지할 수 있다고 말합니다.

원문 두 번째 코드 블록 전체는 다음과 같습니다.

class Cons s t a b | s -> a, t -> b, s b -> t, t a -> s where
  _Cons :: Prism s t (a,s) (b,t)

instance (Applicative f, Cons s s c c)
  => Tokenized c c (Printor s f) where
    anyToken = Printor (pure . cons)

instance (Alternative f, Cons s s c c)
  => Tokenized c c (Parsor s f) where
    anyToken = Parsor (maybe empty pure . uncons)

Cons 클래스 읽기

하이라이트:

class Cons s t a b | s -> a, t -> b, s b -> t, t a -> s where
  _Cons :: Prism s t (a,s) (b,t)

원문 문맥:

The lens library provides a Cons interface which generalizes the (:) pattern, letting us remain polymorphic over the stream type.

class Cons s t a b | s -> a, t -> b, s b -> t, t a -> s where
  _Cons :: Prism s t (a,s) (b,t)

이 두 줄은 lens 라이브러리의 Control.Lens.Cons 모듈에 있는 클래스 선언과 같습니다(lens 문서: Control.Lens.Cons).

매개변수. s는 원소 타입이 a인 스트림이고, t는 원소 타입이 b인 스트림입니다. 예를 들어 String이면 s = String, a = Char입니다.

메서드 _Cons. _Cons :: Prism s t (a,s) (b,t)는 스트림과 "(머리, 꼬리)" 쌍 사이의 프리즘입니다. 비어 있지 않은 스트림은 이 프리즘에 맞고, 맞추면 첫 원소(머리, head)와 나머지(꼬리, tail)의 쌍이 나옵니다. 빈 스트림은 맞지 않습니다. 반대 방향으로는 (머리, 꼬리) 쌍으로 스트림을 만듭니다. 즉 (:) 생성자를 맞추기와 만들기 두 방향 모두로 쓸 수 있게 한 것입니다. 원문 코드가 아닌 예시로 확인해 보겠습니다.

>>> preview _Cons "abc"
Just ('a',"bc")
>>> preview _Cons ""
Nothing
>>> review _Cons ('x',"yz")
"xyz"

네 개의 함수적 종속성. 세로 막대 뒤의 규칙을 하나씩 읽으면 다음과 같습니다.

규칙 뜻 예
s -> a 스트림 타입이 원소 타입을 정합니다. String이면 원소는 Char
t -> b 바뀐 스트림 타입도 자기 원소 타입을 정합니다. [String]이면 원소는 String
s b -> t 원래 스트림과 새 원소 타입이 정해지면, 바뀐 스트림 타입이 정해집니다. [Int]에서 원소를 String으로 바꾸면 [String]
t a -> s 반대 방향도 마찬가지입니다. [String]과 Int에서 [Int]

이 규칙 덕분에 _Cons로 원소 타입을 바꾸는 갱신도 타입 추론이 됩니다. 원문 코드가 아닌 예시입니다.

>>> over _Cons (\(h, t) -> (show h, map show t)) [1,2,3::Int]
["1","2","3"]

s = [Int]이고 새 원소 타입 b = String이므로 s b -> t 규칙이 t = [String]을 정합니다.

인스턴스와 함수 cons, uncons. lens에는 목록, Text(원소는 Char), ByteString(원소는 Word8), Seq, Vector 등에 대한 Cons 인스턴스가 있습니다. 그리고 _Cons를 쓰기 쉽게 감싼 두 함수가 있습니다.

cons   :: Cons s s a a => a -> s -> s
uncons :: Cons s s a a => s -> Maybe (a, s)
>>> uncons "xyz"
Just ('x',"yz")
>>> uncons ""
Nothing
>>> cons 'x' "yz"
"xyz"

cons는 원소를 스트림 앞에 붙이고(프리즘의 만들기 방향), uncons는 첫 원소를 떼어 냅니다(프리즘의 맞추기 방향). 제약 Cons s s a a는 타입을 바꾸지 않는 경우라는 뜻입니다. 이 두 함수만 있으면 Printor와 Parsor가 어떤 스트림 타입에서도 토큰 하나를 다룰 수 있습니다.

두 인스턴스 읽기

프린터: 토큰 하나를 앞에 붙이기

하이라이트: Printor (pure . cons)

원문 문맥:

instance (Applicative f, Cons s s c c)
  => Tokenized c c (Printor s f) where
    anyToken = Printor (pure . cons)

인스턴스 머리 읽기. "결과 컨테이너 f가 Applicative이고 스트림 s의 원소 타입이 c이면, Printor s f는 토큰 타입이 c인 Tokenized이다"라는 뜻입니다. 이때 anyToken :: Printor s f c c이고, 감싼 함수의 타입은 c -> f (s -> s)이어야 합니다.

점 없는 표기 풀기. pure . cons는 인자를 드러내지 않은 점 없는 표기(point-free style)입니다. 인자를 드러내면 다음과 같습니다.

pure . cons  =  \c -> pure (cons c)

타입을 맞추어 보겠습니다.

  • cons :: c -> s -> s이므로 cons c :: s -> s입니다. "남은 스트림 앞에 c를 붙이는 자기 함수"입니다.
  • pure :: (s -> s) -> f (s -> s)는 그 함수를 실패 없는 결과 하나로 컨테이너에 담습니다.

그래서 pure . cons :: c -> f (s -> s)가 되어 Printor가 요구하는 타입과 정확히 맞습니다.

값이 흐르는 모습. 원문 예제를 손으로 계산하면 다음과 같습니다.

runPrintor anyToken 'x'
= (pure . cons) 'x'
= pure (cons 'x')        -- f = [] 이면 [('x':)]
(cons 'x') "yz" = "xyz"

왜 Applicative f면 충분할까요. 토큰 하나를 출력하는 일은 실패할 수 없습니다. 어떤 c든 스트림 앞에 붙일 수 있기 때문입니다. 그래서 성공을 만드는 pure만 있으면 되고, 실패를 만드는 empty는 필요 없습니다. 2쪽의 용어로 이 프린터는 망라적(exhaustive)입니다.

파서: 토큰 하나를 떼어 내기

하이라이트: Parsor (maybe empty pure . uncons)

원문 문맥:

instance (Alternative f, Cons s s c c)
  => Tokenized c c (Parsor s f) where
    anyToken = Parsor (maybe empty pure . uncons)

필요한 타입. anyToken :: Parsor s f c c이므로 감싼 함수의 타입은 s -> f (c, s)여야 합니다. 스트림을 받아 (토큰, 남은 스트림)을 컨테이너에 담아 돌려주는 함수입니다.

uncons가 거의 다 해 줍니다. uncons :: s -> Maybe (c, s)는 이미 비슷한 모양입니다. 차이는 결과가 Maybe라는 점뿐입니다. 그래서 Maybe (c, s)를 f (c, s)로 바꾸는 함수가 필요합니다.

maybe empty pure 읽기. Prelude의 maybe 함수는 다음 타입을 가집니다.

maybe :: r -> (x -> r) -> Maybe x -> r

maybe d k m은 m이 Nothing이면 기본값 d를, Just x이면 k x를 돌려줍니다. 여기에 d = empty, k = pure를 넣으면 다음과 같습니다.

maybe empty pure Nothing  = empty      -- 실패
maybe empty pure (Just x) = pure x     -- 결과 하나로 성공

즉 maybe empty pure :: Maybe x -> f x는 Maybe의 실패와 성공을 임의의 Alternative f의 실패와 성공으로 옮기는 변환입니다. 1쪽에서 설명했듯이 empty는 Alternative의 "실패", pure는 Applicative의 "결과 하나로 성공"입니다.

합성하면. maybe empty pure . uncons는 \s -> maybe empty pure (uncons s)입니다. 스트림을 uncons로 쪼개고, 빈 스트림이면 실패하고, 아니면 (머리, 꼬리)를 결과로 내놓습니다. 원문 예제를 손으로 계산하면 다음과 같습니다.

runParsor anyToken "xyz"
= (maybe empty pure . uncons) "xyz"
= maybe empty pure (Just ('x', "yz"))
= pure ('x', "yz")       -- f = [] 이면 [('x',"yz")], f = Maybe 이면 Just ('x',"yz")

runParsor anyToken ""
= maybe empty pure Nothing
= empty                  -- f = [] 이면 [], f = Maybe 이면 Nothing

왜 Alternative f가 필요할까요. 빈 스트림에서는 토큰을 떼어 낼 수 없으므로 실패를 표현해야 하고, 실패는 empty로만 만들 수 있습니다. 파서는 2쪽의 용어로 부분적(partial)입니다. 같은 anyToken이라는 이름 아래에서 프린터는 Applicative만, 파서는 Alternative를 요구한다는 비대칭이 2쪽의 "출력은 망라적, 파싱은 부분적"이라는 관찰과 정확히 맞아떨어집니다.

첫 프린터-파서 실행

원문은 이 절을 다음 예제로 마무리합니다.

>>> runParsor anyToken "xyz" :: [(Char,String)]
[('x',"yz")]
>>> runParsor anyToken "" :: [(Char,String)]
[]
>>> [pr "yz" | pr <- runPrintor anyToken 'x'] :: [String]
["xyz"]

>>>로 시작하는 줄은 GHCi나 doctest에 넣는 식이고, 그 아래 줄이 결과입니다.

  • 첫 줄: "xyz"에서 토큰 하나를 읽어 'x'와 남은 스트림 "yz"를 얻습니다. 타입 표시 :: [(Char,String)]가 s = String, f = []를 정합니다.
  • 둘째 줄: 빈 문자열에서는 실패하므로 빈 목록입니다.
  • 셋째 줄: 'x'를 출력하면 함수의 목록 [('x':)]가 나오고, 리스트 컴프리헨션이 그 함수를 남은 스트림 "yz"에 적용하여 "xyz"를 얻습니다.

같은 이름 anyToken이 문맥에 따라 파서도 되고 프린터도 된다는 점이 이 글이 처음으로 보여 주는 "한 정의, 두 방향"입니다. 결과 컨테이너를 Maybe로 바꾸면 다음처럼 결과가 하나이거나 없습니다. 이것은 원문 코드가 아닌 예시이며, 위에서 말한 모호성을 피하려고 두 자리를 모두 적었습니다.

>>> runParsor (anyToken :: Parsor String Maybe Char Char) "xyz"
Just ('x',"yz")
>>> runParsor (anyToken :: Parsor String Maybe Char Char) ""
Nothing

이 쪽이 글의 목표에 기여하는 바

이 절로 "한 정의가 파서이자 프린터"가 처음으로 실제 동작합니다. anyToken은 클래스 메서드이므로 p가 Parsor이면 토큰을 떼어 내는 파서, Printor이면 토큰을 붙이는 프린터가 됩니다. 그리고 Identical처럼 아무 일도 하지 않고 "토큰 하나"라는 표시만 남기는 해석도 가능합니다. 하지만 anyToken은 아무 토큰이나 받아들입니다. 특정 글자만 받거나, 조건을 만족하는 글자만 받으려면 결과를 걸러 내고 입력을 검사하는 장치가 필요합니다. 4쪽은 그 장치를 옵틱으로 만들고, 그 결과로 token과 satisfy를 얻습니다.

정리

  • 조합자만으로는 아무것도 만들 수 없으므로 기본 부품이 필요하며, 이 글의 기본 부품은 스트림 맨 앞 토큰 하나를 다루는 anyToken 하나뿐입니다.
  • 다중 매개변수 타입 클래스는 여러 타입 사이의 관계를 표현하고, 함수적 종속성 | p -> a, p -> b는 "프린터-파서 타입이 토큰 타입을 정한다"는 규칙입니다. 이 규칙은 Parsor의 쓰이지 않는 왼쪽 자리를 p로부터 정하려는 장치입니다. 인스턴스 머리가 토큰 타입을 직접 적는 Identical에서는 동작하지만, 원문의 스트림 인스턴스에서는 두 자리를 모두 적어 주어야 합니다.
  • Identical :: Identical a b a b는 GADT 문법으로 쓴 타입 동치 증거입니다. 아무 일도 하지 않고 "토큰 하나"를 표시하며, 어떤 Tokenized 인스턴스로든 나중에 해석할 수 있습니다.
  • lens의 렌즈는 한 부분에(view, over, set), 프리즘은 한 경우에(preview, review) 초점을 맞춥니다. Cons의 _Cons는 스트림과 (머리, 꼬리) 사이의 프리즘이고, cons와 uncons가 그 두 방향입니다.
  • 프린터의 anyToken = Printor (pure . cons)는 실패하지 않으므로 Applicative면 충분하고, 파서의 anyToken = Parsor (maybe empty pure . uncons)는 빈 스트림에서 실패해야 하므로 Alternative가 필요합니다.

이 편의 원문

Tokens

Combinators are great for generating new printer-parsers from existing ones, but if we want to generate examples we need an interface which generates basic printer-parsers from scratch. For that purpose, we define the Tokenized interface.

class Tokenized a b p | p -> a, p -> b where
  anyToken :: p a b

data Identical a b s t where
  Identical :: Identical a b a b
instance Tokenized a b (Identical a b) where
  anyToken = Identical

The Tokenized interface is so abstract it would lack any obvious motivation if not for its name. We want anyToken to sequence any single token from the head of the printer-parser stream type s. Recall that s appears as both input and output in the definitions of Parsor & Printor. If s were String then anyToken would correspond to the "cons" pattern (:) which conses (prints) or unconses (parses) any single Char to or from the head of the String. The lens library provides a Cons interface which generalizes the (:) pattern, letting us remain polymorphic over the stream type.

class Cons s t a b | s -> a, t -> b, s b -> t, t a -> s where
  _Cons :: Prism s t (a,s) (b,t)

instance (Applicative f, Cons s s c c)
  => Tokenized c c (Printor s f) where
    anyToken = Printor (pure . cons)

instance (Alternative f, Cons s s c c)
  => Tokenized c c (Parsor s f) where
    anyToken = Parsor (maybe empty pure . uncons)

Now we can see our first printer-parser in action.

>>> runParsor anyToken "xyz" :: [(Char,String)]
[('x',"yz")]
>>> runParsor anyToken "" :: [(Char,String)]
[]
>>> [pr "yz" | pr <- runPrintor anyToken 'x'] :: [String]
["xyz"]
