Distributors 해설 6/8: 디스트리뷰터 (Distributors)

해설 대상 원문: Eitan Chatav, “Distributors — Unifying Parsers, Printers & Grammars”

검토일: 2026-11-21

이 쪽은 여덟 쪽 시리즈의 여섯 번째 쪽이며, 글의 제목이 된 "Distributors" 절을 다룹니다. 5쪽에서 프린터-파서(printer-parser)를 차례로 잇는 방법(곱)을 얻었으니, 이제 "여러 경우 중 하나"를 다루는 방법(합)과 반복, 실패를 다룹니다. 원문은 Alternative를 쌍대곱(coproduct)의 관점에서 다시 쓰고, 그 모양을 프로펑터(profunctor)로 옮긴 Distributor 클래스를 도입합니다. 이어서 실패를 허용하는 Alternator와 그 쌍대인 Filtrator를 정의하고, 끝에서 양의 십진 정수를 파싱하고 출력하는 첫 번째 "제대로 된" 예제 posDecInt를 완성합니다.

5쪽까지에서 가져올 것

  • Alternative의 empty는 실패, <|>는 "둘 다 시도", many/some/optional은 0번 이상/1번 이상/0번 또는 1번 반복입니다. 1쪽에서 작은 파서 예제와 함께 처음부터 설명했습니다.
  • Monoidal p는 (Profunctor p, forall x. Applicative (p x))이며, oneP :: p () ()와 >*< :: p a b -> p c d -> p (a,c) (b,d)를 줍니다(5쪽). forall x.가 들어간 제약은 양화 제약(quantified constraint)입니다.
  • mapIso는 동형(isomorphism)을, >?는 프리즘(prism)을, >?<는 부분 동형(partial isomorphism)을 프린터-파서에 적용합니다(4쪽).
  • 결과 컨테이너 f에 Applicative만 요구하면 망라적(exhaustive), Alternative를 요구하면 부분적(partial)입니다(2쪽).
  • Parsor는 출력 쪽만, Printor는 입력 쪽만 씁니다(2쪽).

Alternative 다시 보기

원문은 파싱 이야기에서 Applicative가 늘 주인공이고 Alternative는 관심을 덜 받는다고 말하며, Alternative를 다시 봅니다.

class Applicative f => Alternative f where
  empty :: f a
  (<|>) :: f a -> f a -> f a

base의 실제 클래스에는 some과 many도 메서드로 들어 있지만, 최소 정의는 이 두 메서드입니다. empty는 결과가 없는 계산이고, <|>는 같은 타입 f a의 두 계산을 합칩니다.

쌍대곱으로 다시 쓰기: zeroF와 <+>

원문은 empty와 <|> 대신 zeroF와 <+>라는 이름으로 Alternative를 다시 특징짓습니다. 그렇게 하면 Alternative가 0항 쌍대곱 Void, 2항 쌍대곱 Either와 어떤 관계인지 더 분명해진다는 것입니다.

먼저 용어입니다. 쌍대곱(coproduct)은 "둘 중 하나"를 나타내는 타입, 즉 합 타입(sum type)을 범주론(category theory)에서 부르는 이름입니다. 2항 쌍대곱은 Either a b이고, 0항 쌍대곱은 "고를 것이 하나도 없는" 타입 Void입니다. Data.Void 모듈의 Void는 값이 하나도 없는 타입이며, absurd :: Void -> a는 "있을 수 없는 값을 받았으니 아무 타입이나 돌려줄 수 있다"는 함수입니다. 실제로 호출될 일은 없습니다. 곱(product) 쪽에서 (,)와 ()가 하던 일을 합 쪽에서 Either와 Void가 합니다.

zeroF :: Alternative f => f Void
zeroF = empty

(<+>) :: Alternative f => f a -> f b -> f (Either a b)
a <+> b = Left <$> a <|> Right <$> b

prop> empty = absurd <$> zeroF
prop> a <|> b = either id id <$> (a <+> b)
  • zeroF :: f Void: 결과 타입이 Void인 계산입니다. 결과 값이 있을 수 없으므로 실패하는 계산일 수밖에 없습니다.
  • a <+> b: a를 시도해 결과에 Left를 붙이고, b를 시도해 결과에 Right를 붙여 합칩니다. <|>와 달리 두 계산의 결과 타입이 달라도 되고, 결과에서 어느 쪽에서 왔는지 알 수 있습니다.
  • prop>로 시작하는 줄은 정의가 아니라 법칙입니다. doctest의 QuickCheck 속성 표기이며, "왼쪽과 오른쪽이 같아야 한다"는 뜻입니다. 첫 법칙은 zeroF에서 empty를 되찾고, 둘째 법칙은 <+>의 결과에서 Left/Right 표시를 지워(either id id) <|>를 되찾습니다. 즉 두 묶음의 연산은 서로를 정의할 수 있습니다.

다음은 원문 코드가 아닌 예시입니다. 이 쪽의 예시는 모두 원문과 필요한 라이브러리 정의를 최소한으로 다시 만든 코드로 GHC 9.10.3에서 실행한 결과입니다.

>>> Just 1 <+> (Nothing :: Maybe Char)
Just (Left 1)
>>> [1,2] <+> "ab"
[Left 1,Left 2,Right 'a',Right 'b']
>>> either id id <$> ([1,2] <+> [3])
[1,2,3]

왜 Monoidal과 같은 방법이 통하지 않을까요

원문은 "Profunctor와 Applicative를 합쳐 Monoidal을 정의한 방법이 Alternative에는 통하지 않는다"고만 말하고 이유를 길게 설명하지 않습니다. 다음은 원문과 이후의 정의에서 읽어 낸 해석입니다.

(Profunctor p, forall x. Alternative (p x))라고 쓰면, <|>는 p x a -> p x a -> p x a처럼 입력 타입이 같은 두 프린터-파서만 합칠 수 있습니다. 그런데 "여러 경우 중 하나"를 출력하려면, 프린터가 입력 값을 보고 어느 경우인지 판단해 알맞은 하위 프린터로 보내야 합니다. 예를 들어 Either a c를 출력하려면 Left a는 a용 프린터로, Right c는 c용 프린터로 가야 합니다. <|>는 같은 입력을 두 쪽에 모두 줄 뿐 입력을 갈래에 따라 나누지 못합니다. 또한 함수 화살표 (->)는 either f g처럼 경우를 나누는 일을 자연스럽게 하지만, 실패를 뜻하는 empty를 만들 수 없으므로 Alternative가 될 수 없습니다. 그래서 입력 쪽과 출력 쪽 모두에서 Either를 다루는 새 연산이 필요합니다.

Distributor 클래스

class Monoidal p => Distributor p where
  zeroP :: p Void Void
  (>+<) :: p a b -> p c d -> p (Either a c) (Either b d)

<+>를 프로펑터로 옮긴 모양입니다. 5쪽의 oneP와 >*<가 ()와 (,)를 다뤘다면, zeroP와 >+<는 Void와 Either를 다룹니다.

  • zeroP :: p Void Void: 입력도 출력도 있을 수 없는 프린터-파서입니다. 프린터로는 출력할 값이 들어올 수 없고, 파서로는 결과를 낼 수 없으므로 항상 실패합니다.
  • x >+< y: x :: p a b와 y :: p c d로 Either를 다루는 프린터-파서를 만듭니다. 프린터로는 입력이 Left a이면 x로, Right c이면 y로 출력합니다. 즉 입력에 대한 경우 나누기입니다. 파서로는 x로 파싱해 Left를 붙이거나 y로 파싱해 Right를 붙입니다.
  • class Monoidal p => Distributor p: 모든 Distributor는 Monoidal입니다. 곱과 합을 함께 다룹니다.

함수 화살표 (->)가 대표적인 Distributor입니다. 원문은 인스턴스를 보여 주지 않으므로 다음은 재구성입니다.

instance Distributor (->) where
  zeroP = id
  f >+< g = either (Left . f) (Right . g)
>>> (show >+< not) (Right True :: Either Int Bool)
Right False

Right True가 들어오면 오른쪽 함수 not이 처리하고 결과에 Right가 붙습니다. 경우 나누기가 실패 없이 이루어지므로 이것은 망라적인 Distributor입니다.

optionalP와 manyP: 반복을 쌍대곱으로

원문은 Alternative에 0번 이상의 many와 0번 또는 1번의 optional이 있듯이, manyP와 optionalP를 정의할 수 있다고 말합니다.

optionalP :: Distributor p => p a b -> p (Maybe a) (Maybe b)
optionalP p = mapIso eotMaybe (oneP >+< p)

manyP :: p a b -> p [a] [b]
manyP p = mapIso listEot (oneP >+< p >*< manyP p)

eotMaybe :: Iso (Maybe a) (Maybe b) (Either () a) (Either () b)

listEot
  :: (Cons s s a a, AsEmpty t, Cons t t b b)
  => Iso s t (Either () (a,s)) (Either () (b,t))

튜플의 Either 표현

이 정의의 열쇠는 자료형을 Either와 튜플로 다시 쓰는 것입니다.

  • Maybe a는 "아무것도 없음 또는 a 하나"이므로 Either () a와 같은 정보를 담습니다. Nothing은 Left (), Just x는 Right x입니다.
  • 목록 [a]는 "빈 목록 또는 (머리, 꼬리)"이므로 Either () (a, [a])와 같은 정보를 담습니다.

eotMaybe와 listEot는 이 대응을 나타내는 동형(isomorphism)이며, 이름의 eot는 "eithers-of-tuples"(튜플의 Either 표현)의 줄임말입니다. 원문은 타입 시그니처만 주고 본문은 생략했습니다. 다음은 Maybe와 목록에 한정한 재구성입니다.

eotMaybe = iso (maybe (Left ()) Right) (either (const Nothing) Just)

listEot = iso (\xs -> case xs of [] -> Left (); (a:as) -> Right (a, as))
              (either (const []) (uncurry (:)))

원문의 listEot 시그니처는 더 일반적입니다. 3쪽의 Cons 클래스로 스트림(stream)을 (머리, 꼬리)로 나누고, lens의 AsEmpty 클래스로 빈 값을 만듭니다. AsEmpty는 "빈 값"이라는 경우를 가리키는 프리즘 _Empty를 가진 타입들의 클래스입니다.

정의 읽기

  • optionalP p = mapIso eotMaybe (oneP >+< p): "아무것도 하지 않기(oneP) 또는 p 한 번"을 >+<로 만들면 타입이 p (Either () a) (Either () b)가 되고, mapIso eotMaybe가 그것을 p (Maybe a) (Maybe b)로 바꿉니다.
  • manyP p = mapIso listEot (oneP >+< p >*< manyP p): "아무것도 하지 않기 또는 (p 한 번, 그 뒤에 manyP p)"입니다. 목록의 정의 자체를 따라가는 재귀입니다. 5쪽에서 말했듯이 원문은 연산자 우선순위를 적지 않았지만, 패키지는 >+<를 infixr 3, >*<를 infixr 5로 선언하므로 이 식은 oneP >+< (p >*< manyP p)로 읽힙니다.

짧은 주의. 원문의 manyP :: p a b -> p [a] [b]에는 Distributor p => 제약이 빠져 있습니다. 본문이 oneP와 >+<를 쓰므로 이 제약 없이는 타입 검사를 통과하지 못합니다. 오타로 읽으면 됩니다.

값이 흐르는 모습

함수 화살표에서 manyP는 우리가 아는 함수가 됩니다. 원문 코드가 아닌 예시입니다.

>>> manyP (+1) [1,2,3]
[2,3,4]
>>> optionalP not (Just True)
Just False

manyP는 함수에서 map이고, optionalP는 fmap입니다. Distributor 구조가 "경우 나누기와 쌍 다루기"이고, map이 하는 일이 바로 목록에 대한 경우 나누기와 쌍 다루기이기 때문입니다.

프린터-파서에서는 다음과 같습니다.

>>> runParsor (optionalP (token 'x') :: Parsor String [] (Maybe ()) (Maybe ())) "xy"
[(Nothing,"xy"),(Just (),"y")]
>>> runParsor (manyP (satisfy isDigit) :: Parsor String [] String String) "12a"
[("","12a"),("1","2a"),("12","a")]
>>> [pr "" | pr <- runPrintor (manyP (satisfy isDigit) :: Printor String [] String String) "42"]
["42"]

파서의 결과 순서에 주목하십시오. oneP가 >+<의 왼쪽에 있으므로 "아무것도 읽지 않은 경우"가 먼저 나오고, 목록 파서는 짧은 결과부터 돌려줍니다. 1쪽에서 본 base의 many는 반대로 긴 결과부터 돌려주었습니다. 참고로 현재 distributors 패키지는 optionalP와 manyP의 갈래 순서를 원문과 반대로 바꾸어 긴 쪽을 먼저 시도합니다.

이름 이야기: 디스트리뷰터

원문은 (->)가 Distributor의 대표적인 예라고 말한 뒤, 이름의 내력을 설명합니다.

  • 범주론(category theory)에서 디스트리뷰터(distributor)는 프로펑터의 다른 이름입니다. Jean Bénabou가 이 개념을 만들 때 처음에는 "profunctor"라는 말을 썼다가 나중에 "distributor"를 선호했다고 합니다. 이 설명은 nLab의 profunctor 항목과 같고, 원문이 링크한 Bénabou의 강의 노트 Distributors at Work는 디스트리뷰터를 범주 사이의 관계로 다룹니다.
  • "profunctor"가 널리 쓰이는 이름이 되었으므로, 원문은 "distributor"를 더 제한적인 인터페이스, 즉 느슨한 분배 프로펑터(lax distributive profunctor)의 이름으로 씁니다. 분배(distributive)라는 말은 (), (,), Void, Either가 이루는 분배 구조를 쓴다는 뜻입니다. 곱이 합 위로 분배되는 것, 예를 들어 (a, Either b c)가 Either (a, b) (a, c)와 같은 정보를 담는다는 성질입니다.

용어에 관한 짧은 주의. 범주론 문헌에서 "distributor"를 찾으면 이 글의 zeroP와 >+< 같은 추가 구조 없이 그냥 프로펑터를 뜻합니다. 이 글의 Distributor는 그 이름을 빌려 더 많은 구조를 가진 클래스에 붙인 것이며, 원문도 그렇게 밝힙니다. 덧붙여 McBride와 Paterson 논문에는 "applicative distributor"라는 표현이 있는데, 이것은 오늘날의 sequenceA에 해당하는 함수를 가리키는 전혀 다른 쓰임입니다.

원문은 또 디스트리뷰터가 모노이드 프로펑터만큼 연구되지 않았고, Alternative처럼 마땅한 관심을 받지 못하는 것 같다고 말합니다. 이것은 저자의 평가입니다. 관련 인터페이스가 아예 없지는 않습니다. 예를 들어 product-profunctors 패키지의 SumProfunctor 클래스는 (+++!) :: p a b -> p a' b' -> p (Either a a') (Either b b')를 가지며, zeroP는 없지만 >+<와 같은 모양입니다.

디옵터와 위치 패턴

원문은 Distributor에 대응하는 옵틱을 "디옵터(diopter)"라고 이름 붙였고, 이것을 위치 패턴(positional pattern)으로 생각할 수 있다고 말합니다. 이 이름은 저자의 용어이며, 현재 패키지는 Diopter를 forall p f. (Distributor p, Applicative f) => p a (f b) -> p s (f t)로 정의합니다. 4쪽의 Iso나 Prism과 같은 모양에서 p의 제약만 Distributor로 바뀐 것입니다.

"위치 패턴"의 뜻은 다음 문장에 있습니다. 대수적 자료형을 generics-eot 라이브러리의 튜플의 Either 표현으로 바꾸면, 그 대수적 구조를 >*<, oneP, >+<, zeroP로 그대로 맞출 수 있습니다. 예를 들어 generics-eot 문서는 data Foo = A Int Bool | B String을 Either (Int, (Bool, ())) (Either (String, ()) Void)로 나타냅니다. 이 타입의 프린터-파서는 생성자 이름 없이 "첫 번째 갈래의 첫 번째 필드"처럼 위치만으로 구조를 따라 만들 수 있습니다.

Either (Int, (Bool, ())) (Either (String, ()) Void)
   ~   (intP >*< boolP >*< oneP) >+< ((stringP >*< oneP) >+< zeroP)

위 그림은 원문에 없는 설명용 대응이며, intP, boolP, stringP는 가상의 부품 이름입니다.

Alternator: 실패를 허용하는 디스트리뷰터

원문은 Distributor가 프로펑터에 대한 Alternative의 망라적인 대응물이라고 말합니다. 부분성과 실패가 필요하면 Alternative와 더 닮은 다음 인터페이스가 필요합니다.

class (Choice p, Distributor p, forall x. Alternative (p x)) => Alternator p where
  alternate :: Either (p a b) (p c d) -> p (Either a c) (Either b d)
  • 상위 클래스: Choice(4쪽), Distributor, 그리고 양화 제약 forall x. Alternative (p x)입니다. 즉 Alternator는 출력 쪽에 대해 진짜 Alternative이기도 합니다.
  • alternate: 프린터-파서 하나를 받아, 그것을 Either의 한쪽 갈래에 놓습니다. alternate (Left x)는 "왼쪽 갈래만 담당하는 x"입니다. 프린터로는 Left a가 들어오면 x로 출력하고 Right c가 들어오면 실패합니다. 파서로는 x로 파싱해 결과에 Left를 붙입니다.

원문은 alternate가 Distributor의 메서드에 기본 구현을 준다고 말하고 다음 법칙을 적습니다.

prop> zeroP = empty
prop> x >+< y = alternate (Left x) <|> alternate (Right y)

둘째 법칙을 읽어 보겠습니다. 왼쪽 갈래 담당 x와 오른쪽 갈래 담당 y를 <|>로 합칩니다. 프린터로는 입력이 Left a이면 왼쪽 시도만 성공하고 오른쪽 시도는 실패하므로, 결과적으로 x로 출력됩니다. 파서로는 두 시도가 모두 실행되어 Left 결과와 Right 결과가 함께 나옵니다. 이렇게 "실패할 수 있는 갈래 담당 두 개를 <|>로 합치는" 방식으로도 >+<를 얻을 수 있습니다. 다만 이 방식은 empty와 <|>가 필요하므로 부분적입니다.

원문은 이 차이를 다음과 같이 정리합니다. 펑터에서는 zeroF와 <+>로 쓴 Alternative와 empty와 <|>로 쓴 Alternative가 동등하지만, 프로펑터에서는 둘이 갈라집니다. 망라적일 수 있는 Distributor와, 반드시 부분적인 Alternator입니다. 함수 화살표 (->)는 Alternative가 아니므로, Choice이면서 Distributor이지만 Alternator는 아닌 예입니다. 함수는 언제나 값을 돌려줘야 하므로 empty를 만들 수 없기 때문입니다.

Parsor와 Printor의 인스턴스

원문은 Parsor와 Printor가 모두 인스턴스를 가진다고 말하고 다음 코드를 보여 줍니다. alternate의 정의에 쓰인 \case는 LambdaCase 확장의 문법이며, \x -> case x of의 줄임말입니다.

instance (Alternative f, Monad f) => Alternative (Parsor s f a) where
  empty = Parsor (\_ -> empty)
  Parsor p <|> Parsor q = Parsor (\str -> p str <|> q str)

instance (Alternative f, Monad f) => Alternator (Parsor s f) where
  alternate = \case
    Left (Parsor p) -> Parsor (fmap (\(b, str) -> (Left b, str)) . p)
    Right (Parsor p) -> Parsor (fmap (\(b, str) -> (Right b, str)) . p)

instance (Alternative f, Monad f) => Distributor (Parsor s f)

instance Alternative f => Alternative (Printor s f a) where
  empty = Printor (\_ -> empty)
  Printor p <|> Printor q = Printor (\a -> p a <|> q a)

instance Applicative f => Distributor (Printor s f) where
  zeroP = Printor absurd
  Printor p >+< Printor q = Printor (either p q)

instance Alternative f => Alternator (Printor s f) where
  alternate = \case
    Left (Printor p) -> Printor (either p (\_ -> empty))
    Right (Printor p) -> Printor (either (\_ -> empty) p)

파서 쪽

  • Alternative (Parsor s f a): empty는 입력을 무시하고 컨테이너의 empty를 돌려주므로 항상 실패합니다. <|>는 같은 입력을 두 파서에 주고 결과를 컨테이너의 <|>로 합칩니다. 목록이면 두 결과 목록을 이어 붙입니다. Monad f는 상위 클래스인 Applicative (Parsor s f a)(5쪽)가 요구하므로 함께 적혀 있습니다.
  • Alternator (Parsor s f): alternate는 파서를 실행하고 결과에 Left 또는 Right를 붙입니다. 파서는 입력 쪽을 쓰지 않으므로 "다른 갈래면 실패"할 일이 없습니다.
  • Distributor (Parsor s f): 본문이 비어 있습니다. 원문의 설명대로 zeroP와 >+<의 기본 구현, 즉 위의 법칙을 그대로 씁니다. 원문의 클래스 선언에는 기본 구현이 보이지 않습니다. 이 법칙을 기본 구현으로 쓰려면 "p가 Alternator이기도 할 때만 쓸 수 있는 기본 구현"이 필요합니다. 하스켈에서는 DefaultSignatures 확장의 기본 시그니처(default signature)가 이런 기본 구현을 허용합니다. 클래스 안에 default zeroP :: Alternator p => p Void Void처럼 더 강한 제약을 붙인 시그니처와 그 구현을 적어 두면, 그 제약을 만족하는 인스턴스만 본문 없이 기본 구현을 쓸 수 있습니다. 원문은 이것을 "Parsor는 Alternator일 때 정확히 Distributor이다"라고 표현합니다.

프린터 쪽

  • Alternative (Printor s f a): empty는 어떤 값도 출력하지 못합니다. <|>는 같은 값을 두 프린터에 주고 결과를 합칩니다. 목록이면 두 프린터의 출력이 모두 결과에 들어가고, Maybe이면 먼저 성공한 쪽이 쓰입니다.
  • Distributor (Printor s f): zeroP = Printor absurd는 Void 값이 들어올 수 없으므로 absurd로 충분합니다. Printor p >+< Printor q = Printor (either p q)는 입력이 Left이면 p로, Right이면 q로 보냅니다. 실패가 끼어들 자리가 없으므로 Applicative f만 요구합니다. 이것이 망라적인 프린터입니다.
  • Alternator (Printor s f): alternate (Left p)는 Left 값만 p로 출력하고 Right 값에서는 empty로 실패합니다. 실패가 필요하므로 Alternative f를 요구합니다. 이것은 부분적인 프린터입니다.

원문은 이 점을 짚습니다. Printor의 Distributor 인스턴스는 망라적인 프린터에서 동작하고, Alternator 인스턴스는 부분적인 프린터에서만 동작합니다. 2쪽의 "출력은 망라적, 파싱은 부분적"이라는 관찰이 여기서 두 클래스로 나뉘어 나타납니다.

값이 흐르는 모습

다음은 원문 코드가 아닌 예시입니다. tx는 "아무 글자 하나 또는 글자 x"입니다.

tx :: (Tokenized Char Char p, Cochoice p, Distributor p) => p (Either Char ()) (Either Char ())
tx = anyToken >+< token 'x'
>>> runParsor (tx :: Parsor String [] (Either Char ()) (Either Char ())) "xy"
[(Left 'x',"y"),(Right (),"y")]
>>> [pr "" | pr <- runPrintor (tx :: Printor String [] (Either Char ()) (Either Char ())) (Right ())]
["x"]
>>> [pr "" | pr <- runPrintor (tx :: Printor String [] (Either Char ()) (Either Char ())) (Left 'q')]
["q"]

파서는 "xy"의 'x'를 두 갈래 모두로 읽을 수 있으므로 결과가 두 개입니다. 프린터는 입력의 갈래에 따라 정확히 한 갈래로 출력합니다.

someP: 1번 이상 반복

원문은 Alternator가 있으면 Alternative의 1번 이상 반복 some을 프로펑터로 넓힐 수 있다고 말합니다.

someP :: Alternator p => p a b -> p [a] [b]
someP p = _Cons >? p >*< manyP p

패키지의 우선순위(>?는 infixl 4, >*<는 infixr 5)를 따르면 이 식은 _Cons >? (p >*< manyP p)입니다.

  • p >*< manyP p :: p (a, [a]) (b, [b]): 원소 하나를 p로, 나머지를 manyP p로 다룹니다.
  • _Cons >? ...: 3쪽의 _Cons 프리즘으로 목록과 (머리, 꼬리) 쌍을 연결합니다. 4쪽의 (>?)이므로, 프린터로는 목록을 _Cons로 맞추어 보고, 파서로는 결과 쌍을 _Cons로 목록으로 만듭니다.
  • 빈 목록은 _Cons에 맞지 않으므로 프린터가 실패합니다. 1번 이상 반복이 빈 목록을 출력하지 못하는 것은 당연합니다. 이 실패 때문에 Distributor가 아니라 Alternator가 필요합니다. 프린터의 (>?)는 Choice를 쓰는데, Printor의 Choice는 맞지 않는 경우에 empty가 필요하기 때문입니다(4쪽).
>>> runParsor (someP (satisfy isDigit) :: Parsor String [] String String) "a"
[]
>>> [pr "" | pr <- runPrintor (someP (satisfy isDigit) :: Printor String [] String String) ""]
[]
>>> [pr "" | pr <- runPrintor (manyP (satisfy isDigit) :: Printor String [] String String) ""]
[""]

someP는 빈 목록을 출력하지 못하고, manyP는 빈 목록을 빈 출력으로 출력합니다.

Filtrator: Filterable의 프로펑터 버전

원문은 4쪽에서 Filterable이 Alternative의 쌍대라고 했던 것을 떠올리며, Filterable을 프로펑터로 넓혀 Distributor의 쌍대를 만듭니다. 그리고 Alternator이면서 Filtrator인 것을 부분 디스트리뷰터(partial distributor)라고 부릅니다.

class (Cochoice p, forall x. Filterable (p x)) => Filtrator p where
  filtrate :: p (Either a c) (Either b d) -> (p a b, p c d)

instance Filterable f => Filtrator (Parsor s f) where
  filtrate (Parsor p) =
    ( Parsor (mapMaybe leftMay . p)
    , Parsor (mapMaybe rightMay . p)
    ) where
      leftMay (e, str) = either (\b -> Just (b, str)) (\_ -> Nothing) e
      rightMay (e, str) = either (\_ -> Nothing) (\b -> Just (b, str)) e

instance Filtrator (Printor s f) where
  filtrate (Printor p) = (Printor (p . Left), Printor (p . Right))
  • 상위 클래스: Cochoice(4쪽)와 양화 제약 forall x. Filterable (p x)입니다.
  • filtrate: Either를 다루는 프린터-파서 하나를 두 갈래의 프린터-파서 쌍으로 쪼갭니다.
  • 파서 인스턴스: 원래 파서를 실행한 뒤 Left 결과만 남긴 파서와 Right 결과만 남긴 파서를 만듭니다. leftMay와 rightMay는 결과 쌍 (e, str)에서 원하는 갈래이면 Just로, 아니면 Nothing으로 바꾸고, mapMaybe(4쪽)가 Nothing을 버립니다.
  • 프린터 인스턴스: 입력을 Left로 감싸 넘기는 프린터와 Right로 감싸 넘기는 프린터를 만듭니다. 아무 제약도 필요 없습니다.

원문은 filtrate의 타입을 uncurry (>+<)와 비교해 보라고 합니다.

uncurry (>+<) :: (p a b, p c d) -> p (Either a c) (Either b d)
filtrate      :: p (Either a c) (Either b d) -> (p a b, p c d)

화살표가 정확히 반대입니다. >+<는 두 갈래를 합치고, filtrate는 합쳐진 것을 나눕니다. 위의 tx로 확인해 보겠습니다. 원문 코드가 아닌 예시입니다.

>>> let (fl, fr) = filtrate (tx :: Parsor String [] (Either Char ()) (Either Char ()))
>>> runParsor fl "xy"
[('x',"y")]
>>> runParsor fr "xy"
[((),"y")]
>>> runParsor fr "zy"
[]

종합 예제: posDecInt

원문은 이제 기본 조합자(combinator)가 다 갖추어졌다며 양의 십진 정수를 위한 프린터-파서를 씁니다.

>>> :{
posDecInt :: (Tokenized Char Char p, Alternator p, Filtrator p) => p Int Int
posDecInt = iso show read >?<
  someP (satisfy (\c -> generalCategory c == DecimalNumber))
:}
>>> runParsor posDecInt "2001 A Space Odyssey" :: [(Int,String)]
[(2,"001 A Space Odyssey"),(20,"01 A Space Odyssey"),(200,"1 A Space Odyssey"),(2001," A Space Odyssey")]
>>> [pr " A Space Odyssey" | pr <- runPrintor posDecInt 2001] :: [String]
["2001 A Space Odyssey"]

코드 읽기

  • :{와 :}: GHCi에서 여러 줄 입력을 시작하고 끝내는 명령입니다.
  • 시그니처: Char 토큰(token)을 다루고, Alternator이며 Filtrator인(즉 부분 디스트리뷰터인) 모든 p에서 동작합니다. p Int Int이므로 프린터로는 Int를 받고 파서로는 Int를 냅니다.
  • satisfy (\c -> generalCategory c == DecimalNumber): 4쪽의 satisfy로 십진 숫자 하나를 다룹니다. Data.Char의 generalCategory는 글자의 유니코드 일반 범주(Unicode general category)를 돌려주고, DecimalNumber는 유니코드 범주 Nd(십진 숫자)입니다.
  • someP (...): 숫자 글자를 1개 이상 다루므로 p String String입니다.
  • iso show read >?< ...: 동형 iso show read :: Iso Int Int String String을 부분 동형 자리에 넣습니다(4쪽에서 말했듯이 모든 Iso는 PartialIso로 쓸 수 있습니다). 2쪽의 핵심 표대로 프린터는 입력 쪽 함수 show를, 파서는 출력 쪽 함수 read를 씁니다.

두 방향의 흐름

  • 파서: someP가 숫자 글자를 1개 이상 읽고, read로 Int를 만듭니다. 결과 컨테이너가 목록이므로 가능한 모든 길이가 나오고, manyP의 oneP 갈래가 먼저 시도되므로 짧은 것부터 나옵니다. 그래서 "2001 A Space Odyssey"에서 2, 20, 200, 2001 네 결과가 이 순서로 나옵니다. 마지막 결과의 남은 입력 " A Space Odyssey"는 공백으로 시작합니다.
  • 프린터: show 2001 = "2001"을 만들고, someP가 각 글자를 satisfy로 검사하며 출력합니다. 남은 스트림 " A Space Odyssey" 앞에 붙여 "2001 A Space Odyssey"가 됩니다.

경계 사례

다음은 원문에 없는 확인입니다.

>>> [pr "" | pr <- runPrintor (posDecInt :: Printor String [] Int Int) (-5)]
[]
>>> last (runParsor (posDecInt :: Parsor String [] Int Int) "007")
(7,"")
  • 음수는 출력되지 않습니다. show (-5) = "-5"의 '-'가 십진 숫자가 아니어서 satisfy에서 걸러집니다. 프린터 쪽의 검사가 show의 결과를 다시 확인하는 셈입니다.
  • "007"은 7로 파싱됩니다. 앞자리 0이 허용되고, 이름은 "positive"이지만 "0"도 받아들입니다. 따라서 7을 출력하면 "7"이 되어, "007"과 왕복이 같지 않습니다.
  • generalCategory가 DecimalNumber인 글자에는 아라비아-인도 숫자 '\x0663' 같은 비ASCII 숫자도 있습니다. GHC에서 확인해 보면 reads "\x0663" :: [(Int,String)]가 []이므로, 이런 글자를 파싱하면 read가 예외를 던질 수 있습니다.

이 사례들은 예제의 결함이라기보다 "한 정의가 두 방향을 모두 규정한다"는 점이 어디까지 정확한지를 보여 줍니다. 부분 동형의 두 함수가 서로의 역이 아니면 왕복이 깨집니다.

바이포컬

원문은 부분 디스트리뷰터에 대응하는 옵틱을 "바이포컬(bifocal)"이라고 이름 붙였다고 짧게 말합니다. 이 역시 저자의 용어이며, 현재 패키지는 Bifocal을 forall p f. (Alternator p, Filtrator p, Alternative f, Filterable f) => p a (f b) -> p s (f t)로 정의하고 "양방향 파서 옵틱(bidirectional parser optics)"이라고 설명합니다. 지금까지 본 옵틱들과 같은 모양에서 제약만 강해진 것입니다.

이 쪽이 글의 목표에 기여하는 바

이 절로 파서 조합자의 거의 모든 도구가 프린터-파서 버전으로 갖추어졌습니다. 차례로 잇기(>*<, >*, *<), 경우 나누기(>+<), 선택과 실패(<|>, empty), 반복(optionalP, manyP, someP), 걸러 내기(filtrate)입니다. posDecInt는 이 도구들로 쓴 한 정의가 파서와 프린터로 모두 동작하는 것을 보여 줍니다. 7쪽은 이 도구들을 하나의 문법 인터페이스로 묶고, 같은 정의에서 문법 문서까지 만들어 냅니다.

정리

  • Alternative는 zeroF :: f Void와 <+> :: f a -> f b -> f (Either a b)로 다시 쓸 수 있으며, 그러면 쌍대곱 Void와 Either에 관한 인터페이스라는 점이 드러납니다.
  • Distributor는 그 모양을 프로펑터로 옮긴 zeroP와 >+<를 가지며, 프린터로는 입력에 대한 경우 나누기, 파서로는 결과에 갈래 표시를 붙이는 선택입니다. 함수 화살표가 대표적인 예이고 실패 없이 망라적일 수 있습니다.
  • optionalP와 manyP는 Maybe와 목록을 튜플의 Either 표현으로 바꾸는 동형과 oneP >+< ...로 정의됩니다. 원문의 정의에서는 짧은 결과가 먼저 나옵니다.
  • Alternator는 alternate와 Alternative를 더한 부분적인 디스트리뷰터이고, someP처럼 실패가 필요한 조합자를 가능하게 합니다. Filtrator의 filtrate는 >+<의 반대 방향으로 갈래를 나눕니다.
  • posDecInt = iso show read >?< someP (satisfy ...) 한 정의가 파서로는 숫자를 읽어 read하고, 프린터로는 show한 숫자를 출력합니다.
