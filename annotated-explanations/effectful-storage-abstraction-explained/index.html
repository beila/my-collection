Effectful로 저장소 구현을 교체 가능하게 만드는 법

이 문서에서 설명하는 내용

원문은 Haskell 백엔드에서 저장소 작업의 의미와 실제 저장 기술을 분리하는 설계를 설명합니다. 서버는 사용자 조회·생성·거래 삭제 같은 Storage 작업만 요청하고, 바깥 계층에서 메모리 Map 해석기 또는 PostgreSQL 해석기를 고릅니다. 따라서 서버 코드는 SQL, 연결 객체, 메모리 자료구조를 직접 알 필요가 없습니다.

코드에는 ...로 생략된 필드와 설정이 있으므로 독립 실행 예제가 아니라 설계 설명용 조각으로 읽어야 합니다. 특히 ID 생성, SQL 열 목록, 동시성, 트랜잭션은 운영 환경에 맞게 별도로 설계해야 합니다.

먼저 알아야 할 공통 개념

data와 type

data는 실제 자료형과 생성자를 만들고, type은 이미 존재하는 타입 식에 읽기 좋은 별칭을 붙입니다. 원문은 매개변수화된 레코드 하나에 실제 ID 또는 ()를 적용해 저장된 값과 생성 전 값을 구별합니다. Haskell 2010 Report의 선언 규칙이 해당 차이를 정의합니다.

Template Haskell과 렌즈

makeLenses ''User' 같은 Template Haskell 호출은 컴파일 시점에 레코드용 렌즈를 생성합니다. 그래서 userCreate & userId .~ uId는 기존 값을 제자리에서 바꾸는 명령이 아니라, userId만 바뀐 새 레코드를 만드는 표현입니다. GHC의 Template Haskell 문서와 lens의 생성 문서가 이 문법과 생성 규칙을 설명합니다.

Servant와 Effectful의 두 :>

Servant의 :>는 URL 경로와 요청·응답 규칙을 이어 API의 모양을 기술합니다. 반면 Effectful의 (Storage :> es)는 효과 목록 es 안에 Storage 능력이 있다는 제약입니다. 같은 기호이지만 역할이 다릅니다. 후자는 어떤 구현을 선택하지 않으며, interpret가 Storage 작업을 실제 상태 조작 또는 SQL 호출로 해석할 때 구현이 선택됩니다. Servant API 문서와 Effectful 핵심 문서를 함께 보면 두 용법을 구분할 수 있습니다.

효과 인터페이스와 해석기

Storage GADT의 생성자는 애플리케이션이 요청할 수 있는 저장소 작업의 목록입니다. 서버는 생성된 listUsers, createUser 같은 함수를 호출하고, 해석기는 그 요청을 메모리 또는 PostgreSQL 작업으로 바꿉니다. 이 분리는 구현 교체를 쉽게 하지만, 두 구현의 정렬·오류·동시성·트랜잭션 의미까지 자동으로 같게 하지는 않습니다. Effectful의 동적 해석 문서가 이 해석 경계를 설명합니다.

상태와 입출력 효과

메모리 해석기는 State Memory를 사용하고, PostgreSQL 해석기는 데이터베이스 함수의 IO를 liftIO로 Eff 안에 올립니다. liftIO는 IO를 순수하게 만드는 것이 아니라 IO 의존성을 효과 행에 명시한 채 포함합니다. Effectful 상태 문서와 liftIO 문서가 각각의 역할을 설명합니다.

하이라이트와 메모별 해설

생략된 부분

하이라이트: ...

원문 문맥:

data User' id ... = User

...는 Haskell 문법이 아니라 타입 매개변수와 필드 일부를 생략했다는 편집 기호입니다. 이 조각만으로 전체 선언이나 컴파일 가능 여부를 판단하면 안 됩니다.

컴파일러가 제공하는 구조 표현

하이라이트: Generic

원문 문맥:

  }
  deriving (Show, Generic)

Generic은 자료형 구조를 컴파일러가 일반적인 표현으로 제공하게 합니다. 라이브러리는 이를 이용해 필드별 코드를 직접 쓰지 않는 기본 구현을 제공할 수 있습니다. 원문의 빈 FromRow, ToRow 인스턴스가 generic 기본 구현을 활용하려는 예일 가능성이 높지만, 이것만이 유일한 목적이라고 단정할 수는 없습니다. GHC generics 문서와 postgresql-simple의 행 변환 문서를 참고할 수 있습니다.

새 자료형과 타입 별칭의 차이

하이라이트: type

원문 문맥:

type Transaction =
  Transaction'
    TransactionId
    UserId
    ...

사용자 메모: Difference to data?

직접 답하면, data는 새 자료형과 생성자를 정의하고 type은 기존 타입 식의 별칭을 정의합니다. 여기서 Transaction'은 실제 레코드 자료형이고, Transaction은 여기에 TransactionId, UserId를 적용한 편리한 이름입니다. type Transaction = ... 때문에 새 생성자나 새 런타임 값이 생기지는 않습니다.

레코드에서 렌즈를 생성하기

하이라이트: makeLenses ''

원문 문맥:

-- generate lenses for easy and awesome manipulation
makeLenses ''User'
makeLenses ''Transaction'

makeLenses는 레코드 선언을 보고 렌즈를 생성합니다. 보통 _userId 같은 필드에서 userId 렌즈가 만들어집니다. ''User'의 두 작은따옴표는 타입 생성자 이름을 인용하는 Template Haskell 문법이고, 마지막 '는 이름 User'의 일부입니다.

사용자 목록 GET 엔드포인트

하이라이트: :> Get '[JSON] [User]

원문 문맥:

type UserAPI =
       "list" :> Get '[JSON] [User]

"list" :> Get '[JSON] [User]는 JSON으로 사용자 목록을 돌려주는 GET /list 엔드포인트를 기술합니다. 이 API가 바깥의 "user" :> UserAPI 아래에 있으므로 전체 경로는 GET /user/list입니다. '[JSON]의 작은따옴표는 Template Haskell이 아니라 타입 수준 목록을 만드는 DataKinds 문법입니다. Servant API 문서와 GHC DataKinds 문서가 근거입니다.

경로 변수를 받는 Capture

하이라이트: Capture

원문 문맥:

  :<|> "delete" :> Capture "id" TransactionId :> DeleteNoContent

Capture "id" TransactionId는 URL의 한 경로 조각을 TransactionId로 해석합니다. 이 분기는 /delete/:id 모양이며 바깥 경로를 합치면 /transaction/delete/:id입니다. 서버 핸들러는 그 값을 함수 인수로 받습니다. Servant의 Capture 문서를 참고할 수 있습니다.

API와 서버의 선택지

하이라이트: :<|>

원문 문맥:

type API =
  "user" :> UserAPI
    :<|> "transaction" :> TransactionAPI

:<|>는 두 API 갈래를 묶습니다. 값 수준에서도 같은 연산자가 대응하는 서버 구현을 같은 순서로 묶으므로, 뒤의 apiServer = userServer :<|> transactionServer가 API 구조와 일치합니다. Servant의 대안 API 문서가 이 대응을 설명합니다.

Storage의 종류 서명

하이라이트: ::

원문 문맥:

data Storage :: Effect where
  ListUsers :: Storage m [User]

첫 줄의 ::는 값의 타입이 아니라 종류(kind) 서명입니다. Storage가 Effectful이 요구하는 Effect 종류의 타입 생성자임을 말합니다. 다음 줄은 ListUsers 작업이 [User]를 돌려준다는 GADT 생성자 타입입니다.

효과 호출 함수 생성

하이라이트: makeEffect ''

원문 문맥:

  DeleteTransaction :: TransactionId -> Storage m ()

makeEffect ''Storage

makeEffect ''Storage는 Storage 생성자를 보내는 함수를 생성합니다. 예를 들어 ListUsers에 대응하는 listUsers, CreateUser에 대응하는 createUser를 만들므로 서버는 생성자를 직접 다루지 않아도 됩니다. Effectful Template Haskell 문서가 생성 범위를 설명합니다.

효과 목록에 Storage가 있다는 뜻

하이라이트: :>

원문 문맥:

listUsers :: (Storage :> es) => Eff es [User]

여기의 :>는 Servant 경로 연결이 아니라 효과 멤버십 제약입니다. Storage가 es에 있으므로 이 계산은 저장소 작업을 요청할 수 있습니다. 메모리인지 PostgreSQL인지는 이 타입만으로 정해지지 않고 해석기를 적용할 때 정해집니다.

작업 생성자를 분기하는 \case

하이라이트: \case

원문 문맥:

runStorageMemory = interpret $ \_ -> \case
  ListUsers -> gets $ M.elems . _users

\case는 \op -> case op of ...의 짧은 문법입니다. 해석기가 받은 Storage 작업을 ListUsers, CreateUser 같은 생성자로 분기합니다. 앞의 \_는 이 위치에서 쓰지 않는 문맥 인수를 버립니다. GHC LambdaCase 문서가 이 문법을 설명합니다.

Map의 값을 꺼내기

하이라이트: M.elems

원문 문맥:

  ListUsers -> gets $ M.elems . _users

M.elems는 Map의 모든 값을 목록으로 돌려줍니다. Map은 키로 정렬되므로 결과는 삽입 순서가 아니라 키의 오름차순입니다. 이 예제에서는 사용자 ID가 키이므로 보통 ID 순서가 됩니다. Data.Map.elems 문서가 이 순서를 명시합니다.

증가한 값을 함께 돌려주는 렌즈 연산

하이라이트: <+~

원문 문맥:

  CreateUser userCreate -> do
    uId <- state $ nextId <+~ 1

nextId <+~ 1은 nextId를 1 증가시키고 증가 후의 값을 돌려주는 상태 변환입니다. 따라서 state는 상태를 갱신하면서 새 ID를 uId에 바인딩합니다. <+~ 렌즈 연산 문서가 반환값 규칙을 설명합니다.

현재 상태에서 필요한 결과만 읽기

하이라이트: gets

원문 문맥:

  ListUsers -> gets $ M.elems . _users

gets f는 현재 상태에 f를 적용한 결과를 돌려줍니다. 여기서 Memory 전체에서 _users를 꺼내고 M.elems로 사용자 목록을 만듭니다. 상태를 바꾸지 않는 읽기 작업입니다. Effectful 상태 문서가 gets를 f <$> get으로 설명합니다.

왼쪽에서 오른쪽으로 값을 넘기는 &

하이라이트: &

원문 문맥:

    let newUser = userCreate & userId .~ uId

x & f는 f x와 같습니다. 따라서 userCreate를 userId .~ uId 설정 함수에 넘깁니다. 이 표현은 가변 대입이 아니라 ID가 바뀐 새 레코드 값을 만듭니다. (&) 문서가 이 역방향 함수 적용을 정의합니다.

렌즈 초점을 설정하는 .~

하이라이트: .~

원문 문맥:

    let newUser = userCreate & userId .~ uId

userId .~ uId는 userId 렌즈가 가리키는 값을 uId로 교체하는 함수입니다. 기존 userCreate는 바뀌지 않고, 그 필드만 달라진 newUser가 만들어집니다. (.~) setter 문서를 참고할 수 있습니다.

Maybe 초점에 값을 넣는 ?~

하이라이트: ?~

원문 문맥:

    modify $ users . at uId ?~ newUser

?~는 Maybe 초점에 Just 값을 설정합니다. at uId는 맵의 키 uId에 대한 Maybe User를 가리키므로, 이 식은 없으면 삽입하고 있으면 newUser로 교체합니다. (?~) setter 문서와 at 문서가 이 조합을 설명합니다.

효과 계산의 결과를 돌려주는 pure

하이라이트: pure

원문 문맥:

    modify $ users . at uId ?~ newUser
    pure newUser

pure newUser는 보통 값 newUser를 현재 Eff 계산의 결과로 돌려줍니다. 앞의 modify가 상태를 갱신했으므로, pure가 함수 전체에 효과가 없다는 뜻은 아닙니다. pure 문서가 이 역할을 정의합니다.

메모리 맵에서 거래 삭제

하이라이트: modify

원문 문맥:

  DeleteTransaction tId -> modify $ transactions . at tId .~ Nothing

modify는 현재 상태에 순수한 변환을 적용하고 ()을 돌려줍니다. at tId가 가리키는 Maybe Transaction을 Nothing으로 설정하면 맵의 해당 키가 삭제됩니다. 이 인터페이스는 키가 실제로 있었는지는 보고하지 않습니다. Effectful 상태 문서와 at 문서를 참고할 수 있습니다.

함수 합성의 점

하이라이트: .

원문 문맥:

  ListUsers -> gets $ M.elems . _users

이 (.)는 함수 합성입니다. 먼저 _users로 Memory에서 사용자 맵을 꺼내고, 그 결과에 M.elems를 적용합니다. 따라서 전체는 Memory -> [User] 함수입니다. (.) 문서가 이 합성을 정의합니다.

데이터베이스 조회를 효과 계산으로 올리기

하이라이트: liftIO

원문 문맥:

  ListUsers -> liftIO $ query_ conn "SELECT * FROM app_users"

query_는 IO [User] 같은 데이터베이스 작업을 돌려줍니다. liftIO는 이를 Eff 계산에 포함하며, 이 때문에 해석기 타입에 IOE :> es가 필요합니다. IO가 순수해지는 것은 아닙니다. liftIO 문서가 이 올리기 동작을 설명합니다.

query_의 일부인 query

하이라이트: query

원문 문맥:

  ListUsers -> liftIO $ query_ conn "SELECT * FROM app_users"

선택된 문자열은 query_ 식별자의 앞부분입니다. query_는 매개변수 치환을 하지 않는 조회 함수이며, 이 상수 SELECT처럼 ? 자리표시자가 없는 쿼리에 맞습니다. 결과 행은 요구된 [User] 타입에 맞는 FromRow User로 해석됩니다. query_ 문서를 참고할 수 있습니다.

값과 새 상태를 함께 만드는 state

하이라이트: state

원문 문맥:

  CreateUser userCreate -> do
    uId <- state $ nextId <+~ 1

state는 s -> (a, s) 형태의 함수를 받아 상태를 갱신하고 결과 a를 돌려줍니다. 이 위치에서는 증가한 ID를 uId로 돌려주면서 Memory의 다음 ID도 갱신합니다. Effectful 상태 문서가 이 타입과 동작을 설명합니다.

PostgreSQL 해석기의 현재 카운터 읽기

하이라이트: get

원문 문맥:

  CreateUser userCreate -> do
    uId <- get
    modify (+ 1)

이 get은 데이터베이스 조회가 아니라 State Int의 현재 카운터를 읽습니다. 이어지는 modify (+ 1)가 카운터를 증가시킵니다. 메모리 구현은 증가 후 값을 쓰고 이 구현은 증가 전 값을 쓰므로, 초기 상태에 따라 첫 ID가 달라질 수 있습니다.

PostgreSQL 해석기의 카운터 증가

하이라이트: modify

원문 문맥:

  CreateUser userCreate -> do
    uId <- get
    modify (+ 1)

modify (+ 1)은 현재 State Int를 1 증가시킵니다. 이는 시연용 ID 생성 방식입니다. 여러 서버 프로세스, 재시작, 기존 데이터, 데이터베이스 트랜잭션과 조정되지는 않으므로 운영 환경에서는 데이터베이스 시퀀스처럼 동시성을 고려한 방식을 쓰는 편이 일반적입니다.

SQL 영향 행 수를 버리는 void

하이라이트: void

원문 문맥:

  DeleteTransaction tId ->
    void . liftIO $
      execute conn "DELETE FROM transactions where id = ?" (Only tId)

execute는 영향을 받은 행 수를 돌려주지만 DeleteTransaction의 결과형은 ()입니다. void는 바깥 효과를 유지한 채 그 결과값을 버립니다. 따라서 이 예제는 삭제를 실행하지만 실제로 몇 행이 삭제되었는지는 호출자에게 알리지 않습니다. void 문서가 결과값 폐기를 정의합니다.

행을 반환하지 않는 SQL 실행

하이라이트: execute

원문 문맥:

    liftIO $
      execute conn "INSERT INTO app_users values (?)" newUser

execute는 INSERT, UPDATE, DELETE처럼 행을 읽지 않는 SQL 명령에 사용하며, ToRow를 통해 인수를 SQL 매개변수로 바꿉니다. ?의 수는 변환되는 매개변수 수와 맞아야 합니다. 원문은 User 필드와 스키마를 생략했으므로 values (?)가 실제 스키마에서 유효한지는 알 수 없습니다. 운영 코드에서는 보통 열 이름과 각 열의 자리표시자를 명시합니다. execute 문서와 ToRow 문서를 참고할 수 있습니다.

정리

Storage는 서버가 요청할 수 있는 작업을 정의하고, 메모리와 PostgreSQL 해석기는 그 작업을 다른 방식으로 구현합니다. 서버는 구체적인 저장 기술 대신 필요한 능력만 타입으로 요구하므로, 테스트·개발·운영 환경의 구현을 분리할 수 있습니다. 다만 추상화 경계 바깥의 ID 생성, 실패 정책, 트랜잭션, 동시성은 각 구현과 도메인 정책에 맞춰 계속 설계해야 합니다.
