Effectful로 저장소 구현을 분리하는 법: 타입부터 인터프리터까지

문서 형식은 5입니다. 콘텐츠 해시는 cbf9c2aa6f5f7ea7입니다.

이 문서에서 설명하는 내용

Frederick Pringle의 원문은 서버가 요구하는 저장 연산과 그 연산을 인메모리 또는 PostgreSQL로 수행하는 방법을 분리합니다. 핵심 발상은 간결하지만, 예제에는 Haskell의 타입 선언, Template Haskell, Servant의 타입 수준 DSL, Effectful의 효과 목록, State 효과, lens, postgresql-simple이 한꺼번에 등장합니다.

하이라이트는 이 여러 층의 문법과 라이브러리가 맞닿는 곳에 집중되어 있습니다. 따라서 이 문서는 먼저 전체 설계를 설명하고, 이어서 각 하이라이트를 실제 원문 문맥 바로 옆에서 풀이합니다. modify, get, pure, .처럼 짧거나 반복되는 선택은 어느 코드의 어느 발생인지 알아볼 수 있도록 주변 코드를 함께 제시합니다.

이 문서는 원문 전체를 다시 싣지 않습니다. 하이라이트를 식별하고 설명하는 데 필요한 최소한의 코드만 인용하며, 생략된 실제 코드를 확인해야 하는 경우에는 원 프로젝트의 고정 커밋을 사용합니다. 버전에 따라 달라질 수 있는 내용은 원 프로젝트가 사용한 GHC 9.8.4, effectful-core 2.3.1.0, effectful-th 1.0.0.1, servant 0.20.2, lens 5.2.3, postgresql-simple 0.7.0.0을 기준으로 설명합니다.

원문 전체의 설계

원문의 설계를 한 문장으로 줄이면 다음과 같습니다.

서버는 “사용자 목록 조회” 같은 저장 연산이 존재한다는 사실만 알고, 그 연산이 메모리의 Map을 읽는지 PostgreSQL에 질의하는지는 인터프리터가 결정합니다.

HTTP 요청
   |
   v
Servant API 타입              API의 모양을 선언합니다.
   |
   v
Servant 핸들러                listUsers, createUser 등을 호출합니다.
   |
   v
Storage 효과                  가능한 저장 연산을 선언합니다.
   |
   +----------------------+----------------------+
   |                                             |
   v                                             v
인메모리 인터프리터                            PostgreSQL 인터프리터
State Memory + Map                              State Int + IOE + Connection

Servant와 Effectful은 서로 다른 경계를 분리합니다. Servant 타입은 URL, HTTP 메서드, 요청 및 응답 타입을 선언하고, Servant 서버 함수는 그 요청을 처리합니다. Effectful의 Storage 효과는 목록 조회, 생성, 삭제처럼 허용되는 저장 연산을 선언하고, 각 인터프리터는 그 연산을 메모리 갱신이나 SQL 실행으로 해석합니다.

서버 함수에는 Connection이나 Map이 나타나지 않습니다. 반대로 저장소 인터프리터는 HTTP 경로를 알 필요가 없습니다. 이 경계 덕분에 테스트에서는 인메모리 인터프리터를 사용하고 운영에서는 PostgreSQL 인터프리터를 사용할 수 있습니다.

다만 인터프리터를 바꿀 수 있다는 사실만으로 두 구현의 의미가 자동으로 같아지지는 않습니다. 트랜잭션, 동시성, ID 생성, 조회 순서, 오류 의미 같은 계약은 별도로 맞추고 두 구현에 같은 계약 테스트를 실행해야 합니다.

먼저 알아야 할 공통 개념

data, type, Generic: 구조를 만드는 선언과 이름을 붙이는 선언

원 프로젝트의 생략되지 않은 도메인 선언은 다음과 같습니다.

data User' id name = User
  { _userId :: id
  , _userName :: name
  }

type User = User' UserId Text
type UserCreate = User' () Text

data Transaction' id userId amount = Transaction
  { _transactionId :: id
  , _transactionUserId :: userId
  , _transactionAmount :: amount
  }

type Transaction = Transaction' TransactionId UserId Double
type TransactionCreate = Transaction' () () Double

data User' id name = User ...는 User'이라는 타입 생성자와 User라는 값 생성자를 새로 만듭니다. 반면 type User = User' UserId Text는 기존 타입 표현식에 읽기 쉬운 별명을 붙일 뿐 새 타입이나 값 생성자를 만들지 않습니다.

이 패턴은 같은 레코드 구조를 서로 다른 단계에 재사용합니다. User' () Text는 아직 ID가 없는 생성 요청이고, User' UserId Text는 ID가 부여된 저장 결과입니다. 구조는 data로 한 번 정의하고, 각 단계의 구체적인 타입은 type으로 이름 붙입니다.

deriving (Show, Generic)의 Generic은 Java나 C#에서 말하는 제네릭 타입 매개변수와 다릅니다. GHC가 데이터 구조를 공통 표현으로 바꾸는 from과 다시 되돌리는 to를 제공하게 하는 타입 클래스입니다. 이 원문에서는 PostgreSQL 행과 레코드를 변환하는 빈 FromRow 및 ToRow 인스턴스가 제네릭 기본 구현을 사용할 수 있게 합니다.

Servant: 웹 API를 타입으로 기술합니다

Servant에서는 경로, HTTP 메서드, 요청 본문, 응답 형식을 타입 표현식으로 조합합니다.

type UserAPI =
       "list" :> Get '[JSON] [User]
  :<|> "create" :> ReqBody '[JSON] UserCreate :> Post '[JSON] User

이 코드는 실행되는 라우터 값이 아니라 API 명세 타입입니다. Servant는 이 타입을 바탕으로 서버에 필요한 함수의 형태를 계산합니다. Servant API 타입 튜토리얼은 이 대응 관계를 단계적으로 설명합니다.

API
├── /user
│   ├── GET  /list
│   └── POST /create
└── /transaction
    ├── GET    /list
    └── DELETE /delete/{id}

Effectful: 가능한 연산과 수행 방법을 분리합니다

Effectful에서 효과는 프로그램이 요청할 수 있는 연산의 집합으로 볼 수 있습니다.

data Storage :: Effect where
  ListUsers :: Storage m [User]
  CreateUser :: UserCreate -> Storage m User
  ListTransactions :: Storage m [Transaction]
  DeleteTransaction :: TransactionId -> Storage m ()

각 GADT 생성자는 연산의 입력과 결과 타입을 기록합니다. Eff es a는 효과 목록 es에 적힌 효과를 사용할 수 있고 최종적으로 a를 만드는 계산입니다. Storage :> es는 Storage가 그 효과 목록 안에 있어 현재 계산이 저장 연산을 요청할 수 있음을 보장합니다.

인터프리터의 핵심 타입은 다음 모양입니다.

Eff (Storage : es) a -> Eff es a

입력 계산에 있던 Storage 요청을 모두 처리했으므로 출력 효과 목록에서는 Storage가 사라집니다. 인메모리 인터프리터는 요청을 State Memory 연산으로 바꾸고, PostgreSQL 인터프리터는 State Int와 IOE를 사용해 SQL 연산으로 바꿉니다.

State와 lens: 불변 상태를 읽고 갱신합니다

원문의 get, gets, state, modify는 Effectful.State.Static.Local에서 가져옵니다.

get    :: State s :> es => Eff es s
gets   :: State s :> es => (s -> a) -> Eff es a
state  :: State s :> es => (s -> (a, s)) -> Eff es a
modify :: State s :> es => (s -> s) -> Eff es ()

get은 현재 상태 전체를 반환하고, gets f는 상태를 바꾸지 않은 채 f를 적용한 결과만 반환합니다. state f는 결과와 새 상태를 함께 만들고, modify f는 상태만 갱신한 뒤 ()를 반환합니다.

Lens는 큰 불변 값 안의 한 위치를 읽거나 갱신하는 조합 가능한 초점입니다. 원문에서는 Memory 안의 사용자 맵, 거래 맵, 다음 ID를 가리키는 데 사용합니다.

표현 의미
x & f f x와 같으며 데이터를 먼저 적게 합니다.
field .~ value field가 가리키는 값을 바꾸는 순수 함수를 만듭니다.
at key ?~ value Map의 해당 키에 값을 삽입하거나 교체합니다.
at key .~ Nothing Map에서 해당 키를 삭제합니다.
field <+~ n 수치 초점을 늘리고 증가 후 값과 갱신된 구조를 함께 반환합니다.

PostgreSQL 연산을 Eff 안에서 실행합니다

postgresql-simple의 질의와 명령은 IO 작업입니다. PostgreSQL 인터프리터는 IOE :> es를 요구하고 liftIO로 IO a를 Eff es a에 올립니다.

query_  :: FromRow r
        => Connection -> Query -> IO [r]

query   :: (ToRow q, FromRow r)
        => Connection -> Query -> q -> IO [r]

execute :: ToRow q
        => Connection -> Query -> q -> IO Int64

query_는 치환 인수가 없는 조회를 실행하고, query는 SQL의 ?에 넣을 별도 매개변수 행을 받습니다. execute는 결과 행을 읽지 않는 명령을 실행하고 영향받은 행 수를 반환합니다.

도메인 모델

생략 부호는 Haskell 문법이 아닙니다

하이라이트: ...

원문 문맥:

data User' id ... = User

원문은 이 코드 전에 매개변수와 필드의 세부 사항을 생략한다고 밝힙니다. 따라서 선택한 ...는 Haskell의 특별한 연산자나 wildcard가 아니라 게시글에서 내용을 줄였다는 표시입니다. 원 프로젝트의 실제 선언은 data User' id name = User이며, 뒤쪽 생략 부분에는 _userName :: name 같은 필드가 들어갑니다. 원문의 축약 코드를 그대로 복사하면 컴파일되지 않습니다.

Generic은 구조 기반 기본 구현을 지원합니다

하이라이트: Generic

원문 문맥:

data Transaction' id userId ... = Transaction
  { _transactionId :: id
  , _transactionUserId :: userId
  , ...
  }
  deriving (Show, Generic)

이 선택은 Transaction' 선언의 deriving 절에 있습니다. Show가 값을 문자열로 표현하는 기능을 제공한다면, Generic은 데이터 구조를 GHC의 표준 표현으로 변환하는 기능을 제공합니다. 뒤의 PostgreSQL 모듈에 나오는 본문 없는 FromRow Transaction과 ToRow Transaction 인스턴스는 이 구조 표현을 이용해 필드를 순서대로 읽고 SQL 매개변수로 바꿀 수 있습니다.

GHC Generic programming 문서는 Rep, from, to의 관계를 설명합니다. postgresql-simple의 제네릭 기본 구현은 레코드 같은 곱 타입에는 적용되지만 합 타입과 재귀 타입은 지원하지 않습니다.

type과 data는 무엇이 다른가요

하이라이트: type

원문 문맥:

type Transaction =
  Transaction'
    TransactionId
    UserId
    ...

사용자 메모: “Difference to data?”

직접적인 차이는 data가 새 타입과 값 생성자를 만들지만, type은 기존 타입 표현식에 별명을 붙일 뿐이라는 점입니다.

이 문맥에서 data Transaction' ... = Transaction ...은 레코드 구조와 Transaction 값 생성자를 정의합니다. 반면 위의 type Transaction = ...은 그 구조에 구체적인 타입 인수를 채운 표현을 Transaction이라는 짧은 이름으로 부릅니다. Transaction과 완전히 펼친 오른쪽 타입은 타입 검사에서 같은 타입입니다.

선언 새 타입 새 값 생성자 이 원문에서의 역할
data 만듭니다. 만듭니다. 재사용할 레코드 구조를 정의합니다.
type 만들지 않습니다. 만들지 않습니다. 구조를 특정 단계에 맞게 특수화하고 이름을 붙입니다.
newtype 만듭니다. 만듭니다. 런타임 비용을 거의 늘리지 않고 명목적 구분을 만듭니다.

예를 들어 type UserId = Int는 UserId와 Int를 구분하지 않습니다. 사용자 ID와 거래 ID의 혼용을 타입 검사로 막고 싶다면 newtype UserId = UserId Int처럼 새 타입을 만드는 편이 적합합니다. 표준 의미는 Haskell 2010 선언 문법에서 확인할 수 있습니다.

makeLenses의 두 작은따옴표는 타입 이름 인용입니다

하이라이트: makeLenses ''

원문 문맥:

makeLenses ''User'
makeLenses ''Transaction'

첫 번째 호출에서 ''User'는 타입 생성자 User'의 컴파일 시간 이름입니다. makeLenses는 그 선언을 조사해 _userId에서 userId, _userName에서 userName lens를 생성합니다. 앞의 두 작은따옴표는 Template Haskell의 타입 이름 인용이고, User' 끝의 작은따옴표는 원래 식별자 이름의 일부입니다.

Servant API 타입

GET 경로와 응답 형식을 한 타입으로 적습니다

하이라이트: :> Get '[JSON] [User]

원문 문맥:

type UserAPI =
       "list" :> Get '[JSON] [User]

Servant의 :>는 "list" 경로 아래에 오른쪽 API를 둡니다. Get은 HTTP GET과 성공 상태 코드 200을 나타내며, '[JSON]은 사용할 수 있는 응답 콘텐츠 타입의 타입 수준 목록입니다. [User]는 응답 본문의 일반 Haskell 목록 타입입니다. 전체 줄은 GET /list가 JSON으로 인코딩된 사용자 목록을 반환한다고 선언합니다.

'[JSON] 앞의 작은따옴표는 값을 타입 수준으로 승격하는 DataKinds 표기입니다. [User]는 원래부터 타입이므로 같은 승격 표시가 필요하지 않습니다.

Capture는 URL의 가변 경로 조각을 읽습니다

하이라이트: Capture

원문 문맥:

"delete"
  :> Capture "id" TransactionId
  :> DeleteNoContent

Capture "id" TransactionId는 URL의 다음 경로 조각을 TransactionId로 파싱합니다. 예를 들어 /delete/42라면 42가 삭제 핸들러의 TransactionId 인수로 전달됩니다. "id"는 이 경로 조각의 이름이고, DeleteNoContent는 성공한 DELETE 응답에 본문이 없음을 나타냅니다.

전체 사용자 API와 거래 API를 합칩니다

하이라이트: :<|>

원문 문맥:

type API =
  "user" :> UserAPI
    :<|> "transaction" :> TransactionAPI

원문에서 선택한 발생은 UserAPI나 TransactionAPI 내부가 아니라 전체 API를 만드는 위 결합입니다. :<|>는 /user/... 경로 집합과 /transaction/... 경로 집합을 하나의 API로 합칩니다. 값 수준 서버에서도 userServer :<|> transactionServer처럼 같은 모양으로 두 핸들러를 묶으므로 타입 명세와 구현의 구조가 일치합니다.

Storage 효과 선언

Storage의 kind를 선언합니다

하이라이트: ::

원문 문맥:

data Storage :: Effect where

일반적으로 ::는 왼쪽 항목의 타입 또는 kind를 오른쪽에 적는 서명 기호입니다. 여기서 Storage는 값이 아니라 타입 생성자이므로 Effect는 그 타입 생성자의 kind입니다. 원 프로젝트 버전에서 Effect는 다음 모양입니다.

type Effect = (Type -> Type) -> Type -> Type

따라서 Storage는 계산 타입 생성자 자리 m과 연산 결과 타입 a를 받아 Storage m a를 만듭니다. GADT의 각 생성자가 ListUsers :: Storage m [User]처럼 서로 다른 결과 타입을 지정할 수 있습니다.

makeEffect는 효과 요청 함수를 생성합니다

하이라이트: makeEffect ''

원문 문맥:

makeEffect ''Storage

이 Template Haskell splice는 Storage가 동적으로 dispatch되는 효과라는 설정과, 각 GADT 생성자를 send하는 소문자 함수를 생성합니다. 예를 들면 다음과 같은 함수가 만들어집니다.

listUsers
  :: (HasCallStack, Storage :> es)
  => Eff es [User]
listUsers = send ListUsers

위 코드는 공식 API를 바탕으로 펼쳐 쓴 설명용 근사치입니다. 원문도 생성 결과가 이와 “비슷하다”고 설명하며 HasCallStack을 생략합니다. 원 프로젝트 버전의 정확한 계약은 Effectful.TH에서 확인할 수 있습니다.

Effectful의 :>는 효과 목록의 멤버십입니다

하이라이트: :>

원문 문맥:

listUsers :: (Storage :> es) => Eff es [User]

여기의 :>는 Storage 효과가 타입 수준 효과 목록 es 안에 있고 Effectful이 그 환경 슬롯을 찾을 수 있다는 제약입니다. 이 증거가 있어야 listUsers가 현재 효과 환경으로 Storage 요청을 보낼 수 있습니다.

Servant의 "list" :> Get ...에 나온 동명 연산자와는 철자만 같습니다. Servant에서는 경로나 요청 조건을 하위 API와 연결하지만, Effectful에서는 효과가 목록에 포함되어 있음을 표현합니다. 원문의 서버 모듈은 두 이름의 충돌을 피하려고 import Servant.API hiding ((:>))를 사용합니다.

인메모리 인터프리터

다음 해설들은 모두 이 코드의 서로 다른 위치를 가리킵니다.

runStorageMemory = interpret $ \_ -> \case
  ListUsers -> gets $ M.elems . _users
  CreateUser userCreate -> do
    uId <- state $ nextId <+~ 1
    let newUser = userCreate & userId .~ uId
    modify $ users . at uId ?~ newUser
    pure newUser

  ListTransactions -> gets $ M.elems . _transactions
  DeleteTransaction tId ->
    modify $ transactions . at tId .~ Nothing

\case는 인수를 즉시 패턴 매칭하는 람다입니다

하이라이트: \case

원문 문맥:

runStorageMemory = interpret $ \_ -> \case
  ListUsers -> ...
  CreateUser userCreate -> ...

\case는 인수 이름을 먼저 붙이지 않고 바로 case로 분기하는 LambdaCase 문법입니다. 위 코드는 개념적으로 다음과 같습니다.

runStorageMemory =
  interpret $ \_ -> \operation ->
    case operation of
      ListUsers -> ...
      CreateUser userCreate -> ...

앞의 \_는 동적 인터프리터가 전달하는 지역 환경입니다. 이 Storage 효과는 지역 계산을 인수로 받지 않는 일차 효과라서 예제에서는 사용하지 않습니다.

M.elems는 사용자 맵의 값만 꺼냅니다

하이라이트: M.elems

원문 문맥:

ListUsers -> gets $ M.elems . _users

import qualified Data.Map as M이므로 M.elems는 Data.Map.elems입니다. Map의 키를 버리고 키 오름차순에 해당하는 값 목록을 반환합니다. 이 줄에서는 Map UserId User를 [User]로 바꿉니다. Data.Map.elems 문서는 반환 순서와 O(n) 복잡도를 명시합니다.

<+~는 ID를 증가시키고 증가 후 값을 돌려줍니다

하이라이트: <+~

원문 문맥:

uId <- state $ nextId <+~ 1

nextId lens가 가리키는 수를 1만큼 늘리고, 증가 후 값과 갱신된 전체 Memory를 쌍으로 만듭니다. state는 새 Memory를 상태로 저장하고 증가 후 값을 uId에 바인딩합니다.

이전 Memory: nextId = 41
       |
       | nextId <+~ 1
       v
결과 uId: 42
새 Memory: nextId = 42

gets는 상태를 바꾸지 않고 필요한 결과만 읽습니다

하이라이트: gets

원문 문맥:

ListUsers -> gets $ M.elems . _users

이 선택은 사용자 목록 분기의 첫 gets입니다. gets f는 현재 상태에 f를 적용한 결과만 반환하고 상태 자체는 유지합니다. 여기서는 현재 Memory에서 사용자 맵을 꺼낸 뒤 그 값 목록을 반환합니다.

&는 데이터를 왼쪽에 두는 함수 적용입니다

하이라이트: &

원문 문맥:

let newUser = userCreate & userId .~ uId

x & f는 f x와 같습니다. 따라서 userCreate를 먼저 적고 그 뒤에 적용할 lens 갱신을 읽기 순서대로 적을 수 있습니다. 이 연산자는 값을 제자리에서 바꾸지 않으며, 오른쪽 변환이 만든 새 값을 반환합니다.

.~는 lens가 가리키는 필드를 설정합니다

하이라이트: .~

원문 문맥:

let newUser = userCreate & userId .~ uId

userId .~ uId는 userId lens가 가리키는 값을 uId로 설정하는 순수 함수입니다. &가 이 함수를 userCreate에 적용하므로, ID가 비어 있던 생성 요청에서 ID가 채워진 newUser가 만들어집니다.

?~는 맵의 키에 Just 값을 설정합니다

하이라이트: ?~

원문 문맥:

modify $ users . at uId ?~ newUser

users . at uId는 Memory의 사용자 맵을 거쳐 키 uId의 Maybe User 위치를 가리키는 합성 lens입니다. ?~ newUser는 그 위치에 Just newUser를 설정합니다. 키가 없으면 삽입하고 이미 있으면 교체하며, modify가 이 순수 변환을 현재 State Memory에 적용합니다.

pure는 새 사용자를 계산 결과로 반환합니다

하이라이트: pure

원문 문맥:

modify $ users . at uId ?~ newUser
pure newUser

선택한 발생은 인메모리 CreateUser 분기 끝의 pure newUser입니다. pure는 평범한 newUser 값을 현재 Eff es 계산의 결과로 올립니다. 이 호출 자체는 추가 효과를 요청하지 않지만, 앞의 state와 modify가 이미 상태를 바꾸었으므로 분기 전체에 효과가 없다는 뜻은 아닙니다.

이 modify는 거래 맵에서 키를 삭제합니다

하이라이트: modify

원문 문맥:

DeleteTransaction tId ->
  modify $ transactions . at tId .~ Nothing

선택한 발생은 사용자 삽입 줄이 아니라 인메모리 거래 삭제 분기의 modify입니다. transactions . at tId가 Memory 안 거래 맵의 특정 키를 가리키고, .~ Nothing이 그 키를 삭제하는 Memory -> Memory 함수를 만듭니다. modify는 이 함수를 현재 State Memory에 적용하고 ()를 반환합니다.

이 마침표는 일반 함수 합성입니다

하이라이트: .

원문 문맥:

ListUsers -> gets $ M.elems . _users

선택한 마침표는 M.elems . _users 사이에 있습니다. 이는 lens 합성이 아니라 일반 함수 합성입니다.

M.elems . _users

-- 같은 의미입니다.
\memory -> M.elems (_users memory)

먼저 _users가 Memory에서 사용자 맵을 꺼내고, 그 결과에 M.elems가 적용됩니다. 원문의 users . at uId에서도 같은 (.) 기호가 나오지만, 그곳에서는 함수로 표현된 두 lens를 합성합니다. 근본적인 합성 원리는 같아도 선택한 위치의 피연산자는 일반 함수입니다.

state는 결과와 새 상태를 동시에 계산합니다

하이라이트: state

원문 문맥:

uId <- state $ nextId <+~ 1

state는 s -> (a, s) 형태의 순수 함수를 받아 결과 a와 새 상태 s를 동시에 반영합니다. 이 줄에서 <+~가 만든 증가 후 ID가 결과 uId가 되고, 다음 ID가 증가한 Memory가 새 상태가 됩니다. 상태만 바꾸고 별도 결과를 돌려주지 않는 modify와의 차이가 여기에 있습니다.

PostgreSQL 인터프리터

다음 해설들은 PostgreSQL 구현의 서로 다른 위치를 가리킵니다.

runStoragePostgres conn = interpret $ \_ -> \case
  ListUsers ->
    liftIO $ query_ conn "SELECT * FROM app_users"
  CreateUser userCreate -> do
    uId <- get
    modify (+ 1)
    let newUser = userCreate & userId .~ uId
    liftIO $
      execute conn "INSERT INTO app_users values (?)" newUser
    pure newUser

  ListTransactions ->
    liftIO $ query_ conn "SELECT * FROM transactions"
  DeleteTransaction tId ->
    void . liftIO $
      execute conn "DELETE FROM transactions where id = ?" (Only tId)

liftIO는 SQL 조회를 Eff 계산으로 올립니다

하이라이트: liftIO

원문 문맥:

ListUsers ->
  liftIO $ query_ conn "SELECT * FROM app_users"

선택한 발생은 사용자 목록 조회 분기의 첫 liftIO입니다. query_ ...의 결과는 이 문맥에서 IO [User]이고, liftIO는 이를 Eff es [User]로 올립니다. PostgreSQL 인터프리터의 타입에 IOE :> es 제약이 필요한 직접적인 이유입니다.

선택한 query는 실제 함수 이름 query_의 일부입니다

하이라이트: query

원문 문맥:

ListUsers ->
  liftIO $ query_ conn "SELECT * FROM app_users"

하이라이트에는 query만 들어 있지만 호출되는 함수의 전체 이름은 밑줄이 붙은 query_입니다. query_는 치환 매개변수가 없는 SQL 조회에 사용합니다. 별도 함수인 query는 SQL의 ? 자리에 넣을 ToRow q 인수를 하나 더 받습니다. 이 줄의 SELECT에는 매개변수가 없으므로 query_가 맞습니다.

get은 현재 정수 ID를 읽습니다

하이라이트: get

원문 문맥:

CreateUser userCreate -> do
  uId <- get
  modify (+ 1)

이 get이 읽는 상태는 인메모리 인터프리터의 Memory가 아니라 PostgreSQL 인터프리터가 요구하는 State Int입니다. 현재 정수를 uId에 바인딩하며, 이 시점에는 상태를 바꾸지 않습니다.

이 modify는 다음 정수 ID를 준비합니다

하이라이트: modify

원문 문맥:

uId <- get
modify (+ 1)

선택한 발생은 PostgreSQL 생성 분기의 modify (+ 1)입니다. 현재 State Int에 (+ 1)을 적용해 다음 사용자에게 쓸 ID를 준비하고 ()를 반환합니다.

인메모리 구현은 state $ nextId <+~ 1로 증가 후 값을 현재 ID로 사용하지만, PostgreSQL 구현은 증가 전 값을 읽은 다음 상태를 증가시킵니다. 초기 상태를 어떻게 주느냐에 따라 첫 ID가 달라질 수 있으므로 두 인터프리터가 같은 외부 계약을 가져야 한다면 초기값과 증가 시점을 명시해야 합니다.

void는 삭제된 행 수만 버립니다

하이라이트: void

원문 문맥:

DeleteTransaction tId ->
  void . liftIO $
    execute conn "DELETE FROM transactions where id = ?" (Only tId)

함수 적용 우선순위를 풀면 다음과 같습니다.

(void . liftIO)
  (execute conn "DELETE FROM transactions where id = ?" (Only tId))

execute는 IO Int64로 영향받은 행 수를 반환하고, liftIO는 이를 Eff es Int64로 올립니다. void는 정상 반환값만 버려 Eff es ()로 바꿉니다. SQL 오류나 IO 예외를 삼키지는 않습니다. Only tId는 SQL 매개변수가 하나일 때 그 값을 한 필드 행처럼 전달하는 래퍼입니다.

execute는 INSERT를 실행하고 행 수를 반환합니다

하이라이트: execute

원문 문맥:

liftIO $
  execute conn "INSERT INTO app_users values (?)" newUser
pure newUser

선택한 발생은 사용자 생성 분기의 첫 execute입니다. execute는 결과 행을 읽지 않는 SQL 명령을 실행하고 영향받은 행 수를 IO Int64로 반환합니다. 이 호출은 do 블록의 중간 문장이므로 행 수는 사용하지 않고, 다음 pure newUser가 분기의 최종 결과가 됩니다.

원 프로젝트의 완전한 User에는 ID와 이름 두 필드가 있고 제네릭 ToRow User도 SQL 매개변수 두 개를 만듭니다. 그러나 원문의 SQL에는 placeholder가 하나뿐입니다. postgresql-simple은 placeholder 수와 매개변수 수가 다르면 FormatError를 내므로 이 코드는 그대로라면 실패할 가능성이 매우 높습니다. 실제 스키마의 열 이름은 원 저장소에서 확인되지 않았지만, 의도는 다음처럼 두 열과 두 placeholder를 명시하는 형태에 가깝습니다.

-- 설명용 개선 방향이며, 실제 스키마 이름은 확인되지 않았습니다.
execute conn
  "INSERT INTO app_users (id, name) VALUES (?, ?)"
  newUser

예제를 실제 시스템에 적용할 때의 주의점

원문의 목적은 효과 추상화의 구조를 보여 주는 것이며, 완성된 저장 계층을 제공하는 것이 아닙니다.

  1. PostgreSQL에서 프로세스 내부의 State Int로 ID를 만들면 여러 프로세스나 동시 요청 사이에서 안전하지 않습니다. 데이터베이스 sequence, identity, 또는 INSERT ... RETURNING을 사용하는 편이 일반적입니다.
  2. get, modify (+ 1), execute는 하나의 데이터베이스 트랜잭션이 아닙니다. INSERT가 실패해도 다음 ID 상태는 이미 증가했을 수 있습니다.
  3. SELECT *와 제네릭 FromRow의 조합은 데이터베이스 열 순서가 레코드 필드 순서와 같다고 가정합니다. 실제 코드에서는 열 이름을 명시하는 편이 안전합니다.
  4. 인메모리와 PostgreSQL 구현이 삭제 대상이 없을 때 같은 결과를 내는지, 조회 순서가 같은지, 오류를 어떤 타입으로 표현하는지를 효과의 계약으로 정해야 합니다.
  5. 추상화가 테스트를 가능하게 해 주지만 테스트 자체를 대신하지는 않습니다. 같은 계약 테스트를 각 인터프리터에 실행해야 교체 가능성을 검증할 수 있습니다.

이 중 INSERT의 placeholder 수 불일치는 단순한 운영 세부 사항의 생략이 아니라 실행 전에 오류를 일으킬 수 있는 코드 결함입니다. 나머지는 짧은 교육용 예제에서 의도적으로 단순화된 설계로 볼 수 있습니다.

정리

원문의 중심 구조는 다음 세 단계입니다.

Servant API 타입  ->  서버가 호출할 Storage 연산  ->  선택 가능한 인터프리터

data Storage :: Effect where는 가능한 저장 연산과 각 결과 타입을 선언합니다. makeEffect는 서버가 쓰기 좋은 호출 함수를 만들고, 효과 멤버십 제약은 그 연산을 처리할 효과가 환경에 있음을 보장합니다. interpret는 요청 생성자를 패턴 매칭해 인메모리 상태 연산 또는 PostgreSQL IO로 바꾸고, 처리된 Storage를 효과 목록에서 제거합니다.

세부 문법도 이 구조 안에서 역할이 정해집니다. data는 구조를 만들고 type은 그 구조를 특수화한 타입 표현식에 별명을 붙입니다. makeLenses와 makeEffect는 반복 선언을 생성합니다. Servant는 HTTP API의 모양을 타입에 기록하고 Effectful은 프로그램이 요청할 수 있는 연산을 타입에 기록합니다. State 연산과 lens는 인메모리 상태를 불변 방식으로 갱신하며, liftIO는 PostgreSQL의 IO 작업을 Effectful 계산 안으로 가져옵니다.

결국 이 예제에서 타입은 단지 값을 분류하는 표지가 아닙니다. HTTP API의 모양, 프로그램이 요청할 수 있는 저장 연산, 실행에 필요한 효과를 각각 기록하며 컴파일러가 층 사이의 연결을 검사하게 합니다.
