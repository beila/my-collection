Effectful로 저장소 구현을 분리하는 법: 타입부터 인터프리터까지

이 문서에서 설명하는 내용

Frederick Pringle의 원문은 서버가 요구하는 저장 연산과 그 연산을 인메모리 또는 PostgreSQL로 수행하는 방법을 분리합니다. 핵심 발상은 간결하지만, 예제에는 Haskell의 타입 선언, Template Haskell, Servant의 타입 수준 DSL, Effectful의 효과 목록, State 효과, lens, postgresql-simple이 한꺼번에 등장합니다.

하이라이트 분포를 보면 독자께서 원문의 아키텍처 목표보다 이 여러 층의 문법과 라이브러리가 만나는 지점을 집중적으로 확인하신 것으로 보입니다. 이는 독자 이해에 관한 추정이며, 하이라이트가 곧 이해 부족을 뜻한다고 단정하지는 않습니다. 다만 type에 “Difference to data?”라는 메모가 명시되어 있고, Servant 표현식과 Effectful 표현식의 주요 연산자, State와 lens 연산이 연속해서 선택되었다는 점을 고려하면 다음 내용을 먼저 세우는 편이 유용합니다.

  1. data로 새 타입을 만드는 것과 type으로 기존 타입에 별명을 붙이는 것의 차이를 설명합니다.
  2. Template Haskell이 makeLenses와 makeEffect에서 어떤 코드를 생성하는지 설명합니다.
  3. Servant가 웹 API를 타입으로 기술하는 방식과 Effectful이 허용된 효과를 타입으로 기술하는 방식을 구분합니다.
  4. 인메모리 인터프리터에서 State와 lens가 어떻게 하나의 상태 전이로 결합되는지 설명합니다.
  5. PostgreSQL 인터프리터에서 IO 연산이 Eff로 들어오고 SQL 반환값이 어떻게 처리되는지 설명합니다.

이 문서는 원문 전체를 다시 싣지 않습니다. 대신 원문의 전체 구조를 먼저 지도처럼 제시하고, 하이라이트를 이해하는 데 필요한 코드만 정확히 인용합니다. 라이브러리 버전에 따라 달라질 수 있는 부분은 원 프로젝트가 사용한 버전을 기준으로 설명합니다. 조사 시 확인된 원 프로젝트는 GHC 9.8.4, effectful-core 2.3.1.0, effectful-th 1.0.0.1, servant 0.20.2, lens 5.2.3, postgresql-simple 0.7.0.0을 사용합니다.

근거를 읽는 법

이 문서는 근거의 성격을 다음처럼 구분합니다.

  • 검증된 사실은 원문의 고정 커밋, 언어 명세, 또는 원 프로젝트 버전의 공식 API 문서와 패키지 소스에서 확인한 내용입니다.
  • 원문 해석은 여러 코드 조각의 관계를 종합한 설명이며, 저자가 직접 쓴 주장과 구분합니다.
  • 독자 이해에 관한 추정은 하이라이트의 분포와 메모에서 추론한 학습 필요입니다. 실제 이해 상태를 확정하지 않습니다.
  • 교육적 단순화는 작동 원리를 드러내기 위해 세부 타입이나 내부 구현을 줄인 설명입니다. 그런 코드에는 “설명용”이라고 표시합니다.

원문 전체의 아키텍처

원문의 설계를 한 문장으로 줄이면 다음과 같습니다.

서버는 “사용자 목록 조회” 같은 저장 연산이 존재한다는 사실만 알고, 그 연산이 메모리의 Map을 읽는지 PostgreSQL에 질의하는지는 인터프리터가 결정합니다.

다음은 원문을 바탕으로 새로 구성한 정적 구조도입니다.

HTTP 요청
   |
   v
Servant API 타입              API의 모양을 선언합니다.
   |
   v
Servant 핸들러                listUsers, createUser 등을 호출합니다.
   |
   v
Storage 효과                  가능한 저장 연산을 선언합니다.
   |
   +----------------------+----------------------+
   |                                             |
   v                                             v
인메모리 인터프리터                            PostgreSQL 인터프리터
State Memory + Map                              State Int + IOE + Connection

Servant와 Effectful은 서로 다른 문제에 같은 형태의 분리를 적용합니다.

층 선언하는 것 구현하는 것
Servant URL, HTTP 메서드, 요청 및 응답 타입 요청을 처리하는 서버 함수
Effectful Storage 목록 조회, 생성, 삭제 같은 저장 연산 메모리 갱신 또는 SQL 실행

패키지도 이 경계를 반영합니다. 도메인 타입은 core, HTTP API의 모양은 backend-api, 서버 함수는 backend-server, 저장 연산의 정의는 storage, 구체적인 저장 방식은 storage-memory와 storage-postgresql에 둡니다. 서버 함수에는 Connection이나 Map이 나타나지 않습니다. 반대로 각 인터프리터는 HTTP 경로를 알 필요가 없습니다.

중요한 실행 흐름은 다음과 같습니다.

createUser 호출
  -> Effectful이 CreateUser 요청을 효과 환경으로 보냅니다.
  -> 선택된 Storage 인터프리터가 요청을 패턴 매칭합니다.
  -> 메모리 인터프리터라면 Map을 갱신합니다.
  -> PostgreSQL 인터프리터라면 INSERT를 실행합니다.
  -> 어느 경우든 서버에는 User를 돌려줍니다.

이 구조 덕분에 테스트에서는 인메모리 인터프리터를, 운영에서는 PostgreSQL 인터프리터를 선택할 수 있습니다. 다만 “인터프리터를 바꿀 수 있다”는 사실이 두 구현의 의미가 자동으로 같아진다는 뜻은 아닙니다. 트랜잭션, 동시성, ID 생성, 오류 의미 같은 계약은 별도로 맞춰야 합니다.

먼저 알아야 할 공통 개념

1. data, type, Generic: 값의 구조와 타입의 이름

data는 새 타입과 값 생성자를 만듭니다

다음은 원 저장소에서 확인한 도메인 선언 중 필드와 타입 동의어 부분입니다. 원문에서는 집중할 부분만 남기기 위해 일부 매개변수와 필드를 ...로 생략했습니다.

data User' id name = User
  { _userId :: id
  , _userName :: name
  }

type User = User' UserId Text
type UserCreate = User' () Text

data Transaction' id userId amount = Transaction
  { _transactionId :: id
  , _transactionUserId :: userId
  , _transactionAmount :: amount
  }

type Transaction = Transaction' TransactionId UserId Double
type TransactionCreate = Transaction' () () Double

data User' id name = User ...는 다음 두 이름을 새로 만듭니다.

  • User'는 타입 인수 id와 name을 받는 타입 생성자입니다.
  • User는 필드 값을 받아 실제 값을 만드는 값 생성자입니다.

예를 들어 User' Int Text와 User' () Text는 같은 구조를 서로 다른 단계에 특수화한 타입입니다. 전자는 ID가 있는 사용자이고, 후자는 아직 ID가 없는 생성 요청입니다. 타입 매개변수를 이용해 “생성 전”과 “저장 후”의 차이를 표현한 셈입니다.

type은 기존 타입 표현식에 별명을 붙입니다

메모의 질문인 “Difference to data?”에 대한 직접적인 답은 다음과 같습니다.

type Transaction = Transaction' TransactionId UserId Double은 새로운 데이터 구조를 만들지 않습니다. 오른쪽의 기존 타입에 Transaction이라는 읽기 쉬운 별명을 붙입니다. 따라서 Transaction과 Transaction' TransactionId UserId Double은 타입 검사에서 같은 타입으로 취급되며, Transaction 전용 값 생성자도 생기지 않습니다.

반면 data Transaction' ... = Transaction ...은 새로운 명목 타입과 Transaction 값 생성자를 만듭니다. 레코드 값을 만들고 패턴 매칭할 수 있는 근거는 data 선언입니다. Haskell 2010 보고서의 데이터 타입과 타입 동의어 선언에서 해당 차이를 규정합니다.

선언 새 타입을 만듭니까? 새 값 생성자를 만듭니까? 주 용도
data 예 예 값의 구조와 명목적 구분을 정의합니다.
type 아니요 아니요 긴 타입 표현식에 별명을 붙입니다.
newtype 예 예 런타임 비용을 거의 늘리지 않고 명목적 구분을 만듭니다.

예를 들어 원문의 type UserId = Int는 편리하지만 UserId와 TransactionId가 모두 Int이므로 서로 잘못 넘겨도 타입 검사로 막지 못합니다. 이를 막는 것이 목적이라면 다음처럼 newtype을 쓰는 편이 적합합니다. 아래 코드는 새로 만든 설명용 예제입니다.

newtype UserId = UserId Int
newtype TransactionId = TransactionId Int

Generic은 타입 매개변수의 “제네릭”과 다릅니다

deriving (Show, Generic)의 Generic은 GHC가 데이터 구조를 공통 표현으로 바꾸는 from과 되돌리는 to를 생성하게 하는 타입 클래스입니다. Java의 List<T>에서 말하는 타입 매개변수와 같은 개념이 아닙니다. GHC의 Generic programming 문서가 이 표현 구조를 설명합니다.

원문의 PostgreSQL 모듈에는 본문이 비어 있는 다음 인스턴스가 있습니다.

instance FromRow User
instance ToRow User
instance FromRow Transaction
instance ToRow Transaction

postgresql-simple의 FromRow와 ToRow는 각각 Generic a와 내부 표현용 제약을 요구하는 기본 메서드를 제공합니다. 그래서 메서드 본문이 없는 위 인스턴스 선언은 Generic 표현을 통해 각 필드를 순서대로 읽거나 SQL 매개변수로 만듭니다. 이 프로젝트의 User는 Int와 Text 두 필드이므로 ToRow User는 매개변수 두 개를 만들며, FromRow User는 결과 열 두 개를 소비합니다. 이 편의는 각 필드에 ToField 또는 FromField 인스턴스가 있고 SQL 열 순서가 레코드 필드 순서와 맞는다는 전제를 가집니다. 공식 문서가 명시하듯 이 제네릭 기본값은 곱 타입에는 적용되지만 합 타입이나 재귀 타입은 지원하지 않습니다.

2. Template Haskell: 선언을 입력으로 받아 코드를 생성합니다

makeLenses ''User'와 makeEffect ''Storage는 서로 다른 라이브러리 함수지만, 둘 다 Template Haskell로 컴파일 도중 선언을 생성합니다. TemplateHaskell 확장을 활성화한 이유입니다.

여기서 작은따옴표는 세 용법을 구분해야 합니다.

표기 의미
User' 끝의 '는 평범한 Haskell 식별자 이름의 일부입니다.
''User' 앞의 ''는 타입 생성자 User'의 컴파일 시간 이름을 인용합니다.
'[JSON] 앞의 '는 값 수준 목록 문법을 타입 수준으로 승격했음을 나타냅니다.

makeLenses ''User'는 밑줄로 시작하는 레코드 필드를 보고 기본 규칙에 따라 lens를 생성합니다. 원문의 경우 _userId에서 userId, _userName에서 userName을 만듭니다. _userId는 읽기만 하는 일반 레코드 선택자이지만, userId lens는 읽기와 불변 갱신을 모두 조합할 수 있습니다. 정확한 생성 규칙은 Control.Lens.TH에 나옵니다.

makeEffect ''Storage는 DispatchOf Storage를 동적 dispatch로 지정하는 타입 패밀리 인스턴스와, Storage GADT의 각 생성자를 send하는 함수를 만듭니다. 예를 들어 ListUsers로부터 대략 다음 선언을 생성합니다.

listUsers
  :: (HasCallStack, Storage :> es)
  => Eff es [User]
listUsers = send ListUsers

이 코드는 공식 API를 바탕으로 펼쳐 쓴 설명용 근사치입니다. 원문 자체도 “looks like”라고 표현하며 HasCallStack을 생략합니다. 원 프로젝트의 effectful-th 1.0.0.1에서는 실제 생성 시그니처에 HasCallStack이 포함됩니다. 자세한 계약은 makeEffect 문서에서 확인할 수 있습니다.

3. Servant: 웹 API의 모양을 타입으로 기술합니다

Servant에서는 URL 경로, HTTP 메서드, 요청 본문, 응답 타입을 하나의 타입 표현식으로 조합합니다. 다음 원문 코드를 읽어 보겠습니다.

type UserAPI =
       "list" :> Get '[JSON] [User]
    -- ^ list all the users
  :<|> "create" :> ReqBody '[JSON] UserCreate :> Post '[JSON] User
    -- ^ create a new user

이 표현은 값으로 실행되는 라우터가 아니라 API 명세 타입입니다. Servant는 이 타입에서 필요한 서버 함수의 타입, 클라이언트 함수, 문서화에 필요한 구조 등을 계산할 수 있습니다. Servant 공식 API 타입 튜토리얼은 이 방식을 단계적으로 설명합니다.

"list" :> Get '[JSON] [User]를 왼쪽부터 해석하면 다음과 같습니다.

  1. "list"는 타입 수준 문자열인 고정 경로 조각입니다.
  2. Servant의 :>는 왼쪽 경로나 요청 조건 아래에 오른쪽 API를 둡니다.
  3. Get은 HTTP GET과 상태 코드 200을 나타내는 Verb의 타입 동의어입니다.
  4. '[JSON]은 응답에 사용할 수 있는 콘텐츠 타입의 타입 수준 목록입니다.
  5. [User]는 응답 본문의 평범한 Haskell 목록 타입입니다.

따라서 이 한 줄은 개념적으로 GET /list가 JSON 사용자 배열을 반환한다는 뜻입니다. '[JSON]의 '와 [User] 앞에 '가 없는 이유도 중요합니다. 전자는 콘텐츠 타입 값을 타입 수준으로 올린 목록이고, 후자는 원래부터 타입인 User의 목록입니다. 이는 GHC의 DataKinds 기능입니다.

Capture "id" TransactionId는 고정 문자열이 아닌 경로 한 조각을 받습니다.

"delete" :> Capture "id" TransactionId :> DeleteNoContent

개념적으로 /delete/42의 42를 TransactionId로 파싱하고, 성공하면 삭제 핸들러의 인수로 넘깁니다. Capture 문서에서 이 타입과 핸들러 인수의 관계를 확인할 수 있습니다.

:<|>는 두 API의 대안, 즉 합을 만듭니다.

type API =
  "user" :> UserAPI
    :<|> "transaction" :> TransactionAPI

타입 수준에서는 사용자 API와 거래 API를 모두 포함합니다. 값 수준의 서버 구현에서도 같은 생성자를 써서 userServer :<|> transactionServer처럼 두 핸들러 묶음을 만듭니다. 이 대응 관계는 Servant의 :<|> 문서에 정의되어 있습니다.

API
├── /user
│   ├── GET  /list
│   └── POST /create
└── /transaction
    ├── GET    /list
    └── DELETE /delete/{id}

이 도식은 원문의 API 타입을 새로 시각화한 정적 대안입니다.

4. Effectful: 가능한 연산과 수행 방법을 분리합니다

Effectful에서 효과는 “이 프로그램이 요청할 수 있는 연산의 집합”으로 볼 수 있습니다. 원문은 이를 GADT로 선언합니다.

data Storage :: Effect where
  ListUsers :: Storage m [User]
  CreateUser :: UserCreate -> Storage m User

  ListTransactions :: Storage m [Transaction]
  DeleteTransaction :: TransactionId -> Storage m ()

선택된 ::는 평소의 value :: Type과 같은 서명 기호이지만, 왼쪽의 Storage가 값이 아니라 타입 생성자이므로 오른쪽 Effect는 kind입니다. 원 프로젝트의 Effectful 버전에서 Effect는 다음 형태의 타입 동의어입니다.

type Effect = (Type -> Type) -> Type -> Type

즉 Storage는 계산 타입 생성자 자리 m :: Type -> Type과 연산 결과 타입 a :: Type을 받아 Storage m a를 만드는 타입 생성자입니다. 고차 효과라면 m에 들어 있는 계산을 연산의 인수로 가질 수 있지만, 이 Storage 생성자들은 그런 인수를 사용하지 않는 일차 효과입니다. ListUsers는 결과가 [User]인 요청이고, DeleteTransaction은 결과가 ()인 요청입니다. GADT 문법 덕분에 인터프리터가 각 생성자를 패턴 매칭하면 그 분기에서 돌려줘야 할 타입도 정해집니다. GHC의 GADT 안내서가 이 생성자별 결과 타입을 설명합니다.

Eff es a는 “효과 목록 es에 적힌 효과를 사용할 수 있으며 최종적으로 a를 만드는 계산”으로 읽을 수 있습니다. 여기서 es는 타입 수준 목록입니다. 다음 제약은 그 목록 안에 Storage가 있어야 한다고 요구합니다.

listUsers :: (Storage :> es) => Eff es [User]

Effectful의 Storage :> es는 효과 멤버십 제약입니다. 정확히는 Storage가 타입 수준 효과 목록 es의 어딘가에 있으며 Effectful이 그 환경 슬롯의 위치를 찾을 수 있다는 증거입니다. 따라서 listUsers는 해당 환경으로 Storage 요청을 보낼 수 있습니다. 실제 실행에서는 바깥쪽의 runStorageMemory나 runStoragePostgres가 그 슬롯에 처리기를 설치하고 효과를 제거합니다. Effectful 2.3.1.0의 Eff, Effect, :> 문서에서 정확한 정의를 확인할 수 있습니다.

같은 :>라도 Servant와 Effectful에서는 완전히 다릅니다

문맥 예 의미
Servant "list" :> Get ... 경로나 요청 조건과 하위 API를 연결합니다.
Effectful Storage :> es Storage가 효과 목록 es의 구성원임을 요구합니다.

철자만 같고 패키지와 타입 역할이 다릅니다. 실제 서버 모듈은 충돌을 피하려고 다음처럼 Servant의 :>를 숨깁니다.

import Servant.API hiding ((:>))

인터프리터는 효과 목록에서 Storage를 제거합니다

인메모리 인터프리터의 핵심 타입은 다음과 같습니다.

runStorageMemory ::
  (State Memory :> es) => Eff (Storage : es) a -> Eff es a

입력은 Storage가 목록 맨 앞에 있는 계산이고, 출력에서는 Storage가 사라집니다. 인터프리터가 모든 Storage 요청을 State Memory 연산으로 바꾸어 처리했기 때문입니다.

실행 전 효과 목록:  Storage : State Memory : 기타 효과
                         |
                         | runStorageMemory
                         v
실행 후 효과 목록:            State Memory : 기타 효과

PostgreSQL 인터프리터도 Storage를 제거하지만, 이를 처리하기 위해 바깥 환경에 State Int와 IOE가 있어야 합니다. Effectful의 interpret는 요청 생성자를 받아 이 변환을 수행합니다.

원문이 추천한 Alexis King의 효과 시스템 강연은 대수적 효과의 더 넓은 배경을 설명하는 선택적 보조 자료입니다. 영상 없이도 이 문서를 이해할 수 있도록 필요한 모델은 위에서 모두 설명했습니다. 후속 HTML에 영상을 넣더라도 제목, 발표자, 링크와 이 정적 요약을 함께 유지해야 합니다.

5. State, 함수 합성, Lens: 상태를 읽고 불변 갱신합니다

원문의 get, gets, state, modify는 mtl이 아니라 Effectful.State.Static.Local에서 가져옵니다. 이름과 기본 모델은 익숙한 State 인터페이스와 비슷합니다.

get    :: State s :> es => Eff es s
gets   :: State s :> es => (s -> a) -> Eff es a
state  :: State s :> es => (s -> (a, s)) -> Eff es a
modify :: State s :> es => (s -> s) -> Eff es ()
연산 현재 상태를 읽습니까? 새 상태를 만듭니까? 계산 결과
get 예 아니요 현재 상태 전체
gets f 예 아니요 f를 적용한 결과
state f 예 예 f가 만든 별도 결과
modify f 예 예 ()

정확한 시그니처와 동작은 원 프로젝트 버전의 Effectful.State.Static.Local에 나옵니다.

Lens는 큰 불변 값 안의 한 지점을 읽거나 갱신하는 조합 가능한 초점입니다. 원문에서 사용한 연산은 다음처럼 읽으면 됩니다.

표현 의미
x & f f x와 같으며, 데이터를 먼저 쓰고 변환을 뒤에 씁니다.
field .~ value field가 가리키는 값을 value로 바꾸는 순수 함수를 만듭니다.
at key ?~ value Map의 key 위치에 Just value를 설정하여 삽입하거나 교체합니다.
at key .~ Nothing Map에서 key를 삭제합니다.
field <+~ n 수치 초점을 n만큼 늘리고 증가 후 값과 갱신된 전체 값을 반환합니다.

Control.Lens.Setter, Control.Lens.At, Control.Lens.Lens가 각각 이 연산을 정의합니다.

일반 함수 합성 (.)도 함께 구분해야 합니다.

(f . g) x = f (g x)

M.elems . _users는 먼저 _users로 사용자 맵을 꺼내고 그 결과에 M.elems를 적용합니다. 반면 users . at uId는 lens가 함수 형태로 표현된다는 성질을 이용해 두 lens를 합성합니다. 같은 (.)이지만 선택된 마침표는 전자의 일반 함수 합성입니다.

6. IOE, liftIO, PostgreSQL 연산

postgresql-simple의 질의와 명령은 IO 안에서 실행됩니다. 하지만 인터프리터 분기는 Eff es 안에 있으므로 liftIO로 IO a를 Eff es a에 올립니다.

liftIO :: IO a -> Eff es a

이는 이 문맥에 특수화한 모양이며, 일반 시그니처는 MonadIO m => IO a -> m a입니다. Eff es에서 이를 사용하려면 IOE :> es가 필요합니다. 그래서 PostgreSQL 인터프리터의 제약에 IOE가 명시됩니다. 원 프로젝트 버전의 Effectful 문서가 IOE와 MonadIO (Eff es)의 관계를 뒷받침합니다.

postgresql-simple의 세 함수를 비교하면 다음과 같습니다.

query_  :: FromRow r
        => Connection -> Query -> IO [r]

query   :: (ToRow q, FromRow r)
        => Connection -> Query -> q -> IO [r]

execute :: ToRow q
        => Connection -> Query -> q -> IO Int64
  • query_는 ? 치환 인수가 없는 조회를 실행합니다.
  • query는 별도의 매개변수 행 q를 받아 ?에 안전하게 치환하고 결과 행을 읽습니다.
  • execute는 INSERT, UPDATE, DELETE처럼 결과 행을 읽지 않는 명령을 실행하고 영향받은 행 수를 반환합니다.

선택된 텍스트는 query이지만 실제 원문 호출은 query_입니다. 밑줄까지 포함한 함수 이름이므로 “원문이 query를 호출한다”고 설명하면 틀립니다. 세 함수의 정확한 계약은 Database.PostgreSQL.Simple에서 확인할 수 있습니다.

하이라이트와 메모별 해설

도메인 모델의 네 선택 항목

관련 주석: 27422280, 27422281, 27422282, 27422283

27422280: 첫 번째 ...

정확한 발생 위치는 원문의 다음 선언입니다.

data User' id ... = User

여기의 ...는 Haskell 문법이 아닙니다. 저자가 앞에서 “parameters and fields”를 생략한다고 밝힌 데 따른 문서용 생략 표시입니다. 원 저장소의 실제 줄은 다음과 같습니다.

data User' id name = User

필드 쪽의 다른 ...에는 _userName :: name이 들어갑니다. 따라서 복사한 원문 조각을 그대로 컴파일하면 구문 오류가 납니다.

27422281: Transaction'의 두 번째 Generic

이 선택은 Transaction' 선언의 deriving (Show, Generic)에 있습니다. 앞서 설명했듯 Generic은 Transaction'의 필드 구조를 표준 표현으로 변환하는 인스턴스를 GHC가 생성하게 합니다. 이 원문에서는 특히 PostgreSQL 모듈의 빈 FromRow Transaction과 ToRow Transaction 인스턴스가 제네릭 기본 구현을 이용할 수 있게 합니다. 단순히 출력하기 위한 Show와 역할이 다릅니다.

27422282: type Transaction = ...의 type

이것이 “Difference to data?” 메모가 붙은 정확한 위치입니다.

type Transaction =
  Transaction'
    TransactionId
    UserId
    ...

이 type은 Transaction'을 구체적인 타입 인수로 채운 표현에 Transaction이라는 별명을 붙입니다. 새 타입이나 새 값 생성자는 만들지 않습니다. data Transaction' ... = Transaction ... 쪽이 실제 레코드 구조와 값 생성자를 만듭니다. 즉 이 코드에서 data는 재사용할 구조를 정의하고, type은 그 구조를 특정 단계에 맞게 특수화하여 이름 붙입니다.

27422283: 첫 번째 makeLenses ''

정확한 호출은 다음과 같습니다.

makeLenses ''User'

''User'는 타입 생성자 이름 User'를 Template Haskell 값으로 인용합니다. makeLenses는 그 선언을 조사해 _userId에서 userId, _userName에서 userName lens를 생성합니다. 두 앞쪽 작은따옴표와 이름 끝의 작은따옴표를 한 덩어리 문법으로 오해하면 안 됩니다.

Servant API 타입의 세 선택 항목

관련 주석: 27422289, 27422291, 27422294

27422289: :> Get '[JSON] [User]

정확한 전체 줄은 다음과 같습니다.

"list" :> Get '[JSON] [User]

Servant의 :>는 "list" 경로 아래에 Get ... API를 둡니다. Get은 GET 요청, '[JSON]은 가능한 응답 콘텐츠 타입 목록, [User]는 응답 값 타입입니다. 결과적으로 이 줄은 GET /list가 JSON으로 인코딩된 사용자 목록을 반환한다고 선언합니다.

27422291: 삭제 경로의 Capture

정확한 줄은 다음과 같습니다.

"delete" :> Capture "id" TransactionId :> DeleteNoContent

Capture "id" TransactionId는 URL의 다음 한 조각을 TransactionId로 읽습니다. "id"는 문서와 타입 수준 식별에 쓰는 이름이고, 실제 핸들러는 파싱된 TransactionId 인수를 받습니다. 마지막 DeleteNoContent는 DELETE 요청이 성공 시 본문 없는 응답을 돌려준다는 뜻입니다.

27422294: 전체 API를 잇는 세 번째 :<|>

position: 2는 원문의 세 번째 발생을 뜻하며, 선택된 곳은 UserAPI 내부나 TransactionAPI 내부가 아니라 두 하위 API를 합치는 다음 위치입니다.

type API =
  "user" :> UserAPI
    :<|> "transaction" :> TransactionAPI

이 :<|>는 /user/... 경로 집합과 /transaction/... 경로 집합을 하나의 전체 API로 합칩니다. 서버 값도 같은 모양으로 userServer :<|> transactionServer가 되어 타입 명세와 구현의 구조가 일치합니다.

Storage 효과 선언의 세 선택 항목

관련 주석: 27422295, 27422296, 27422297

27422295: data Storage :: Effect where의 ::

여기의 ::는 Storage 타입 생성자의 kind가 Effect라고 선언합니다. Storage라는 값의 타입을 적는 것이 아닙니다. 이후 ListUsers :: Storage m [User]처럼 각 생성자가 연산의 결과 타입을 지정할 수 있게 하는 GADT 헤더입니다.

27422296: makeEffect ''Storage

정확한 원문 호출은 다음과 같습니다.

makeEffect ''Storage

이 splice는 DispatchOf Storage = 'Dynamic에 해당하는 타입 패밀리 인스턴스와 listUsers, createUser, listTransactions, deleteTransaction 같은 소문자 호출 함수를 생성합니다. 서버는 GADT 생성자 ListUsers를 직접 다루지 않고 listUsers를 호출하며, 생성된 함수가 내부에서 send ListUsers를 수행합니다. 원문에 나온 생성 시그니처는 교육적 축약이며, 이 버전의 실제 시그니처에는 HasCallStack 제약도 들어갑니다.

27422297: 생성 예시의 Storage :> es

이 선택은 Servant API 정의가 아니라 다음 Effectful 제약에 있습니다.

listUsers :: (Storage :> es) => Eff es [User]

여기의 :>는 Storage 효과가 es 안에 포함되어 있고 Effectful이 그 환경 슬롯을 찾을 수 있어야 한다는 뜻입니다. Servant의 경로 연결 연산자와는 다른 정의입니다. 이 제약이 없으면 listUsers는 현재 효과 환경으로 Storage 요청을 보낼 수 없습니다.

인메모리 인터프리터를 줄 단위로 읽기

관련 주석: 27422314, 27422315, 27422316, 27422319, 27422321, 27422322, 27422328, 27422330, 27422332, 27422335, 27422373

먼저 질문과 직접 관련된 원문 부분을 그대로 보겠습니다.

runStorageMemory = interpret $ \_ -> \case
  ListUsers -> gets $ M.elems . _users
  CreateUser userCreate -> do
    uId <- state $ nextId <+~ 1
    let newUser = userCreate & userId .~ uId
    modify $ users . at uId ?~ newUser
    pure newUser

  ListTransactions -> gets $ M.elems . _transactions
  DeleteTransaction tId -> modify $ transactions . at tId .~ Nothing

27422314: \case

\case는 인수를 별도 이름으로 받지 않고 즉시 case로 패턴 매칭하는 LambdaCase 문법입니다. 위 코드는 개념적으로 다음처럼 펼칠 수 있습니다. 아래는 새로 만든 설명용 전개입니다.

runStorageMemory =
  interpret $ \_ -> \operation ->
    case operation of
      ListUsers -> ...
      CreateUser userCreate -> ...
      ListTransactions -> ...
      DeleteTransaction tId -> ...

첫 번째 \_ 인수는 동적 인터프리터가 받는 지역 환경이며, 이 Storage 효과는 그 값을 사용할 필요가 없어 _로 버립니다. LambdaCase 문서가 이 축약 문법을 정의합니다.

27422319, 27422315, 27422335: gets $ M.elems . _users

세 선택은 같은 줄에 있습니다.

ListUsers -> gets $ M.elems . _users

27422319의 gets는 현재 Memory에 함수 하나를 적용해 결과만 돌려주며 상태를 바꾸지 않습니다.

27422315의 M.elems는 Data.Map.elems입니다. Map의 키는 버리고 값을 키 오름차순에 해당하는 순서로 반환합니다. 복잡도는 O(n)입니다. Data.Map.elems 문서가 이 순서와 복잡도를 명시합니다.

27422335의 선택된 .은 정확히 M.elems . _users 사이의 마침표입니다. 이는 lens 합성이 아니라 일반 함수 합성입니다. 다음 두 식은 같은 뜻입니다.

M.elems . _users

\memory -> M.elems (_users memory)

따라서 전체 줄은 현재 Memory를 읽고, _users로 Map UserId User를 꺼낸 다음, M.elems로 [User]를 반환합니다. gets이므로 Memory 자체는 그대로입니다.

27422373, 27422316: state $ nextId <+~ 1

정확한 줄은 다음과 같습니다.

uId <- state $ nextId <+~ 1

27422373의 state는 s -> (a, s) 형태의 순수 상태 전이 함수를 실행합니다. 새 상태뿐 아니라 별도 결과 a도 돌려줄 수 있습니다.

27422316의 <+~는 nextId가 가리키는 수를 1 증가시키고, 증가 후 ID와 갱신된 Memory를 쌍으로 만듭니다. state는 갱신된 Memory를 상태로 저장하고 증가 후 ID를 uId에 바인딩합니다.

다음 정적 단계도는 새로 만든 설명용 예제입니다.

이전 Memory: nextId = 41
       |
       | nextId <+~ 1
       v
결과값: 42
새 Memory: nextId = 42

새 사용자의 식별자를 설정하는 과정

관련 주석: 27422321, 27422322

정확한 줄은 다음과 같습니다.

let newUser = userCreate & userId .~ uId

27422321의 &는 역방향 함수 적용입니다. x & f는 f x와 같아서 데이터를 왼쪽에 두고 변환을 읽기 순서대로 쓸 수 있습니다.

27422322의 .~는 lens가 가리키는 값을 지정한 값으로 설정하는 순수 함수를 만듭니다. 따라서 이 줄은 userCreate의 userId 필드를 uId로 바꾼 새 값 newUser를 만듭니다. 기존 값을 제자리에서 변경하는 명령형 대입이 아닙니다.

27422328: 사용자 맵에 삽입하기

정확한 줄은 다음과 같습니다.

modify $ users . at uId ?~ newUser

users . at uId는 Memory 안의 사용자 맵을 거쳐 특정 키 uId의 Maybe User 위치까지 lens를 합성합니다. 27422328의 ?~ newUser는 그 위치에 Just newUser를 설정합니다. 결과적으로 키가 없으면 삽입하고, 있으면 교체합니다. modify는 이 Memory -> Memory 함수를 현재 상태에 적용합니다.

27422330: 두 번째 pure

선택된 position: 1은 문서 안의 두 번째 pure이며, 인메모리 CreateUser 분기의 다음 줄입니다.

pure newUser

pure는 평범한 newUser 값을 현재 Eff es 계산의 결과로 올립니다. 이 호출 자체는 추가 효과를 요청하지 않습니다. 그러나 앞에서 state와 modify가 이미 상태를 바꾸었으므로, 이 분기 전체가 “순수하고 아무 효과도 없다”는 뜻은 아닙니다.

27422332: 두 번째 modify

선택된 position: 1은 사용자 삽입의 modify가 아니라 인메모리 삭제 분기의 modify입니다.

DeleteTransaction tId -> modify $ transactions . at tId .~ Nothing

transactions . at tId는 Memory 안 거래 맵의 tId 위치를 가리킵니다. .~ Nothing은 그 키를 삭제하는 순수 함수를 만들고, modify가 이를 State Memory에 적용합니다. 이 선택은 뒤의 PostgreSQL modify (+ 1)과 이름만 같고 상태 타입과 변환 내용이 다릅니다.

PostgreSQL 인터프리터를 줄 단위로 읽기

관련 주석: 27422370, 27422371, 27422374, 27422375, 27422379, 27422380

관련 원문 코드는 다음과 같습니다.

runStoragePostgres conn = interpret $ \_ -> \case
  ListUsers -> liftIO $ query_ conn "SELECT * FROM app_users"
  CreateUser userCreate -> do
    uId <- get
    modify (+ 1)
    let newUser = userCreate & userId .~ uId
    liftIO $
      execute conn "INSERT INTO app_users values (?)" newUser
    pure newUser

  ListTransactions ->
    liftIO $ query_ conn "SELECT * FROM transactions"
  DeleteTransaction tId ->
    void . liftIO $
      execute conn "DELETE FROM transactions where id = ?" (Only tId)

27422370: 첫 번째 liftIO

선택된 첫 발생은 ListUsers 분기에 있습니다.

ListUsers -> liftIO $ query_ conn "SELECT * FROM app_users"

query_ ...의 결과 타입은 이 문맥에서 IO [User]입니다. liftIO가 이를 Eff es [User]로 올려 인터프리터 분기의 반환 타입에 맞춥니다. runStoragePostgres에 IOE :> es 제약이 필요한 직접적인 이유입니다.

27422371: 선택 문자열 query와 실제 함수 query_

하이라이트 문자열은 query이지만 실제 토큰 전체는 위 줄의 query_입니다. query_는 치환 인수 없는 SQL 조회를 실행합니다. 반면 query는 SQL의 ? 자리에 넣을 ToRow q 인수를 하나 더 받습니다. 이 줄은 매개변수 없는 SELECT * FROM app_users이므로 query_가 맞습니다.

27422374: CreateUser의 get

정확한 줄은 다음과 같습니다.

uId <- get

여기서 상태 타입은 인메모리 인터프리터의 Memory가 아니라 Int입니다. get은 현재 State Int 값을 읽어 uId에 바인딩하며, 아직 상태를 바꾸지는 않습니다.

27422375: 세 번째 modify

선택된 position: 2는 문서 안의 세 번째 modify이며 다음 줄입니다.

modify (+ 1)

(+ 1)은 현재 정수에 1을 더하는 함수이고, modify는 이를 State Int에 적용합니다. 반환값은 ()입니다. 앞에서 읽은 uId를 현재 사용자의 ID로 쓰고 상태는 다음 ID로 진행합니다.

인메모리 분기의 state $ nextId <+~ 1은 증가 후 값을 돌려주므로 ID 규칙이 미묘하게 다를 수 있습니다. PostgreSQL 분기는 증가 전 값을 uId로 읽은 뒤 상태를 증가시킵니다. 초기값을 어떻게 주느냐에 따라 첫 ID가 달라질 수 있으므로, 두 인터프리터가 같은 외부 계약을 가져야 한다면 초기 상태와 증가 시점을 명시해야 합니다.

27422380: 첫 번째 execute

선택된 첫 발생은 사용자 삽입입니다.

execute conn "INSERT INTO app_users values (?)" newUser

execute는 SQL 명령을 실행하고 영향받은 행 수를 IO Int64로 반환합니다. 여기서는 do 블록 중간 문장이므로 그 정수 결과를 사용하지 않습니다. 뒤의 pure newUser가 분기의 최종 결과가 됩니다.

다만 이 원문 코드는 그대로 실행할 수 있는 INSERT 예제가 아닙니다. 완전한 User에는 ID와 이름이라는 두 필드가 있고 제네릭 ToRow User는 SQL 매개변수 두 개를 만드는데, SQL 템플릿에는 ?가 하나뿐입니다. postgresql-simple 0.7.0.0은 placeholder 수와 toRow가 만든 매개변수 수가 다르면 쿼리를 서버에 보내기 전 formatQuery 단계에서 FormatError를 던집니다. 따라서 원 저장소의 이 호출은 코드 그대로라면 실패합니다. 또한 SELECT *는 데이터베이스 열 순서와 레코드 필드 순서가 같다는 전제를 숨깁니다. 다음은 새로 만든 개선 방향 예시이며 실제 스키마 이름은 원 저장소에 스키마가 없어 확인되지 않았습니다.

execute conn
  "INSERT INTO app_users (id, name) VALUES (?, ?)"
  newUser

27422379: 두 번째 void

선택된 position: 1은 삭제 분기의 다음 표현입니다.

void . liftIO $
  execute conn "DELETE FROM transactions where id = ?" (Only tId)

함수 적용 우선순위를 풀면 다음과 같습니다.

(void . liftIO)
  (execute conn "DELETE FROM transactions where id = ?" (Only tId))

타입은 세 단계로 변합니다.

execute ... :: IO Int64
liftIO      :: IO Int64 -> Eff es Int64
void        :: Eff es Int64 -> Eff es ()

void는 영향받은 행 수를 버려 DeleteTransaction이 요구하는 () 결과에 맞춥니다. 오류를 삼키지는 않습니다. execute가 예외를 내면 그 예외는 그대로 전파됩니다. Only tId는 SQL 매개변수가 하나일 때 그 값을 한 필드 행처럼 전달하는 래퍼입니다. void 문서는 정상 결과 값만 ()로 바꾼다는 점을 명시합니다.

예제의 한계와 실무에서 추가할 계약

원문의 목적은 효과 추상화의 구조를 보여 주는 것이며, 완성된 저장 계층을 제공하는 것이 아닙니다. 다음 사항은 추상화를 실제 시스템에 적용할 때 별도로 설계해야 합니다.

  1. PostgreSQL에서 State Int로 ID를 만들면 여러 프로세스나 동시 요청 사이에서 안전하지 않습니다. 데이터베이스 sequence, identity, 또는 INSERT ... RETURNING을 쓰는 편이 일반적입니다.
  2. get, modify (+ 1), execute는 하나의 데이터베이스 트랜잭션이 아닙니다. INSERT가 실패해도 메모리의 다음 ID 상태는 이미 증가했을 수 있습니다.
  3. SELECT *와 제네릭 FromRow의 조합은 스키마 열 순서에 결합됩니다. 실제 코드에서는 열 이름을 명시하는 편이 안전합니다.
  4. 인메모리와 PostgreSQL 인터프리터가 삭제 대상이 없을 때 같은 결과를 내는지, 조회 순서가 같은지, 오류를 어떤 타입으로 표현하는지를 계약으로 정해야 합니다.
  5. Storage 효과를 분리했다고 해서 테스트가 자동으로 충분해지지는 않습니다. 같은 계약 테스트를 각 인터프리터에 실행해야 교체 가능성을 검증할 수 있습니다.

이 한계들은 Effectful 접근 자체의 오류가 아니라 원문이 교육을 위해 생략한 운영 세부 사항입니다. 다만 사용자 INSERT의 placeholder 수는 단순화가 아니라 실행 전에 FormatError를 일으키는 코드 결함입니다.

정리

원문의 중심 구조는 세 단계입니다.

Servant API 타입  ->  서버가 호출할 Storage 연산  ->  선택 가능한 인터프리터

data Storage :: Effect where는 가능한 저장 연산과 각 결과 타입을 선언합니다. makeEffect는 서버가 쓰기 좋은 호출 함수를 만들고, Storage :> es는 그 연산을 처리할 효과가 환경에 있음을 보장합니다. interpret는 요청 생성자를 패턴 매칭하여 인메모리 상태 연산 또는 PostgreSQL IO로 바꾸고, 처리된 Storage를 효과 목록에서 제거합니다.

세부 문법도 이 구조 안에 놓으면 역할이 분명해집니다.

  • data는 구조를 만들고 type은 그 구조를 특수화한 타입 표현식에 별명을 붙입니다.
  • Generic은 SQL 행 변환의 기본 구현에 필요한 구조 표현을 제공합니다.
  • makeLenses와 makeEffect는 Template Haskell로 반복 선언을 생성합니다.
  • Servant의 :>는 API 조합이고 Effectful의 :>는 효과 멤버십입니다.
  • gets, state, modify는 상태 읽기와 전이를 구분합니다.
  • &, .~, ?~, <+~는 불변 값을 조합 가능한 방식으로 갱신합니다.
  • 선택된 .은 M.elems . _users의 일반 함수 합성입니다.
  • 실제 호출 query_는 매개변수 없는 조회이고, execute는 영향받은 행 수를 반환하는 명령 실행입니다.
  • liftIO는 SQL의 IO를 Eff로 올리고 void는 정상 반환값만 버립니다.

결국 이 예제에서 타입은 단지 값을 분류하는 표지가 아닙니다. HTTP API의 모양, 프로그램이 요청할 수 있는 저장 연산, 실행에 필요한 효과를 각각 기록하며, 컴파일러가 층 사이의 연결이 맞는지 검사하게 합니다.

  6. PostgreSQL과 인메모리 인터프리터의 ID 증가 시점이 동일한 외부 의미를 갖는지는 초기 상태가 제시되지 않아 확정할 수 없습니다. 본문에서는 차이 가능성만 표시했습니다.
  7. 외부 미디어는 Alexis King의 강연 링크 하나만 선택적으로 제시했습니다. 영상이 없어도 문서는 완결됩니다. HTML 생성 시 영상을 임베드한다면 제목과 발표자, 링크, 본문의 정적 요약을 대체 콘텐츠로 유지해야 합니다.
  8. 구조도와 상태 전이도는 텍스트로 제공되어 별도 이미지 없이 접근 가능합니다. 시각 이미지로 바꿀 경우 동일한 텍스트를 대체 설명으로 보존해야 합니다.
