MCAP 파서의 lift와 Record Schema: ParsecT 아래의 StateT로 상태가 전달되는 방식

해설 대상 원문: James Bowen, “Schemas, Channels & Messages in MCAP”

검토일: 2026-10-31

이 해설의 EPUB 전자책 판: EPUB 파일 내려받기

이 문서에서 설명하는 내용

James Bowen의 Schemas, Channels & Messages in MCAP은 ROS bag 파일을 MCAP 형식으로 파싱하는 연재의 세 번째 글입니다. 이 글은 Message 레코드에 토픽 정보가 없다는 문제에서 출발합니다. 토픽과 디코딩 정보는 앞서 나온 Channel 레코드와 Schema 레코드에 들어 있으므로, 파서는 이미 읽은 채널과 스키마를 기억해야 합니다. 저자는 이를 위해 Megaparsec의 ParsecT 아래에 StateT TopicState 계층을 추가하고, 각 레코드 파서가 읽은 값을 그 상태에 저장하게 합니다.

두 메모는 모두 parseSchema 함수의 완성본에서 서로 이웃한 두 줄에 달려 있습니다. 하나는 lift가 그 자리에서 무엇을 하는지 묻고, 다른 하나는 Record Schema가 생성자인지, 그리고 schema’를 담은 상태가 어떻게 전달되는지 묻습니다.

독자 이해에 관한 추정: 두 질문은 모두 "파서 계층과 상태 계층이 어떻게 맞물리는가"라는 같은 메커니즘을 향하고 있습니다. 또한 이 연재의 1부와 2부 코드에는 lift가 한 번도 나오지 않으므로, 연재를 순서대로 읽은 독자도 이 글에서 처음 lift를 만났을 가능성이 높습니다. 그래서 이 문서는 먼저 모나드 변환기 스택(monad transformer stack), StateT, lift, 데이터 생성자라는 공통 개념을 설명한 다음 각 메모에 직접 답합니다. 반면 MCAP 레코드 구조 자체에 관한 질문은 없었으므로 MCAP 형식은 질문에 답하는 데 필요한 만큼만 다룹니다. 이는 메모에서 추론한 내용이며 확정된 사실은 아닙니다.

먼저 알아야 할 공통 개념

이 글의 모나드 스택: ParsecT, 그 아래의 StateT, 맨 아래의 IO

원문은 파서 타입을 다음과 같이 바꿉니다.

type Parser a = ParsecT Void ByteString (StateT TopicState IO) a

Megaparsec 문서에 따르면 ParsecT e s m a는 사용자 정의 오류 성분 e, 입력 스트림 타입 s, 기반 모나드(underlying monad) m, 결과 타입 a를 갖는 파서입니다. 같은 문서는 Parsec을 "the more general ParsecT monad transformer"의 변환기가 아닌 변형이라고 설명하므로, ParsecT는 다른 모나드 위에 쌓는 모나드 변환기입니다(Megaparsec Text.Megaparsec 문서). 위 정의에서 각 자리는 다음과 같습니다.

  • e = Void: 사용자 정의 오류를 쓰지 않습니다.
  • s = ByteString: MCAP 파일의 바이트열을 입력으로 읽습니다.
  • m = StateT TopicState IO: 파서 아래에 있는 기반 모나드입니다.

즉 이 글의 Parser는 세 계층으로 이루어진 스택입니다. 바깥에서 안쪽 순서로 정리하면 다음과 같습니다.

계층 담당하는 일 이 글에서 쓰는 연산
ParsecT Void ByteString 입력 위치, 파싱 오류, 되돌아가기(backtracking) parseUint16LE, parseString, count, anySingle
StateT TopicState 채널, 스키마, 메시지를 담은 TopicState 상태 get, put
IO 파일 읽기, 화면 출력 BS.readFile, print

각 계층은 자기 연산만 직접 이해합니다. parseString은 Parser의 연산이고, get과 put은 StateT TopicState IO의 연산입니다. 한 do 블록 안에서 이 둘을 섞으려면 안쪽 계층의 연산을 바깥 계층의 연산으로 바꾸는 장치가 필요한데, 그 장치가 lift입니다. 이는 lift를 직접 쓰는 방식을 기준으로 한 단순화된 설명입니다. mtl의 타입 클래스를 쓰면 get과 put 같은 일부 연산은 lift 없이도 쓸 수 있으며, 이 내용은 아래 lift 해설의 참고 단락에서 다룹니다.

연재의 1부와 2부에서는 Parser가 IO 위에 ParsecT 한 겹만 쌓은 구조였습니다. 원문도 "We’re already operating within a ParsecT IO monad transformer stack"이라고 말합니다. 이 글에서 StateT 계층이 가운데에 끼어들면서 계층을 건너는 일이 처음 생겼고, 그래서 lift도 이 글에서 처음 등장합니다.

StateT: 상태를 보이지 않는 인자로 넘기는 함수

transformers 패키지는 StateT를 다음과 같이 정의합니다(Control.Monad.Trans.State.Strict 문서).

newtype StateT s m a = StateT { runStateT :: s -> m (a, s) }

StateT s m a 값은 "현재 상태 s를 받아서, 기반 모나드 m 안에서 결과 a와 새 상태 s를 돌려주는 함수"입니다. 상태를 다루는 기본 연산은 다음과 같습니다.

  • get :: Monad m => StateT s m s: 현재 상태를 결과로 꺼냅니다.
  • put :: Monad m => s -> StateT s m (): 상태를 주어진 값으로 바꿉니다.
  • runStateT: 초기 상태를 넣어 실행하고 (결과, 최종 상태)를 돌려받습니다.
  • evalStateT: 같은 방식으로 실행하되 결과만 돌려받고 최종 상태는 버립니다.
  • execStateT: 최종 상태만 돌려받습니다.

핵심은 do 블록이 상태를 자동으로 전달한다는 점입니다. Haskell 2010 보고서에 따르면 do 블록의 각 문장은 >>=와 >>로 번역됩니다(Haskell 2010 보고서 3장 §3.14). StateT의 >>=는 앞 동작이 돌려준 새 상태를 다음 동작의 입력 상태로 넘깁니다. 이를 단순화한 모델로 적으면 다음과 같습니다. 엄격성(strictness) 표시와 클래스 선언은 생략했습니다.

-- 이 문서에서 단순화해 적은 StateT의 >>= 모델입니다.
m >>= k = StateT $ \s -> do
  (a, s') <- runStateT m s   -- 앞 동작을 현재 상태 s로 실행합니다.
  runStateT (k a) s'         -- 다음 동작을 새 상태 s'로 실행합니다.

s'가 다음 동작에 그대로 넘어가는 이 한 줄이 상태 전달의 전부입니다. 그래서 코드에 상태 매개변수가 보이지 않아도 각 문장은 직전 문장이 남긴 상태를 받습니다. 이 글이 Strict 모듈과 Lazy 모듈 중 어느 쪽의 StateT를 쓰는지는 import 목록이 없어 확인되지 않았지만, 두 모듈의 StateT는 같은 형태이므로 이 설명은 어느 쪽에도 적용됩니다.

다음은 이 문서에서 만든 예제이며 원문 코드가 아닙니다.

-- 이 문서에서 만든 예제입니다.
counter :: StateT Int IO ()
counter = do
  n <- get        -- 상태 0을 꺼냅니다.
  put (n + 1)     -- 상태를 1로 바꿉니다.
  m <- get        -- 바뀐 상태 1을 꺼냅니다.
  lift (print m)  -- IO 계층에서 1을 출력합니다.

runStateT counter 0을 실행하면 1이 출력되고 결과로 ((), 1)이 나옵니다. 두 번째 get이 1을 보는 이유는 put이 만든 새 상태를 >>=가 다음 문장에 넘겼기 때문입니다.

lift: 안쪽 모나드의 동작을 바깥 모나드의 동작으로 옮기기

lift는 MonadTrans 타입 클래스의 메서드입니다. 상위 클래스 제약을 생략하고 쓰면 다음과 같습니다(Control.Monad.Trans.Class 문서).

class MonadTrans t where
  lift :: Monad m => m a -> t m a

문서는 이를 "Lift a computation from the argument monad to the constructed monad."라고 설명합니다. 변환기 t가 기반 모나드 m 위에 만든 모나드 t m으로, m의 계산을 그대로 옮긴다는 뜻입니다. Megaparsec은 ParsecT e s에 대해 이 클래스의 인스턴스를 제공합니다(instance Stream s => MonadTrans (ParsecT e s), Megaparsec 문서).

이 글에 대입하면 t = ParsecT Void ByteString, m = StateT TopicState IO이므로 lift의 타입은 다음과 같이 구체화됩니다.

-- 이 문서에서 타입을 대입해 적은 것입니다.
lift :: StateT TopicState IO a -> ParsecT Void ByteString (StateT TopicState IO) a
--      즉, StateT TopicState IO a -> Parser a

lift는 한 계층만 올립니다. IO 동작을 Parser로 올리려면 StateT 계층과 ParsecT 계층을 차례로 지나야 하므로 lift (lift (print x))처럼 두 번 써야 합니다. 원문이 "If you put in any print statements using lift, these would just need an additional lift"라고 말하는 이유가 이것입니다. 원문이 대안으로 든 liftIO는 몇 계층이든 한 번에 IO를 올립니다. Megaparsec 소스에서 ParsecT의 liftIO는 lift . liftIO로 정의되어 있습니다(Text.Megaparsec.Internal 소스).

데이터 생성자와 타입 생성자는 이름이 같아도 다른 것입니다

Haskell의 data 선언은 타입 생성자(type constructor) 하나와 데이터 생성자(data constructor) 여러 개를 함께 만듭니다(Haskell 2010 보고서 4장 §4.2.1). 타입 생성자는 타입 시그니처 안에서 쓰이고, 데이터 생성자는 값을 만드는 함수처럼 식(expression) 안에서 쓰입니다. 두 종류의 이름은 서로 다른 이름 공간(namespace)에 속하므로 같은 철자를 써도 충돌하지 않습니다(Haskell 2010 보고서 1장 §1.4).

이 글에도 이런 예가 많습니다. data MsgSchema = MsgSchema { ... }에서 등호 왼쪽의 MsgSchema는 타입이고, 오른쪽의 MsgSchema는 데이터 생성자입니다. 필드 이름이 붙은 생성자도 일반 생성자처럼 인자를 순서대로 넣어 쓸 수 있으므로(§4.2.1), 원문의 MsgSchema sid sname sencoding schema는 네 필드를 순서대로 채워 MsgSchema 값을 만드는 식입니다.

하이라이트와 메모별 해설

여기서 lift는 무엇을 하나요

하이라이트: lift

원문 문맥:

  let schema' = MsgSchema sid sname sencoding schema
  lift (addSchema schema’)
  return $ (totalLen, Record Schema)
  where
    addSchema :: MsgSchema -> StateT TopicState IO ()

사용자 메모: “What does this do here?”

이 문맥은 "Parsing a Schema" 절의 세 번째이자 완성된 parseSchema 코드 블록입니다. 이 해설은 위 문맥의 lift (addSchema schema’) 줄을 기준으로 합니다. parseChannel의 lift (addChannel channel)처럼 원문의 다른 lift 호출에도 같은 설명이 적용됩니다.

짧은 답: 여기서 lift는 상태 계층의 동작인 addSchema schema'를 파서 계층의 동작으로 바꿔서 parseSchema의 do 블록 안에 끼워 넣습니다. 그 결과 파서가 실행되는 도중에 새 스키마가 TopicState의 tsSchemas 맵에 저장됩니다.

타입으로 본 설명: parseSchema의 시그니처는 Parser (Word64, Record)이므로 그 do 블록의 모든 문장은 Parser 동작이어야 합니다. 그런데 where 절에 적힌 대로 addSchema의 타입은 MsgSchema -> StateT TopicState IO ()입니다. 따라서 각 식의 타입은 다음과 같습니다.

  • addSchema schema' :: StateT TopicState IO ()
  • lift (addSchema schema') :: ParsecT Void ByteString (StateT TopicState IO) (), 즉 Parser ()

lift가 없으면 Parser 블록 안에 StateT 동작이 놓이므로 타입 오류가 납니다. 이를 확인하려고 원문과 같은 구조의 작은 예제를 만들었습니다. 이 예제는 원문 코드가 아닙니다.

-- 이 문서에서 만든 예제입니다. 의도적으로 lift를 빼서 컴파일에 실패합니다.
import Control.Monad.Trans.State.Strict (StateT, modify)
import Data.Void (Void)
import Text.Megaparsec

type Parser a = ParsecT Void String (StateT Int IO) a

step :: StateT Int IO ()
step = modify (+ 1)

p :: Parser ()
p = do
  step        -- lift step이라고 써야 합니다.
  return ()

main :: IO ()
main = return ()

GHC 9.10.3과 megaparsec 9.7.0으로 이 예제를 컴파일하면 다음 오류가 납니다. 이 문서가 링크한 Megaparsec 문서는 9.8.3판이며, 9.8.3으로 직접 컴파일하지는 않았습니다. 다만 이 예제에 쓰인 MonadTrans 인스턴스와 ParsecT의 타입은 9.8.3 문서에도 같은 형태로 나옵니다.

• Couldn't match type: StateT Int IO
                 with: ParsecT Void String (StateT Int IO)
  Expected: ParsecT Void String (StateT Int IO) ()
    Actual: StateT Int IO ()

입력에는 영향을 주지 않습니다: Megaparsec의 lift 구현은 안쪽 동작을 기반 모나드에서 실행한 뒤, 입력을 소비하지 않은 성공으로 처리합니다(Text.Megaparsec.Internal 소스). 이 문서에서 따로 만든 예제에서 lift 앞뒤의 입력 오프셋을 getOffset으로 출력해 보니 두 값이 같았습니다. 따라서 lift (addSchema schema')는 파싱 위치를 옮기지 않고 상태만 바꿉니다. 바이트를 읽는 일은 앞 줄들의 parseUint16LE, parseString, count ... anySingle이 이미 끝냈습니다.

글 전체에서 반복되는 같은 패턴: 원문에서 lift는 모두 같은 역할을 합니다.

  • lift (addChannel channel): 채널을 상태에 저장합니다.
  • tops <- lift get: parseMessage에서 현재 TopicState를 읽습니다. 원문은 여기서도 lift로 StateT의 get을 Parser로 올립니다.
  • lift $ addMessage ...: 메시지 데이터를 상태에 저장합니다.

원문 산문의 "we just lift our stateful action into the Parser monad"도 정확히 이 뜻입니다.

lift 없이 쓰는 방법(참고): Megaparsec은 기반 모나드가 MonadState이면 ParsecT도 MonadState가 되도록 인스턴스를 제공하며, 그 안에서 get = lift get, put = lift . put으로 정의합니다(Text.Megaparsec.Internal 소스). 따라서 mtl의 Control.Monad.State에 있는 클래스 기반 get과 put을 쓰고 addSchema의 타입을 MonadState TopicState m => MsgSchema -> m ()처럼 일반화하면, Parser 안에서 lift 없이 호출할 수 있습니다. 이 문서에서 같은 구성을 작은 예제로 실행해 확인했습니다. 다만 이것은 원문 코드가 아닌 대안이며, 원문이 어느 모듈에서 get과 put을 가져오는지는 글에 import 목록이 없어 확인되지 않았습니다. 그래서 parseMessage의 lift get이 꼭 필요한지는 import에 따라 달라집니다. 반면 원문의 addSchema는 타입이 StateT TopicState IO ()로 고정되어 있으므로, 원문 코드 그대로라면 lift (addSchema schema')의 lift는 반드시 필요합니다.

Record Schema는 생성자인가요, 그리고 schema’를 담은 상태는 어떻게 전달되나요

하이라이트: Record Schema

원문 문맥:

  let schema' = MsgSchema sid sname sencoding schema
  lift (addSchema schema’)
  return $ (totalLen, Record Schema)

사용자 메모: “Is this a constructor? How is the state that includes schema’ passed?”

이 메모에는 두 질문이 있으므로 차례로 답합니다.

첫 번째 질문: Record Schema는 생성자인가요

짧은 답: 네, Record는 데이터 생성자입니다. 더 정확히 말하면 Record Schema는 데이터 생성자 Record에 인자 Schema를 적용한 식이고, 그 결과는 Record 타입의 값입니다. Schema 역시 인자가 없는 데이터 생성자입니다.

두 정의는 이 글이 아니라 연재의 2부 "The Structure of an MCAP File"에 있습니다. 2부의 정의를 요약하면 다음과 같습니다. 줄바꿈과 공백은 이 문서에서 정리했으며, 원문 그대로의 서식은 2부를 참고하시기 바랍니다.

-- 2부의 정의를 요약해 옮긴 것입니다.
data RecordType = FileHeader | FileFooter | Schema | Channel | Message | Chunk
                | MessageIndex | ChunkIndex | Attachment | AttachmentIndex
                | Statistics | Metadata | MetadataIndex | SummaryOffset | DataEnd
  deriving (Show, Eq, Enum)

data Record = Record RecordType | ChunkRecord [Record]
  deriving (Show, Eq)

여기서 각 이름의 정체는 다음과 같습니다.

  • RecordType은 MCAP 레코드 종류를 나열한 열거형 타입이고, Schema는 그중 하나의 값, 즉 인자 없는 데이터 생성자입니다. 따라서 Schema :: RecordType입니다.
  • Record는 같은 철자로 두 가지를 동시에 가리킵니다. 등호 왼쪽의 Record는 타입 생성자이고, 오른쪽의 Record RecordType에 있는 Record는 RecordType 값 하나를 받는 데이터 생성자입니다. 따라서 데이터 생성자로서 Record :: RecordType -> Record입니다.

원문 함수의 시그니처와 반환 줄을 나란히 보면 두 가지 쓰임이 구분됩니다.

parseSchema :: Parser (Word64, Record)

이 시그니처의 Record는 타입 자리에 있으므로 타입 생성자입니다. 반면 return $ (totalLen, Record Schema)의 Record는 식 자리에 있으므로 데이터 생성자입니다. 그래서 (totalLen, Record Schema)의 타입은 (Word64, Record)가 되어 시그니처와 맞습니다.

자주 생기는 오해: 여기의 Schema는 이 글에서 새로 만든 MsgSchema 타입이 아니며, 방금 파싱한 스키마 데이터를 담고 있지도 않습니다. Record Schema는 "방금 읽은 레코드의 종류는 Schema였다"는 표시(tag)일 뿐입니다. 원문도 이를 "return the same record signifying the type that we have been so far"라고 설명합니다. 즉 2부에서 레코드 종류만 돌려주던 방식을 그대로 유지한 것입니다. parseChannel의 Record Channel, parseMessage의 Record Message, 그리고 parseSingleRecord의 나머지 경우에 쓰는 Record typ도 모두 같은 표시입니다. 이 Schema는 parseSingleRecord의 case typ of 분기에서 Schema -> do로 매칭하는 바로 그 생성자이기도 합니다.

이 점이 두 번째 질문과 연결됩니다. 반환값에는 스키마가 없으며, 스키마는 상태를 통해 다음 파서로 전달됩니다.

두 번째 질문: schema’를 담은 상태는 어떻게 전달되나요

질문의 "schema’를 담은 상태"를 정확히 나누어 보겠습니다. schema'는 처음부터 상태 안에 있는 값이 아니라, addSchema가 실행된 뒤에야 상태에 들어갑니다. 이 함수에서 전달되는 것은 두 가지이며 전달 방식이 서로 다릅니다.

  1. schema' 값은 보통의 함수 인자로 전달됩니다. addSchema schema'라고 쓰면 addSchema s = do ...의 s에 schema'가 묶입니다.
  2. TopicState 상태는 StateT가 보이지 않게 전달합니다. 코드 어디에도 상태 매개변수가 보이지 않는 이유가 이것입니다.

schema'는 addSchema가 실행되는 순간에 비로소 상태 안으로 들어갑니다. 원문의 addSchema는 다음과 같습니다.

    addSchema :: MsgSchema -> StateT TopicState IO ()
    addSchema s = do
      tops <- get
      let newS = HM.insert (schemaId s) s (tsSchemas tops)
      put $ tops { tsSchemas = newS }

전체 흐름을 순서대로 따라가면 다음과 같습니다.

  1. 초기 상태 준비: 진입점 함수에서 initialTopicState를 만듭니다. 빈 맵 세 개, 원하는 토픽 집합 /simple_topic, 빈 채널 집합으로 이루어진 값입니다.
  2. 상태 계층 실행: 원문의 진입점은 runStateT (runParserT parseMcapFile' fp input) initialTopicState를 실행합니다. runParserT를 적용하면 파서가 기반 모나드의 동작, 즉 StateT TopicState IO (Either ...)가 됩니다. 여기에 runStateT로 초기 상태를 넣습니다. 이때부터 모든 레코드 파서는 같은 상태 줄기 위에서 실행됩니다.
  3. 상태 읽기: addSchema 안의 tops <- get이 그 시점의 현재 TopicState를 꺼냅니다. 이 값에는 이전 레코드들이 저장한 내용이 이미 들어 있습니다.
  4. 새 상태 만들기: HM.insert (schemaId s) s (tsSchemas tops)는 기존 스키마 맵에 새 스키마를 ID 키로 넣은 새 맵을 만듭니다. tops { tsSchemas = newS }는 레코드 갱신 문법(record update syntax)으로, tops를 바꾸지 않고 tsSchemas 필드만 다른 복사본을 만듭니다(Haskell 2010 보고서 3장 §3.15.3).
  5. 상태 교체: put이 그 복사본을 새 상태로 정합니다.
  6. 파서 쪽으로 이어 붙이기: lift가 이 StateT 동작을 Parser 동작으로 바꿉니다. 이 단계가 바깥 ParsecT를 지나서도 상태가 이어지는 이유이므로 아래에서 따로 설명합니다.
  7. 표시만 반환: parseSchema는 (totalLen, Record Schema)를 반환합니다. 앞에서 본 것처럼 이 반환값에는 스키마가 없습니다. 스키마는 이미 상태 안에 있습니다.
  8. 나중에 꺼내 쓰기: 이후 parseMessage가 tops <- lift get으로 같은 상태를 읽고, findSchema tops channelId로 채널 ID에서 채널을, 채널의 schema_id에서 스키마를 찾습니다.

ParsecT를 지나서도 상태가 이어지는 이유: 여기에는 서로 다른 두 가지 "상태"가 있으므로 먼저 구분해야 합니다.

  • Megaparsec 자신의 상태: 남은 입력, 오프셋, 오류 정보처럼 파싱에 필요한 상태입니다. ParsecT 계층이 직접 관리합니다.
  • 사용자 상태 TopicState: 채널, 스키마, 메시지를 담은 이 글의 상태입니다. 이 상태는 전적으로 기반 모나드인 StateT TopicState IO 안에 있으며, ParsecT는 이 값을 읽지도 바꾸지도 않습니다.

따라서 TopicState를 ParsecT 안에서 찾을 필요는 없습니다. Parsec 라이브러리의 "사용자 상태(user state)"를 알고 있다면 혼동하기 쉬운 부분입니다. 이 글의 TopicState는 그런 내장 기능이 아니라 아래 계층의 StateT가 관리하는 값입니다.

Megaparsec 소스에서 ParsecT는 "다음에 할 일"을 함수로 받는 연속 전달 방식(continuation-passing style)으로 구현되어 있고, lift는 안쪽 동작을 기반 모나드에서 실행한 뒤 그 결과를 받아 파서의 나머지 부분을 계속 실행합니다(Text.Megaparsec.Internal 소스). 단순화해서 말하면, lift (addSchema schema') 뒤에 오는 파서의 나머지 부분 전체가 기반 모나드의 >>= 사슬 안에서 이어서 실행됩니다. 그 >>=가 바로 앞에서 본 StateT의 >>=이므로, put이 남긴 새 TopicState가 다음 문장과 다음 레코드 파서로 넘어갑니다. 이 설명은 실제 구현의 세부 사항(성공과 실패를 위한 여러 연속 함수, 오류 힌트 처리)을 생략한 교육적 단순화입니다.

그림으로 정리하면 다음과 같습니다. 이 도식은 이 문서에서 만든 것입니다.

initialTopicState
   │  runStateT가 초기 상태로 넣음
   ▼
parseSchema ── lift (addSchema schema') ──▶ tsSchemas에 스키마 추가
   │  반환값: (totalLen, Record Schema)   ← 스키마는 들어 있지 않음
   ▼
parseChannel ── lift (addChannel channel) ──▶ tsChannels, tsDesiredChannels 갱신
   ▼
parseMessage ── lift get ──▶ findSchema로 채널과 스키마 조회
             ── lift $ addMessage ... ──▶ tsMessages에 메시지 추가
   ▼
최종 TopicState (runStateT 결과의 두 번째 성분)

이 방식이 한 번의 순차 파싱으로 동작하는 이유는 MCAP 명세의 순서 규칙에 있습니다. 명세는 Schema 레코드가 그것을 참조하는 Channel 레코드보다 앞에, Channel 레코드가 그것을 참조하는 Message 레코드보다 앞에 적어도 한 번 나와야 한다고 정합니다(MCAP 형식 명세). 원문도 이 순서를 "Schemas and Channels" 절에서 강조합니다. 그래서 관심 있는 토픽의 메시지라면, parseMessage가 실행될 때 그 메시지의 채널과 스키마가 이미 상태에 저장되어 있습니다. 다만 명세는 schema_id가 0인 채널, 즉 스키마가 없는 채널도 허용합니다. 원문 코드를 해석하면, 그런 채널의 메시지와 addChannel이 저장하지 않은 관심 밖 토픽의 메시지는 findSchema가 Nothing을 돌려주므로 저장되지 않고 건너뛰어집니다.

원문 코드의 표기 오류: schema'와 schema’: 원문 문맥의 두 줄을 자세히 보면 문자가 다릅니다. 위 줄의 let schema' = ...는 ASCII 작은따옴표(U+0027)를 쓰고, 아래 줄의 addSchema schema’는 오른쪽 둥근 작은따옴표(U+2019)를 씁니다. 메모에 적힌 schema’도 이 둥근 따옴표입니다.

  • 사실: Haskell 식별자에는 문자, 숫자, 밑줄, ASCII 작은따옴표만 쓸 수 있습니다(Haskell 2010 보고서 2장 §2.4). U+2019는 식별자 문자가 아닙니다. 이 문서에서 let schema' = 1 :: Int 다음 줄에 print (schema’)를 쓴 작은 예제를 GHC 9.10.3으로 컴파일하자 "Unicode character '’' ('\8217') looks like ''' (Single Quote), but it is not"라는 오류가 났습니다. 따라서 원문의 그 줄은 적힌 그대로는 컴파일되지 않습니다.
  • 해석: 앞 줄에서 정의한 이름이 schema'이므로, 저자가 의도한 코드는 lift (addSchema schema')입니다. 이 문서의 설명도 그 의도를 기준으로 합니다.
  • 추정: 같은 글의 HS.singleton “/simple_topic”에도 둥근 큰따옴표가 들어 있는 점으로 보아, 블로그 편집기가 따옴표를 자동으로 둥근 따옴표로 바꾼 것으로 보입니다. 원인은 확인되지 않았습니다.

원문 진입점 코드의 불일치: 최종 상태를 받는 부분에도 원문 산문과 코드가 서로 맞지 않는 곳이 있습니다. 원문 산문은 "we need to use evalStateT"라고 말하지만 코드는 runStateT를 씁니다.

  result <- runStateT (runParserT parseMcapFile' fp input) initialTopicState
  • 사실: runStateT의 결과는 (Either ..., TopicState) 쌍이므로, 이 코드 그대로라면 뒤의 case result of Left e -> ...와 타입이 맞지 않습니다. 또 마지막 줄의 print st에서 st는 어디에서도 정의되지 않았습니다. 반대로 산문대로 evalStateT를 쓰면 case는 맞지만 최종 상태를 버리므로 print st로 출력할 상태가 남지 않습니다.
  • 사실: 같은 코드 블록에서 타입 시그니처는 printRecordTypesFromFile이라는 이름을 쓰지만, 정의는 parseBareRecordsFromFile이라는 이름으로 시작합니다. 이 불일치는 질문과 직접 관련은 없지만, 코드를 그대로 옮겨 컴파일할 때 함께 고쳐야 합니다.
  • 추정: 최종 TopicState를 출력한다는 글의 목적과 타입을 함께 고려하면, 의도한 코드는 (result, st) <- runStateT (runParserT parseMcapFile' fp input) initialTopicState일 가능성이 높습니다. 이렇게 쓰면 result로 파싱 결과를, st로 상태의 최종 모습을 받습니다.

참고: 실패한 분기의 상태 변경은 되돌려지지 않습니다: 이 글은 상태 계층을 ParsecT 아래에 두었습니다. Mark Karpov의 Megaparsec 튜토리얼은 이런 배치에서는 파서가 되돌아가도 사용자 상태가 되돌려지지 않고, 반대로 StateT를 ParsecT 바깥에 두면 상태도 함께 되돌려진다고 설명합니다(Megaparsec 튜토리얼). 이 문서에서 try 안에서 상태를 바꾼 뒤 실패하는 예제를 실행해 보니, 대안 분기로 넘어간 뒤에도 바뀐 상태가 남아 있었습니다. 이 성질은 레코드 파서가 try나 <|>로 감싸여 실패 후 다른 분기로 넘어갈 때만 의미가 있습니다. 올바른 MCAP 파일을 읽는 정상 경로에서는 상태를 저장한 레코드 파서가 그 뒤에 실패하지 않으므로 문제가 되지 않습니다. 원문 구조에서 도출한 해석을 덧붙이면, 2부의 parseMcapFile은 레코드를 many (try parseSingleRecord)로 읽으므로, 어떤 레코드 파서가 상태를 저장한 뒤 길이 검사에서 실패하더라도 그 저장 내용은 최종 TopicState에 남습니다.

정리

  • 이 글의 Parser는 ParsecT가 바깥, StateT TopicState가 가운데, IO가 맨 아래인 모나드 스택입니다.
  • lift는 한 계층 아래의 동작을 바로 위 계층의 동작으로 바꿉니다. lift (addSchema schema')는 StateT TopicState IO () 동작을 Parser () 동작으로 바꿔 파서 안에서 상태를 갱신하게 하며, 입력은 소비하지 않습니다.
  • Record Schema는 데이터 생성자 Record를 인자 없는 생성자 Schema :: RecordType에 적용한 값입니다. 레코드 종류를 나타내는 표시일 뿐 스키마 데이터를 담지 않습니다.
  • 스키마 값은 addSchema에 보통 인자로 전달되고, addSchema가 get과 put으로 TopicState에 넣습니다. TopicState는 StateT의 >>=가 문장과 문장 사이에서 보이지 않게 전달하며, 시작 상태는 runStateT가 넣고 최종 상태도 runStateT가 돌려줍니다.
  • 원문의 schema’는 schema'의 표기 오류이며, 진입점 코드는 산문과 맞지 않습니다. 두 곳 모두 의도는 문맥에서 분명합니다.
