Distributors 해설 8/8: 맺음말 (Extroduction)

해설 대상 원문: Eitan Chatav, “Distributors — Unifying Parsers, Printers & Grammars”

검토일: 2026-11-21

이 쪽은 여덟 쪽 시리즈의 마지막 쪽이며, 원문의 마지막 절 "Extroduction"을 다룹니다. 이 절에는 코드가 없습니다. 대신 원문 코드를 어떻게 대해야 하는지에 관한 안내와, 저자가 남긴 열린 질문들이 있습니다. 이 쪽은 먼저 원문 코드와 현재 패키지의 관계를 정리하고, 시리즈 전체를 한 장의 표로 복습한 뒤, 열린 질문을 하나씩 풀어 읽습니다. 질문 중 하나인 자유(free) 문법(grammar) 디스트리뷰터(distributor)는 작은 예시로 구체적인 모습을 보여 드립니다.

"Extroduction"이라는 제목

"Extroduction"은 기술 용어가 아니라, 들어가는 말(introduction)의 앞부분을 뒤집은 말장난입니다. "나가는 말", 즉 맺음말이라는 뜻으로 읽으면 됩니다.

이 글은 literate Haskell이 아닙니다

원문은 이렇게 시작합니다.

This post is not literate Haskell. Instead of trying to compile the post, play with this code on GitHub where it is hopefully kept compiling & tested.

문학적 하스켈(literate Haskell)은 설명 글과 코드를 한 파일에 쓰고, 컴파일러가 그 파일에서 코드 부분만 뽑아 컴파일하는 방식입니다. 보통 .lhs 확장자를 쓰며, 코드 줄 앞에 >를 붙이거나 \begin{code}와 \end{code}로 코드를 감쌉니다. 이런 글은 글 자체가 컴파일되므로 코드가 실제로 동작한다는 보장이 있습니다. 원문은 그런 글이 아니라고 분명히 밝히고, 실제로 동작하는 코드는 GitHub 저장소에서 보라고 안내합니다.

이 시리즈에서 짚은 부분

이 안내 덕분에, 이 시리즈의 각 쪽에서 원문 코드가 그대로는 컴파일되지 않거나 표현이 일반적인 용법과 다른 부분을 차분히 짚을 수 있었습니다. 한곳에 모으면 다음과 같습니다.

쪽 내용
1 "invariant"를 유령(phantom) 또는 상수 펑터의 뜻으로 썼습니다. 하스켈의 보통 용법과 다릅니다.
3 runParsor anyToken "xyz" 예제는 인스턴스 머리를 그대로 옮기면 GHC 9.10.3에서 모호성 오류가 나며, 두 자리를 모두 적으면 동작합니다.

6 manyP의 시그니처에 Distributor p =>가 빠져 있습니다. 범주론(category theory)의 "distributor"는 추가 구조 없는 프로펑터(profunctor)입니다.

이것들은 글의 생각을 흔드는 문제가 아니라, 설명을 위해 다듬은 코드 조각에서 흔히 생기는 틈입니다.

원문 코드와 현재 패키지

원문의 코드는 Hackage의 distributors 패키지로 이어졌고, 이 시리즈를 쓰는 시점의 최신 판은 0.6.0.0(2026년 4월 25일 업로드)입니다. 그런데 패키지는 원문 이후 설계가 여러 곳에서 달라졌습니다. 패키지 소스에서 확인되는 차이는 다음과 같습니다.

  • Printor는 이제 a -> f (b, s -> s)를, Parsor는 Maybe a -> s -> f (b, s)를 감쌉니다. 즉 두 타입 모두 더 이상 한쪽 매개변수가 유령이 아닙니다. 2쪽에서 본 "파서(parser)는 오른쪽만, 프린터(printer)는 왼쪽만 쓴다"는 원문의 설계와 다릅니다.
  • Tokenized는 class Categorized token => Tokenized token p | p -> token이 되었고, anyToken 외에 token, oneOf, notOneOf, asIn, notAsIn 같은 메서드를 가집니다.
  • optionalP와 manyP의 갈래 순서가 원문과 반대여서 긴 쪽을 먼저 시도하고, someP의 정의도 달라졌습니다.

그러므로 이 시리즈가 읽은 코드는 원문의 코드이며, 현재 패키지의 API와 같다고 보면 안 됩니다. 패키지를 실제로 쓸 때는 패키지 문서를 기준으로 삼아야 합니다.

시리즈 전체 복습

원문은 "수년에 걸친 집착의 결과"라고 스스로 말합니다. 그 결과를 한 장으로 모으면 다음과 같습니다.

인터페이스 핵심 연산 쪽 Parsor Printor (->)
Profunctor dimap 2 예 예 예
Tokenized anyToken 3 예 예 원문에 없음
Choice, Cochoice left', unright (>?, ?<, >?<) 4 예 예 예
Monoidal oneP, >*< 5 예 예 예
Distributor zeroP, >+< 6 예 예 예
Alternator alternate, empty, `< >` 6 예 예
Filtrator filtrate 6 예 예 아니요
Grammatical inClass, rule, ruleRec 7 예 예 아니요

(->) 열은 이 시리즈의 각 쪽에서 본 인스턴스를 기준으로 했으며, Choice, Cochoice, Monoidal의 인스턴스는 원문이 아니라 profunctors 패키지와 이 시리즈가 예시를 위해 다시 만든 코드에 따른 것입니다. 함수는 언제나 결과를 하나 돌려줘야 하므로 실패(empty)도, 결과 걸러 내기(Filterable)도 표현할 수 없습니다. 그래서 함수 화살표는 Alternator, Filtrator, 그리고 그 둘을 요구하는 Grammatical이 될 수 없습니다. Tokenized는 원문이 함수 화살표의 인스턴스를 정의하지 않았습니다.

옵틱(optic) 쪽의 계층도 함께 정리할 수 있습니다. 모든 동형(Iso)은 프리즘(Prism)으로, 모든 프리즘은 부분 동형(PartialIso)으로 쓸 수 있습니다. 요구하는 p의 능력이 Profunctor, Choice, Choice와 Cochoice 순으로 늘어나기 때문입니다(4쪽). 원문과 패키지는 여기에 모노클(monocle, Monoidal), 디옵터(diopter, Distributor), 바이포컬(bifocal, Alternator와 Filtrator)이라는 이름을 더했습니다(5쪽, 6쪽).

그리고 이 모든 것 밑에 있는 생각은 하나입니다. 프린터-파서(printer-parser)는 p a b 타입을 가지며, 파서로는 b를 만들고 프린터로는 a를 읽습니다. 함수 쌍을 받는 조합자(combinator)는 한 함수를 파서에, 다른 함수를 프린터에 줍니다.

열린 질문 하나씩 읽기

원문의 나머지는 질문의 연속입니다. 저자는 자신의 집착이 채워졌지만 따라갈 길이 더 있다며 독자를 초대합니다. 질문들은 주장이 아니라 연구 방향이므로, 아래의 해설에도 이 시리즈의 해석이 섞여 있습니다. 해석인 부분은 그렇게 밝히겠습니다.

파서 말고 또 어디에 쓸 수 있을까요

원문은 Applicative와 Alternative가 파서 말고도 쓸모가 많다는 점을 상기시키며, Monoidal, Distributor, Alternator, Filtrator는 또 어디에 쓸 수 있는지 묻습니다. 이 시리즈에서 이미 한 가지 실마리를 보았습니다. 6쪽에서 함수 화살표에 manyP를 적용하면 map이 되었습니다. 즉 이 인터페이스들은 "같은 구조를 두 방향으로, 또는 갈래마다 처리하는" 일반적인 언어입니다. 직렬화와 역직렬화처럼 두 방향이 짝을 이루는 다른 문제에도 같은 구조가 나타날 수 있다는 것이 이 시리즈의 짐작이며, 원문이 구체적인 예를 든 것은 아닙니다.

더 많은 예제, 정리, 문서화

원문은 Grammar의 의미 있는 예제가 하나뿐이라는 점을 스스로 지적하고, 예제를 더 만들어 올려 달라고, 코드를 최적화하거나 정리하거나 문서화해 달라고 부탁합니다. 7쪽에서 본 regexGrammar의 거친 부분, 즉 원자 자리 단말 기호의 출력 같은 것이 그런 정리의 대상이 될 수 있습니다.

자유 Grammatical 디스트리뷰터

Can you construct a useful free Grammatical distributor, starting with a base of Identical Char Char?

자유 구조란. 7쪽에서 언어를 담는 두 방법을 보았습니다. 클래스의 메서드로 담는 파이널 인코딩(final encoding)과, 자료형의 생성자로 담는 초기 인코딩(initial encoding)입니다. 어떤 클래스의 자유 구조(free structure)는 그 클래스의 메서드를 생성자로 가진 자료형입니다. 엄밀히 말하면 자유 구조는 클래스의 법칙이 같다고 보는 값들을 하나로 묶어야 하지만, 여기서는 그 부분을 생략한 단순화로 설명합니다. 문법을 이 자료형의 값으로 만들면 아무것도 실행되지 않고 문법의 모양이 데이터로 남으며, 나중에 그 데이터를 어떤 인스턴스로든 해석할 수 있습니다.

Identical이 그 씨앗입니다. 3쪽의 Identical a b는 Tokenized의 가장 헐벗은 인스턴스였습니다. 아무 일도 하지 않고 "토큰(token) 하나"라는 표시만 남기며, fromIdentical로 어떤 Tokenized 인스턴스로든 해석할 수 있었습니다. 즉 Identical은 토큰 하나에 대한 자유 구조입니다. 원문의 질문은 이 생각을 Grammatical 전체로 넓혀, "토큰 하나"(Identical Char Char)에서 출발해 연접, 선택, 반복, 패턴, 규칙까지 데이터로 담는 자유 구조를 만들 수 있느냐는 것입니다.

작은 예시. 다음은 원문의 코드도, 원문 저자가 생각한 설계도 아닙니다. 자유 구조가 어떤 느낌인지 보여 주기 위해 메서드 몇 개만 담은 작은 예시이며, 3쪽의 GADT 문법을 씁니다. 아래 결과는 원문과 필요한 라이브러리 정의를 최소한으로 다시 만든 코드 위에서 GHC 9.10.3으로 실행한 것입니다.

data FreeG a b where
  Tok  :: FreeG Char Char
  Lit  :: String -> FreeG () ()
  Pair :: FreeG a b -> FreeG c d -> FreeG (a, c) (b, d)
  Alt  :: FreeG a b -> FreeG c d -> FreeG (Either a c) (Either b d)
  Many :: FreeG a b -> FreeG [a] [b]

-- Interpret the data with any Grammatical instance.
interpret :: Grammatical p => FreeG a b -> p a b
interpret Tok        = anyToken
interpret (Lit s)    = fromString s
interpret (Pair x y) = interpret x >*< interpret y
interpret (Alt x y)  = interpret x >+< interpret y
interpret (Many x)   = manyP (interpret x)

-- Inspect the data directly.
describe :: FreeG a b -> String
describe Tok        = "."
describe (Lit s)    = s
describe (Pair x y) = describe x ++ describe y
describe (Alt x y)  = "(" ++ describe x ++ "|" ++ describe y ++ ")"
describe (Many x)   = "(" ++ describe x ++ ")*"
  • 각 생성자는 지금까지 본 연산 하나에 대응합니다. Tok은 anyToken(3쪽), Lit은 문자열 리터럴(5쪽), Pair는 >*<(5쪽), Alt는 >+<(6쪽), Many는 manyP(6쪽)입니다. Tok이 3쪽의 Identical Char Char와 같은 역할을 합니다.
  • GADT의 결과 타입이 각 연산의 타입을 그대로 따르므로, FreeG a b 값은 p a b와 같은 타입 정보를 담습니다.
  • interpret는 데이터를 어떤 Grammatical 인스턴스로든 해석합니다. 파이널 인코딩으로 되돌리는 함수입니다.
  • describe는 인스턴스를 거치지 않고 데이터를 직접 들여다봅니다. 7쪽의 DiRegEx와 비슷한 일을 하지만, 클래스 인스턴스가 아니라 평범한 함수입니다.
yesNo :: FreeG (Either () ()) (Either () ())
yesNo = Alt (Lit "yes") (Lit "no")

hashChars :: FreeG ((), [Char]) ((), [Char])
hashChars = Pair (Lit "#") (Many Tok)
>>> (describe yesNo, describe hashChars)
("(yes|no)","#(.)*")
>>> runParsor (interpret yesNo :: Parsor String [] (Either () ()) (Either () ())) "no!"
[(Right (),"!")]
>>> [pr "" | pr <- runPrintor (interpret yesNo :: Printor String [] (Either () ()) (Either () ())) (Left ())]
["yes"]
>>> runParsor (interpret hashChars :: Parsor String [] ((), String) ((), String)) "#ab"
[(((),""),"ab"),(((),"a"),"b"),(((),"ab"),"")]
>>> [pr "" | pr <- runPrintor (interpret hashChars :: Printor String [] ((), String) ((), String)) ((), "hi")]
["#hi"]

같은 데이터 값 하나가 설명 문자열, 파서, 프린터로 해석되었습니다. "쓸모 있는" 자유 Grammatical 디스트리뷰터가 되려면 여기에 실패, 선택, 4쪽의 패턴(>?<), 7쪽의 정규 술어와 규칙까지 담아야 합니다. 특히 >?<를 담으려면 다형적인 부분 동형을 생성자의 필드로 넣어야 하므로 쉽지 않습니다. 원문이 이것을 열린 질문으로 남긴 이유로 보입니다.

문법 변환: 왼쪽 인수분해

원문은 이어서 그 자유 구조로 왼쪽 인수분해(left factoring) 같은 문법 변환을 정의할 수 있는지 묻습니다.

왼쪽 인수분해란. 두 선택지가 같은 앞부분으로 시작하는 규칙 A = α β | α γ를 A = α (β | γ)로 바꾸는 변환입니다. 되돌아가기(backtracking)를 하는 파서는 앞의 규칙에서 α를 두 번 파싱할 수 있고, 다음 토큰만 보고 갈래를 정하는 예측 파서는 앞의 규칙을 아예 다룰 수 없습니다. 인수분해하면 α를 한 번만 파싱하고 그다음에 갈래를 고릅니다.

왜 자유 구조가 필요할까요. 파이널 인코딩의 Grammar a는 다형적인 값이어서, 그 안에 "같은 앞부분을 가진 두 갈래"가 있는지 직접 들여다볼 방법이 없습니다. 변환을 하려면 먼저 문법을 데이터로 만들어야 하고, 그 데이터가 자유 구조입니다. 위의 FreeG에서는 Alt (Pair x y) (Pair x z) 같은 모양을 패턴 매칭으로 찾을 수 있습니다.

타입이 걸림돌이 되는 지점. 이 시리즈의 해석을 하나 덧붙이겠습니다. 위의 예시에서 Alt (Pair x y) (Pair x z)의 타입은 Either (a, c) (a, e) 모양이고, 인수분해한 Pair x (Alt y z)의 타입은 (a, Either c e) 모양입니다. 두 타입은 다르므로 그냥 바꿔 쓸 수 없고, 둘 사이의 동형이 필요합니다. 그런데 그 동형이 바로 6쪽에서 본 분배 법칙, 즉 "곱이 합 위로 분배된다"는 성질입니다. 이 인터페이스가 "분배(distributive)" 프로펑터라는 이름을 가진 것과 문법 변환 사이에 자연스러운 연결이 있는 셈입니다.

문자 스트림 너머

원문은 문자 스트림(stream) 문법 말고 어떤 확장이 가능한지 묻고, 예로 aeson을 쓴 JSON 문법과 TypeScript 타입 생성기를 듭니다. 원문은 이름만 언급하므로 다음은 이 시리즈의 해석입니다.

  • JSON 문법: 이 글의 토큰은 Char였지만, 3쪽의 Tokenized와 Cons는 토큰 타입을 추상화했습니다. 토큰이나 스트림 자리에 JSON 값을 두면, 하나의 기술에서 JSON 디코더와 인코더를 함께 얻을 수 있을 것입니다. aeson은 하스켈의 대표적인 JSON 라이브러리이며, 보통은 디코더(FromJSON)와 인코더(ToJSON)를 따로 씁니다. 1쪽의 반복 금지 원칙 문제가 여기서도 똑같이 나타납니다.
  • TypeScript 타입 생성기: 7쪽에서 같은 문법을 DiRegEx로 해석해 정규 표현식(regular expression)을 얻었듯이, 데이터 기술을 다른 해석기로 해석해 그 데이터의 TypeScript 타입 선언을 출력하는 생성기를 생각할 수 있습니다. 파이널 태그리스 방식에서 새 생성기는 새 인스턴스라는 7쪽의 관점을 그대로 넓힌 것입니다.

패턴 옵틱 계층 안의 문법

원문은 문법이 패턴 옵틱 계층 안에서 어디에 놓이는지 연구해 보자고 합니다. 위의 복습에서 보았듯이 Iso, Prism, PartialIso, 그리고 모노클, 디옵터, 바이포컬은 모두 forall p f. (제약) => p a (f b) -> p s (f t) 꼴이고, p에 대한 제약만 다릅니다. Grammatical도 p에 대한 제약이므로 같은 꼴의 옵틱을 생각할 수 있고, 그것이 기존 옵틱들과 어떤 포함 관계를 가지는지가 질문의 내용으로 읽힙니다.

더 높은 수준의 조합자

원문은 쓸모 있는 고수준 문법 조합자를 더해 보자고 합니다. 7쪽의 SepBy, chainl1, chainl이 그런 조합자의 예이며, 원문은 그 본문조차 생략했습니다. 구분자로 나뉜 목록, 괄호로 둘러싼 식, 연산자 우선순위 표 같은 것이 후보가 될 수 있습니다.

망라적 문법과 정규 문법 분리하기

원문은 문법 인터페이스에서 망라적 문법(exhaustive grammar)이나 정규 문법(regular grammar)을 따로 떼어 내 보자고 합니다.

  • 망라적 문법: 2쪽과 6쪽에서 보았듯이 Distributor만 쓰고 Alternator를 쓰지 않으면 프린터가 실패하지 않습니다. 이런 문법만 모은 인터페이스가 있으면, "이 문법의 프린터는 모든 값을 출력한다"는 사실을 타입으로 보장할 수 있습니다.
  • 정규 문법: 재귀 규칙(ruleRec)이 없는 문법은 정규 표현식 하나로 나타낼 수 있습니다. 이런 문법을 따로 구분하면, 예를 들어 정규 표현식 엔진에 그대로 넘기는 것 같은 다른 해석이 가능해집니다.

재귀 하강이 아닌 파서: Earley

Can Grammars generate parsers which aren't recursive descent like an Earley parser, by over-writing ruleRec perhaps?

재귀 하강 파서. 재귀 하강 파서(recursive descent parser)는 규칙마다 함수 하나를 두고, 규칙이 다른 규칙을 가리키면 그 함수를 호출하는 방식입니다. Parsor가 정확히 이런 파서이며, 결과 컨테이너가 목록이면 모든 가능성을 시도하는 되돌아가기 파서입니다.

왼쪽 재귀의 문제. 재귀 하강 파서는 왼쪽 재귀(left recursion), 즉 규칙이 자기 자신으로 시작하는 경우(e = e "+" t | t)를 다루지 못합니다. 이 시리즈의 추론으로는, ruleRec "e" (\e -> e >*< ...)처럼 쓰면 Parsor는 e를 파싱하려고 입력을 하나도 소비하지 않은 채 다시 e를 호출하므로 끝나지 않습니다(직접 실행해 보지는 않았습니다). 7쪽의 chainl1과 chainl은 왼쪽 재귀를 직접 쓰지 않고 같은 모양의 구문을 다루는 한 방법으로 볼 수 있지만, 원문이 그 조합자를 쓴 이유를 이렇게 밝히지는 않습니다.

Earley 파서. Jay Earley가 1970년에 발표한 Earley 알고리즘은 왼쪽 재귀나 모호한 문법을 포함한 모든 문맥 자유 문법(context-free grammar)을 파싱할 수 있습니다. 이 알고리즘은 문법의 규칙 구조를 미리 알고 그 위에서 상태를 관리합니다. 그런데 ruleRec의 기본 구현은 fix로 재귀의 매듭을 묶어 버리므로, 해석기는 "어디서 재귀가 일어나는지"를 볼 수 없습니다. 원문의 제안은 ruleRec을 덮어써서, 재귀 지점을 이름과 본문으로 기록하게 하자는 것으로 읽힙니다. 그러면 해석기가 문법 전체를 규칙의 그래프로 보고 Earley 파서를 만들 수 있습니다. 7쪽에서 rule을 덮어써 규칙 이름을 모으는 DiGrammar가 같은 방향의 예입니다.

함께 하자는 초대

원문은 이 주제들 가운데 하나를 함께 페어 프로그래밍(pair programming)하자는 제안으로 끝납니다. 페어 프로그래밍은 두 사람이 한 화면에서 함께 코드를 쓰는 방식입니다. 글 전체가 완결된 결과 보고라기보다 진행 중인 연구로의 초대라는 점이 마지막 문장에서 드러납니다.

이 시리즈를 마치며

이 시리즈는 "구문을 한 번만 기술해서 파서와 프린터를 함께 얻는다"는 1쪽의 목표에서 출발했습니다. 원문은 그 목표를 다음 순서로 이루었습니다.

  1. 공변(covariance)과 반변(contravariance)의 충돌을 매개변수 두 개짜리 프로펑터로 풀었습니다(1쪽, 2쪽).
  2. 토큰 하나를 다루는 기본 부품을 하나만 두었습니다(3쪽).
  3. 옵틱에서 함수 쌍을 꺼내, 파서에는 한 함수를 프린터에는 다른 함수를 주었습니다(4쪽).
  4. Applicative와 Alternative의 모양을 프로펑터로 옮겨 차례로 잇기와 경우 나누기를 얻었습니다(5쪽, 6쪽).
  5. 이 모든 능력을 문법 인터페이스로 묶고, 해석기를 바꾸어 파서, 프린터, 문법 문서를 얻었습니다(7쪽).

7쪽의 작은 예제 pairG = rule "pair" $ "(" >* boolG >*< "," >* natG *< ")" 한 줄이 "(true,42)"를 (True,42)로 파싱하고, (False,7)을 "(false,7)"로 출력했습니다. 이 한 줄이 시리즈 전체가 설명한 생각을 담고 있습니다.

정리

  • 원문은 literate Haskell이 아니며, 동작하는 코드는 GitHub 저장소에 있습니다. 원문 코드에는 그대로 컴파일되지 않는 조각과 독특한 용어가 있고, 현재 distributors 패키지는 Parsor, Printor, Tokenized 등의 설계가 원문과 다릅니다.
  • 시리즈 전체의 계층은 Profunctor, Tokenized, Choice/Cochoice, Monoidal, Distributor, Alternator/Filtrator, Grammatical 순서로 쌓이며, 함수 화살표는 실패가 필요한 Alternator부터 빠집니다.
  • 자유 Grammatical 디스트리뷰터는 문법을 데이터로 담는 초기 인코딩이며, Identical이 그 씨앗입니다. 문법을 데이터로 만들면 왼쪽 인수분해 같은 변환이 가능해지고, 그 변환에는 분배 법칙에 해당하는 동형이 필요합니다.
  • JSON 같은 다른 토큰, TypeScript 타입 같은 다른 생성기, 망라적 문법과 정규 문법의 분리, ruleRec을 덮어쓴 Earley 파서는 모두 "하나의 기술, 여러 해석"이라는 생각을 넓히는 열린 질문입니다.
