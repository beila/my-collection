Megaparsec 파서 타입으로 읽는 <$>와 anySingle

이 문서에서 설명하는 내용

원문은 Haskell의 Megaparsec으로 MCAP 파일의 기본 직렬화 타입을 파싱하는 과정을 설명합니다. 첫 고정폭 정수 예제에서는 anySingle로 바이트를 하나씩 읽고, <$>로 그 바이트의 정수 타입을 바꾼 뒤, 두 바이트를 리틀엔디언 순서로 조립합니다.

두 하이라이트는 첫 parseUint16LE의 fromIntegral <$> anySingle 표현과 그 직후 이어지는 anySingle 설명 문장을 함께 가리킵니다. 따라서 개별 기호만 풀이하기 전에 다음 질문을 함께 해결할 필요가 있습니다.

  • Parser Word16에서 입력 타입과 결과 타입은 각각 어디에 있는지 설명합니다.
  • anySingle이 어떤 파서이며, 이 글에서는 왜 바이트 하나를 내놓는지 설명합니다.
  • <$>가 파서의 성공 결과 타입을 어떻게 바꾸는지 설명합니다.
  • 실제 입력 바이트는 언제 어디에서 파서에 전달되는지 설명합니다.

먼저 알아야 할 공통 개념

Parser Word16은 입력을 숨긴 타입 별칭입니다

원문은 파서 타입을 짧게 쓰기 위해 다음 별칭을 제시합니다.

import Text.Megaparsec
import Data.ByteStrint.Lazy (ByteString)
import Data.Void

type Parser a = ParserT Void ByteString IO a

이 원문 코드에는 타입 설명에 직접 영향을 주는 오탈자가 두 개 있습니다. Data.ByteStrint.Lazy는 Data.ByteString.Lazy여야 하며, Megaparsec의 파서 변환기 이름은 ParserT가 아니라 ParsecT입니다. 원문의 의도를 교정하면 다음과 같습니다.

import Data.ByteString.Lazy (ByteString)
import Data.Void (Void)
import Text.Megaparsec (ParsecT)

type Parser a = ParsecT Void ByteString IO a

공식 Megaparsec API에서 핵심 타입은 ParsecT e s m a입니다. 네 매개변수는 다음과 같이 읽습니다.

자리 이 글에서의 타입 의미
e Void 사용자 정의 오류 구성 요소의 타입입니다. 일반적인 파싱 오류가 없어진다는 뜻은 아닙니다.
s ByteString 파서가 소비하는 입력 스트림의 타입입니다.
m IO 파서 변환기의 바탕 모나드입니다. 입력 타입은 아닙니다.
a Word16 등 파서가 성공했을 때 내놓는 결과값의 타입입니다.

그러므로 원문의 짧은 타입 서명은 다음 두 줄이 같은 뜻입니다.

parseUint16LE :: Parser Word16
parseUint16LE :: ParsecT Void ByteString IO Word16

입력 스트림 타입은 ByteString 자리에 이미 들어 있습니다. 마지막 Word16은 입력이 아니라 성공 결과의 타입입니다. Parser라는 별칭이 앞의 세 매개변수를 감췄기 때문에 Parser Word16만 보면 입력이 없는 것처럼 보일 뿐입니다. 이 구조는 Megaparsec 9.7.0의 ParsecT API 문서에서 확인할 수 있습니다.

스트림과 토큰의 관계가 anySingle의 결과를 정합니다

anySingle의 일반 타입은 다음과 같습니다.

anySingle :: MonadParsec e s m => m (Token s)

이 함수는 스트림 s에서 토큰 하나를 소비하고 그 토큰을 성공 결과로 내놓는 파서입니다. 입력이 이미 끝났다면 실패합니다. 중요한 점은 anySingle이 언제나 Word8을 내놓는 것이 아니라, 결과 타입이 스트림의 토큰 타입인 Token s로 정해진다는 사실입니다. 이 일반 서명과 동작은 Megaparsec의 anySingle 문서에서 확인할 수 있습니다.

이 글에서는 s가 lazy ByteString입니다. ByteString의 원소는 8비트 바이트인 Word8이므로, 이 문맥에서 일반 타입을 구체화하면 다음과 같습니다.

anySingle :: Parser Word8

즉, anySingle 자체가 Word8 값이라는 뜻이 아닙니다. 바이트 하나를 소비한 뒤 성공하면 Word8 값을 내놓는 파서 동작이라는 뜻입니다. Lazy ByteString이 Word8 바이트의 시퀀스라는 점은 Data.ByteString.Lazy 공식 문서의 pack, singleton, head 같은 함수 타입에서도 확인할 수 있습니다.

<$>는 파서가 내놓을 값에 함수를 적용합니다

<$>는 fmap의 중위 연산자이며, 일반 타입은 다음과 같습니다.

(<$>) :: Functor f => (a -> b) -> f a -> f b

컨테이너나 계산 문맥 f 안의 값을 직접 꺼내지 않고, 그 값에 함수 a -> b를 적용해 결과 문맥을 f b로 바꿉니다. 이 정의는 Prelude의 Functor와 <$> 문서에서 확인할 수 있습니다.

원문의 표현에서는 f가 Parser이며, 타입 추론 결과를 구체적으로 적으면 다음과 같습니다.

anySingle                  :: Parser Word8
fromIntegral               :: Word8 -> Word16
fromIntegral <$> anySingle :: Parser Word16

fromIntegral의 일반 타입은 (Integral a, Num b) => a -> b입니다. 위의 Word8 -> Word16은 일반 정의가 아니라, parseUint16LE :: Parser Word16이라는 주변 문맥에 맞춰 이 위치에서 특수화된 타입입니다.

실행 순서는 다음과 같습니다. 먼저 anySingle이 입력에서 바이트 하나를 소비해 Word8을 내놓습니다. 그 성공 결과에 <$>가 fromIntegral을 적용하여 Word16으로 변환합니다. 실패 가능성과 파싱 상태는 그대로 이어지며, <$> 자체는 입력을 추가로 소비하지 않습니다.

따라서 다음 줄에서 오른쪽 전체의 타입은 Parser Word16이고, <-로 바인딩된 b1의 타입은 Word16입니다.

b1 <- fromIntegral <$> anySingle

b2도 같은 과정을 거칩니다. 전체 do 블록은 바이트 두 개를 차례로 소비하고 Word16 하나를 내놓는 파서가 됩니다.

실제 입력값은 파서를 실행할 때 전달합니다

타입 서명의 ByteString은 입력의 종류를 나타내지만, 실제 바이트값까지 포함하지는 않습니다. 실제 입력은 runParserT 같은 실행 함수에 전달합니다. 이 글의 타입에 맞춘 호출 형태는 다음과 같습니다.

runParserT parseUint16LE "<memory>" input
  :: IO (Either (ParseErrorBundle ByteString Void) Word16)

여기서 input :: ByteString이 실제 입력값입니다. "<memory>"는 오류 메시지에 사용할 소스 이름이며, 결과의 Either는 실패와 성공을 구분합니다. IO는 원문이 선택한 바탕 모나드입니다. runParserT의 일반 타입도 Megaparsec 공식 API 문서에서 확인할 수 있습니다.

이 때문에 parseUint16LE을 단순히 ByteString -> Word16 함수라고 부르면 중요한 정보가 사라집니다. parseUint16LE은 입력 스트림의 현재 위치, 실패 정보, 남은 입력을 관리하는 파서 값이며, 실행 함수가 실제 스트림을 공급하고 성공 또는 실패 결과를 돌려줍니다.

두 바이트가 리틀엔디언 정수로 조립됩니다

원문의 첫 정수 파서는 두 번 읽은 바이트를 다음 식으로 합칩니다.

(shift b2 8) + b1

MCAP의 uint16은 2바이트 부호 없는 리틀엔디언 정수입니다. 먼저 읽은 b1이 하위 8비트이고, 다음에 읽은 b2가 상위 8비트이므로 b2를 왼쪽으로 8비트 이동한 뒤 b1을 더합니다. 예를 들어 입력이 차례로 0x34, 0x12라면 결과는 0x1234, 즉 4660입니다. 이 직렬화 규칙은 MCAP 공식 명세의 Serialization 절에서 확인할 수 있습니다.

이 파서는 성공할 때 두 바이트만 소비합니다. 뒤에 바이트가 더 있어도 그것은 다음 파서가 읽을 입력으로 남습니다. 입력 전체가 정확히 두 바이트인지까지 검사하려면 더 바깥쪽에서 eof 검사를 결합해야 합니다.

하이라이트와 메모별 해설

<$>가 fromIntegral과 anySingle 사이에서 하는 일

하이라이트: <$>

원문 문맥:

parseUint16LE :: Parser Word16
parseUint16LE = do
  b1 <- fromIntegral <$> anySingle

이 위치의 <$>는 anySingle이 성공해서 내놓은 바이트에 fromIntegral을 적용합니다. 타입은 Parser Word8에서 Parser Word16으로 바뀌지만, 파서가 읽는 입력 스트림은 같은 ByteString이고 소비하는 바이트 수도 여전히 하나입니다.

같은 코드를 do 표기법으로 더 풀어 쓰면 다음과 같은 의미입니다. 아래 코드는 설명을 위해 만든 동등한 형태이며 원문의 추가 인용이 아닙니다.

rawByte <- anySingle
let b1 = fromIntegral rawByte

따라서 <$>는 “입력에 함수를 적용한다”기보다 “파서의 성공 결과에 함수를 적용한다”고 이해하는 편이 정확합니다. 입력 소비는 anySingle이 담당하고, 결과값 변환은 fromIntegral과 <$>가 담당합니다.

anySingle의 타입과 parseUint16LE에 숨은 입력 타입

하이라이트: anySingle

원문 문맥:

Each call to anySingle gives us a “token” of a bytestring, which is a Word8.

사용자 메모: What’s the type? How is the input indicated in the type of parseUint16LE?

anySingle의 일반 타입은 MonadParsec e s m => m (Token s)입니다. 이 글에서는 스트림 s가 lazy ByteString이고 그 토큰이 Word8이므로, 구체적인 타입은 anySingle :: Parser Word8입니다. 원문의 문장은 이 글의 ByteString 문맥에서는 맞지만, 모든 스트림에 대해 anySingle의 결과가 항상 Word8이라는 뜻은 아닙니다.

parseUint16LE :: Parser Word16에서 Word16은 성공 결과 타입입니다. 입력 스트림 타입은 Parser 별칭 안에 숨겨져 있습니다. 별칭을 펼친 타입은 다음과 같습니다.

parseUint16LE :: ParsecT Void ByteString IO Word16

여기서 ByteString이 입력 스트림 타입이고 Word16이 결과 타입입니다. 실제 ByteString 값은 타입 서명에 적는 것이 아니라, runParserT parseUint16LE "<memory>" input처럼 파서를 실행할 때 input 인수로 전달합니다.

짧게 연결하면 타입 흐름은 다음과 같습니다.

anySingle                  :: Parser Word8
fromIntegral <$> anySingle :: Parser Word16
parseUint16LE              :: Parser Word16

첫 줄은 바이트 하나를 읽는 동작이고, 둘째 줄은 읽은 바이트를 Word16으로 변환한 동작이며, 마지막 줄은 그런 동작을 두 번 조합해 16비트 값을 만드는 전체 파서입니다.

정리

  • Parser Word16의 Word16은 성공 결과 타입이며, 입력 타입 ByteString은 Parser 별칭 안에 들어 있습니다.
  • 이 글에서 anySingle의 구체적인 타입은 Parser Word8이며, 입력 바이트 하나를 소비합니다.
  • <$>는 anySingle의 성공 결과에 fromIntegral을 적용해 Parser Word8을 Parser Word16으로 바꾸며, 추가 입력은 소비하지 않습니다.
  • 실제 입력값은 runParserT로 파서를 실행할 때 전달합니다.
  • 원문의 Data.ByteStrint.Lazy와 ParserT는 각각 Data.ByteString.Lazy와 ParsecT로 읽어야 하는 오탈자입니다.
