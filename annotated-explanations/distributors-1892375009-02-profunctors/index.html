Distributors 해설 2/8: 프로펑터 (Profunctors)

해설 대상 원문: Eitan Chatav, “Distributors — Unifying Parsers, Printers & Grammars”

검토일: 2026-11-21

이 쪽은 여덟 쪽 시리즈의 두 번째 쪽이며, 원문의 "Profunctors" 절을 다룹니다. 1쪽에서는 파서(parser)가 공변(covariant)이고 프린터(printer)가 반변(contravariant)이어서 하나의 타입 매개변수로는 둘을 묶을 수 없다는 문제를 보았습니다. 이 절은 그 해결의 출발점인 프로펑터(profunctor)를 정의하고, 그 위에 이 글 전체에서 쓰이는 두 타입 Parsor와 Printor를 세웁니다. 이 쪽에서 "어느 쪽 매개변수를 누가 쓰는가"를 분명히 잡아 두면, 3쪽부터 나오는 거의 모든 "왜 이것이 동작하는가"라는 질문에 같은 답을 적용할 수 있습니다.

1쪽에서 가져올 것

  • 공변(covariant) 매개변수는 출력 자리에 있고, fmap :: (a -> b) -> f a -> f b처럼 함수와 같은 방향으로 바뀝니다. 파서의 결과 타입이 그렇습니다.
  • 반변(contravariant) 매개변수는 입력 자리에 있고, contramap :: (a' -> a) -> f a -> f a'처럼 함수와 반대 방향으로 바뀝니다. 프린터의 입력 타입이 그렇습니다.
  • 한 매개변수가 공변이면서 반변이면 그 매개변수는 실제로 쓰이지 않는 유령 타입 매개변수(phantom type parameter)가 됩니다.
  • Applicative는 "차례로 잇기"(pure, <*>)를, Alternative는 "실패와 선택"(empty, <|>)을 제공합니다. 1쪽에서 작은 파서 예제와 함께 처음부터 설명했습니다.

프로펑터의 정의

원문은 프로펑터를 한 문장으로 정의합니다.

A profunctor is a bifunctor which is contravariant in its first argument and covariant in its second argument.

먼저 이항 펑터(bifunctor)부터 보겠습니다. 이항 펑터는 타입 매개변수가 두 개이고 둘 다 공변인 구조입니다. base 라이브러리의 Data.Bifunctor에 있는 Bifunctor 클래스는 bimap :: (a -> b) -> (c -> d) -> p a c -> p b d를 제공합니다. Either와 (,)가 대표적인 예입니다. 예를 들어 bimap show not (1, True)는 ("1", False)입니다. 쌍의 두 원소가 모두 "들어 있는 값"이므로 두 자리 모두 출력 자리입니다.

프로펑터는 이항 펑터와 비슷하지만 첫 번째 매개변수만 방향이 뒤집힙니다. 직관적으로 p a b는 "a를 받아서 b를 내놓는 무언가"입니다. 받는 쪽 a는 반변이고, 내놓는 쪽 b는 공변입니다. 1쪽의 문제와 맞추어 보면, 프린터가 받는 값을 a 자리에, 파서가 내는 값을 b 자리에 두면 두 방향이 서로 다른 매개변수에 들어가므로 충돌이 생기지 않습니다.

코드 읽기: Profunctor 클래스

class Profunctor p where
  dimap :: (s -> a) -> (b -> t) -> p a b -> p s t

  lmap :: (s -> a) -> p a b -> p s b
  lmap f = dimap f id

  rmap :: (b -> t) -> p a b -> p a t
  rmap g = dimap id g

이 클래스는 Edward Kmett의 profunctors 패키지에 있는 Data.Profunctor의 클래스와 모양이 같습니다.

타입 변수 이름 읽는 법

이 글과 lens 계열 라이브러리는 타입 변수 이름에 일정한 약속을 씁니다. s와 t는 "바깥" 타입이고, a와 b는 "안쪽" 타입입니다. s와 a는 들어오는 쪽, b와 t는 나가는 쪽입니다. 값 이름도 타입을 따라 짓습니다. sa는 s -> a 함수, bt는 b -> t 함수, ab는 a -> b 함수입니다. 이 약속을 알면 긴 시그니처를 읽는 일이 훨씬 쉬워집니다.

dimap

dimap :: (s -> a) -> (b -> t) -> p a b -> p s t는 인자를 세 개 받습니다.

  1. s -> a: 새 입력 s를 원래 입력 a로 바꾸는 전처리 함수입니다.
  2. b -> t: 원래 출력 b를 새 출력 t로 바꾸는 후처리 함수입니다.
  3. p a b: 원래의 프로펑터 값입니다.

결과는 s를 받아 t를 내는 p s t입니다. 한쪽씩 보면 방향의 차이가 분명해집니다. p a b를 p s b로 바꾸려면 s -> a가 필요합니다. 타입은 a에서 s로 바뀌는데 함수는 s에서 a로 가므로 방향이 반대이고, 이것이 반변입니다. p a b를 p a t로 바꾸려면 b -> t가 필요합니다. 타입도 b에서 t로, 함수도 b에서 t로 가므로 방향이 같고, 이것이 공변입니다.

lmap과 rmap

lmap은 입력 쪽만, rmap은 출력 쪽만 바꿉니다. 클래스 선언 안의 lmap f = dimap f id와 rmap g = dimap id g는 기본 구현(default method)입니다. 인스턴스가 dimap만 정의하면 lmap과 rmap은 이 기본 구현을 그대로 씁니다. 바꾸지 않는 쪽에는 항등 함수 id를 넣었습니다.

profunctors 패키지 문서는 인스턴스가 다음 법칙을 지켜야 한다고 적습니다. dimap id id는 아무것도 바꾸지 않아야 하고(dimap id id ≡ id), 두 번 나누어 dimap한 것과 함수를 합성해 한 번 dimap한 것이 같아야 합니다(dimap (f . g) (h . i) ≡ dimap g h . dimap f i). 두 번째 법칙에서 입력 쪽 함수의 순서가 뒤집히는 것도 반변성 때문입니다.

함수 화살표 (->): 대표적인 프로펑터

왜 함수 화살표가 "대표적인 예"일까요

하이라이트:

The prototypical example of a Profunctor is (->).

instance Profunctor (->) where
  dimap sa bt ab = bt . ab . sa

원문 문맥:

The Profunctor interface was introduced to Haskell by Ed Kmett who noticed their utility in representing optics, more on which later. The prototypical example of a Profunctor is (->).

instance Profunctor (->) where
  dimap sa bt ab = bt . ab . sa

Let's see how we can unify parsers & printers with a Profunctor interface.

이 하이라이트는 "프로펑터"라는 추상적인 정의를 가장 익숙한 대상에 연결하는 문장입니다. 차례로 풀어 보겠습니다.

(->)는 타입 생성자입니다. a -> b라는 함수 타입은 사실 타입 생성자 (->)를 두 타입에 적용한 (->) a b를 중위 표기로 쓴 것입니다. 그래서 (->) 자체를 클래스의 인스턴스로 만들 수 있습니다. Profunctor (->)에서 p가 (->)이므로 p a b는 a -> b, p s t는 s -> t가 됩니다.

dimap의 타입이 무엇이 되는지 봅시다. p에 (->)를 넣으면 다음과 같습니다.

dimap :: (s -> a) -> (b -> t) -> (a -> b) -> (s -> t)

즉 "s -> a, b -> t, a -> b가 주어졌을 때 s -> t를 만들라"는 요구입니다. 방법은 하나뿐입니다. s를 받아 sa로 a를 만들고, ab로 b를 만들고, bt로 t를 만듭니다.

s --sa--> a --ab--> b --bt--> t

bt . ab . sa는 오른쪽부터 읽습니다. 합성 연산자 .는 (f . g) x = f (g x)이므로 bt . ab . sa는 \x -> bt (ab (sa x))입니다. 가장 오른쪽의 sa가 먼저 실행되고, 가장 왼쪽의 bt가 마지막에 실행됩니다. 위의 화살표 그림을 오른쪽에서 왼쪽으로 적은 것입니다.

값이 흐르는 모습. 다음은 원문 코드가 아니라 작은 예시입니다. 이 쪽의 예시는 모두 원문의 정의를 최소한으로 다시 만든 코드로 GHC 9.10.3에서 실행한 결과입니다.

>>> dimap length show (*2) ("abc" :: String)
"6"
>>> lmap length (*2) ("abcd" :: String)
8
>>> rmap show (*(2::Int)) 21
"42"

첫 줄에서 원래 함수는 (*2) :: Int -> Int입니다. dimap length show는 그 앞에 length :: String -> Int를, 뒤에 show :: Int -> String을 붙입니다. 그래서 "abc"는 길이 3이 되고, 2를 곱해 6이 되고, 문자열 "6"이 됩니다. 둘째 줄은 입력 쪽만, 셋째 줄은 출력 쪽만 바꿨습니다.

왜 "대표적"일까요. 프로펑터는 "입력을 받아 출력을 내는 것"을 추상화한 개념이고, 함수는 그 가장 순수한 형태입니다. 함수는 입력을 받아 출력을 낼 뿐 다른 구조가 없습니다. 이후에 나오는 프로펑터들, 즉 파서, 프린터, 4쪽의 Exchange와 Market 같은 것은 모두 "함수처럼 생겼지만 무언가가 더 붙은 것"으로 볼 수 있습니다. 실제로 이 글에서 (->)는 계속 기준점 역할을 합니다. 4쪽에서는 p를 (->)로 고정하면 lens 라이브러리의 익숙한 렌즈(lens) 타입이 나온다는 점을 보고, 6쪽에서는 (->)가 Distributor의 대표 예이면서 Alternator는 될 수 없다는 점을 봅니다.

Ed Kmett와 옵틱(optic). 같은 문단의 앞 문장은 Ed Kmett가 프로펑터를 하스켈에 도입했고, 옵틱을 표현하는 데 유용하다는 점을 알아차렸다고 말합니다. profunctors 패키지의 저자가 Kmett인 것은 Hackage에서 확인할 수 있습니다. 다만 "그 전에는 아무도 하스켈에서 프로펑터를 쓰지 않았다"는 뜻까지는 확인되지 않았으므로, 저자의 역사 서술로 읽으면 됩니다. 옵틱은 4쪽의 주제입니다.

파서와 프린터를 프로펑터로: Parsor와 Printor

원문은 이어서 1쪽의 Parser와 Printer를 프로펑터 모양으로 다시 정의합니다.

newtype Parsor s f a b = Parsor {runParsor :: s -> f (b,s)}

instance Functor f => Profunctor (Parsor s f) where
  dimap _ g (Parsor p) = Parsor (fmap (\(c,str) -> (g c, str)) . p)

newtype Printor s f a b = Printor {runPrintor :: a -> f (s -> s)}

instance Profunctor (Printor s f) where
  dimap f _ (Printor p) = Printor (p . f)

레코드 문법의 newtype

newtype Parsor s f a b = Parsor {runParsor :: s -> f (b,s)}는 필드 이름이 붙은 newtype입니다. 생성자 Parsor가 함수 하나를 감싸고, 필드 이름 runParsor는 그 함수를 꺼내는 함수가 됩니다. 즉 runParsor :: Parsor s f a b -> s -> f (b, s)입니다. 원문 예제의 runParsor anyToken "xyz"는 "anyToken이라는 파서에서 함수를 꺼내 입력 "xyz"에 적용하라"는 뜻입니다. runPrintor도 같습니다.

네 개의 타입 매개변수

Parsor s f a b에는 매개변수가 네 개 있습니다.

매개변수 뜻
s 스트림(stream) 타입입니다. 파서가 읽고 프린터가 쓰는 토큰(token) 열이며, 보통 String입니다.
f 결과를 담는 컨테이너(container)입니다. 보통 [] 또는 Maybe입니다.
a 프로펑터의 첫 번째(반변) 자리입니다.
b 프로펑터의 두 번째(공변) 자리입니다.

인스턴스 머리 Profunctor (Parsor s f)를 보면, 프로펑터는 Parsor 전체가 아니라 s와 f를 고정한 Parsor s f입니다. 남은 두 매개변수 a와 b가 프로펑터의 두 자리입니다.

Parsor 읽기

  • runParsor :: s -> f (b,s): 스트림 s를 받아, (결과 b, 남은 스트림 s) 쌍들을 컨테이너 f에 담아 돌려줍니다. f가 []이면 1쪽의 성공 목록 파서와 같은 모양입니다.
  • 타입 어디에도 a가 나오지 않습니다. 즉 Parsor에게 a는 유령 타입 매개변수입니다.
  • instance Functor f => Profunctor (Parsor s f): 컨테이너 f 안의 결과를 바꾸려면 fmap이 필요하므로 Functor f를 요구합니다.
  • dimap _ g (Parsor p) = ...: 첫 번째 함수 자리에 밑줄 _이 있습니다. 입력 쪽 함수를 무시한다는 뜻입니다. a를 쓰지 않으니 바꿀 것도 없습니다.
  • fmap (\(c,str) -> (g c, str)) . p: 원래 파서 p를 실행한 뒤, 각 결과 쌍에서 결과 c에만 g를 적용하고 남은 스트림 str은 그대로 둡니다. 여기서 c는 문자가 아니라 "결과 값"을 뜻하는 이름입니다.

Printor 읽기

  • runPrintor :: a -> f (s -> s): 출력할 값 a를 받아, "남은 스트림을 받아 그 앞에 출력을 붙인 스트림을 돌려주는 함수"를 컨테이너 f에 담아 돌려줍니다. 이 s -> s 모양은 바로 아래 하이라이트에서 자세히 봅니다.
  • 타입 어디에도 b가 나오지 않습니다. 즉 Printor에게 b는 유령 타입 매개변수입니다.
  • dimap f _ (Printor p) = Printor (p . f): 두 번째 함수 자리가 밑줄입니다. 출력 쪽 함수를 무시합니다. 입력 쪽 함수 f는 원래 프린터 앞에 붙입니다. 1쪽 contramap과 같은 모양입니다.
  • 이름 주의: 여기서 f는 함수 값의 이름이고, 타입 매개변수 f(컨테이너)와는 다른 것입니다. 원문 코드에서 같은 글자가 두 가지 뜻으로 쓰이니 헷갈리지 않도록 조심하십시오.

이 글 전체의 핵심: 누가 어느 쪽을 쓰는가

타입 a(왼쪽, 반변) b(오른쪽, 공변) dimap f g에서 쓰는 함수
Parsor s f a b 쓰지 않음 파싱 결과 g만 씀
Printor s f a b 출력할 값 쓰지 않음 f만 씀

이 표가 이 글 전체의 열쇠입니다. 프린터-파서(printer-parser) 하나는 p a b 타입을 가지며, 프린터로 쓰일 때는 a를 읽고, 파서로 쓰일 때는 b를 만듭니다. 그래서 함수 쌍을 받는 조합자(dimap, 그리고 4쪽의 mapIso, >?, ?<, >?<)는 한 함수를 파서에게, 다른 함수를 프린터에게 줍니다. 예를 들어 6쪽의 iso show read >?< digits는 파서로 쓰일 때 read를, 프린터로 쓰일 때 show를 씁니다.

작은 예시: 값이 흐르는 모습

다음은 원문 코드가 아니라 이해를 돕기 위한 예시입니다. 3쪽의 anyToken이 나오기 전이므로 글자 하나를 다루는 파서와 프린터를 손으로 만들었습니다.

charPs :: Parsor String [] () Char
charPs = Parsor (\s -> case s of (c:cs) -> [(c, cs)]; [] -> [])

charPr :: Printor String [] Char ()
charPr = Printor (\c -> [(c:)])

charPs는 첫 글자를 읽습니다. 왼쪽 매개변수는 쓰이지 않으므로 아무 타입이나 넣을 수 있어 ()를 넣었습니다. charPr는 글자 c를 받아 "남은 스트림 앞에 c를 붙이는 함수" (c:)를 목록 하나에 담아 돌려줍니다. 오른쪽 매개변수는 쓰이지 않으므로 ()를 넣었습니다.

>>> runParsor (rmap toUpper charPs) "hi"
[('H',"i")]
>>> [pr " apples" | pr <- runPrintor (lmap intToDigit charPr) 7]
["7 apples"]

파서에는 rmap으로 결과 쪽 함수 toUpper를 붙였고, 프린터에는 lmap으로 입력 쪽 함수 intToDigit을 붙였습니다. 프린터 예제의 리스트 컴프리헨션은 이렇게 읽습니다. runPrintor (lmap intToDigit charPr) 7은 함수들의 목록(여기서는 [('7':)])을 돌려주고, pr <- ...는 그 목록의 각 함수를 pr로 꺼내며, pr " apples"는 그 함수를 남은 스트림 " apples"에 적용합니다.

한쪽 함수가 정말 무시되는지도 확인할 수 있습니다. 무시되는 자리에 undefined를 넣어도 아무 문제가 없습니다. undefined는 평가되면 프로그램을 멈추는 값이므로, 이 결과는 그 자리가 한 번도 평가되지 않았다는 증거입니다.

>>> runParsor (dimap undefined toUpper charPs) "hi"
[('H',"i")]
>>> [pr "!" | pr <- runPrintor (dimap intToDigit undefined charPr) 7]
["7!"]

네 가지 일반화

원문은 Parser/Printer에서 Parsor/Printor로 바꾸면서 무엇이 달라졌는지 한 문단으로 정리합니다. 하나씩 보겠습니다.

이름의 모음. "Besides changing a vowel in the names"라는 말대로 Parser의 e와 Printer의 e가 o로 바뀌었습니다. 1쪽의 타입과 구별하기 위한 이름 변경입니다.

유령 매개변수의 추가. "both types get a phantom type parameter, the a in Parsor and the b in Printor." 두 타입 모두 프로펑터의 두 자리를 채우기 위해 쓰이지 않는 매개변수를 하나씩 얻었습니다. 위의 표에서 "쓰지 않음" 칸이 그것입니다. 1쪽에서 유령 매개변수는 파서에 "너무 강한" 제약이라고 했는데, 여기서는 사정이 다릅니다. 파서의 결과 b는 여전히 실제로 쓰이고, 쓰이지 않는 것은 반대쪽 자리 a뿐입니다.

스트림 타입의 일반화. "String has been polymorphized to s." 입력과 출력이 꼭 String일 필요가 없습니다. Text, ByteString, 또는 미리 잘라 둔 어휘 토큰(lexical token)의 목록일 수도 있습니다. 3쪽에서 lens의 Cons 클래스를 써서 이 일반화를 실제로 다룹니다.

결과 컨테이너의 일반화. "the "container" for the result of a parse or print has been polymorphized to f." 파서의 결과와 프린터의 결과를 담는 그릇이 f로 추상화되었습니다. 보통은 [] 또는 Maybe이며, 이 선택의 의미는 아래에서 망라적(exhaustive) 출력과 부분적(partial) 파싱을 다룰 때 설명합니다.

그리고 네 번째 일반화가 프린터의 결과 타입입니다. 이것은 하이라이트된 문장이므로 따로 보겠습니다.

프린터의 결과가 왜 s -> s일까요

하이라이트: the printer type's "result" is upgraded to an endofunction s -> s.

원문 문맥:

Next, String has been polymorphized to s. After all, we might want to parse & print Text or ByteStrings or any streams of some lexical token type. Next, the printer type's "result" is upgraded to an endofunction s -> s. This makes it a more fully dualized definition to the parser type, and is a common trick used in printer types such as ShowS.

자기 함수란. 자기 함수(endofunction)는 정의역과 공역이 같은 함수, 즉 s -> s 꼴의 함수입니다. 1쪽의 Printer a는 결과로 완성된 문자열(Maybe String)을 돌려주었습니다. Printor는 대신 "남은 스트림을 받으면 그 앞에 내 출력을 붙여 돌려주는 함수"를 돌려줍니다. 예를 들어 글자 '7'을 출력하는 결과는 문자열 "7"이 아니라 함수 ('7':)입니다.

이유 1: 파서와의 쌍대성(duality). 두 newtype이 감싼 함수 타입을 나란히 놓아 보겠습니다.

Parsor  s f a b   감싼 함수:  s -> f (b, s)
Printor s f a b   감싼 함수:  a -> f (s -> s)

파서는 "스트림을 받아 값과 나머지 스트림을 내놓습니다". 프린터는 "값을 받아, 나머지 스트림에서 전체 스트림을 만드는 함수를 내놓습니다". 두 타입 모두에서 "나머지 스트림" s가 입력과 출력 양쪽에 나타나고, 값(b 또는 a)의 방향만 반대입니다. 원문이 말하는 "more fully dualized"는 이런 대칭을 가리킵니다. 쌍대(dual)는 같은 구조에서 방향만 뒤집은 것을 말합니다.

이유 2: ShowS 기법. 하스켈 Prelude에는 type ShowS = String -> String이 있고, shows와 showString이 이 타입의 값을 만듭니다.

>>> shows (42::Int) " apples"
"42 apples"
>>> (showString "ab" . showString "cd") "!"
"abcd!"

shows 42는 문자열이 아니라 "뒤에 올 문자열 앞에 "42"를 붙이는 함수"입니다. 두 출력을 이어 붙이고 싶으면 함수 합성 .을 쓰면 됩니다. 이 방식은 차이 목록(difference list)이라고도 불리며, 왼쪽으로 쌓인 (xs ++ ys) ++ zs 같은 연결이 앞부분을 거듭 다시 훑는 비용을 피합니다. 출력이 길고 여러 조각으로 나뉠수록 이 차이가 커집니다.

이유 3: 이어 붙이기에 필요한 것이 줄어듭니다. 결과가 완성된 스트림 s라면 두 출력을 잇기 위해 s에 ++ 같은 연결 연산이 있어야 합니다. 결과가 s -> s이면 연결은 언제나 함수 합성이므로 s에 대해 아무것도 요구하지 않습니다. 남는 요구는 "토큰 하나를 스트림 앞에 붙이는 방법"뿐인데, 이것은 3쪽에서 lens의 cons가 맡습니다. 5쪽에서 보게 될 Printor의 Applicative 인스턴스는 바로 이 합성으로 두 프린터를 차례로 잇습니다.

값이 흐르는 모습. 위의 charPr 예제가 이 모양을 그대로 보여 줍니다. runPrintor charPr 'x'는 [('x':)]이고, 여기에 남은 스트림 "yz"를 주면 "xyz"가 됩니다. 두 출력 함수 ('a':)와 ('b':)를 합성한 ('a':) . ('b':)에 "!"를 주면 "ab!"가 됩니다. 합성 순서가 곧 출력 순서입니다.

결과 컨테이너 f의 역할

Parsor는 f (b, s)를, Printor는 f (s -> s)를 돌려줍니다. f가 []이면 가능한 결과를 모두 모으고, f가 Maybe이면 결과가 하나이거나 없습니다. 이 글의 예제는 대부분 []를 씁니다. 그래서 예제마다 [pr "yz" | pr <- runPrintor ...]처럼 목록 안의 함수에 남은 스트림을 하나씩 적용하는 코드가 나옵니다.

망라적 출력과 부분적 파싱

원문은 f를 일반화한 이유를 "미묘한 점"이라며 따로 설명합니다.

Printing is usually conceived as an exhaustive affair; one defines a single function X -> String by pattern matching on each case of an X. Parsing however is usually a partial affair; one defines a bunch of partial parsers for each case of the X and combines them into one with the Alternative combinator (<|>).

망라적(exhaustive)이라는 말은 "모든 경우를 빠짐없이 처리한다"는 뜻이고, 부분적(partial)이라는 말은 "어떤 경우에는 실패할 수 있다"는 뜻입니다.

  • 출력은 보통 망라적입니다. 자료형 X의 값을 받아 생성자마다 패턴 매칭하는 함수 X -> String 하나를 쓰면, 모든 값이 출력됩니다.
  • 파싱은 보통 부분적입니다. X의 생성자마다 그 경우만 인식하는 작은 파서를 쓰고, 그것들을 1쪽에서 본 <|>로 합칩니다. 작은 파서 하나하나는 자기 경우가 아니면 실패합니다.

원문은 이어서 f를 일반화하면 두 상황을 모두 다룰 수 있다고 말합니다. 망라성이 필요하면 Applicative f만 요구하고, 부분성을 허용하려면 Alternative f를 요구합니다. 이유는 1쪽에서 본 두 인터페이스의 차이에 있습니다. Applicative에는 성공(pure)만 있고 실패를 만드는 연산이 없습니다. Alternative에는 실패(empty)가 있습니다. 그래서 Applicative f만 아는 프린터는 실패할 방법이 없으므로 반드시 망라적이고, Alternative f를 아는 프린터는 일부 값에서 empty로 실패할 수 있습니다.

다음은 원문 코드가 아니라 이 차이를 보여 주는 작은 예시입니다.

-- Print every Bool. Applicative f is enough.
boolPr :: Applicative f => Printor String f Bool ()
boolPr = Printor $ \b -> pure (showString (if b then "true" else "false"))

-- Print only True. Failure needs Alternative f.
truePr :: Alternative f => Printor String f Bool ()
truePr = Printor $ \b -> if b then pure (showString "true") else empty
>>> fmap ($ "!") (runPrintor boolPr False :: Maybe ShowS)
Just "false!"
>>> fmap ($ "!") (runPrintor truePr False :: Maybe ShowS)
Nothing
>>> fmap ($ "!") (runPrintor truePr True :: Maybe ShowS)
Just "true!"

boolPr는 Applicative만 요구하므로 Alternative가 아닌 Identity 같은 컨테이너에서도 쓸 수 있습니다. truePr는 empty를 쓰므로 Alternative를 요구하고, False에서 실패합니다. 이 구분은 6쪽에서 망라적인 Distributor와 부분적인 Alternator라는 두 클래스로 다시 나타납니다.

이 쪽이 글의 목표에 기여하는 바

이 절로 "한 정의가 파서이자 프린터"가 되기 위한 타입의 틀이 갖추어졌습니다. 프린터-파서는 p a b라는 하나의 타입을 가지고, 프린터로 해석하면 a를 읽어 스트림을 쓰고, 파서로 해석하면 스트림을 읽어 b를 만듭니다. 앞으로 글이 정의하는 조합자는 모두 "어떤 p에서도 동작하는" 다형적인 함수이고, p를 Parsor로 고르면 파서가, Printor로 고르면 프린터가 됩니다. 남은 과제는 이 틀 안에서 실제로 무언가를 읽고 쓰는 기본 부품을 만드는 것이며, 3쪽이 그 일을 합니다.

정리

  • 프로펑터 p a b는 "a를 받아 b를 내는 것"을 추상화한 구조입니다. 첫 자리는 반변, 둘째 자리는 공변이며, dimap은 입력 쪽 전처리와 출력 쪽 후처리를 함께 붙입니다.
  • 함수 화살표 (->)는 가장 순수한 프로펑터입니다. dimap sa bt ab = bt . ab . sa는 sa, ab, bt를 차례로 실행하는 합성이며, 오른쪽부터 읽습니다.
  • Parsor s f a b는 a를 쓰지 않고 b를 만들며, Printor s f a b는 a를 읽고 b를 쓰지 않습니다. 그래서 dimap의 두 함수 중 파서는 출력 쪽 함수만, 프린터는 입력 쪽 함수만 씁니다.
  • 프린터의 결과는 자기 함수 s -> s입니다. 파서 타입과 대칭을 이루고, ShowS처럼 합성만으로 출력을 이어 붙일 수 있게 해 줍니다.
  • 결과 컨테이너 f에 Applicative만 요구하면 프린터가 망라적이 되고, Alternative를 요구하면 부분적인 프린터도 허용됩니다.

Profunctors

A profunctor is a bifunctor which is contravariant in its first argument and covariant in its second argument.

class Profunctor p where
  dimap :: (s -> a) -> (b -> t) -> p a b -> p s t

  lmap :: (s -> a) -> p a b -> p s b
  lmap f = dimap f id

  rmap :: (b -> t) -> p a b -> p a t
  rmap g = dimap id g

The Profunctor interface was introduced to Haskell by Ed Kmett who noticed their utility in representing optics, more on which later. The prototypical example of a Profunctor is (->).

instance Profunctor (->) where
  dimap sa bt ab = bt . ab . sa

Let's see how we can unify parsers & printers with a Profunctor interface.

newtype Parsor s f a b = Parsor {runParsor :: s -> f (b,s)}

instance Functor f => Profunctor (Parsor s f) where
  dimap _ g (Parsor p) = Parsor (fmap (\(c,str) -> (g c, str)) . p)

newtype Printor s f a b = Printor {runPrintor :: a -> f (s -> s)}

instance Profunctor (Printor s f) where
  dimap f _ (Printor p) = Printor (p . f)

Besides changing a vowel in the names, we added a few generalizations to the parser & printer types. First, both types get a phantom type parameter, the a in Parsor and the b in Printor. Next, String has been polymorphized to s. After all, we might want to parse & print Text or ByteStrings or any streams of some lexical token type. Next, the printer type's "result" is upgraded to an endofunction s -> s. This makes it a more fully dualized definition to the parser type, and is a common trick used in printer types such as ShowS. Finally, the "container" for the result of a parse or print has been polymorphized to f. Usually this will be [] or Maybe but we should take a moment to address a subtle point here.

Printing is usually conceived as an exhaustive affair; one defines a single function X -> String by pattern matching on each case of an X. Parsing however is usually a partial affair; one defines a bunch of partial parsers for each case of the X and combines them into one with the Alternative combinator (<|>). By polymorphizing f in the definitions of the Printor, we can address either situation by restricting to only Applicative f when we want exhaustivity and allowing Alternative f when we want partiality.
