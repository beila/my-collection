해설 대상 원문: Eitan Chatav, “Distributors — Unifying Parsers, Printers & Grammars”

검토일: 2026-11-21

이 쪽은 여덟 쪽 시리즈의 네 번째 쪽이며, 원문에서 가장 긴 "Optics & Patterns" 절을 다룹니다. 3쪽의 anyToken은 스트림(stream) 맨 앞의 토큰(token)을 아무것이나 하나 받아들였습니다. 이 절은 그 결과를 원하는 모양으로 바꾸고, 원하는 값만 걸러 내는 장치를 옵틱(optic)으로 만듭니다. 동형(isomorphism), 프리즘(prism), 코프리즘(coprism), 부분 동형(partial isomorphism)을 차례로 다루고, 끝에서 "조건을 만족하는 토큰 하나"를 파싱하고 출력하는 satisfy를 얻습니다. 이 쪽에는 동형 옵틱의 "표현"에 관한 하이라이트가 네 개 있고, 그중 세 개에는 "어떻게 쓰는지 보여 달라"는 메모가 붙어 있으므로, 그 부분은 값이 실제로 흐르는 예제로 자세히 답합니다.

이 쪽의 지도

이 쪽은 길고 정의가 많으므로, 먼저 큰 흐름을 적어 둡니다. 네 가지 옵틱이 차례로 나오며, 뒤로 갈수록 "실패할 수 있는 정도"가 커집니다.

  1. 동형(Iso): 정보 손실 없이 양방향으로 바꾸는 함수 쌍입니다. 구체 표현(concrete representation) Exchange와 케밋 표현(Kmett representation) Iso, 그리고 둘 사이의 변환을 봅니다. 독자의 하이라이트 네 개가 모두 이 부분에 있습니다. mapIso로 동형을 프린터-파서에 적용합니다.
  2. 프리즘(Prism): 합 타입(sum type)의 한 경우에 맞추는 패턴(pattern)입니다. Choice와 (>?)로 프린터-파서에 적용하며, 맞지 않는 값은 출력하지 못합니다.
  3. 코프리즘: 프리즘을 거꾸로 써서 파서의 결과를 거릅니다. Cochoice와 (?<)를 쓰며, 그 결과로 정해진 글자 하나를 다루는 token을 얻습니다.
  4. 부분 동형(PartialIso): 두 방향 모두 실패할 수 있는 함수 쌍입니다. dimapMaybe, Filterable, (>?<)를 쓰며, 그 결과로 조건을 만족하는 글자 하나를 다루는 satisfy를 얻습니다.

3쪽까지에서 가져올 것

  • 프린터-파서(printer-parser)는 프로펑터(profunctor) 타입 p a b를 가지며, Parsor는 오른쪽 b만, Printor는 왼쪽 a만 씁니다. 그래서 dimap f g를 적용하면 파서는 g만, 프린터는 f만 씁니다(2쪽).
  • lens 라이브러리의 렌즈(lens)는 한 부분을 가리키고(view, over, set), 프리즘(prism)은 합 타입의 한 경우를 가리킵니다(preview, review). 옵틱 타입의 네 매개변수 s t a b에서 s와 t는 바깥 타입, a와 b는 안쪽 타입입니다(3쪽).
  • anyToken은 스트림 맨 앞의 토큰 하나를 파싱하거나 출력하는 기본 부품입니다(3쪽).

옵틱이란 무엇인가

원문은 옵틱의 정확한 정의는 어렵다고 먼저 밝힌 뒤, 하스켈에서의 흐름을 한 문장으로 요약합니다. "의미 편집 조합자(semantic editor combinators)" 연구에서 레코드 필드 접근자나 자료 생성자 패턴 같은 조합자가 서로 합성된다는 점을 알아차렸고, 그것이 옵틱의 발견으로 이어졌다는 것입니다. 실제 역사는 몇 단계로 나뉩니다. Conal Elliott의 2008년 글 Semantic editor combinators가 "구조 안쪽을 고치는 함수"를 합성하는 방식을 보였고, Twan van Laarhoven이 2009년에 함수자를 이용한 참조 표현을 제안했으며, 그 표현을 바탕으로 Edward Kmett의 lens 라이브러리가 나왔고, 이후 Pickering, Gibbons, Wu가 프로펑터 옵틱을 정리했습니다. 원문의 한 문장은 이 과정을 압축한 요약으로 읽으면 됩니다.

옵틱의 종류는 많지만 이 쪽에서 필요한 것은 다음과 같습니다.

옵틱 하는 일 예
렌즈(lens) 정확히 한 부분에 초점을 맞춥니다. 쌍의 첫 원소 _1
프리즘(prism) 합 타입의 한 경우에 맞춥니다. 맞지 않을 수 있습니다. Maybe의 Just 경우 _Just
동형(isomorphism, iso) 정보 손실 없이 양방향으로 바꿉니다. 섭씨와 화씨, 목록과 뒤집은 목록
트래버설(traversal) 0개 이상의 부분에 초점을 맞춥니다. 목록의 모든 원소

원문은 이 가운데 "패턴(pattern)"을 나타내는 옵틱에 관심을 둡니다. 여기서 패턴은 자료 생성자의 패턴 매칭을 값으로 만든 것, 즉 "맞추는 쪽"과 "만드는 쪽"을 한 쌍으로 묶은 것입니다. 3쪽에서 보았듯이 이 쌍은 파서(맞추어 꺼내기)와 프린터(값으로 만들기)의 관계와 같은 모양입니다. 그리고 원문은 "우리에게 가장 중요한 것은 프로펑터와 옵틱의 관계"라고 말합니다.

필요한 문법: forall과 랭크-N 타입

이 절의 타입 정의에는 모두 forall이 들어 있습니다. 처음부터 설명하겠습니다.

숨은 forall. 하스켈에서 id :: a -> a라고 쓰면 사실 id :: forall a. a -> a라는 뜻입니다. "모든 타입 a에 대해 a -> a"이며, a를 고르는 쪽은 id를 쓰는 쪽입니다. id 3이라고 쓰면 쓰는 쪽이 a를 숫자 타입으로 고른 것입니다.

타입 동의어 안의 forall. 원문의 type Iso s t a b = forall p f. (Profunctor p, Functor f) => p a (f b) -> p s (f t)는 Iso s t a b 타입의 값이 "어떤 프로펑터 p와 어떤 펑터 f를 골라도 동작하는 함수"라는 뜻입니다. 여기서도 p와 f를 고르는 쪽은 그 값을 쓰는 쪽입니다. 같은 동형 값 하나를 쓰는 쪽이 p를 함수로 고르면 값 읽기가 되고, p를 파서로 고르면 파서 변환이 됩니다. 이것이 이 절 전체의 비밀입니다.

랭크-N 타입. 그런 다형적인 값을 함수의 인자로 받으면, 인자 자체가 다형적이어야 합니다. 예를 들어 원문의 mapIso :: Profunctor p => Iso s t a b -> p a b -> p s t에서 첫 인자는 "모든 p와 f에 대해 동작하는" 함수입니다. 이처럼 forall이 화살표 왼쪽 안쪽에 들어간 타입을 랭크-N 타입(rank-N type)이라고 부르고, RankNTypes 확장이 이를 허용합니다. 이 확장은 GHC2021에 들어 있습니다.

비유. 다형적인 동형 값은 "어느 부엌에서나 따라 할 수 있는 조리법"과 같습니다. 조리법 자체는 dimap과 fmap만 쓰라고 적혀 있고, 어떤 부엌(p와 f)을 고르느냐에 따라 결과물이 달라집니다. 특별한 부엌을 골라 조리법이 무엇을 하는지 관찰하는 기법을 이 쪽에서는 탐침(probe)이라고 부르겠습니다. 아래의 Exchange가 바로 그런 부엌입니다.

동형 옵틱의 두 표현

원문은 동형 옵틱부터 시작합니다. 동형 옵틱은 "앞으로" 가는 함수와 "뒤로" 가는 함수의 쌍이며, newtype 생성자 패턴과 비슷하다고 설명합니다. 예를 들어 newtype Age = Age Int가 있으면 Age :: Int -> Age와 \(Age n) -> n :: Age -> Int가 서로의 역이므로 Int와 Age 사이의 동형이 됩니다.

data Exchange a b s t = Exchange (s -> a) (b -> t)

type Iso s t a b = forall p f.
  (Profunctor p, Functor f) => p a (f b) -> p s (f t)

기본 읽기

Exchange. data Exchange a b s t = Exchange (s -> a) (b -> t)는 함수 두 개를 담는 자료형입니다. s -> a는 바깥에서 안쪽으로 가는 앞방향 함수이고, b -> t는 안쪽에서 바깥으로 돌아오는 뒷방향 함수입니다. 타입 매개변수의 순서가 Iso s t a b와 달리 a b s t인 이유는, Exchange a b가 남은 두 매개변수 s t에 대해 프로펑터가 되도록 하기 위해서입니다. 프로펑터 인스턴스는 마지막 두 매개변수에 대해 정의되기 때문입니다.

Iso. Iso s t a b는 "p a (f b)를 p s (f t)로 바꾸는 함수, 단 p는 아무 프로펑터, f는 아무 펑터"입니다. 이 함수가 사용할 수 있는 연산은 Profunctor의 dimap과 Functor의 fmap뿐입니다. 안쪽 타입 a와 b에서 바깥 타입 s와 t로 넘어가려면 입력 쪽에 s -> a를, 출력 쪽(f 안쪽)에 b -> t를 붙이는 수밖에 없습니다. 그래서 Iso 값은 사실상 함수 두 개를 품고 있습니다. 타입을 바꾸지 않는 단순한 경우는 Iso' s a = Iso s s a a로 씁니다.

iso 스마트 생성자. lens 라이브러리는 함수 두 개로 Iso 값을 만드는 스마트 생성자(smart constructor) iso를 제공하며, 정의는 위의 설명 그대로입니다.

iso :: (s -> a) -> (b -> t) -> Iso s t a b
iso sa bt = dimap sa (fmap bt)

입력 쪽에 sa를 붙이고, 출력 쪽에는 f 안쪽에 bt를 붙이기 위해 fmap bt를 붙입니다.

이 쪽에서 쓰는 도우미 타입 세 개. 아래의 사용 예제에서는 f와 p 자리에 다음 세 타입을 골라 넣습니다. Identity와 Const는 base 라이브러리(Data.Functor.Identity, Data.Functor.Const)에 있고, Tagged는 tagged 패키지에 있는 타입이며, 정의는 다음과 같습니다.

newtype Identity a = Identity { runIdentity :: a }
instance Functor Identity where
  fmap f (Identity x) = Identity (f x)

newtype Const r a = Const { getConst :: r }
instance Functor (Const r) where
  fmap _ (Const x) = Const x

newtype Tagged s b = Tagged { unTagged :: b }
instance Profunctor Tagged where
  dimap _ g (Tagged b) = Tagged (g b)
  • Identity는 값 하나를 감싸기만 하는, "아무 일도 하지 않는" 펑터입니다. fmap f는 감싼 값에 f를 그대로 적용합니다. 그래서 "Identity로 감싼 뒤 fmap f하기"(fmap f . Identity)와 "f를 적용한 뒤 감싸기"(Identity . f)는 같습니다. runIdentity는 감싼 값을 꺼냅니다.
  • Const r a는 상수 펑터(constant functor)입니다. r 값 하나만 담고 a는 쓰지 않으므로, fmap은 함수를 무시하고 값을 그대로 둡니다. getConst는 담긴 r 값을 꺼냅니다.
  • Tagged s b는 입력 쪽 s를 쓰지 않고 출력 쪽 값 b 하나만 들고 있는 프로펑터입니다. 그래서 dimap은 입력 쪽 함수를 무시하고 출력 쪽 함수 g만 적용합니다. unTagged는 그 값을 꺼냅니다.

정리하면, 동형 값 안의 fmap bt는 f = Identity에서는 실제로 실행되고 f = Const r에서는 무시됩니다. 입력 쪽 함수 sa는 p = Tagged에서 무시됩니다. 아래의 사용 예제는 이 세 가지 성질을 골라 쓰는 방법입니다.

예제로 쓸 동형 두 개. 다음은 원문 코드가 아니라 이 쪽의 예제에서 계속 쓸 값입니다. 이 쪽의 예시는 모두 실제 lens 라이브러리 대신 원문과 lens의 정의를 따라 필요한 부분만 다시 만든 코드로 GHC 9.10.3에서 실행한 결과입니다. lens의 정의를 그대로 따랐으므로 lens 문서가 설명하는 동작과 같은 결과가 나옵니다.

-- View a Celsius value as Fahrenheit.
fahrenheit :: Iso' Double Double
fahrenheit = iso (\c -> c * 9 / 5 + 32) (\f -> (f - 32) * 5 / 9)

-- View a list as its reverse.
reversed :: Iso' [a] [a]
reversed = iso reverse reverse

아래에서는 fahrenheit의 앞방향 함수를 toF, 뒷방향 함수를 fromF라고 부르겠습니다. toF 0 = 32, toF 100 = 212이고 fromF는 그 역입니다.

Exchange는 어떻게 쓰나요

하이라이트: data Exchange a b s t = Exchange (s -> a) (b -> t)

원문 문맥:

Let's start with two definitions of isomorphism optics. Isomorphism optics are pairs of functions, one in a "backwards" direction and one in a "forwards" direction, like a newtype constructor pattern.

data Exchange a b s t = Exchange (s -> a) (b -> t)

type Iso s t a b = forall p f.
  (Profunctor p, Functor f) => p a (f b) -> p s (f t)

사용자 메모: “Show me how it is used”

Exchange의 주된 쓰임은 한마디로 다형적인 Iso 값에서 그 안의 함수 두 개를 꺼내는 탐침입니다. 단계별로 보겠습니다.

1단계: Exchange는 그 자체로 프로펑터입니다. 원문은 이 인스턴스를 보여 주지 않지만, lens 내부(Control.Lens.Internal.Iso)에 같은 인스턴스가 있습니다. 다음은 그 재구성입니다.

instance Profunctor (Exchange a b) where
  dimap f g (Exchange sa bt) = Exchange (sa . f) (g . bt)

새 입력 쪽 함수 f는 앞방향 함수 앞에 붙고(sa . f), 새 출력 쪽 함수 g는 뒷방향 함수 뒤에 붙습니다(g . bt). 즉 Exchange의 dimap은 함수를 실행하지 않고 기록해 둡니다.

2단계: 다형적인 Iso에 Exchange를 넣습니다. fahrenheit는 어떤 p에서도 동작하므로 p = Exchange Double Double, f = Identity를 고를 수 있습니다. 넣을 값은 "아무것도 바꾸지 않는 교환" Exchange id Identity입니다. 앞방향은 id, 뒷방향은 값을 위에서 본 Identity로 감싸기만 합니다. 손으로 계산해 보겠습니다.

fahrenheit (Exchange id Identity)
= dimap toF (fmap fromF) (Exchange id Identity)      -- iso의 정의
= Exchange (id . toF) (fmap fromF . Identity)        -- Exchange의 dimap
= Exchange toF (Identity . fromF)                    -- Identity의 fmap 정의

마지막 줄은 위의 도우미 타입 설명에서 본 성질, 즉 fmap fromF . Identity와 Identity . fromF가 같다는 성질을 쓴 것입니다.

동형 값이 한 일은 dimap 호출 하나뿐이었는데, Exchange가 그 호출에 들어온 두 함수를 그대로 담아 두었습니다. 이제 패턴 매칭으로 꺼내 쓸 수 있습니다.

>>> let Exchange sa bt = fahrenheit (Exchange id Identity)
>>> (sa 0, runIdentity (bt 32))
(32.0,0.0)

3단계: lens의 withIso가 바로 이 일을 합니다. lens는 이 탐침을 withIso라는 함수로 감싸 두었습니다.

type AnIso s t a b = Exchange a b a (Identity b) -> Exchange a b s (Identity t)

withIso :: AnIso s t a b -> ((s -> a) -> (b -> t) -> r) -> r
withIso ai k = case ai (Exchange id Identity) of
  Exchange sa bt -> k sa (runIdentity . bt)

AnIso s t a b는 Iso s t a b에서 p를 Exchange a b로, f를 Identity로 고정한 타입입니다. 모든 Iso는 모든 p와 f에서 동작하므로 당연히 AnIso 자리에도 넣을 수 있습니다. withIso는 탐침으로 두 함수를 꺼낸 뒤 그것을 받는 함수 k에 넘깁니다.

>>> withIso fahrenheit (\toF fromF -> (toF 100, fromF 212))
(212.0,100.0)

4단계: 꺼낸 함수로 새 옵틱을 만듭니다. 함수 두 개를 꺼낼 수 있으면 그것을 재조합할 수 있습니다. lens의 from은 동형을 뒤집습니다. 정의는 withIso로 두 함수를 꺼내 순서를 바꿔 iso에 다시 넣는 것입니다.

from :: AnIso s t a b -> Iso b a t s
from i = withIso i (\sa bt -> iso bt sa)
>>> view (from fahrenheit) 212
100.0

여기서 view는 3쪽에서 본 "읽기"이며, 아래 Iso 하이라이트에서 내부를 자세히 봅니다. lens의 under처럼 동형을 "거꾸로 적용"하는 다른 함수들도 같은 방식으로 withIso 위에 만들어집니다.

5단계: 원문에서의 쓰임. 바로 아래에서 읽을 원문의 mapIso는 mapIso pattern = withIso pattern dimap입니다. 즉 Exchange 탐침으로 두 함수를 꺼내 그대로 dimap에 넘깁니다. 그 결과 Iso를 Parsor나 Printor 같은 임의의 프로펑터에 바로 적용할 수 있게 됩니다. 이 글에서 Exchange는 "lens의 동형을 프린터-파서에 쓰기 위한 다리"입니다.

정리하면, Exchange를 직접 만들어 쓰는 일은 드뭅니다. Exchange는 다형적인 동형 값에 넣어 그 값이 품은 두 함수를 관찰하는 부엌이며, withIso, from, 그리고 원문의 mapIso가 모두 이 관찰 위에 서 있습니다. 원문의 표현으로 Exchange는 동형 옵틱의 "구체 표현(concrete representation)"입니다.

Iso는 어떻게 쓰나요

하이라이트:

type Iso s t a b = forall p f.
  (Profunctor p, Functor f) => p a (f b) -> p s (f t)

원문 문맥:

data Exchange a b s t = Exchange (s -> a) (b -> t)

type Iso s t a b = forall p f.
  (Profunctor p, Functor f) => p a (f b) -> p s (f t)

The Exchange type is a "concrete representation" of the isomorphism optic and Iso is a "Kmett representation".

사용자 메모: “Show me how it’s used”

Iso 값을 "쓴다"는 것은 p와 f를 골라서 그 함수에 알맞은 인자를 넣는다는 뜻입니다. 같은 값 fahrenheit 하나가 고르는 방법에 따라 전혀 다른 일을 합니다.

고르는 p 고르는 f 얻는 동작 넣는 값
(->) Const a 읽기 view Const
(->) Identity 고치기 over Identity . f
Tagged Identity 거꾸로 만들기 review Tagged (Identity b)
Exchange a b Identity 두 함수 꺼내기 withIso Exchange id Identity
Parsor s f, Printor s f (아래 mapIso로) 파서 변환, 프린터 변환 프린터-파서

앞의 세 줄은 lens의 view, over, review를 단순화한 정의로 확인할 수 있습니다. 다음은 원문 코드가 아닌 재구성입니다.

view :: ((a -> Const a a) -> s -> Const a s) -> s -> a
view l s = getConst (l Const s)

over :: ((a -> Identity b) -> s -> Identity t) -> (a -> b) -> s -> t
over l f = runIdentity . l (Identity . f)

review :: (Tagged a (Identity b) -> Tagged s (Identity t)) -> b -> t
review l = runIdentity . unTagged . l . Tagged . Identity

view와 over의 인자 타입은 Iso에서 p = (->)로 고른 모양입니다. 세 정의는 위의 도우미 타입을 씁니다. view는 fmap이 함수를 무시하는 Const를, over는 fmap이 함수를 실행하는 Identity를, review는 입력 쪽 함수를 무시하는 Tagged와 Identity를 씁니다.

읽기: view fahrenheit 100. p = (->)에서 dimap sa bt ab = bt . ab . sa이므로(2쪽), 계산은 다음과 같습니다.

view fahrenheit 100
= getConst (fahrenheit Const 100)
= getConst ((dimap toF (fmap fromF) Const) 100)
= getConst ((fmap fromF . Const . toF) 100)
= getConst (fmap fromF (Const 212))
= getConst (Const 212)          -- Const의 fmap은 함수를 무시합니다
= 212

Const가 앞방향 결과 212를 붙잡고, 뒷방향 함수 fromF는 Const의 fmap이 무시합니다. 그래서 "앞방향으로 한 번 보기"가 됩니다.

고치기: over fahrenheit (+18) 0. 이번에는 Identity가 fmap을 실제로 실행합니다.

over fahrenheit (+18) 0
= runIdentity ((fmap fromF . Identity . (+18) . toF) 0)
= fromF (toF 0 + 18)
= fromF 50
= 10

섭씨 0도를 화씨로 보면 32도이고, 거기에 18도를 더하면 화씨 50도이며, 이것을 섭씨로 되돌리면 10도입니다. 즉 over는 "앞방향으로 보고, 고치고, 뒷방향으로 되돌리기"입니다.

거꾸로 만들기: review fahrenheit 212. Tagged의 dimap은 입력 쪽 함수 toF를 무시하고 출력 쪽 fmap fromF만 적용하므로 뒷방향 함수만 실행됩니다.

실행 결과는 다음과 같습니다.

>>> view fahrenheit 100
212.0
>>> over fahrenheit (+18) 0
10.0
>>> review fahrenheit 212
100.0
>>> view reversed "abc"
"cba"
>>> over reversed (drop 1) "abc"
"ab"
>>> over reversed ('z':) "abc"
"abcz"
>>> review reversed "abc"
"cba"

reversed의 예가 동형 옵틱의 쓸모를 잘 보여 줍니다. drop 1은 목록의 첫 원소를 버리는 함수인데, over reversed (drop 1)은 마지막 원소를 버립니다. 뒤집어 보고, 앞에서 하나 버리고, 다시 뒤집기 때문입니다. 마찬가지로 over reversed ('z':)는 맨 뒤에 원소를 붙입니다.

프린터-파서에 쓰기. 이 글의 목적에서 가장 중요한 선택은 p를 Parsor나 Printor로 고르는 것입니다. 원문은 이를 위해 바로 아래의 mapIso를 정의합니다. 미리 결과만 보면 다음과 같습니다. 다음은 원문 코드가 아닌 예시이며, 글자와 그 유니코드 코드 포인트 사이의 동형 iso chr ord :: Iso Int Int Char Char를 3쪽의 anyToken에 적용합니다.

>>> runParsor (mapIso (iso chr ord) anyToken :: Parsor String [] Int Int) "A!"
[(65,"!")]
>>> [pr "" | pr <- runPrintor (mapIso (iso chr ord) anyToken :: Printor String [] Int Int) 66]
["B"]

파서는 글자 'A'를 읽고 뒷방향 함수 ord(b -> t)로 65를 만들었습니다. 프린터는 66을 받아 앞방향 함수 chr(s -> a)로 'B'를 만든 뒤 출력했습니다. 2쪽의 핵심 표 그대로, 파서는 출력 쪽 함수를, 프린터는 입력 쪽 함수를 씁니다.

정리하면 Iso 값은 "어떤 p와 f에서도 dimap과 fmap만으로 일하는 함수"이고, 그 값을 쓰는 사람은 p와 f를 골라 읽기, 고치기, 거꾸로 만들기, 함수 꺼내기, 파서 변환, 프린터 변환 중 원하는 동작을 얻습니다.

표현 사이를 어떻게 오가나요

하이라이트: They're equivalent and you can convert between representations.

원문 문맥:

The Exchange type is a "concrete representation" of the isomorphism optic and Iso is a "Kmett representation". They're equivalent and you can convert between representations. The lens library uses Kmett's representation as it provides a convenient specialization to a "Van Laarhoven representation" when p is (->).

사용자 메모: “Show me how”

같은 동형을 적는 방법은 적어도 네 가지입니다.

이름 타입 비고
구체 표현(concrete representation) Exchange a b s t 함수 두 개를 그대로 담습니다.
케밋 표현(Kmett representation) forall p f. (Profunctor p, Functor f) => p a (f b) -> p s (f t) lens의 Iso입니다. 이 이름은 원문 저자가 붙인 것입니다.
순수 프로펑터 표현(pure profunctor representation) forall p. Profunctor p => p a b -> p s t f가 없습니다. 원문이 선호하는 형태입니다.
반 라르호번 표현(van Laarhoven representation) forall f. Functor f => (a -> f b) -> s -> f t 케밋 표현에서 p = (->)로 고른 것입니다.

다음은 각 방향의 변환 함수입니다. 원문 코드가 아니라 재구성입니다.

-- concrete -> Kmett
fromExchange :: Exchange a b s t -> Iso s t a b
fromExchange (Exchange sa bt) = iso sa bt

-- Kmett -> concrete
toExchange :: AnIso s t a b -> Exchange a b s t
toExchange i = withIso i Exchange

-- Kmett -> pure profunctor
type ProIso s t a b = forall p. Profunctor p => p a b -> p s t

isoToPro :: Iso s t a b -> ProIso s t a b
isoToPro i = mapIso i

-- pure profunctor -> concrete -> Kmett
proToIso :: ProIso s t a b -> Iso s t a b
proToIso l = case l (Exchange id id) of Exchange sa bt -> iso sa bt

-- Kmett -> van Laarhoven: choose p = (->)
type Lens s t a b = forall f. Functor f => (a -> f b) -> s -> f t

isoAsLens :: Iso s t a b -> Lens s t a b
isoAsLens i = i

하나씩 읽겠습니다.

  • 구체 → 케밋: 함수 두 개가 있으면 iso로 감싸면 됩니다. iso sa bt = dimap sa (fmap bt)입니다.
  • 케밋 → 구체: 위에서 본 Exchange 탐침입니다. withIso i Exchange는 꺼낸 두 함수를 생성자 Exchange에 그대로 넣습니다.
  • 케밋 → 순수 프로펑터: 두 함수를 꺼내 dimap에 넘기면 p a b -> p s t가 됩니다. 이것이 원문의 mapIso입니다.
  • 순수 프로펑터 → 구체: 순수 프로펑터 표현도 아무 p에서나 동작하므로 p = Exchange a b를 고르고 Exchange id id를 넣어 두 함수를 꺼냅니다. 케밋 표현에서 Identity가 하던 일을 할 f가 없으므로 뒷방향 초기값이 그냥 id입니다. 꺼낸 함수를 다시 iso로 감싸면 케밋 표현이 됩니다.
  • 케밋 → 반 라르호번: 아무것도 할 필요가 없습니다. 모든 p에서 동작하는 함수는 p = (->)에서도 동작하므로 그대로 Lens 타입이 됩니다.

왕복해도 같은 동형이 나오는지 확인해 보겠습니다.

>>> view (fromExchange (toExchange fahrenheit)) 100
212.0
>>> isoToPro fahrenheit (+18) 0
10.0
>>> mapIso fahrenheit (+18) 0
10.0
>>> view (proToIso (isoToPro fahrenheit)) 100
212.0
>>> view (isoAsLens reversed) "abc"
"cba"

둘째 줄과 셋째 줄은 순수 프로펑터 표현에서 p = (->)를 고른 것입니다. dimap toF fromF (+18)은 fromF . (+18) . toF이므로 over fahrenheit (+18)과 같은 결과가 나옵니다.

왜 "동등"하다고 말할 수 있을까요. 다형적인 함수가 쓸 수 있는 연산은 dimap과 fmap뿐이므로, 그 함수가 할 수 있는 일은 결국 "입력 쪽에 무언가를 붙이고 출력 쪽에 무언가를 붙이는 것"뿐입니다. Exchange는 붙인 것을 빠짐없이 기록하는 프로펑터이므로, 기록된 두 함수만 알면 원래의 다형적인 함수를 다시 만들 수 있습니다. Pickering, Gibbons, Wu의 논문 Profunctor Optics: Modular Data Accessors는 이런 프로펑터 기반 표현이 익숙한 구체 표현과 "정확히 동등(precisely equivalent)"하다는 것을 보였습니다. 원문의 "They're equivalent"는 이 결과를 가리킵니다.

한 가지 주의. 반 라르호번 방향은 한쪽으로만 갑니다. 모든 Iso는 Lens로 쓸 수 있지만, 모든 Lens가 Iso인 것은 아닙니다. 예를 들어 쌍의 첫 원소를 가리키는 _1은 두 번째 원소를 버리고 되돌릴 수 없으므로 동형이 아닙니다. 그래서 "케밋 → 반 라르호번"은 동등성이 아니라 **특수화(specialization)**입니다. 원문도 바로 그 단어를 씁니다.

lens는 왜 f가 있는 표현을 쓸까요

하이라이트: Kmett's representation as it provides a convenient specialization to a "Van Laarhoven representation" when p is (->)

원문 문맥:

The lens library uses Kmett's representation as it provides a convenient specialization to a "Van Laarhoven representation" when p is (->). However, a pure profunctorial representation (without f), which is also equivalent, can be simpler. We can observe the profunctorial representation with a combinator.

반 라르호번 표현이란. Twan van Laarhoven은 2009년 글 CPS based functional references에서 "구조의 한 부분에 대한 참조"를 forall f. Functor f => (a -> f b) -> s -> f t 꼴의 함수로 표현할 수 있다고 제안했습니다. 이 표현의 장점은 참조 두 개를 보통의 함수 합성 .으로 이어 붙일 수 있다는 것입니다. lens 라이브러리의 Lens와 Traversal이 이 표현을 씁니다.

p = (->)이면 그대로 들어맞습니다. 케밋 표현 p a (f b) -> p s (f t)에서 p를 (->)로 바꾸면 (a -> f b) -> (s -> f t)가 되어 반 라르호번 표현과 글자 그대로 같습니다. 따라서 lens에서는 모든 Iso가 그대로 Lens이고, 렌즈와 동형을 .으로 섞어 합성할 수 있습니다. 다음은 원문 코드가 아닌 예시입니다.

_1 :: Lens (a, c) (b, c) a b
_1 f (a, c) = (\b -> (b, c)) <$> f a
>>> view (_1 . reversed) ("abc", True)
"cba"
>>> over (_1 . reversed) (drop 1) ("abc", True)
("ab",True)

_1 . reversed는 "쌍의 첫 원소를, 뒤집어서 본다"는 합성 옵틱입니다. 렌즈 _1은 반 라르호번 표현으로 정의되었고 reversed는 케밋 표현의 Iso인데, p = (->)에서 두 타입이 맞으므로 .으로 곧바로 이어집니다. 이것이 원문이 말하는 "편리한 특수화(convenient specialization)"입니다. lens 문서도 동형이 (.)과 id로 다른 렌즈와 합성된다고 적고 있습니다(lens 문서: Control.Lens.Iso).

대가와 원문의 선택. 대신 케밋 표현에는 f가 끼어 있어서 프린터-파서에 바로 쓰기에는 번거롭습니다. 프린터-파서는 p a b 모양이지 p a (f b) 모양이 아니기 때문입니다. 원문은 그래서 f가 없는 순수 프로펑터 표현 p a b -> p s t가 "더 단순할 수 있다"고 말합니다. lens는 다른 옵틱과의 호환성을 택했고, 이 글은 lens의 옵틱을 그대로 가져다 쓰되 조합자(mapIso, >?, ?<, >?<)로 순수 프로펑터 표현을 꺼내 프린터-파서에 적용합니다. 두 선택은 같은 정보를 담은 서로 다른 포장이므로 이렇게 오갈 수 있습니다.

mapIso: 순수 프로펑터 표현 꺼내기

mapIso :: Profunctor p => Iso s t a b -> p a b -> p s t
mapIso pattern = withIso pattern dimap
  • 타입: 동형 하나와 프로펑터 값 p a b를 받아 p s t를 돌려줍니다. Iso 자리의 인자는 다형적이어야 하므로 랭크-N 타입입니다.
  • 정의: withIso pattern dimap은 Exchange 탐침으로 꺼낸 두 함수 sa와 bt를 dimap에 넘깁니다. 즉 mapIso pattern = dimap sa bt입니다. withIso는 원문에 정의가 없고 lens에서 가져온 함수이며, 위의 Exchange 하이라이트에서 그 정의를 보았습니다.
  • 이름 pattern은 평범한 변수 이름입니다. 동형이 "패턴"이라는 원문의 관점을 반영한 이름입니다.

프린터-파서에서의 동작은 2쪽의 표를 그대로 따릅니다. 파서로 쓰면 결과에 bt가 적용되고, 프린터로 쓰면 입력에 sa가 먼저 적용됩니다. 6쪽의 optionalP, manyP가 이 조합자를 씁니다.

프리즘과 Choice

원문은 이어서 프리즘을 다룹니다. 프리즘을 프로펑터로 표현하려면 Either를 다룰 수 있는 프로펑터가 필요합니다.

class Profunctor p => Choice p where
  left' :: p a b -> p (Either a c) (Either b c)
  right' :: p a b -> p (Either c a) (Either c b)
  • class Profunctor p => Choice p: Choice는 Profunctor의 하위 클래스입니다. 모든 Choice는 프로펑터입니다.
  • left': a에서 b로 가는 p를 Either의 왼쪽 갈래에서 쓰도록 들어 올립니다. 입력이 Left a이면 원래 p로 처리해 Left b를 내고, 입력이 Right c이면 건드리지 않고 그대로 통과시킵니다.
  • right': 같은 일을 오른쪽 갈래에서 합니다.

함수 화살표 (->)의 Choice 인스턴스로 감을 잡아 보겠습니다. 다음은 원문 코드가 아닌 예시입니다.

instance Choice (->) where
  left' f = either (Left . f) Right
  right' = fmap
>>> right' (+1) (Right 1 :: Either String Int)
Right 2
>>> right' (+1) (Left "x" :: Either String Int)
Left "x"
>>> left' length (Left "abc" :: Either String Bool)
Left 3

원문은 Parsor와 Printor에도 Choice 인스턴스가 있다고만 말하고 정의는 보여 주지 않습니다. 이 시리즈의 재구성에서는 다음처럼 동작합니다. 파서의 right' p는 p를 실행하고 결과를 Right로 표시합니다(입력은 파서가 쓰지 않으므로). 프린터의 right' p는 Right 값이 들어오면 p로 출력하고, Left 값이 들어오면 출력할 방법이 없으므로 empty로 실패합니다. 그래서 프린터의 Choice 인스턴스는 Alternative f를 요구합니다.

Market과 Prism

data Market a b s t = Market (b -> t) (s -> Either t a)

type Prism s t a b = forall p f.
  (Choice p, Applicative f) => p a (f b) -> p s (f t)

type Prism' s a = Prism s s a a
  • Market: 프리즘의 구체 표현입니다. 원문은 이것을 "패턴 매칭의 생성자(constructor)와 분해자(destructor) 한 쌍"이라고 설명합니다. b -> t는 안쪽 값으로 바깥 값을 만드는 함수이고, s -> Either t a는 바깥 값을 맞추어 보는 함수입니다. 맞으면 Right a로 안쪽 값을 돌려주고, 맞지 않으면 Left t를 돌려줍니다.
  • 왜 Maybe a가 아니라 Either t a일까요. 타입을 바꾸는 프리즘 때문입니다. 예를 들어 _Just :: Prism (Maybe a) (Maybe b) a b에서 Nothing :: Maybe a는 맞지 않는 값인데, 내용이 없으므로 그대로 Nothing :: Maybe b로 다시 타입을 붙일 수 있습니다. 맞지 않는 값을 바뀐 바깥 타입 t로 돌려주는 자리가 Left t입니다.
  • Prism: 케밋 표현입니다. Iso와 비교하면 Profunctor가 Choice로, Functor가 Applicative로 강해졌습니다. Choice는 "맞지 않는 경우를 통과시키는" 데 필요하고, Applicative는 아래에서 말할 트래버설과의 호환을 위한 것입니다.
  • Prism': 타입을 바꾸지 않는 단순한 프리즘입니다.

원문은 Applicative f 덕분에 모든 Prism이 자동으로 Traversal이 된다고 덧붙입니다. 트래버설(traversal)은 0개 이상의 부분에 초점을 맞추는 옵틱이며, 반 라르호번 표현에서 Applicative f를 요구합니다. 프리즘은 "0개 또는 1개"의 부분에 초점을 맞추므로 트래버설의 특수한 경우입니다. 하지만 원문은 곧바로 "우리의 목적에서는 순수 프로펑터 표현이 더 중요하다"고 말합니다.

Market도 Exchange처럼 탐침으로 쓰입니다. lens의 withPrism은 프리즘에 Market을 넣어 만들기 함수와 맞추기 함수를 꺼냅니다. 3쪽의 _Cons로 확인해 보겠습니다. 원문 코드가 아닌 예시입니다.

>>> withPrism (_Cons :: Prism' String (Char, String)) (\build match -> (build ('x',"yz"), match "abc", match ""))
("xyz",Right ('a',"bc"),Left "")

만들기 함수는 ('x',"yz")로 "xyz"를 만들었고, 맞추기 함수는 "abc"를 Right ('a',"bc")로 분해했으며, 빈 문자열에는 맞지 않아 Left ""를 돌려주었습니다.

용어에 관한 짧은 주의. 원문은 "Prisms encode exhaustive patterns."라고 씁니다. 보통은 반대로 말합니다. 프리즘은 맞지 않을 수 있는 패턴이기 때문입니다. distributors 패키지의 문서도 PartialIso를 "일급 비망라적 패턴(a first class inexhaustive pattern)"이라고 부릅니다. 원문의 "exhaustive"(망라적)는 아마 맞추기 함수 s -> Either t a가 **전함수(total function)**라는 점, 즉 맞지 않아도 실패하지 않고 Left t라는 답을 돌려준다는 점을 가리키는 것으로 보입니다. 이 해석은 원문에 명시되어 있지 않으므로 추정입니다. 아래에서 볼 것처럼 프리즘을 함수 화살표에 적용하면 결과가 여전히 전함수이지만, 프린터에 적용하면 맞지 않는 값에서 출력이 실패합니다.

(>?): 프리즘을 프린터-파서에 적용하기

(>?) :: Choice p => Prism s t a b -> p a b -> p s t
(>?) pattern = withPrism pattern $ \f g -> dimap g (either id f) . right'
  • 타입: 프리즘과 p a b를 받아 p s t를 만듭니다. mapIso의 프리즘 버전이며, 순수 프로펑터 표현을 꺼내는 조합자입니다.
  • withPrism pattern $ \f g -> ...: Market 탐침으로 만들기 함수 f :: b -> t와 맞추기 함수 g :: s -> Either t a를 꺼냅니다.
  • right': 먼저 p a b를 p (Either t a) (Either t b)로 들어 올립니다. 오른쪽 갈래는 원래 p가 처리하고, 왼쪽 갈래 t는 통과합니다.
  • dimap g (either id f): 입력 쪽에는 맞추기 함수 g를 붙여 s를 Either t a로 만들고, 출력 쪽에는 either id f를 붙여 Left t는 그대로, Right b는 f로 만들어 t를 얻습니다.

프린터-파서에서의 동작은 2쪽의 표에서 바로 나옵니다.

  • 프린터: 입력 쪽만 중요합니다. 값 s를 맞추기 함수 g로 맞추어 보고, 맞으면 안쪽 값을 원래 프린터로 출력합니다. 맞지 않으면 Left 갈래가 되는데, 프린터의 right'는 Left에서 empty로 실패하므로 출력도 실패합니다.
  • 파서: 출력 쪽만 중요합니다. 원래 파서로 안쪽 값을 파싱하고, 결과에 만들기 함수 f를 적용해 바깥 값을 만듭니다.

원문 코드가 아닌 예시로 확인해 보겠습니다. _Just = prism Just (maybe (Left Nothing) Right)입니다.

>>> runParsor (_Just >? anyToken :: Parsor String [] (Maybe Char) (Maybe Char)) "q!"
[(Just 'q',"!")]
>>> [pr "" | pr <- runPrintor (_Just >? anyToken :: Printor String [] (Maybe Char) (Maybe Char)) (Just 'q')]
["q"]
>>> [pr "" | pr <- runPrintor (_Just >? anyToken :: Printor String [] (Maybe Char) (Maybe Char)) Nothing]
[]

파서는 'q'를 읽어 Just 'q'로 감쌌습니다. 프린터는 Just 'q'에서 'q'를 꺼내 출력했고, Nothing은 맞지 않으므로 출력하지 못했습니다. 원문은 Parsor와 Printor가 모두 Choice 인스턴스를 가지므로 (>?)가 파서 조합자이자 프린터 조합자가 된다고 말합니다.

only와 프리즘 스마트 생성자

원문은 lens가 Template Haskell로 대수적 자료형의 생성자마다 프리즘을 만들어 준다고 말합니다. 템플릿 하스켈(Template Haskell)은 컴파일 시간에 코드를 생성하는 기능이며, 7쪽의 makePrisms ''RegEx가 그 예입니다. 또는 함수 쌍에서 스마트 생성자 prism'이나 prism으로 프리즘을 직접 만들 수 있습니다. lens의 두 스마트 생성자는 다음 타입을 가집니다.

prism  :: (b -> t) -> (s -> Either t a) -> Prism s t a b
prism' :: (b -> s) -> (s -> Maybe a) -> Prism s s a b

prism은 Market의 두 함수를 그대로 받고, prism'은 맞추기 함수가 Maybe를 돌려주는 단순한 경우를 위한 것입니다. 원문의 예는 only입니다.

only :: Eq a => a -> Prism' a ()
only a = prism' (\() -> a) $ guard . (a ==)
  • only a는 "값이 정확히 a인 경우"에 맞추는 프리즘이며, 안쪽 값은 아무 정보도 없는 ()입니다.
  • 만들기 함수 \() -> a는 ()를 받아 a를 만듭니다.
  • 맞추기 함수 guard . (a ==)는 x를 받아 guard (a == x)를 계산합니다. Control.Monad의 guard :: Alternative f => Bool -> f ()는 True이면 pure (), False이면 empty이므로, Maybe에서는 같으면 Just (), 다르면 Nothing입니다.
>>> preview (only 'x') 'y'
Nothing
>>> preview (only 'x') 'x'
Just ()
>>> review (only 'x') ()
'x'

코프리즘과 Cochoice

원문은 프리즘의 쌍대(dual)인 코프리즘(coprism)으로 넘어갑니다. 프리즘이 패턴 매칭을 나타낸다면 코프리즘은 패턴 필터링(pattern filtering)을 나타낸다고 말합니다. 코프리즘에는 Choice의 화살표를 뒤집은 Cochoice가 필요합니다.

class Profunctor p => Cochoice p where
  unleft :: p (Either a c) (Either b c) -> p a b
  unright :: p (Either c a) (Either c b) -> p a b

left' :: p a b -> p (Either a c) (Either b c)와 비교하면 unleft는 정확히 그 화살표를 뒤집은 타입입니다. Either를 다루는 p에서 한 갈래만 다루는 p를 되찾습니다. 프린터-파서에서의 의미는 다음과 같습니다.

  • 파서: unright p는 p를 실행한 뒤 Right로 표시된 결과만 남기고 Left 결과는 버립니다. 결과를 걸러 내는 연산이므로, 이 시리즈의 재구성에서 파서의 Cochoice 인스턴스는 아래에서 볼 Filterable f를 요구합니다.
  • 프린터: unright p는 입력 a를 Right a로 감싸서 p에 넘깁니다. 아무 제약도 필요 없습니다.

원문은 이 인스턴스들의 정의를 보여 주지 않고 "있다"고만 말하므로, 위의 설명은 재구성에 따른 것입니다.

(?<)와 token

원문은 코프리즘을 따로 정의할 필요가 없다고 말합니다. 프리즘의 타입 매개변수 순서를 바꾸면 코프리즘이 되기 때문입니다.

(?<) :: Cochoice p => Prism b a t s -> p a b -> p s t
(?<) pattern = withPrism pattern $ \f g -> unright . dimap (either id f) g

token :: (Cochoice p, Eq c, Tokenized c c p) => c -> p () ()
token c = only c ?< anyToken

>>> runParsor (token 'x') "xyz" :: [((),String)]
[((),"yz")]
>>> [pr "yz" | pr <- runPrintor (token 'x') ()] :: [String]
["xyz"]

뒤바뀐 매개변수 읽기. (?<)의 첫 인자 타입은 Prism s t a b가 아니라 Prism b a t s입니다. 그러면 withPrism이 꺼내는 두 함수의 타입도 바뀝니다. 만들기 함수 f는 s -> a가 되고, 맞추기 함수 g는 b -> Either a t가 됩니다. 즉 프리즘을 거꾸로 씁니다.

  • dimap (either id f) g: 입력 쪽에는 either id f :: Either a s -> a를 붙이고 출력 쪽에는 맞추기 함수 g :: b -> Either a t를 붙여, p a b를 p (Either a s) (Either a t)로 만듭니다.
  • unright: 오른쪽 갈래만 남겨 p s t를 얻습니다.

token c 따라가기. only c :: Prism' c ()는 Prism c c () ()이므로 (?<)의 Prism b a t s에서 b = c, a = c, t = (), s = ()입니다. 만들기 함수는 \() -> c, 맞추기 함수는 "c와 같은가"입니다.

프린터: () 를 출력
  unright 가 () 를 Right () 로 감쌉니다
  either id f (Right ()) = f () = c
  anyToken 이 c 를 출력합니다

파서: "xyz" 를 파싱 (c = 'x')
  anyToken 이 'x' 를 읽습니다
  g 'x' = Right ()        -- 같으므로 맞음
  unright 가 Right () 를 남깁니다   ==> [((),"yz")]

파서: "ayz" 를 파싱
  anyToken 이 'a' 를 읽습니다
  g 'a' = Left 'a'        -- 다르므로 맞지 않음
  unright 가 Left 를 버립니다       ==> []

마지막 경우는 원문에 없는 예시입니다.

>>> runParsor (token 'x') "ayz" :: [((),String)]
[]

token c의 타입이 p () ()인 점도 중요합니다. 정해진 글자 하나는 정보를 담지 않으므로, 프린터는 ()만 받으면 되고 파서는 ()만 돌려주면 됩니다. 이것이 원문이 말하는 "패턴 필터링"입니다. 파서 쪽에서 프리즘의 맞추기 함수가 결과를 거르는 필터 역할을 합니다.

부분 프로펑터와 dimapMaybe

원문은 Choice와 Cochoice 인스턴스를 모두 가진 프로펑터를 부분 프로펑터(partial profunctor)라고 부릅니다. 이 이름은 원문 저자의 용어입니다. 부분 프로펑터에서는 실패할 수 있는 두 함수로 dimap을 할 수 있습니다.

dimapMaybe
  :: (Choice p, Cochoice p)
  => (s -> Maybe a) -> (b -> Maybe t)
  -> p a b -> p s t
dimapMaybe f g =
  let
    m2e h = maybe (Left ()) Right . h
    fg = dimap (>>= m2e f) (>>= m2e g)
  in
    unright . fg . right'
  • 타입: dimap과 같지만 두 함수가 Maybe를 돌려줍니다. 입력 쪽 함수 f가 실패하면 출력하지 않고, 출력 쪽 함수 g가 실패하면 그 파싱 결과를 버립니다.
  • m2e h = maybe (Left ()) Right . h: Maybe를 돌려주는 함수 h를 Either ()를 돌려주는 함수로 바꿉니다. Nothing은 Left (), Just x는 Right x가 됩니다. 이름은 "Maybe to Either"의 줄임말로 보입니다.
  • fg = dimap (>>= m2e f) (>>= m2e g): Either () 모나드의 >>=를 씁니다. Left ()는 그대로 Left ()로 남고, Right x이면 m2e f x를 계산합니다. 즉 "이미 실패했으면 실패, 아니면 함수를 적용해 실패할 수 있으면 실패"입니다.
  • unright . fg . right': right'로 p a b를 p (Either () a) (Either () b)로 들어 올리고, fg로 양쪽에 실패할 수 있는 함수를 붙인 뒤, unright로 오른쪽 갈래만 남깁니다.

프린터-파서에서의 흐름은 다음과 같습니다.

  • 프린터: 값 s가 들어오면 unright가 Right s로 감싸고, m2e f가 f s를 계산합니다. Nothing이면 Left ()가 되어 right'의 프린터가 empty로 실패하고, Just a이면 원래 프린터가 a를 출력합니다.
  • 파서: 원래 파서가 b를 읽으면 right'가 Right b로 표시하고, m2e g가 g b를 계산합니다. Nothing이면 Left ()가 되어 unright가 버리고, Just t이면 결과로 남습니다.

다음은 원문 코드가 아닌 예시입니다. 숫자 한 글자를 Int로 다루는 프린터-파서입니다.

digitI :: (Choice p, Cochoice p, Tokenized Char Char p) => p Int Int
digitI = dimapMaybe (\n -> if 0 <= n && n <= 9 then Just (intToDigit n) else Nothing)
                    (\c -> if isDigit c then Just (digitToInt c) else Nothing) anyToken
>>> runParsor (digitI :: Parsor String [] Int Int) "7x"
[(7,"x")]
>>> runParsor (digitI :: Parsor String [] Int Int) "x7"
[]
>>> [pr "" | pr <- runPrintor (digitI :: Printor String [] Int Int) 3]
["3"]
>>> [pr "" | pr <- runPrintor (digitI :: Printor String [] Int Int) 12]
[]

파서는 숫자가 아닌 'x'를 버렸고, 프린터는 한 자리가 아닌 12를 출력하지 않았습니다. 한 정의가 두 방향에서 각자 알맞은 검사를 합니다.

부분 동형: PartialExchange와 PartialIso

원문은 dimapMaybe의 두 부분 함수를 또 하나의 옵틱, 부분 동형(partial isomorphism)으로 묶습니다. 1쪽에서 Rendel과 Ostermann이 쓴 바로 그 개념입니다.

data PartialExchange a b s t = PartialExchange (s -> Maybe a) (b -> Maybe t)

type PartialIso s t a b = forall p f.
  ( Choice p, Cochoice p
  , Applicative f, Filterable f
  ) => p a (f b) -> p s (f t)

type PartialIso' s a = PartialIso s s a a
  • PartialExchange: 구체 표현입니다. Exchange와 같지만 두 함수가 모두 실패할 수 있습니다.
  • PartialIso: 케밋 표현입니다. p에는 Choice와 Cochoice를, f에는 Applicative와 아래의 Filterable을 요구합니다.
  • PartialIso': 타입을 바꾸지 않는 경우입니다.

Iso와 Prism도 PartialIso로 쓸 수 있습니다. Iso는 Profunctor와 Functor만, Prism은 Choice와 Applicative만 요구합니다. PartialIso가 요구하는 제약은 그보다 많으므로, 더 적게 요구하는 Iso나 Prism은 PartialIso가 필요한 자리에 그대로 넣을 수 있습니다. 6쪽의 iso show read >?< ...와 7쪽의 only True >?< "true"가 이 성질을 씁니다. 패키지 문서도 "모든 Iso와 Prism은 APartialIso"라고 적습니다.

PartialExchange도 탐침으로 쓸 수 있습니다. 다음은 원문 코드가 아닌 예시이며, 아래에서 읽을 satisfied even의 두 함수를 꺼내 봅니다(withPartialIso는 원문에 이름이 나오지 않는 재구성 함수입니다).

>>> withPartialIso (satisfied even) (\f g -> (f 2, f 3, g (4::Int)))
(Just 2,Nothing,Just 4)

Filterable

class Functor f => Filterable f where
  mapMaybe :: (a -> Maybe b) -> f a -> f b
  mapMaybe f = catMaybes . fmap f

  catMaybes :: f (Maybe a) -> f a
  catMaybes = mapMaybe id

  filter :: (a -> Bool) -> f a -> f a
  filter f = mapMaybe $ \a -> if f a then Just a else Nothing

원문은 Filterable이 witherable 라이브러리의 아주 단순한 인터페이스이며, 목록 함수 catMaybes, filter, mapMaybe를 일반화한다고 설명합니다.

  • mapMaybe f: 각 원소에 f를 적용하고 Nothing이 나온 원소는 버립니다.
  • catMaybes: Maybe 원소 중 Just만 남겨 꺼냅니다.
  • filter f: 조건을 만족하는 원소만 남깁니다.
  • 세 메서드는 서로를 기본 구현으로 정의합니다. 인스턴스는 mapMaybe나 catMaybes 중 하나만 정의하면 됩니다.
>>> mapMaybe (\x -> if x > 1 then Just (x*10) else Nothing) [1,2,3]
[20,30]
>>> catMaybes [Just 1, Nothing, Just 3]
[1,3]

PartialIso가 Filterable f를 요구하는 이유는 파서 쪽에서 실패한 결과를 걸러 내야 하기 때문입니다.

원문은 Filterable이 Alternative의 쌍대라고 말하며 catMaybes와 optional의 타입을 비교하라고 합니다.

optional :: Alternative f => f a -> f (Maybe a)

optional p는 "p를 시도하되 실패하면 Nothing으로 성공"하는 연산이고(1쪽), catMaybes는 반대로 f (Maybe a)에서 Nothing을 지워 f a를 만듭니다. 두 타입의 화살표가 정반대입니다.

>>> optional [1,2]
[Just 1,Just 2,Nothing]

이 "쌍대"는 타입 모양의 비유로 읽으면 됩니다. 6쪽의 Filtrator가 이 비유를 프로펑터로 넓힙니다.

(>?<)

(>?<) :: (Choice p, Cochoice p) => PartialIso s t a b -> p a b -> p s t

원문은 이 조합자를 "dimapMaybe를 PartialIso의 조합자로 바꾼 것"이라고만 말하고 정의는 보여 주지 않습니다. 현재 distributors 패키지의 소스는 이것을 withPartialIso로 두 부분 함수를 꺼내 dimapMaybe에 넘기는 방식으로 정의합니다. 즉 mapIso, (>?), (?<)와 같은 "탐침으로 꺼내서 프로펑터에 적용" 패턴입니다. 5쪽과 6쪽에서 이 조합자는 Applicative의 <$> 자리를 대신합니다.

satisfied와 satisfy

satisfied :: (a -> Bool) -> PartialIso' a a
satisfied f = partialIso satiate satiate where
  satiate a = if f a then Just a else Nothing

satisfy :: (Choice p, Cochoice p, Tokenized c c p) => (c -> Bool) -> p c c
satisfy f = satisfied f >?< anyToken

>>> runParsor (satisfy isLower) "xyz" :: [(Char,String)]
[('x',"yz")]
>>> runParsor (satisfy isLower) "X" :: [(Char,String)]
[]
>>> [pr "" | pr <- runPrintor (satisfy isLower) 'X'] :: [String]
[]
>>> [pr "yz" | pr <- runPrintor (satisfy isLower) 'x'] :: [String]
["xyz"]
  • satisfied f: 조건 f를 만족하는 값의 부분집합을 나타내는 부분 동형입니다. 원문은 이것을 PartialIso의 대표적인 예라고 부릅니다. 두 방향 모두 같은 함수 satiate를 씁니다. 만족하면 그대로 Just a, 아니면 Nothing입니다. 즉 "조건을 만족하는 값에서만 정의된 항등 함수"입니다.
  • partialIso: 두 부분 함수로 PartialIso를 만드는 스마트 생성자입니다. 원문에는 정의가 없습니다.
  • satisfy f: 아무 토큰 하나(anyToken)를 satisfied f로 걸러, 조건을 만족하는 토큰 하나를 다루는 프린터-파서를 만듭니다.
  • 예제: isLower는 소문자인지 검사합니다. 파서는 "xyz"의 'x'를 받아들이고 "X"의 'X'를 거부합니다. 프린터는 'X'를 출력하지 않고 'x'는 출력합니다. 프린터 쪽의 검사는 입력 쪽 함수가, 파서 쪽의 검사는 출력 쪽 함수가 합니다.

이 쪽의 큰 그림

이 쪽에서 만든 네 조합자는 모두 같은 일을 합니다. 옵틱에서 탐침으로 함수 쌍을 꺼내 프로펑터의 두 쪽에 붙입니다. 차이는 함수가 실패할 수 있는 정도이고, 그에 따라 p에 요구하는 능력이 늘어납니다.

조합자 받는 옵틱 p에 대한 제약 함수 쌍의 성격
mapIso Iso Profunctor 양쪽 모두 전함수
(>?) Prism Choice 맞추기가 실패할 수 있음(프린터 쪽)
(?<) 뒤집은 Prism Cochoice 맞추기가 실패할 수 있음(파서 쪽)
(>?<) PartialIso Choice, Cochoice 양쪽 모두 실패할 수 있음

글의 목표에 비추어 보면, 이 쪽으로 "한 정의가 두 방향에서 각자 알맞은 함수를 쓰는" 장치가 완성되었습니다. 이제 남은 것은 토큰 하나를 넘어 여러 토큰을 차례로 잇는 방법(5쪽)과, 여러 경우 중 하나를 고르고 반복하는 방법(6쪽)입니다.

정리

  • 옵틱은 구조의 일부를 읽고 고치고 맞추어 보는 일을 값으로 만든 것이며, 이 글은 그중 "맞추기와 만들기의 쌍", 즉 패턴을 나타내는 옵틱을 씁니다.
  • Iso 같은 케밋 표현은 forall p f.로 다형적인 함수입니다. 쓰는 쪽이 p와 f를 골라 읽기(view), 고치기(over), 거꾸로 만들기(review), 프린터-파서 변환(mapIso) 같은 서로 다른 동작을 얻습니다.
  • Exchange는 다형적인 동형에 넣어 그 안의 두 함수를 꺼내는 탐침입니다. withIso, from, mapIso가 이 탐침 위에 서 있습니다.
  • 구체, 케밋, 순수 프로펑터 표현은 서로 오갈 수 있는 동등한 표현이며, 케밋 표현에서 p = (->)를 고르면 반 라르호번 렌즈가 됩니다. lens는 이 호환성 때문에 f가 있는 표현을 쓰고, 원문은 프린터-파서에 바로 맞는 p a b -> p s t 모양을 꺼내 씁니다.
  • 프리즘(Choice, >?), 코프리즘(Cochoice, ?<), 부분 동형(dimapMaybe, >?<)은 실패할 수 있는 패턴을 프린터-파서에 적용합니다. 그 결과로 정해진 글자 하나를 다루는 token과 조건을 만족하는 글자 하나를 다루는 satisfy를 얻습니다.

Optics & Patterns

Optics are an ongoing field of advanced study in applied category theory and computer science which makes giving an exact definition challenging. In Haskell, research into "semantic editor combinators" led to noticing the composability of such combinators as record field accessors or data constructor patterns, leading to the discovery of optics. Much can and has been written about lenses, traversals & prisms that can't be written about here. The most important thing from our perspective will be the relation between profunctors and optics. Moreover the variety of optics that we will be most interested in will represent "patterns".

Let's start with two definitions of isomorphism optics. Isomorphism optics are pairs of functions, one in a "backwards" direction and one in a "forwards" direction, like a newtype constructor pattern.

data Exchange a b s t = Exchange (s -> a) (b -> t)

type Iso s t a b = forall p f.
  (Profunctor p, Functor f) => p a (f b) -> p s (f t)

The Exchange type is a "concrete representation" of the isomorphism optic and Iso is a "Kmett representation". They're equivalent and you can convert between representations. The lens library uses Kmett's representation as it provides a convenient specialization to a "Van Laarhoven representation" when p is (->). However, a pure profunctorial representation (without f), which is also equivalent, can be simpler. We can observe the profunctorial representation with a combinator.

mapIso :: Profunctor p => Iso s t a b -> p a b -> p s t
mapIso pattern = withIso pattern dimap

Now, let's move on to our next optic example, prisms. Prisms encode exhaustive patterns. To encode them we first need the Choice interface.

class Profunctor p => Choice p where
  left' :: p a b -> p (Either a c) (Either b c)
  right' :: p a b -> p (Either c a) (Either c b)

Now we can define a concrete prism type consisting of a pair of functions, a constructor and destructor for a pattern match, as well as defining the abstract Prism type.

data Market a b s t = Market (b -> t) (s -> Either t a)

type Prism s t a b = forall p f.
  (Choice p, Applicative f) => p a (f b) -> p s (f t)

type Prism' s a = Prism s s a a

The Applicative f in the definition of Prism makes it so that every Prism is automatically a Traversal. But again, for our purpose we're most interested in the pure profunctor representation which we can observe with a new combinator.

(>?) :: Choice p => Prism s t a b -> p a b -> p s t
(>?) pattern = withPrism pattern $ \f g -> dimap g (either id f) . right'

It turns out that both Parsor and Printor have Choice instances so that (>?) becomes both a parser combinator and a printer combinator. The lens library provides Template Haskell functions to make Prisms from the pattern constructors of algebraic datatypes. Or we can construct Prisms like only from a pair of functions using the prism' or prism smart constructors.

only :: Eq a => a -> Prism' a ()
only a = prism' (\() -> a) $ guard . (a ==)

Next, we may consider the dual to prisms, coprisms. If Prisms encode pattern matching, then coprisms encode pattern filtering. To encode them we first need the Cochoice interface, which we get from Choice by reversing arrows.

class Profunctor p => Cochoice p where
  unleft :: p (Either a c) (Either b c) -> p a b
  unright :: p (Either c a) (Either c b) -> p a b

Actually, we don't really need to encode coprisms. Since they are dual to prisms we can just shuffle the indices of the Prism type to encode coprisms and observe the pure profunctor representation with our next combinator.

(?<) :: Cochoice p => Prism b a t s -> p a b -> p s t
(?<) pattern = withPrism pattern $ \f g -> unright . dimap (either id f) g

token :: (Cochoice p, Eq c, Tokenized c c p) => c -> p () ()
token c = only c ?< anyToken

>>> runParsor (token 'x') "xyz" :: [((),String)]
[((),"yz")]
>>> [pr "yz" | pr <- runPrintor (token 'x') ()] :: [String]
["xyz"]

Both Parsor and Printor have Cochoice instances too. We will call a profunctor with both Choice & Cochoice instances a "partial profunctor". Partial profunctors support a combinator dimapMaybe.

dimapMaybe
  :: (Choice p, Cochoice p)
  => (s -> Maybe a) -> (b -> Maybe t)
  -> p a b -> p s t
dimapMaybe f g =
  let
    m2e h = maybe (Left ()) Right . h
    fg = dimap (>>= m2e f) (>>= m2e g)
  in
    unright . fg . right'

We can turn the pair of partial functions into another optic, partial isomorphisms.

data PartialExchange a b s t = PartialExchange (s -> Maybe a) (b -> Maybe t)

type PartialIso s t a b = forall p f.
  ( Choice p, Cochoice p
  , Applicative f, Filterable f
  ) => p a (f b) -> p s (f t)

type PartialIso' s a = PartialIso s s a a

You may not have seen the Filterable interface before. It is a very simple interface from the witherable library that generalizes the list functions catMaybes, filter and mapMaybe.

class Functor f => Filterable f where
  mapMaybe :: (a -> Maybe b) -> f a -> f b
  mapMaybe f = catMaybes . fmap f

  catMaybes :: f (Maybe a) -> f a
  catMaybes = mapMaybe id

  filter :: (a -> Bool) -> f a -> f a
  filter f = mapMaybe $ \a -> if f a then Just a else Nothing

Filterable is dual to the Alternative interface, which can be seen by comparing the signature of catMaybes to optional.

optional :: Alternative f => f a -> f (Maybe a)

We can now turn dimapMaybe into a combinator on PartialIsos.

(>?<) :: (Choice p, Cochoice p) => PartialIso s t a b -> p a b -> p s t

The prototypical example of a PartialIso is a subset which has satisfied a predicate which we can construct from a pair of functions with the smart constructor partialIso.

satisfied :: (a -> Bool) -> PartialIso' a a
satisfied f = partialIso satiate satiate where
  satiate a = if f a then Just a else Nothing

satisfy :: (Choice p, Cochoice p, Tokenized c c p) => (c -> Bool) -> p c c
satisfy f = satisfied f >?< anyToken

>>> runParsor (satisfy isLower) "xyz" :: [(Char,String)]
[('x',"yz")]
>>> runParsor (satisfy isLower) "X" :: [(Char,String)]
[]
>>> [pr "" | pr <- runPrintor (satisfy isLower) 'X'] :: [String]
[]
>>> [pr "yz" | pr <- runPrintor (satisfy isLower) 'x'] :: [String]
["xyz"]
