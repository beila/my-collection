Distributors 해설 5/8: 모노이드 프로펑터 (Monoidal Profunctors)

해설 대상 원문: Eitan Chatav, “Distributors — Unifying Parsers, Printers & Grammars”

검토일: 2026-11-21

이 쪽은 여덟 쪽 시리즈의 다섯 번째 쪽이며, 원문의 "Monoidal Profunctors" 절을 다룹니다. 4쪽까지 만든 부품(anyToken, token, satisfy)은 모두 토큰(token) 하나를 다룹니다. 실제 구문은 여러 요소가 차례로 이어진 것이므로, 프린터-파서(printer-parser) 두 개를 이어 붙이는 방법이 필요합니다. 이 절은 하스켈에서 애로우(arrow)가 걸어온 길을 되짚으며 "프로펑터(profunctor)에서 Applicative에 해당하는 것"을 찾고, 그것이 모노이드 프로펑터(monoidal profunctor)라는 결론에 이릅니다. 그 결과로 순차 조합자(sequencing combinator) oneP, >*<, >*, *<와, 문자열 리터럴 자체를 프린터-파서로 쓰게 해 주는 IsString 인스턴스를 얻습니다.

4쪽까지에서 가져올 것

  • 프로펑터 p a b는 반변(contravariant)인 왼쪽 자리에서 받고 공변(covariant)인 오른쪽 자리에서 냅니다. lmap은 입력 쪽만 바꿉니다. Parsor는 오른쪽만, Printor는 왼쪽만 씁니다(2쪽).
  • Printor의 결과는 자기 함수(endofunction) s -> s이며, 두 출력은 함수 합성으로 이어집니다(2쪽).
  • token c :: p () ()는 정해진 토큰 c 하나를 다루고, Cochoice를 요구합니다(4쪽).
  • Applicative의 pure, <*>, <$>, *>, <*는 1쪽에서 작은 파서 예제와 함께 처음부터 설명했습니다. 느슨한 모노이드 펑터(lax monoidal functor)의 unit :: f ()와 (⋆) :: f a -> f b -> f (a, b)도 1쪽에서 이름만 소개했습니다.
  • forall은 "모든 타입에 대해"라는 뜻이며, 4쪽에서 값의 타입 안에 쓰이는 경우(랭크-N 타입)를 설명했습니다. 이 쪽에서는 제약 안에 쓰이는 경우를 봅니다.

애로우: 프로펑터보다 먼저 온 인터페이스

원문은 프로펑터가 하스켈에 들어오기 전에 Arrow라는 인터페이스가 먼저 있었다고 말합니다. John Hughes는 Generalizing Monads to Arrows에서 이 인터페이스를 소개했고, 그 동기가 된 예가 파서였습니다. 참고로 이 논문의 원래 제목은 영국식 철자인 "Generalising Monads to Arrows"이며(Science of Computer Programming 37권, 2000년), 원문은 미국식 철자로 적었습니다.

애로우(arrow)는 "일반화된 함수"입니다. base 라이브러리의 Control.Arrow 모듈에 있는 Arrow 클래스는 대략 다음 능력을 제공합니다.

  • arr :: (b -> c) -> a b c: 보통 함수를 애로우로 만듭니다.
  • (>>>): 두 애로우를 차례로 합성합니다.
  • first :: a b c -> a (b, d) (c, d): 쌍의 첫 원소에만 애로우를 적용하고 두 번째 원소는 통과시킵니다.

함수 화살표 (->)가 가장 단순한 애로우입니다. 다음은 원문 코드가 아닌 예시입니다. 이 쪽의 예시는 모두 원문의 정의를 최소한으로 다시 만든 코드로 GHC 9.10.3에서 실행한 결과입니다.

>>> first (+1) (1, "x")
(2,"x")
>>> (show >>> length) 123
3

애로우 타입 a b c도 프로펑터처럼 매개변수가 둘이며, b를 받아 c를 냅니다. 그래서 애로우와 프로펑터는 가까운 관계입니다.

인용문 읽기

원문은 McBride와 Paterson의 Applicative Programming with Effects에서 애로우에 관한 두 구절을 인용합니다.

By fixing the first argument of an arrow type, we obtain an applicative functor. .. Indeed one of Hughes’s motivations was the parsers of Swierstra and Duponcheel (1996). It may turn out that applicative functors are more convenient for applications of the second class

첫 구절. 애로우 타입 a b c에서 첫 매개변수 b를 고정하면 a b는 매개변수 하나짜리 타입 생성자가 되고, 이것은 출력 c에 대해 Applicative가 됩니다. pure c는 입력을 무시하고 c를 내는 애로우이고, f <*> g는 같은 입력을 두 애로우에 나누어 주고 결과를 적용합니다. base에는 이것을 그대로 구현한 WrappedArrow가 있습니다(instance Arrow a => Applicative (WrappedArrow a b)). 원문 코드가 아닌 예시입니다.

>>> unwrapArrow ((,) <$> WrapArrow (+1) <*> WrapArrow show) 5
(6,"5")

같은 입력 5가 (+1)과 show에 모두 들어가고, 두 결과가 쌍으로 묶였습니다. 이 모양을 기억해 두십시오. 아래에서 볼 Printor의 <*>가 정확히 같은 일을 합니다.

두 번째 구절과 생략된 문장. 인용 중간의 ..는 원래 논문의 문장 하나를 건너뛴 표시입니다. 건너뛴 문장은 애로우가 모나드보다 일반적이라는 점을 활용한 응용이 대부분 두 부류였다고 말합니다. 첫째는 여러 형태의 프로세스(process)이고, 둘째는 구성 요소의 **정적 성질을 계산하는 것(computing static properties of components)**입니다. 그러므로 인용문의 "the second class"는 이 두 번째 부류, 즉 정적 분석을 가리킵니다. 이 문맥이 없으면 인용문을 읽기 어렵습니다.

Swierstra와 Duponcheel의 1996년 파서("Deterministic, error-correcting combinator parsers")는 파서를 실행하기 전에 문법(grammar)의 구조를 미리 분석해서 효율과 오류 복구를 얻었습니다. 모나드의 >>=는 다음 계산을 앞 계산의 결과에 따라 정하므로, 실행하기 전에는 구조를 볼 수 없습니다. 반면 Applicative로 쓴 계산은 구조가 고정되어 있어서 미리 들여다볼 수 있습니다. McBride와 Paterson이 "이런 응용에는 Applicative가 더 편할 수 있다"고 말한 이유입니다.

이 이야기는 이 글의 목표와도 이어집니다. 7쪽에서는 같은 문법 기술에서 파서와 프린터뿐 아니라 문법 문서도 만들어 냅니다. 문법 문서를 만드는 일은 실행이 아니라 구조를 들여다보는 정적 분석입니다.

빠진 칸 찾기

원문은 애로우가 이미 Applicative이면서 동시에 이미 (Strong) 프로펑터라고 말합니다. 강한 프로펑터(strong profunctor)는 profunctors 패키지의 Strong 클래스로, first' :: p a b -> p (a, c) (b, c)를 가진 프로펑터입니다. 애로우의 first와 같은 모양이며, 4쪽의 Choice가 Either에 대해 하는 일을 쌍에 대해 합니다. 원문은 애로우와 프로펑터의 관계가 모나드와 펑터의 관계와 같다고 말하고, 다음 표의 빈칸을 찾자고 합니다.

(Type -> Type) -> Constraint (Type -> Type -> Type) -> Constraint
Functor Profunctor
Applicative ???
Monad Arrow

표의 제목 읽기. Type은 값이 있는 보통 타입들의 종류(kind)입니다. Type -> Type은 Maybe나 []처럼 타입 하나를 받아 타입을 만드는 타입 생성자의 종류이고, Type -> Type -> Type은 (->), Either, Parsor s f처럼 타입 두 개를 받는 타입 생성자의 종류입니다. -> Constraint는 그런 타입 생성자에 대한 클래스라는 뜻입니다. 즉 왼쪽 열은 매개변수 하나짜리 타입에 대한 클래스, 오른쪽 열은 매개변수 두 개짜리 타입에 대한 클래스입니다.

표의 행 읽기. 왼쪽 열에서 Functor, Applicative, Monad는 차례로 능력이 강해집니다. 오른쪽 열에서는 Profunctor가 Functor에, Arrow가 Monad에 대응합니다. 이것은 엄밀한 정리라기보다 비유입니다. 예를 들어 Arrow는 프로펑터 구조 외에 >>> 합성도 요구합니다. 빈칸 ???는 "프로펑터에서 Applicative에 해당하는 것", 즉 두 프로펑터 값을 나란히 이어 붙이는 능력입니다.

원문은 이 인터페이스가 곱 프로펑터(product profunctor) 또는 (느슨한) 모노이드 프로펑터(lax monoidal profunctor)라는 이름으로 불려 왔다고 말합니다. product-profunctors 패키지의 ProductProfunctor 클래스가 한 예이며, p () () 값과 p a b -> p a' b' -> p (a, a') (b, b') 연산을 가집니다. 그리고 원문은 이 인터페이스가 인용문이 암시한 대로 제약 동의어(constraint synonym) 하나와 동등하다고 말합니다. 그 제약 동의어를 읽으려면 새 문법이 필요합니다.

필요한 문법: 제약 동의어와 양화 제약

제약 동의어

Show a나 Applicative f 같은 제약(constraint)도 하스켈에서는 일종의 타입이며, 그 종류는 Constraint입니다. ConstraintKinds 확장을 쓰면 여러 제약을 묶은 것에 type으로 이름을 붙일 수 있습니다. 이것을 제약 동의어(constraint synonym)라고 부릅니다. 원문 코드가 아닌 예시입니다.

type ShowNum a = (Show a, Num a)

double :: ShowNum a => a -> String
double x = show (x + x)

ShowNum a라고 쓰면 (Show a, Num a)라고 쓴 것과 같습니다. 새 클래스를 만드는 것이 아니라 기존 제약에 별명을 붙이는 것입니다. ConstraintKinds는 GHC2021에 들어 있습니다.

양화 제약

양화 제약(quantified constraint)은 제약 안에 forall을 쓰는 것입니다.

forall x. Applicative (p x)

이것은 "모든 타입 x에 대해 p x가 Applicative이다"라는 하나의 제약입니다. 4쪽에서는 forall이 값의 타입 안에서 "쓰는 쪽이 고른다"는 뜻으로 쓰였는데, 여기서는 제약 안에서 "어떤 x를 골라도 성립한다"는 뜻으로 쓰입니다. GHC 사용자 안내서는 양화 제약을 "지역적인 인스턴스 선언(a local instance declaration)처럼" 생각하라고 설명합니다(GHC 사용자 안내서: Quantified constraints). 이 기능은 QuantifiedConstraints 확장이며 GHC 8.6.1부터 쓸 수 있고, GHC2021에는 들어 있지 않습니다.

이것이 왜 필요할까요. 프린터-파서 p a b에서 Applicative는 출력 쪽 b에 대해서만 말할 수 있습니다. Applicative는 매개변수 하나짜리 타입에 대한 클래스이므로 p x처럼 입력 쪽 x를 고정해야 적용할 수 있습니다. 그런데 고정할 x는 하나가 아니라 모든 입력 타입이어야 합니다. forall x.가 바로 그 요구를 적습니다.

코드 읽기: Monoidal

type Monoidal p = (Profunctor p, forall x. Applicative (p x))

"p가 Monoidal이다"는 "p는 프로펑터이고, 입력 타입을 무엇으로 고정하든 출력 쪽에 대해 Applicative이다"라는 뜻입니다. 원문은 이것이 전혀 새로운 것이 아니라 두 인터페이스의 결합일 뿐이며, 양화 제약 확장 덕분에 가능해졌다고 강조합니다. 위의 첫 인용 구절, 즉 "애로우의 첫 인자를 고정하면 Applicative"를 프로펑터 일반으로 넓힌 것입니다.

짧은 주의. GHC 9.10.3으로 확인해 보면, GHC는 양화 제약이 들어 있는 이런 제약 동의어를 받아들이려면 ImpredicativeTypes 확장도 요구합니다. distributors 패키지는 ImpredicativeTypes, QuantifiedConstraints, UndecidableSuperClasses 등을 기본 확장으로 켜 둡니다. 원문의 코드 조각만 그대로 옮겨 컴파일할 때 참고할 점입니다.

Parsor와 Printor의 Applicative 인스턴스

원문은 Parsor와 Printor가 Applicative 인스턴스를 가지므로 이 인터페이스를 지원한다고 말하고, 두 인스턴스를 보여 줍니다.

instance Monad f => Applicative (Parsor s f a) where
  pure b = Parsor (\str -> return (b,str))
  Parsor x <*> Parsor y = Parsor $ \str -> do
    (f, str') <- x str
    (a, str'') <- y str'
    return (f a, str'')

instance Applicative f => Applicative (Printor s f a) where
  pure _ = Printor (\_ -> pure id)
  Printor p <*> Printor q = Printor (\a -> (.) <$> p a <*> q a)

파서 인스턴스

  • 인스턴스 머리 Applicative (Parsor s f a): s, f, 그리고 입력 쪽 a를 고정하고, 마지막 매개변수인 결과 b에 대해 Applicative입니다. 인스턴스가 아무 a에 대해서나 선언되어 있으므로 forall x. Applicative (Parsor s f x)가 성립합니다.
  • Monad f =>: 두 파서를 차례로 실행하려면 첫 파서가 남긴 스트림(stream)을 두 번째 파서에 넘겨야 하고, 이것은 컨테이너 f 안에서 do 표기로 결과를 꺼내는 일이므로 Monad f가 필요합니다. f = []이면 리스트 모나드이므로 가능한 모든 조합이 나옵니다.
  • pure b: 스트림을 읽지 않고 (b, str)를 돌려줍니다.
  • Parsor x <*> Parsor y: x를 실행해 함수 f와 남은 스트림 str'을 얻고, y를 str'에서 실행해 값 a와 str''을 얻은 뒤 (f a, str'')를 돌려줍니다. 여기서 f는 파싱 결과로 나온 함수 값이며 컨테이너 f와는 다른 것입니다. 1쪽에서 리스트 컴프리헨션으로 쓴 Parser의 <*>와 같은 일을 do 표기로 적었습니다.

프린터 인스턴스

  • 인스턴스 머리 Applicative (Printor s f a): 입력 a를 고정하고 쓰이지 않는 b에 대해 Applicative입니다. 컨테이너에는 Applicative f만 요구합니다.
  • pure _ = Printor (\_ -> pure id): 값을 무시하고 아무것도 출력하지 않습니다. 출력 결과가 항등 함수 id이므로 남은 스트림이 그대로 남습니다.
  • Printor p <*> Printor q = Printor (\a -> (.) <$> p a <*> q a): 같은 입력 a를 두 프린터에 모두 줍니다. 위의 WrappedArrow 예와 같은 모양입니다. p a와 q a는 각각 f (s -> s)이고, (.) <$> p a <*> q a는 컨테이너 f 안에서 두 자기 함수를 합성합니다. 합성 pe . qe를 남은 스트림에 적용하면 qe가 먼저 붙고 그 앞에 pe가 붙으므로, 최종 출력에서는 p의 출력이 q의 출력 앞에 옵니다. 2쪽에서 본 ShowS 합성과 같습니다.
  • 원문은 보여 주지 않지만 Printor s f a의 Functor 인스턴스도 있어야 합니다. 오른쪽 매개변수가 쓰이지 않으므로 fmap은 함수를 무시하고 프린터를 그대로 돌려주면 됩니다.

순차 조합자

원문은 이제 Monoidal 프로펑터에 대한 순차 조합자(sequencing combinator)를 정의합니다.

oneP :: Monoidal p => p () ()
oneP = pure ()

(>*<) :: Monoidal p => p a b -> p c d -> p (a,c) (b,d)
x >*< y = (,) <$> lmap fst x <*> lmap snd y

(>*) :: Monoidal p => p () c -> p a b -> p a b
x >* y = lmap (const ()) x *> y

(*<) :: Monoidal p => p a b -> p () c -> p a b
x *< y = x <* lmap (const ()) y

oneP

oneP :: p () ()는 아무 일도 하지 않는 프린터-파서입니다. 프린터로는 ()를 받아 아무것도 출력하지 않고, 파서로는 아무것도 읽지 않고 ()를 돌려줍니다. 1쪽의 느슨한 모노이드 펑터에서 unit :: f ()에 해당합니다.

>*<: 쌍 다루기

x >*< y는 x :: p a b와 y :: p c d로 쌍을 다루는 p (a,c) (b,d)를 만듭니다. 1쪽의 (⋆) :: f a -> f b -> f (a, b)를 입력 쪽까지 넓힌 것입니다. 정의를 조각내어 읽겠습니다.

  • lmap fst x :: p (a,c) b: 입력으로 쌍을 받아 첫 원소를 x에 넘깁니다.
  • lmap snd y :: p (a,c) d: 입력으로 쌍을 받아 두 번째 원소를 y에 넘깁니다.
  • 이제 두 값의 입력 타입이 (a,c)로 같으므로 Applicative (p (a,c))를 쓸 수 있습니다. (,) <$> ... <*> ...는 두 결과를 쌍으로 묶습니다.

두 방향에서의 동작은 다음과 같습니다.

  • 프린터: 쌍 (a, c)를 받아 a를 x로, c를 y로 차례로 출력합니다. Printor의 <*>가 같은 입력을 두 프린터에 주고, lmap fst와 lmap snd가 각자 필요한 원소를 고릅니다.
  • 파서: x로 b를 읽고 이어서 y로 d를 읽은 뒤 (b, d)를 돌려줍니다. 입력 쪽 lmap은 파서에게 아무 영향이 없습니다.

>*와 *<: 구분자 붙이기

x >* y에서 x :: p () c는 주로 괄호나 쉼표 같은 구분자입니다. token '('처럼 p () () 타입이 전형적입니다.

  • lmap (const ()) x: 입력이 무엇이든 ()로 바꾸어 x에 줍니다. 그래서 x를 p a c로 쓸 수 있습니다.
  • ... *> y: Applicative의 *>로 x를 먼저 실행하고 y의 결과만 남깁니다.

프린터로는 구분자를 먼저 출력하고 값 a를 y로 출력합니다. 파서로는 구분자를 읽어 결과를 버리고 y의 결과를 돌려줍니다. *<는 같은 일을 오른쪽에서 합니다. 연산자에서 *가 붙은 쪽이 "버려지는" 쪽이고 >나 <가 가리키는 쪽이 "남는" 쪽이라고 기억하면 됩니다. Applicative의 *>, <*와 화살표 방향은 같지만 이름이 다른 이유는, 구분자를 p a b 옆에 놓기 위해 lmap (const ())를 덧붙였기 때문입니다.

연산자 우선순위에 관한 짧은 주의

원문은 이 연산자들의 결합 방향과 우선순위(fixity)를 적지 않습니다. 현재 distributors 패키지의 소스는 infixr 5 >*<, infixl 6 >*, *<로 선언합니다. 이를 따르면 >*와 *<가 >*<보다 먼저 묶이므로, 예를 들어 token '(' >* anyToken *< token ')'는 (token '(' >* anyToken) *< token ')'로 읽힙니다. 아래 예제와 7쪽의 문법 예제는 이 우선순위를 전제로 합니다.

값이 흐르는 모습

다음은 원문 코드가 아닌 예시입니다.

>>> runParsor (anyToken >*< anyToken :: Parsor String [] (Char,Char) (Char,Char)) "xyz"
[(('x','y'),"z")]
>>> [pr "!" | pr <- runPrintor (anyToken >*< anyToken :: Printor String [] (Char,Char) (Char,Char)) ('a','b')]
["ab!"]
>>> runParsor (token '(' >* anyToken *< token ')' :: Parsor String [] Char Char) "(x)rest"
[('x',"rest")]
>>> [pr "" | pr <- runPrintor (token '(' >* anyToken *< token ')' :: Printor String [] Char Char) 'q']
["(q)"]

같은 정의 token '(' >* anyToken *< token ')'가 파서로는 괄호 안의 글자를 꺼내고, 프린터로는 글자를 괄호로 감싸 출력합니다. 함수 화살표 (->)도 Monoidal입니다. (->) x는 잘 알려진 "같은 입력을 나누어 주는" Applicative이기 때문입니다. 그래서 다음도 동작합니다.

>>> (show >*< not) (3, True)
("3",False)

"동등하다"는 말의 반대 방향

원문은 Monoidal이 곱 프로펑터와 동등하다고 말했습니다. 위에서는 pure와 <*>로 oneP와 >*<를 만들었습니다. 반대로 oneP와 >*<만으로 pure와 <*>를 되찾을 수도 있습니다. 다음은 원문 코드가 아닌 예시입니다.

pureFromOne :: Monoidal p => b -> p a b
pureFromOne b = dimap (const ()) (const b) oneP

apFromProd :: Monoidal p => p a (b -> c) -> p a b -> p a c
apFromProd f x = dimap (\a -> (a, a)) (\(g, y) -> g y) (f >*< x)

pureFromOne은 아무것도 하지 않는 oneP의 입력을 버리고 출력을 b로 바꿉니다. apFromProd는 입력을 복제해 두 프린터-파서에 나누어 주고, 두 결과(함수와 값)를 적용합니다.

>>> pureFromOne 'k' 99
'k'
>>> apFromProd (+) (*10) 2
22
>>> runParsor (apFromProd (fmap (,) anyToken) anyToken :: Parsor String [] Char (Char,Char)) "ab"
[(('a','b'),"")]

apFromProd (+) (*10) 2는 p = (->)에서 2 + 2*10 = 22입니다. 이렇게 두 묶음의 연산이 서로를 정의할 수 있으므로 같은 표현력을 가집니다. 1쪽에서 Applicative와 느슨한 모노이드 펑터가 동등하다고 한 것과 같은 이야기이며, 패키지의 Data.Profunctor.Monoidal 문서도 "Profunctor가 Applicative이기도 한 것과 동등하다"고 적습니다.

이디엄 스타일 그대로

원문은 Applicative 파싱의 이디엄 스타일(idiom style)을 Monoidal 파싱에서도 그대로 쓸 수 있다고 말합니다. 대응 관계는 다음과 같습니다.

Applicative 파서 Monoidal 프린터-파서 하는 일
<$> >?< (4쪽) 결과 바꾸기
<*> >*< 차례로 잇기
*> >* 왼쪽 결과 버리기
<* *< 오른쪽 결과 버리기

1쪽의 파서 charP '(' *> item <* charP ')'와 위의 token '(' >* anyToken *< token ')'를 비교하면 모양이 거의 같습니다. 차이는 두 가지입니다.

  1. <$> 대신 >?<를 씁니다. <$>는 함수 하나로 결과를 바꾸는데, 프린터는 그 함수의 역방향이 필요합니다. 그래서 함수 쌍을 담은 부분 동형(partial isomorphism)을 받는 >?<를 씁니다.
  2. <*> 대신 >*<를 씁니다. <*>는 "함수를 파싱하고 값을 파싱해 적용"하는데, 적용된 결과에서 원래 함수와 값을 되찾을 방법이 없으므로 프린터로 되돌릴 수 없습니다. >*<는 결과를 쌍으로 남기므로 프린터가 쌍을 다시 나눌 수 있습니다. 쌍을 원하는 자료형으로 바꾸는 일은 >?<와 부분 동형에 맡깁니다.

즉 Monoidal의 이디엄 스타일은 "어떤 함수도 되돌릴 수 있게" 연산을 고른 이디엄 스타일입니다.

tokens와 IsString: 문자열 리터럴을 프린터-파서로

필요한 문법: IsString과 OverloadedStrings

하스켈에서 문자열 리터럴 "abc"는 보통 String 타입입니다. OverloadedStrings 확장을 켜면 "abc"는 fromString "abc"라는 뜻이 되고, Data.String 모듈의 IsString 클래스 인스턴스가 있는 어떤 타입이든 될 수 있습니다.

class IsString a where
  fromString :: String -> a

Text나 ByteString 리터럴을 쓸 때 흔히 쓰는 기능입니다. 원문은 이 기능으로 문자열 리터럴 자체를 프린터-파서로 만듭니다.

코드 읽기

tokens :: (Cochoice p, Monoidal p, Eq c, Tokenized c c p) => [c] -> p () ()
tokens [] = oneP
tokens (c:cs) = token c *> tokens cs

instance (Alternative f, Filterable f, Monad f, Cons s s Char Char)
  => IsString (Parsor s f () ()) where
    fromString = tokens

instance (Applicative f, Cons s s Char Char)
  => IsString (Printor s f () ()) where
    fromString = tokens

>>> :set -XOverloadedStrings
>>> runParsor "abc" "abcxyz" :: [((),String)]
[((),"xyz")]
>>> [pr "xyz" | pr <- runPrintor "abc" ()] :: [String]
["abcxyz"]

tokens. 토큰 목록을 받아 그 토큰들을 차례로 다루는 p () ()를 만듭니다. 빈 목록이면 아무것도 하지 않는 oneP이고, 아니면 첫 토큰을 token c로 다루고 나머지를 재귀로 다룹니다. 두 값이 모두 p () ()이므로 Applicative의 *>를 그대로 씁니다. 결국 tokens "abc"는 token 'a' *> token 'b' *> token 'c' *> oneP와 같습니다. 제약에 Cochoice p가 있는 이유는 token이 4쪽의 (?<)를 쓰기 때문입니다.

두 IsString 인스턴스. Parsor s f () ()와 Printor s f () ()에 fromString = tokens를 줍니다. 스트림 s의 토큰이 Char여야 하므로 Cons s s Char Char를 요구합니다. 파서 쪽 제약은 anyToken의 Alternative f, 파서 Cochoice의 Filterable f, 파서 Applicative의 Monad f를 모은 것입니다. 프린터 쪽은 Applicative f만 요구하므로, 정해진 문자열을 출력하는 일은 실패하지 않는 망라적(exhaustive)인 출력입니다. 인스턴스 머리에 구체 타입 ()가 들어가므로 FlexibleInstances가 필요합니다(3쪽).

예제 읽기. :set -XOverloadedStrings는 GHCi에서 확장을 켜는 명령입니다. 그 뒤로 runParsor "abc" "abcxyz"의 첫 "abc"는 문자열이 아니라 프린터-파서 Parsor String [] () ()이고, 두 번째 "abcxyz"는 입력 문자열입니다. 파서는 "abc"를 읽고 "xyz"를 남깁니다. 프린터는 ()를 받아 "abc"를 출력하고, 남은 스트림 "xyz" 앞에 붙여 "abcxyz"를 만듭니다. 맞지 않는 입력에서는 실패합니다. 원문 코드가 아닌 예시입니다.

>>> runParsor ("abc" :: Parsor String [] () ()) "abxyz"
[]

이 기능 덕분에 7쪽의 문법 정의에서는 "(", "|", "\\p{" 같은 구분자를 문자열 리터럴로 바로 쓸 수 있습니다.

모노클, 그리고 이 분야의 연구

원문은 이 절을 한 문장으로 마무리합니다. 더 많은 조합자를 추가할 수 있고, 모노이드 프로펑터는 잘 연구되어 왔으며, 그에 대응하는 옵틱인 모노클(monocle)은 트래버설(traversal)과 그레이트(grate) 옵틱과 관련이 있다는 것입니다.

  • 연구 예로 Oliveira, Jaskelioff, de Melo의 On Structuring Functional Programs with Monoidal Profunctors(MSFP 2022)가 있습니다. 이 논문은 모노이드 프로펑터를 프로펑터 범주의 모노이드로 다루고, 자유 모노이드 프로펑터와 옵틱과의 관계를 논의합니다.
  • distributors 패키지의 Control.Lens.Monocle 모듈은 모노클을 forall p f. (Monoidal p, Applicative f) => p a (f b) -> p s (f t)로 정의합니다. 4쪽의 Iso, Prism과 같은 모양에서 p에 대한 제약만 Monoidal로 바뀐 것입니다. "모노클"이라는 이름은 패키지의 명명이며, 널리 확립된 용어인지는 확인되지 않았습니다.
  • 트래버설은 4쪽에서 본 "0개 이상의 부분에 초점을 맞추는" 옵틱입니다. 그레이트는 렌즈(lens)의 쌍대(dual)로 알려진 옵틱(optic)이며, 이 글의 이해에는 필요하지 않습니다.

이 쪽이 글의 목표에 기여하는 바

이 절로 프린터-파서를 차례로 이어 붙일 수 있게 되었습니다. 한 번의 정의 token '(' >* anyToken *< token ')'가 파서이자 프린터이고, 문자열 리터럴도 그대로 프린터-파서가 됩니다. 그러나 아직 "여러 경우 중 하나"를 고르는 방법과 "반복"하는 방법이 없습니다. 1쪽의 파서 조합자에서 <|>, many, some, optional이 하던 일입니다. 원문은 이것을 Monoidal과 같은 방식으로 풀 수 없다고 말하며, 6쪽에서 새로운 인터페이스 Distributor를 도입합니다.

정리

  • 애로우는 파서에서 영감을 받은 "일반화된 함수"이며, 첫 인자를 고정하면 Applicative가 됩니다. 원문은 이 관찰을 프로펑터로 넓혀 "프로펑터의 Applicative"를 찾습니다.
  • 그 답이 모노이드 프로펑터이며, 양화 제약 덕분에 type Monoidal p = (Profunctor p, forall x. Applicative (p x))라는 제약 동의어 하나로 쓸 수 있습니다.
  • Parsor의 <*>는 첫 파서가 남긴 스트림을 두 번째 파서에 넘기고(Monad f 필요), Printor의 <*>는 같은 입력을 두 프린터에 주고 출력 함수를 합성합니다.
  • oneP, >*<, >*, *<는 각각 "아무것도 하지 않기", "쌍을 차례로 다루기", "왼쪽 구분자 붙이기", "오른쪽 구분자 붙이기"이며, >?<와 함께 되돌릴 수 있는 이디엄 스타일을 이룹니다.
  • tokens와 IsString 인스턴스 덕분에 OverloadedStrings에서 문자열 리터럴 "abc"가 그 문자열을 파싱하고 출력하는 p () ()가 됩니다.
