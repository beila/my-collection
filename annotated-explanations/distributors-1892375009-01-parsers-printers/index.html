문제: 파서와 프린터를 따로 쓰면 생기는 일

파서(parser)는 텍스트를 읽어서 값을 만듭니다. 예를 들어 "42"라는 문자열을 읽어 Int 값 42를 만드는 함수가 파서입니다. 프린터(printer)는 반대 방향으로, 값을 받아 텍스트를 씁니다. 42를 받아 "42"를 쓰는 함수가 프린터입니다. 설정 파일, JSON, 프로그래밍 언어의 소스 코드처럼 "사람이 읽고 쓰는 형식"을 다루는 프로그램은 대개 둘 다 필요합니다.

원문은 이 상황을 다음과 같이 지적합니다.

When designing a language syntax, programmers usually have to write both a parser and a printer, violating the Don't Repeat Yourself principle.

반복 금지 원칙(Don't Repeat Yourself, DRY)은 "같은 지식을 두 곳에 쓰지 말라"는 원칙입니다. 파서와 프린터는 같은 지식, 즉 "이 형식의 구문이 어떻게 생겼는가"를 서로 반대 방향으로 두 번 적은 것입니다. 두 번 적으면 둘이 서로 어긋날 수 있습니다. 예를 들어 새 구문 요소를 파서에만 추가하고 프린터에는 빠뜨리면, 프린터가 쓴 텍스트를 파서가 다시 읽지 못하거나, 반대로 파서가 받아들이는 값을 프린터가 쓰지 못하는 일이 생깁니다. 이상적으로는 모든 값 x에 대해 "x를 출력한 텍스트를 다시 파싱하면 x가 나온다"는 왕복(round-trip) 성질이 성립해야 하는데, 두 코드를 따로 관리하면 이 성질을 사람이 계속 지켜야 합니다.

이 글의 목표는 구문을 한 번만 기술하고, 그 하나의 기술에서 파서와 프린터를 모두 얻는 것입니다. 원문은 이렇게 두 방향으로 쓰이는 값 하나를 프린터-파서(printer-parser)라고 부릅니다. 7쪽에서는 같은 기술로 문법 문서까지 얻습니다.

배경 1: 파서 조합자와 Applicative/Alternative

원문 첫 문단은 McBride와 Paterson의 논문 Applicative Programming with Effects를 언급하며, 이 논문이 Applicative 인터페이스를 소개했고 이후 Alternative 인터페이스와 "파서 조합자(parser combinator)"에 관한 많은 연구를 낳았다고 말합니다. 이 글의 모든 쪽이 이 두 인터페이스를 전제로 하므로, 파서 코드에서 이들이 어떻게 쓰이는지 처음부터 정리하겠습니다.

성공 목록 파서

가장 단순한 파서 타입은 다음과 같습니다. 이 타입은 원문의 코드 블록에도 그대로 나옵니다.

newtype Parser a = Parser (String -> [(a,String)])

Parser a는 입력 문자열을 받아서 (결과, 남은 입력) 쌍의 목록을 돌려주는 함수입니다. 목록이 비어 있으면 파싱이 실패한 것이고, 원소가 여러 개이면 입력을 해석하는 방법이 여러 가지라는 뜻입니다. 이 방식을 성공 목록(list of successes) 방식이라고 부릅니다(Wadler의 1985년 논문 제목 "How to replace failure by a list of successes"에서 온 이름입니다). 이후의 쪽에서도 예제는 대부분 이 목록 방식으로 결과를 보여 줍니다.

이제부터 보이는 코드는 원문 코드가 아니라 개념을 보여 주기 위한 작은 예시입니다. 원문이 정의하지 않은 Applicative, Alternative 인스턴스를 직접 써서, 파서 조합자가 어떻게 동작하는지 보여 줍니다. 결과는 GHC 9.10.3에서 실행하여 확인했습니다.

runParser :: Parser a -> String -> [(a, String)]
runParser (Parser p) = p

-- Read one character.
item :: Parser Char
item = Parser $ \s -> case s of
  (c:cs) -> [(c, cs)]
  []     -> []

-- Read one character only when it is equal to c.
charP :: Char -> Parser Char
charP c = Parser $ \s -> case s of
  (x:xs) | x == c -> [(x, xs)]
  _               -> []

-- Read one decimal digit.
digitP :: Parser Char
digitP = Parser $ \s -> case s of
  (c:cs) | isDigit c -> [(c, cs)]
  _                  -> []

item은 첫 글자를 하나 읽습니다. charP 'a'는 첫 글자가 'a'일 때만 성공합니다. digitP는 첫 글자가 숫자일 때만 성공합니다. 이 세 개가 가장 작은 "부품"입니다. 여기와 아래에서 쓰는 isDigit, digitToInt, intToDigit은 Data.Char 모듈의 함수이고, Alternative 관련 이름은 Control.Applicative 모듈에서 옵니다.

Functor: 결과 바꾸기

fmap f p는 파서 p를 실행한 뒤 결과에 f를 적용하는 파서입니다. 남은 입력은 그대로 둡니다. 원문이 보여 주는 Functor Parser 인스턴스가 바로 이것이며, 아래에서 코드를 자세히 읽습니다.

>>> runParser (fmap digitToInt digitP) "7up"
[(7,"up")]
>>> runParser digitP "up"
[]

Applicative: 차례로 이어 붙이기

Applicative는 "여러 파서를 차례로 실행하고 결과를 모으는" 방법을 줍니다. 파서 코드에서 자주 보이는 연산자는 다섯 가지입니다.

  • pure x: 입력을 하나도 읽지 않고 결과 x로 성공합니다.
  • pf <*> px: 먼저 pf를 실행해 함수를 얻고, 남은 입력에 px를 실행해 값을 얻은 뒤, 함수를 값에 적용합니다.
  • f <$> p: fmap f p의 연산자 표기입니다.
  • p *> q: p와 q를 차례로 실행하고 q의 결과만 남깁니다.
  • p <* q: p와 q를 차례로 실행하고 p의 결과만 남깁니다.

예시 인스턴스는 다음과 같습니다. 리스트 컴프리헨션 안에서 pf가 남긴 입력 s'를 px에 넘기는 부분이 "차례로"의 핵심입니다.

instance Applicative Parser where
  pure x = Parser $ \s -> [(x, s)]
  Parser pf <*> Parser px = Parser $ \s ->
    [(f a, s'') | (f, s') <- pf s, (a, s'') <- px s']

이 연산자들을 한 줄에 이어 쓰는 방식을 이디엄 스타일(idiom style)이라고 부릅니다.

>>> runParser ((,) <$> item <*> item) "abc"
[(('a','b'),"c")]
>>> runParser (charP '(' *> item <* charP ')') "(x)!"
[('x',"!")]

첫 번째 예는 "글자 하나, 그다음 글자 하나를 읽어 쌍으로 묶기"입니다. (,) <$> item은 "글자를 읽어 그 글자를 첫 원소로 하는 쌍을 만드는 함수"를 결과로 내고, <*> item이 두 번째 글자를 읽어 그 함수에 넣습니다. 두 번째 예는 괄호를 읽되 결과에서는 버리고, 괄호 사이의 글자만 남깁니다. 화살표 모양 *>와 <*에서 화살표가 가리키는 쪽의 결과가 남는다고 기억하면 됩니다.

McBride와 Paterson은 pure f <*> u1 <*> ... <*> un을 ⟦f u1 ... un⟧처럼 쓰는 이디엄 괄호(idiom brackets) 표기도 제안했습니다. 같은 논문은 자료 구조 전체에 효과를 순회시키는 Traversable 인터페이스(traverse)도 소개했습니다. 이 둘은 이 글의 뒷부분에서 다시 쓰이지 않으므로 이름만 알아 두면 됩니다.

Alternative: 실패와 선택

Alternative는 "실패"와 "둘 중 하나"를 표현합니다.

  • empty: 항상 실패하는 파서입니다.
  • p <|> q: p로도 시도하고 q로도 시도합니다. 성공 목록 방식에서는 두 결과 목록을 이어 붙입니다.
  • many p: p를 0번 이상 반복합니다.
  • some p: p를 1번 이상 반복합니다.
  • optional p: p를 0번 또는 1번 적용하고, 결과를 Maybe로 감쌉니다.
instance Alternative Parser where
  empty = Parser (\_ -> [])
  Parser p <|> Parser q = Parser $ \s -> p s ++ q s
>>> runParser (charP 'a' <|> charP 'b') "bc"
[('b',"c")]
>>> runParser (empty :: Parser Char) "abc"
[]
>>> runParser (many digitP) "12a"
[("12","a"),("1","2a"),("","12a")]
>>> runParser (some digitP) "a"
[]
>>> runParser (optional (charP '-')) "-5"
[(Just '-',"5"),(Nothing,"-5")]

many digitP의 결과가 세 개인 점에 주목하십시오. 성공 목록 파서는 가능한 해석을 모두 돌려주므로 "숫자 두 개를 읽은 경우", "한 개를 읽은 경우", "하나도 읽지 않은 경우"가 모두 나옵니다. 이런 동작은 6쪽의 posDecInt 예제에서 다시 보게 됩니다.

이처럼 작은 파서를 연산자로 조합하여 큰 파서를 만드는 함수를 파서 조합자(parser combinator)라고 부릅니다. 원문이 말하는 "the usual Applicative and Alternative parser combinators"가 바로 이 연산자들입니다.

느슨한 모노이드 펑터 (이름만 미리)

원문은 McBride와 Paterson 논문의 마지막 부분이 Applicative를 범주론의 느슨한 모노이드 펑터(lax monoidal functor)와 같은 것으로 본다고 말합니다. 대략 말하면, 느슨한 모노이드 펑터는 pure와 <*> 대신 다음 두 연산을 가진 펑터입니다.

unit :: f ()
(⋆)  :: f a -> f b -> f (a, b)

unit은 "아무것도 하지 않는 계산"이고, (⋆)은 "두 계산을 차례로 하고 결과를 쌍으로 묶는 연산"입니다. 이 두 연산과 pure/<*>는 서로를 정의할 수 있어서 같은 표현력을 가집니다. 이 형태는 5쪽에서 oneP와 >*<라는 이름으로 프로펑터 버전이 되어 돌아옵니다. 참고로 논문 원문은 이 결론을 "strong lax monoidal functors"라고 쓰고, 이 내용은 결론 절 바로 앞인 7절에 있습니다. 원문의 "final section"이라는 표현은 이 마지막 기술 절을 가리키는 것으로 보입니다.

배경 2: Rendel과 Ostermann의 가역 구문 기술

원문 둘째 문단은 Tillmann Rendel과 Klaus Ostermann의 논문 Invertible Syntax Descriptions(Haskell Symposium 2010)를 소개합니다. 이 논문의 착안은 단순합니다. 파싱과 출력은 서로 역방향이므로, 구문을 파서 조합자로 기술했다면 같은 조합자로 파서와 프린터를 모두 만들 수 있어야 한다는 것입니다.

The paper reasons that if a syntax is described using parser combinators, then one should be able to use the same combinators to generate both parsers and printers. But unifying the interfaces runs into an immediate issue; while the Parser type is a covariant Functor, the Printer type is instead a Contravariant functor.

이 "즉각적인 문제"를 이해하려면 공변과 반변을 먼저 알아야 합니다.

공변성과 반변성

공변: 출력 자리에 있는 타입

타입 매개변수가 "출력" 자리에 있으면 그 매개변수는 공변(covariant)입니다. Parser a는 a를 만들어 내므로 a가 출력 자리에 있습니다. 이 경우 함수 a -> b가 있으면 Parser a를 Parser b로 바꿀 수 있습니다. 먼저 a를 만들고, 그 뒤에 a -> b를 적용하면 되기 때문입니다. 이것이 Functor의 fmap입니다.

fmap :: Functor f => (a -> b) -> f a -> f b

화살표 a -> b와 결과 f a -> f b가 같은 방향을 가리킵니다. "공변"이라는 이름이 여기서 나옵니다.

반변: 입력 자리에 있는 타입

타입 매개변수가 "입력" 자리에 있으면 그 매개변수는 반변(contravariant)입니다. Printer a는 a를 받아들이므로 a가 입력 자리에 있습니다. 이번에는 Printer a를 Printer b로 바꾸려면 a -> b가 아니라 b -> a가 필요합니다. b를 받아서 먼저 a로 바꾼 뒤, 원래 프린터에 넘기면 되기 때문입니다. 이 연산을 제공하는 클래스가 base 라이브러리 Data.Functor.Contravariant 모듈의 Contravariant입니다.

contramap :: Contravariant f => (a' -> a) -> f a -> f a'

화살표 a' -> a와 결과 f a -> f a'가 반대 방향을 가리킵니다. 그래서 "반변"입니다.

원문 코드 읽기: Parser와 Printer

원문의 첫 코드 블록은 Rendel과 Ostermann 논문의 4.1절과 4.2절에 나오는 두 타입과 같습니다.

newtype Parser a = Parser (String -> [(a,String)])

instance Functor Parser where
  fmap f (Parser p) = Parser $ \str ->
    [(f a, str') | (a, str') <- p str]

newtype Printer a = Printer (a -> Maybe String)

instance Contravariant Printer where
  contramap f (Printer p) = Printer $ p . f

한 줄씩 읽겠습니다.

  • newtype Parser a = Parser (String -> [(a,String)]): 위에서 본 성공 목록 파서입니다. newtype은 기존 타입(여기서는 함수 타입)에 새 이름을 붙이고 생성자 하나로 감싸는 선언입니다. 생성자 이름과 타입 이름이 모두 Parser입니다.
  • instance Functor Parser where: Parser가 Functor라는 선언입니다. Parser는 매개변수 a를 출력 자리에 두므로 공변이고, 따라서 Functor가 될 수 있습니다.
  • fmap f (Parser p) = Parser $ \str -> ...: 파서 p를 꺼내고, 입력 str을 받는 새 함수를 만듭니다.
  • [(f a, str') | (a, str') <- p str]: p str이 돌려준 각 (결과, 남은 입력) 쌍에서 결과 a에만 f를 적용하고, 남은 입력 str'은 그대로 둡니다.
  • newtype Printer a = Printer (a -> Maybe String): 프린터는 값 a를 받아 텍스트를 돌려줍니다. 결과가 Maybe String인 이유는 출력이 실패할 수 있기 때문입니다. 예를 들어 "숫자 한 글자"만 출력하는 프린터에 'x'를 주면 Nothing을 돌려줘야 합니다. 여러 경우가 있는 자료형에서 한 경우만 담당하는 프린터도 다른 경우에는 실패해야 합니다.
  • instance Contravariant Printer where: Printer가 반변 펑터라는 선언입니다.
  • contramap f (Printer p) = Printer $ p . f: 새 입력을 먼저 f로 바꾸고(f), 그 결과를 원래 프린터 p에 넘깁니다. p . f는 "f를 먼저, p를 나중에" 적용하는 합성입니다.

작은 예시로 값이 흐르는 모습을 보겠습니다. 원문 코드는 아니며, 위의 digitP와 짝을 이루는 프린터를 하나 정의했습니다.

runPrinter :: Printer a -> a -> Maybe String
runPrinter (Printer p) = p

-- Print one decimal digit. Refuse other characters.
digitPr :: Printer Char
digitPr = Printer $ \c -> if isDigit c then Just [c] else Nothing
>>> runPrinter digitPr 'x'
Nothing
>>> runPrinter (contramap intToDigit digitPr) 7
Just "7"

digitPr는 Char를 받습니다. Int를 출력하고 싶으면 Int -> Char 함수인 intToDigit을 앞에 붙이면 됩니다. 반대로 Printer Char와 Char -> Int 함수(digitToInt)만으로는 Printer Int를 만들 수 없습니다. Int를 받았을 때 그것을 Char로 되돌릴 방법이 없기 때문입니다. 그래서 Printer에는 Functor 인스턴스를 줄 수 없습니다.

이제 문제가 분명해집니다. 파서 조합자 라이브러리는 보통 Functor를 바탕으로 한 Applicative와 Alternative 위에 세워집니다. 그런데 프린터는 Functor가 될 수 없습니다. 파서와 프린터가 같은 인터페이스를 공유하려면 무언가를 바꿔야 합니다.

둘 다인 펑터는 왜 쓸모가 없나

원문의 다음 문장은 "그러면 Functor이면서 Contravariant인 타입을 쓰면 되지 않느냐"는 생각을 미리 막습니다.

Any covariant Functor which is also Contravariant is an "invariant", or "phantom", a.k.a. constant functor, which is too strong of a constraint for parsers.

어떤 f가 fmap과 contramap을 모두 가지면, 아무 함수 없이도 f a를 f b로 바꿀 수 있습니다. base 라이브러리에는 이 사실을 그대로 담은 함수가 있습니다.

phantom :: (Functor f, Contravariant f) => f a -> f b

a와 b가 아무 관계가 없어도 바꿀 수 있다는 것은, f a라는 값이 실제로는 a를 하나도 담고 있지 않고 a를 사용하지도 않는다는 뜻입니다. 이런 매개변수를 유령 타입 매개변수(phantom type parameter)라고 부릅니다. 대표적인 예가 상수 펑터(constant functor) Const r a입니다. Const r a는 r 값 하나만 담고 a는 무시합니다.

>>> getConst (phantom (Const "hi" :: Const String Int) :: Const String Bool)
"hi"

Const String Int가 아무 변환 없이 Const String Bool이 되었고, 안에 든 값 "hi"는 그대로입니다. 파서가 이런 타입이라면 "Int를 파싱하는 파서"와 "Bool을 파싱하는 파서"를 구별할 수 없습니다. 파서의 결과 타입은 실제 결과를 나타내야 하므로, 이 제약은 파서에게 "너무 강합니다".

용어에 관한 짧은 주의

원문은 이 타입을 "invariant", 또는 "phantom", 다른 말로 상수 펑터라고 부릅니다. 이 가운데 "invariant"라는 말은 하스켈 생태계의 일반적인 용법과 다릅니다. 하스켈에서 불변 펑터(invariant functor)는 보통 invariant 패키지의 Invariant 클래스, 즉 invmap :: (a -> b) -> (b -> a) -> f a -> f b처럼 양방향 함수가 모두 있어야 바꿀 수 있는 타입을 가리킵니다. 예를 들어 a -> a 꼴의 함수를 감싼 Endo a가 그렇습니다. Functor이면서 동시에 Contravariant인 타입은 그런 함수가 하나도 필요 없는 경우이므로 "유령" 또는 "상수"라고 부르는 것이 정확합니다. 원문의 "invariant"는 느슨한 표현으로 읽으면 됩니다. 7쪽에서도 같은 단어가 비슷하게 쓰입니다.

Rendel과 Ostermann의 선택, 그리고 이 글의 선택

원문에 따르면 Rendel과 Ostermann은 Functor 제약을 버리는 길을 택했습니다.

So, the paper instead drops the Functor constraint from the usual Applicative and Alternative parser combinators.

실제로 그 논문은 Functor를 상위 클래스로 두지 않는 새 클래스들을 정의합니다. 부분 동형(partial isomorphism)을 따라 결과를 바꾸는 IsoFunctor(논문의 <$>), 두 기술을 차례로 이어 결과를 쌍으로 묶는 ProductFunctor(논문의 <*>), 상위 클래스에 의존하지 않는 자체 Alternative가 있고, 이들을 모은 Syntax 클래스에 글자 하나를 다루는 token이 들어 있습니다.

여기서 부분 동형(partial isomorphism)은 서로 반대 방향인 두 부분 함수의 쌍입니다. 논문은 이를 data Iso α β = Iso (α → Maybe β) (β → Maybe α)로 정의합니다. 파서는 한쪽 함수로 결과를 바꾸고, 프린터는 다른 쪽 함수로 입력을 되돌립니다. 두 함수가 모두 Maybe를 돌려주는 까닭은, 예를 들어 "문자열을 숫자로"는 숫자 모양이 아닌 문자열에서 실패하기 때문입니다. 이 생각은 4쪽에서 PartialExchange와 PartialIso라는 이름으로 다시 나타나고, 6쪽과 7쪽의 모든 예제에서 쓰입니다.

원문 첫 절은 다음 문장으로 끝납니다.

At the time another natural interface from category theory had not yet found its way to Haskell, profunctors.

그 논문이 나온 2010년에는 하스켈에 프로펑터(profunctor)라는 인터페이스가 아직 널리 들어와 있지 않았다는 뜻입니다. Hackage의 profunctors 패키지 첫 판(0.1, Edward Kmett)은 2011년 7월 25일에 올라왔으므로 이 설명과 시기가 맞습니다(profunctors 0.1).

프로펑터는 타입 매개변수가 두 개이고, 첫 번째는 반변, 두 번째는 공변인 구조입니다. 이 쪽의 문제에 비추어 보면 답이 자연스럽게 보입니다. 하나의 매개변수에 공변과 반변을 동시에 요구하면 유령 타입이 되어 버리지만, 매개변수를 두 개로 나누어 하나는 프린터가 받는 입력, 하나는 파서가 내는 출력으로 쓰면 충돌이 생기지 않습니다. 2쪽은 이 생각을 코드로 옮깁니다.

이 쪽이 글의 목표에 기여하는 바

이 절은 아직 해결책을 내놓지 않습니다. 대신 해결책이 만족해야 할 조건을 정합니다.

  1. 하나의 기술이 파서로도, 프린터로도 해석되어야 합니다.
  2. 파서는 결과를 내놓고(공변), 프린터는 값을 받아들입니다(반변). 한 타입 매개변수로 두 방향을 모두 표현할 수는 없습니다.
  3. 결과를 바꾸는 연산에는 양방향 함수 쌍, 특히 실패할 수 있는 부분 동형이 필요합니다.
  4. 파서 조합자의 익숙한 문법(<$>, <*>, <|>, many)과 비슷한 문법을 유지하면 좋습니다.

다음 쪽부터 저자는 2번 조건을 프로펑터로 풀고, 3번 조건을 옵틱(optic)으로 풀고, 4번 조건을 프로펑터 버전의 조합자로 풉니다.

정리

  • 이 글의 목표는 구문을 한 번만 기술해서 파서, 프린터, 문법을 함께 얻는 것입니다. 파서와 프린터를 따로 쓰면 같은 지식을 두 번 쓰게 되어 둘이 어긋날 수 있습니다.
  • 파서 조합자는 작은 파서를 <$>, <*>, *>, <*(차례로 잇기)와 empty, <|>, many, some, optional(실패와 선택)로 조합합니다. 이들은 Functor, Applicative, Alternative 인터페이스에서 옵니다.
  • 파서는 결과를 내므로 공변(fmap)이고, 프린터는 값을 받으므로 반변(contramap)입니다. 둘 다인 타입은 매개변수를 실제로 쓰지 않는 유령 타입이므로 파서에 쓸 수 없습니다.
  • Rendel과 Ostermann은 Functor 상위 클래스를 버리고 부분 동형 위에 새 클래스를 세웠습니다. 이 글은 대신 매개변수를 둘로 나누는 프로펑터를 택하며, 그 내용이 2쪽입니다.
