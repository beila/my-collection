원저자의 핵심 주장은 저장소 작업의 정의와 저장 방식의 구현을 분리하자는 것입니다. 서버는 Storage 효과를 통해 사용자 조회, 사용자 생성, 거래 조회, 거래 삭제를 요청합니다. 메모리 해석기와 PostgreSQL 해석기는 같은 요청을 각각 Map 상태 조작과 데이터베이스 입출력으로 실행합니다. 서버 타입은 필요한 능력만 표시하고, 실제 구현은 바깥에서 해석기를 적용할 때 선택됩니다.

먼저 알아야 할 공통 개념

값, 타입, 종류는 서로 다른 층입니다

Haskell 코드를 읽을 때는 다음 세 층을 구분해야 합니다.

  • 3, "list", User ...는 실행 중 존재하는 값입니다.
  • Int, User, [User], IO User는 값의 형태를 분류하는 타입입니다.
  • Type, Type -> Type, [Effect]는 타입이나 타입 생성자의 형태를 분류하는 종류(kind)입니다.

예를 들어 Maybe는 아직 원소 타입을 받지 않았으므로 보통 값의 타입이 될 수 없습니다. Maybe의 종류는 Type -> Type이고, Maybe Int처럼 인수 하나를 적용하면 종류가 Type인 완성된 타입이 됩니다. 이처럼 타입을 받아 다른 타입을 만드는 것을 타입 생성자(type constructor)라고 합니다. Data.Kind 문서는 Type과 종류 수준의 함수 화살표를 정의합니다.

Functor는 종류가 아닙니다. Functor는 fmap을 제공하는 타입 클래스이며, 보통 종류가 Type -> Type인 f가 그 클래스의 인스턴스가 될 수 있습니다. 즉 Type -> Type이라는 모양은 Functor f가 되기 위한 구조적 전제일 뿐, f가 실제로 Functor라는 증명은 아닙니다. Data.Functor 문서가 클래스와 fmap의 계약을 보여 줍니다.

::, :, ->는 문맥에 따라 층과 역할이 달라집니다

Haskell에서 일반적인 타입 서명 기호는 ::입니다. x :: Int는 값 x의 타입이 Int라는 뜻이고, Storage :: Effect는 타입 생성자 Storage의 종류가 Effect라는 뜻입니다. 어느 층의 대상을 서명하느냐에 따라 타입 서명 또는 종류 서명으로 읽습니다.

반면 :는 보통 목록의 맨 앞에 원소를 붙이는 생성자입니다. 값 수준에서는 1 : [2, 3]이 [1, 2, 3]을 만듭니다. DataKinds가 활성화된 타입 수준 목록에서도 같은 구조를 사용하므로 Storage : es는 효과 Storage를 타입 수준 효과 목록 es의 앞에 붙입니다. 여기서 :는 타입 주석의 콜론이 아닙니다. GHC는 기호형 생성자와 클래스를 타입 표현식에서 사용할 수 있도록 타입 연산자(type operator) 문법을 제공합니다. TypeOperators 문서가 이 규칙을 설명합니다.

->도 위치에 따라 읽는 법이 달라집니다.

  • 타입이나 종류에서 a -> b는 a를 받아 b를 내놓는 함수의 타입을 뜻합니다.
  • 람다식 \x -> body에서는 매개변수와 본문을 나눕니다.
  • case의 갈래 ListUsers -> ...에서는 패턴과 그 결과 표현식을 나눕니다.

같은 글자 모양을 쓰지만, 주변이 타입 서명인지 실행 표현식인지 보면 역할을 구별할 수 있습니다. Haskell 2010 Report의 타입 선언과 타입 문법을 기준으로 읽을 수 있습니다.

DataKinds는 값의 실행 중 변환이 아니라 타입 수준 표현을 허용합니다

'[JSON]은 실행 중인 목록을 타입으로 바꾸라는 명령이 아닙니다. DataKinds가 제공하는 승격된 목록 문법으로, 타입 JSON 하나를 원소로 갖는 타입 수준 목록을 직접 적은 것입니다. 앞의 작은따옴표는 이 목록을 값 수준 목록과 구별합니다. Servant는 이 타입 수준 목록으로 응답의 콘텐츠 유형을 기술합니다. GHC의 DataKinds 문서가 데이터 생성자의 승격과 타입 수준 목록 문법을 설명합니다.

Effectful의 Effect, es, :>, :는 한 문장을 이룹니다

Effectful은 효과의 모양을 다음 종류 별칭으로 정의합니다.

type Effect = (Type -> Type) -> Type -> Type

따라서 원문의 Storage :: Effect는 개념적으로 다음과 같습니다.

Storage :: (Type -> Type) -> Type -> Type

Storage m a에서 m의 종류는 Type -> Type이고 a의 종류는 Type입니다. Storage 전체의 종류는 더 큰 Effect이며, 인수 m을 적용한 Storage m의 종류가 Type -> Type입니다.

Eff es a의 es는 실행 중 전달하는 값이 아니라, 이 계산에서 사용할 수 있는 효과들을 기록한 타입 수준 목록을 나타내는 타입 변수입니다. 별도 선언을 찾아야 하는 이름이 아니라 listUsers :: ... 같은 다형적 타입 서명 안에서 암묵적으로 도입됩니다. 명시적으로 쓰면 대략 forall es. ...와 같은 뜻입니다. GHC의 명시적·암묵적 forall 문서가 이 규칙을 설명합니다.

Storage :> es는 Effectful이 제공하는 제약으로, Storage가 효과 스택 es에서 사용 가능하다는 뜻입니다. :>가 효과를 새로 추가하거나 메모리와 PostgreSQL 중 하나를 선택하지는 않습니다. 반면 Storage : es의 :는 실제 타입 수준 목록의 머리에 Storage를 붙입니다. 해석기는 대략 다음 모양으로 그 선두 효과를 처리해 제거합니다.

Eff (Storage : es) a -> Eff es a

Effectful의 Effect, Eff, IOE, (:>) 문서와 interpret 문서에서 이 관계를 확인할 수 있습니다.

GADT는 각 작업과 결과 타입의 관계를 보존합니다

원문의 Storage 선언은 GADT 문법을 사용합니다.

data Storage :: Effect where
  ListUsers :: Storage m [User]
  CreateUser :: UserCreate -> Storage m User

각 생성자에 독립적인 타입을 적을 수 있기 때문에 ListUsers는 결과가 [User]인 작업, CreateUser는 UserCreate를 받아 결과가 User인 작업이라는 관계가 타입에 남습니다. 생성자는 아직 메모리 조회나 SQL 실행을 하지 않습니다. 단지 “어떤 작업을 요청했고 결과 타입이 무엇인가”를 표현하며, 해석기가 생성자별 실행 의미를 부여합니다. GHC의 GADT 문서가 생성자별 결과 타입을 갖는 선언 형식을 설명합니다.

렌즈는 큰 구조 안의 한 부분을 가리키는 조합 가능한 접근자입니다

렌즈(lens)는 레코드 전체와 그 안의 한 필드 사이의 읽기·갱신 관계를 표현합니다. 원문의 nextId 렌즈는 Memory 전체에서 _nextId 필드를 가리키고, userId 렌즈는 사용자 레코드에서 ID 필드를 가리킵니다. makeLenses ''Memory 같은 Template Haskell 호출이 이러한 렌즈를 생성합니다.

렌즈가 값을 직접 변경하는 가변 참조인 것은 아닙니다. userCreate & userId .~ uId는 기존 값을 제자리에서 바꾸지 않고 ID 필드만 다른 새 레코드를 만듭니다. Lens 문서와 makeLenses 문서가 이 초점과 생성 규칙을 설명합니다.

liftIO는 IO를 없애지 않고 Eff 안에 포함합니다

PostgreSQL의 query_와 execute는 IO 동작입니다. Effectful의 liftIO는 본질적으로 다음 조건을 요구합니다.

liftIO :: IOE :> es => IO a -> Eff es a

즉 IO a를 실행하지 않는 순수한 값으로 바꾸는 것이 아니라, IOE 능력이 있는 Eff es a 계산으로 포함합니다. 그래서 PostgreSQL 해석기의 남은 효과 스택 es에는 IOE가 있어야 합니다. 이 정확한 제약은 Effectful 핵심 API에서 확인할 수 있습니다.

원문 문맥:

이전 해설의 “사용자 목록 GET 엔드포인트” 절에는 “'[JSON]의 작은따옴표는 Template Haskell이 아니라 타입 수준 목록을 만드는 DataKinds 문법입니다.”라고 적혀 있습니다.

하이라이트 문구는 현재 읽을 수 있는 이전 해설의 문장과 표현이 조금 다르지만, 같은 Get '[JSON] [User] 코드를 설명합니다. “목록을 타입 수준으로 승격한다”는 말은 축약으로는 통하지만, 실행 중 존재하던 목록 값을 변환하는 것처럼 들릴 수 있습니다.

       "list" :> Get '[JSON] [User]

정확히는 DataKinds 아래에서 '[JSON]이 타입 JSON 하나를 담은 타입 수준 목록을 나타내는 문법입니다. 이 목록은 Servant가 응답 콘텐츠 유형을 타입으로 기술하는 데 사용합니다. 값 수준의 [JSON]을 나중에 타입으로 옮기는 절차가 아닙니다.

렌즈는 레코드의 한 부분을 가리킵니다

하이라이트: lens

원저자의 원문은 Control.Lens를 가져오고 다음 코드를 사용합니다.

여기서 렌즈는 큰 레코드 안의 특정 필드를 가리키는 조합 가능한 접근자입니다. 예를 들어 생성된 userId 렌즈는 User' 레코드의 _userId 필드를 가리킵니다. 뒤의 userCreate & userId .~ uId에서는 그 렌즈를 이용해 ID 필드만 바뀐 새 값을 만듭니다. 따라서 렌즈를 객체 지향 언어의 가변 필드 참조로 이해하기보다는, “전체 구조와 관심 부분 사이의 읽기·갱신 규칙”으로 이해하는 편이 정확합니다.

Storage가 GADT인 이유는 작업마다 결과 타입이 다르기 때문입니다

하이라이트: GADT

원문 문맥:

이전 해설의 “효과 인터페이스와 해석기” 절은 “Storage GADT의 생성자는 애플리케이션이 요청할 수 있는 저장소 작업의 목록입니다.”라고 설명합니다.

원저자의 원문 선언은 다음과 같습니다.

data Storage :: Effect where
  ListUsers :: Storage m [User]
  CreateUser :: UserCreate -> Storage m User

  ListTransactions :: Storage m [Transaction]

GADT는 일반화된 대수적 데이터 타입을 뜻하지만, 이름보다 이 코드에서 얻는 효과가 중요합니다. 마지막 타입 인수에 각 작업의 결과가 기록됩니다. ListUsers의 결과는 [User], CreateUser의 결과는 User, DeleteTransaction의 결과는 ()입니다. 해석기가 생성자를 패턴 매칭하면 그 갈래에서 반환해야 할 타입도 함께 정해집니다. 이 때문에 하나의 Storage 인터페이스 안에 결과 타입이 서로 다른 작업들을 안전하게 모을 수 있습니다.

es는 타입 변수이고 :>는 효과 멤버십 제약입니다

하이라이트: :> es

원문 문맥:

이전 해설의 “효과 목록에 Storage가 있다는 뜻” 절은 listUsers :: (Storage :> es) => Eff es [User]를 제시하고, Storage가 es에 있으므로 이 계산이 저장소 작업을 요청할 수 있다고 설명합니다.

사용자 메모: Is es type parameter? Then what is :> ?

직접 답하면, es는 타입 매개변수라고 불러도 되지만 더 정확히는 암묵적으로 전칭 정량화된 타입 변수입니다. 이 문맥에서 그 종류는 Effectful 효과들의 타입 수준 목록인 [Effect]로 추론됩니다. 실행 시 함수에 넘기는 값 매개변수는 아닙니다.

Storage :> es의 :>는 Effectful이 제공하는 기호형 타입 수준 제약입니다. “효과 스택 es 안에서 Storage를 사용할 수 있다”는 멤버십을 표현합니다. 전체 타입을 풀어 읽으면 “어떤 효과 스택 es든, 그 안에 Storage가 있다면 Eff es [User] 계산을 만들 수 있다”가 됩니다.

원저자의 서버 모듈은 Servant의 동명 (:>)를 숨깁니다.

import Servant.API hiding ((:>))

Servant의 :>는 API 경로 조각을 연결하지만, 여기서 묻는 Effectful의 :>는 효과 멤버십 제약입니다. 모양만 같고 정의와 역할은 다릅니다.

Storage : es의 :는 타입 수준 목록 생성자입니다

하이라이트: :

원문 문맥:

이전 해설의 “효과 인터페이스와 해석기” 절은 “interpret가 Storage 작업을 실제 상태 조작 또는 SQL 호출로 해석할 때 구현이 선택됩니다.”라고 설명합니다. 다만 Storage : es의 단일 콜론에는 별도 설명을 두지 않았습니다.

사용자 메모: Is this an operator? What does it do?

네, 다음 원문 타입에서 :는 타입 수준에서 쓰이는 기호형 생성자, 즉 연산자처럼 쓰이는 목록 cons입니다.

runStorageMemory ::
  (State Memory :> es) => Eff (Storage : es) a -> Eff es a

Storage : es는 Storage를 기존 효과 목록 es의 맨 앞에 붙인 목록입니다. runStorageMemory는 그 입력 계산을 받아 선두의 Storage 요청을 처리하고, 결과로 Storage가 제거된 Eff es a를 돌려줍니다.

이 기호는 ::와 다릅니다. Haskell에서 값이나 타입 생성자의 타입·종류를 적을 때는 ::를 사용합니다. 단일 :는 여기서 타입 주석이 아니라 목록을 만드는 생성자입니다. 또한 :>와도 다릅니다. :는 목록을 구성하고, :>는 어떤 효과가 목록에서 사용 가능하다는 제약을 표현합니다.

수치 초점보다 “렌즈가 가리키는 숫자 값”이 정확합니다

하이라이트: 수치 초점

원문 문맥:

이전 해설의 “증가한 값을 함께 돌려주는 렌즈 연산” 절은 “nextId <+~ 1은 nextId를 1 증가시키고 증가 후의 값을 돌려주는 상태 변환입니다.”라고 설명합니다.

수치 초점은 렌즈 문서의 “numeric target”이나 “focus”를 너무 직역한 표현으로 보입니다. 이 코드에서는 추상 용어를 새로 만들 필요 없이 “nextId 렌즈가 가리키는 _nextId 숫자 값”이라고 하면 충분합니다.

원저자의 원문은 다음과 같습니다.

uId <- state $ nextId <+~ 1

nextId는 Memory 안의 _nextId 필드를 가리키는 렌즈입니다. <+~ 1은 그 숫자 필드에 1을 더한 새 상태를 만들고, 더한 뒤의 값을 함께 반환합니다. 여기서 “초점”은 별도의 런타임 객체가 아니라 렌즈가 전체 구조 중 어느 부분을 대상으로 삼는지를 설명하는 비유입니다.

“값을 승격한다”는 표현은 타입 수준 문법과 구별해야 합니다

하이라이트: 값을 타입 수준으로 승격

원문 문맥:

이전 해설은 Get '[JSON] [User]를 설명하면서 “'[JSON]의 작은따옴표는 Template Haskell이 아니라 타입 수준 목록을 만드는 DataKinds 문법입니다.”라고 적습니다.

DataKinds를 일반적으로 설명할 때 “값 생성자가 타입 생성자로 승격된다”고 말할 수는 있습니다. 그러나 특정 코드 '[JSON]을 읽으며 “어떤 값이 지금 타입 수준으로 올라간다”고 이해하면 잘못입니다.

원저자의 원문에서 JSON은 이 자리에 실행 중 JSON 값으로 놓인 것이 아니라 Servant의 콘텐츠 유형을 나타내는 타입으로 사용됩니다. '[JSON] 전체는 처음부터 타입 표현식이며, JSON을 원소로 갖는 타입 수준 목록입니다. 따라서 이 위치의 뜻은 “값 변환”보다 “DataKinds가 허용하는 승격된 생성자와 타입 수준 목록 표기”라고 설명하는 편이 정확합니다.

Type -> Type은 Functor가 아니라 종류입니다

하이라이트: Type -> Type

원문 문맥:

이전 해설의 “Storage의 종류 서명” 절은 data Storage :: Effect where를 제시하고, Storage가 Effectful이 요구하는 Effect 종류의 타입 생성자라고 설명합니다.

사용자 메모: Is this functor?

아닙니다. Type -> Type은 종류이며, 보통 타입 인수 하나를 받아 완성된 타입을 만드는 타입 생성자의 모양입니다. 예를 들어 Maybe :: Type -> Type이지만, 이 종류 서명만으로 Maybe의 Functor 동작이 정의되지는 않습니다. Functor Maybe 인스턴스와 fmap 구현이 별도로 있어야 합니다.

Effectful에서 다음 별칭을 사용합니다.

type Effect = (Type -> Type) -> Type -> Type

그러므로 Storage 자체는 Type -> Type이 아니라 (Type -> Type) -> Type -> Type 종류입니다. 첫 인수 m을 적용한 Storage m이 Type -> Type 종류를 갖습니다. 원문의 생성자 ListUsers :: Storage m [User]에서는 마지막 [User]가 해당 작업의 결과 타입입니다.

여기서 효과는 작업군의 타입과 실행 능력을 함께 가리킵니다

하이라이트: 효과

원문 문맥:

이전 해설은 “Storage가 Effectful이 요구하는 Effect 종류의 타입 생성자임을 말합니다.”라고 적고, 다른 절에서는 Storage를 서버가 요청할 수 있는 저장소 작업의 인터페이스로 설명합니다.

효과는 이전 해설에서 여러 번 나타나므로 선택 위치를 하나로 확정할 수 없습니다. 여기서는 인접한 종류 관련 하이라이트와 의미가 가장 잘 이어지는 Storage :: Effect 설명을 가장 근거가 강한 문맥으로 보고, 일반 명사로 쓰인 “효과”의 의미도 함께 설명합니다.

이전 해설의 두 용법을 구분해야 합니다. 대문자 코드 Effect는 Effectful이 정의한 종류 별칭이고, 일반 명사 “효과”는 계산이 상태 읽기, 저장소 요청, 입출력처럼 추가 능력을 사용한다는 더 넓은 개념입니다.

원저자의 원문에서 Storage 효과는 다음 작업군을 표현합니다.

ListUsers
CreateUser
ListTransactions
DeleteTransaction

이 생성자들은 작업의 의미와 결과 타입을 정의하지만 실행 방법은 담지 않습니다. 메모리 해석기는 이를 State Memory 조작으로, PostgreSQL 해석기는 SQL IO로 구현합니다. 따라서 “효과를 정의한다”는 것은 여기서 가능한 저장소 요청의 언어를 정의한다는 뜻이고, “효과를 해석한다”는 것은 그 요청에 구체적인 실행 의미를 부여한다는 뜻입니다.

es는 다른 선언에서 찾는 이름이 아니라 서명에서 도입됩니다

하이라이트: es

원문 문맥:

이전 해설은 listUsers :: (Storage :> es) => Eff es [User]를 보여 주며 es를 효과 목록이라고 설명합니다.

사용자 메모: Where is this?

es는 별도의 data es = ... 선언이나 실행 중 변수에서 찾는 이름이 아닙니다. 소문자로 시작하는 이 이름은 타입 서명 안에서 도입되는 타입 변수입니다. GHC의 암묵적 정량화에 따라 다음처럼 읽을 수 있습니다.

listUsers :: forall es. (Storage :> es) => Eff es [User]

원저자의 코드에서는 같은 이름이 여러 서명에서 반복됩니다.

userServer :: (Storage :> es) => ServerT UserAPI (Eff es)

runStoragePostgres ::
  (State Int :> es, IOE :> es) =>
  Connection ->
  Eff (Storage : es) a ->
  Eff es a

각 서명의 es는 그 함수가 구체적인 효과 목록 하나에 고정되지 않고 여러 효과 스택에서 동작할 수 있게 합니다. 제약은 필요한 효과만 지정합니다. userServer에는 Storage가 필요하고, PostgreSQL 해석기 뒤에 남는 스택에는 State Int와 IOE가 필요합니다.

IOE :> es는 liftIO가 요구하는 능력입니다

하이라이트: PostgreSQL 인터프리터의 타입에 IOE :> es 제약이 필요한 직접적인 이유입니다.

원문 문맥:

이전 해설의 “데이터베이스 조회를 효과 계산으로 올리기” 절은 ListUsers -> liftIO $ query_ conn "SELECT * FROM app_users"를 제시하고, liftIO 때문에 해석기 타입에 IOE :> es가 필요하다고 설명합니다.

이전 해설의 결론은 맞습니다. 다만 일반적인 MonadIO 설명보다 Effectful 자체의 타입을 보면 연결이 더 직접적입니다.

liftIO :: IOE :> es => IO a -> Eff es a

원저자의 PostgreSQL 해석기에는 다음 제약과 호출이 함께 있습니다.

runStoragePostgres ::
  (State Int :> es, IOE :> es) =>
  ...

ListUsers -> liftIO $ query_ conn "SELECT * FROM app_users"

query_ conn ...이 IO [User] 같은 데이터베이스 동작을 만들고, liftIO가 이를 Eff es [User] 계산에 포함합니다. 그 함수의 타입이 IOE :> es를 요구하므로 해석기 타입에도 같은 능력이 필요합니다. 이 제약은 “PostgreSQL을 쓴다”는 이름 때문에 자동으로 생기는 것이 아니라, 구현 내부에서 IO 동작을 liftIO로 포함하기 때문에 생깁니다.

->는 주변이 타입인지 표현식인지 보고 읽습니다

하이라이트: ->

원문 문맥:

이전 해설의 “함수 합성의 점” 절은 M.elems . _users의 전체 타입을 Memory -> [User]라고 설명합니다.

하이라이트 하나만으로는 이전 해설에 반복되는 여러 -> 중 어느 글자를 선택했는지 유일하게 정할 수 없습니다. 다만 위 문맥의 Memory -> [User]에서는 ->가 함수 타입 생성자 (->)입니다. Memory 값을 받아 [User]를 내놓는 함수 타입을 뜻합니다.

원저자의 원문에는 다른 역할도 함께 나옵니다.

Connection ->
Eff (Storage : es) a ->
Eff es a

여기서는 오른쪽 결합이므로 Connection을 받고, 이어 Eff (Storage : es) a를 받아, 최종적으로 Eff es a를 돌려주는 커리된 함수 타입입니다.

runStoragePostgres conn = interpret $ \_ -> \case
  ListUsers -> liftIO $ query_ conn "SELECT * FROM app_users"

이 표현식에서 첫 ->는 람다 매개변수 \_와 본문을 나누고, 둘째 ->는 ListUsers 패턴과 실행할 표현식을 나눕니다. Type -> Type에 나타나면 같은 함수 화살표가 종류 수준에서 “종류 Type의 인수를 받아 다시 Type을 만든다”는 모양을 표현합니다.

이 코드의 \case는 일반 case 표현식을 줄여 쓰는 GHC 확장 문법입니다. GHC의 LambdaCase 문서가 이 주변 문법을 설명합니다.

“올린다”는 말은 IO 동작을 Eff에 포함한다는 뜻입니다

하이라이트: 올립니다

원문 문맥:

이전 해설의 “상태와 입출력 효과” 절은 “PostgreSQL 해석기는 데이터베이스 함수의 IO를 liftIO로 Eff 안에 올립니다.”라고 설명합니다.

“올린다(lift)”는 한 계산 문맥의 동작을 더 큰 계산 문맥 안에서 사용할 수 있게 감싼다는 함수형 프로그래밍 용어입니다. 원저자의 다음 코드에서 query_는 IO 동작이고 결과 전체는 Eff 계산이어야 합니다.

ListUsers -> liftIO $ query_ conn "SELECT * FROM app_users"

liftIO는 데이터베이스 접근을 순수 계산으로 바꾸지 않습니다. 실제 IO 의미를 유지한 채 Eff es 안에 포함하고, 타입에 IOE :> es를 남겨 이 계산이 입출력 능력을 요구한다는 사실을 드러냅니다. 따라서 “IO를 없앤다”거나 “결과값만 꺼낸다”가 아니라 “IO 동작을 Effectful 계산 안에서 실행할 수 있도록 포함한다”로 이해해야 합니다.

정리

원저자의 설계에서 Storage는 저장소 작업의 언어이고, 서버는 Storage :> es 제약을 통해 그 언어를 사용할 능력만 요구합니다. es는 효과들의 타입 수준 목록을 나타내는 타입 변수입니다. :>는 멤버십 제약이고, Storage : es의 :는 목록 앞에 효과를 붙이는 생성자입니다. 해석기는 Eff (Storage : es) a를 받아 Storage 작업을 처리하고 Eff es a로 바꿉니다.

이 구조를 읽으려면 층을 섞지 않는 것이 중요합니다. '[JSON]은 값의 실행 중 변환이 아니라 타입 수준 목록 문법이고, Type -> Type은 Functor가 아니라 타입 생성자의 종류입니다. Storage GADT는 작업마다 다른 결과 타입을 기록합니다. 렌즈는 레코드 안의 한 부분을 가리키며, 수치 초점보다는 구체적으로 “렌즈가 가리키는 숫자 필드”라고 설명하는 편이 낫습니다. PostgreSQL 해석기의 liftIO는 IO를 순수하게 만들지 않고 IOE 능력이 있는 Eff 계산에 포함합니다.

이전 해설은 대체로 이 방향을 설명했지만, 승격·종류·초점 같은 표현은 원저자의 실제 코드와 공식 문서에 맞춰 더 정밀하게 읽어야 합니다. 특히 이전 해설의 한국어 문장을 원저자의 표현으로 돌리면 안 되며, 설계의 근거는 원문의 코드와 논지에 두어야 합니다.
