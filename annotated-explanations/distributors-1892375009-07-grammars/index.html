Distributors 해설 7/8: 문법 (Grammars)

해설 대상 원문: Eitan Chatav, “Distributors — Unifying Parsers, Printers & Grammars”

검토일: 2026-11-21

이 쪽은 여덟 쪽 시리즈의 일곱 번째 쪽이며, 원문의 "Grammars" 절을 다룹니다. 6쪽까지 프린터-파서(printer-parser)를 만드는 도구가 모두 갖추어졌습니다. 이 절은 그 도구들을 하나의 문법(grammar) 인터페이스 Grammatical로 묶고, "어떤 해석기로도 해석할 수 있는 문법"이라는 타입 Grammar를 정의합니다. 그리고 정규 표현식(regular expression)의 구문을 이 방식으로 기술한 큰 예제를 보인 뒤, 같은 기술에서 파서와 프린터뿐 아니라 문법 문서 자체를 만들어 냅니다. 글의 부제 "Unifying Parsers, Printers & Grammars"가 여기서 완성됩니다.

6쪽까지에서 가져올 것

  • Alternator는 실패와 선택(empty, <|>)을 갖춘 디스트리뷰터(distributor)이고, Filtrator는 갈래를 나누는 filtrate를 가집니다. 둘을 모두 가진 것이 부분 디스트리뷰터(partial distributor)입니다(6쪽).
  • optionalP, manyP, someP는 0~1번, 0번 이상, 1번 이상 반복입니다(6쪽).
  • >*<는 차례로 잇기, >*와 *<는 구분자 붙이기이며, 문자열 리터럴은 IsString 덕분에 그 문자열을 다루는 p () ()가 됩니다(5쪽).
  • >?<는 동형(isomorphism), 프리즘(prism), 부분 동형(partial isomorphism)을 프린터-파서에 적용하며, 파서는 결과 쪽 함수를, 프린터는 입력 쪽 함수를 씁니다(2쪽, 4쪽).
  • satisfy는 조건을 만족하는 토큰(token) 하나를 다룹니다(4쪽). Tokenized는 기본 부품 anyToken을 주는 클래스입니다(3쪽).
  • 양화 제약(quantified constraint) forall x. ...는 "모든 x에 대해 성립하는 제약"이며 5쪽에서 설명했습니다. 값의 타입 안의 forall, 즉 다형적인 값을 인자로 받는 랭크-N 타입(rank-N type)은 4쪽에서 설명했습니다.
  • 연산자 우선순위는 원문에 없고, 패키지의 선언(infixl 4 >?<, infixr 5 >*<, infixl 6 >*, *<, infixr 3 >+<)을 따릅니다. base의 <|>는 infixl 3입니다(5쪽, 6쪽).

출발점: Breitner의 "Showcasing Applicative"

원문은 Joachim Breitner의 블로그 글 Showcasing Applicative(2016)에서 영감을 받았다고 밝힙니다. 그 글은 확장 배커스-나우르 형식(extended Backus-Naur form, EBNF) 문법을 상수 Applicative 펑터(constant applicative functor)로 표현하는 예를 보여 줍니다. 구체적으로는 fmap이 함수를 무시하는 Grammar 타입을 만들고, 파서와 문법 둘 다의 인스턴스를 가진 클래스로 구문을 한 번만 기술한 뒤, 같은 기술에서 파서와 EBNF 문서를 함께 얻습니다. 1쪽에서 본 상수 펑터(constant functor), 즉 매개변수를 쓰지 않는 펑터가 여기서는 쓸모 있는 역할을 합니다. 문법 문서는 파싱 결과의 타입과 상관없이 구문의 모양만 기록하면 되기 때문입니다.

원문은 이 생각과 "Applicative로서의 정규 표현식이라는 비슷한 예"에서 영감을 받아 부분 디스트리뷰터를 Grammatical 디스트리뷰터로 확장한다고 말합니다. Breitner의 글은 정규 표현식을 다루지 않으므로, 후자가 무엇을 가리키는지는 원문만으로는 알 수 없습니다(예를 들어 regex-applicative 라이브러리일 수 있지만 확인되지 않았습니다).

배경: BNF와 정규 표현식

배커스-나우르 형식. 배커스-나우르 형식(Backus-Naur form, BNF)은 언어의 구문을 규칙(rule)의 모음으로 적는 표기법입니다. 각 규칙은 이름 = 식 꼴이고, 식 안에는 그대로 나타나는 글자인 단말 기호(terminal)와, 다른 규칙의 이름을 가리키는 비단말 기호(nonterminal)가 들어갑니다. 확장 BNF(EBNF)는 여기에 반복(*), 생략 가능(?), 괄호 묶기를 더합니다.

정규 표현식. 정규 표현식은 문자열의 패턴을 적는 작은 언어입니다. 이 쪽의 예제에 필요한 구성 요소는 다음과 같습니다.

표기 뜻
abc 글자 그대로
xy x 다음에 y (연접)
x|y x 또는 y (선택)
x?, x*, x+ 0~1번, 0번 이상, 1번 이상 (클레이니 연산자, Kleene operators)
. 아무 글자 하나
[abc], [^abc] 나열한 글자 중 하나, 나열하지 않은 글자 하나 (문자 클래스, character class)
\p{Lu}, \P{Ll} 유니코드 일반 범주 Lu(대문자)에 속하는 글자, 범주 Ll(소문자)에 속하지 않는 글자

\p{...}와 \P{...}는 Perl이나 PCRE 같은 정규 표현식 엔진의 유니코드 확장 표기입니다. 원문은 여기에 자기만의 표기 두 가지를 더합니다. \q는 항상 실패하는 식이고, \q{rule-name}은 이름이 rule-name인 규칙을 가리키는 비단말 기호입니다. 이 두 표기는 표준 정규 표현식 문법이 아니라 원문 저자가 만든 것입니다. 정규 표현식에 비단말 기호를 더하면 BNF 규칙의 오른쪽을 적을 수 있으므로, 원문은 이것을 "정규 표현식으로 확장한 BNF(regexBNF)"라고 부릅니다.

Grammatical 클래스

class
  ( Alternator p, Filtrator p
  , Tokenized Char Char p
  , forall t. t ~ p () () => IsString t
  ) => Grammatical p where

    inClass :: String -> p Char Char
    inClass str = satisfy $ \ch -> elem ch str

    notInClass :: String -> p Char Char
    notInClass str = satisfy $ \ch -> notElem ch str

    inCategory :: GeneralCategory -> p Char Char
    inCategory cat = satisfy $ \ch -> cat == generalCategory ch

    notInCategory :: GeneralCategory -> p Char Char
    notInCategory cat = satisfy $ \ch -> cat /= generalCategory ch

    rule :: String -> p a a -> p a a
    rule _ = id

    ruleRec :: String -> (p a a -> p a a) -> p a a
    ruleRec name = rule name . fix

instance (Alternative f, Cons s s Char Char)
  => Grammatical (Printor s f)
instance (Monad f, Alternative f, Filterable f, Cons s s Char Char)
  => Grammatical (Parsor s f)

상위 클래스

Grammatical p는 세 묶음의 조건을 요구합니다.

  1. Alternator p, Filtrator p: p는 부분 디스트리뷰터입니다(6쪽).
  2. Tokenized Char Char p: 토큰이 Char입니다. 즉 문자 스트림(stream) 문법입니다(3쪽).
  3. forall t. t ~ p () () => IsString t: 문자열 리터럴이 p () ()가 될 수 있습니다(5쪽).

세 번째 줄은 처음 보면 "모든 타입이 문자열"이라는 말처럼 보입니다. 하나씩 풀겠습니다.

  • ~는 타입 동치 제약(type equality constraint)입니다. t ~ p () ()는 "t는 p () ()와 같은 타입"이라는 제약입니다. 3쪽의 Identical이 값으로 나타낸 증거를 제약으로 쓴 것입니다.
  • forall t. 전제 => 결론 꼴의 양화 제약은 "어떤 타입 t에 대해서든, 전제가 성립하면 결론이 성립한다"는 지역적인 인스턴스 규칙입니다(5쪽).
  • 합치면 "어떤 타입 t든, t가 p () ()이기만 하면 IsString t"입니다. 결국 IsString (p () ())와 같은 내용을 다르게 적은 것입니다.

왜 그냥 IsString (p () ())라고 쓰지 않았을까요. GHC로 확인해 보면 차이가 있습니다. 5쪽의 >* 타입은 p () c -> p a b -> p a b이므로, "#" >* x라고 쓰면 리터럴 "#"의 타입은 p () c이고 c는 아직 정해지지 않았습니다. 상위 클래스가 IsString (p () ())이면 GHC는 IsString (p () c)를 찾다가 c를 모른다는 이유로 실패합니다. 양화 제약 형태에서는 GHC가 먼저 "아무 t에나 맞는" 규칙을 골라 IsString을 해결하고, 그 대가로 t ~ p () ()를 요구받아 c를 ()로 정합니다. 그래서 "(" >* boolG처럼 리터럴을 구분자 자리에 자유롭게 쓸 수 있습니다.

다만 부작용도 있습니다. Grammatical p를 아는 코드 안에서는 모든 문자열 리터럴이 우선 이 규칙에 잡혀 p () ()로 해석되려 합니다. 그래서 진짜 String이어야 하는 리터럴에는 타입 표시가 필요할 수 있습니다. 아래 atomG의 pure ""가 그런 경우입니다.

메서드: 정규 술어

inClass, notInClass, inCategory, notInCategory는 글자 하나를 다루는 프린터-파서이며, 모두 4쪽의 satisfy로 기본 구현이 주어집니다.

  • inClass str: str에 들어 있는 글자 하나입니다. 정규 표현식의 [abc]에 해당합니다.
  • notInClass str: str에 들어 있지 않은 글자 하나입니다. [^abc]에 해당합니다.
  • inCategory cat: 유니코드 일반 범주가 cat인 글자 하나입니다. \p{...}에 해당합니다. GeneralCategory는 Data.Char의 열거형이며 생성자가 30개입니다.
  • notInCategory cat: 범주가 cat이 아닌 글자 하나입니다. \P{...}에 해당합니다.

원문은 이것들을 정규 술어(regular predicate)라고 부릅니다. 저자의 용어이며, "정규 표현식에 전용 표기가 있는 술어"라는 뜻입니다. 이것들이 그냥 satisfy가 아니라 메서드인 이유는, 나중에 정규 표현식을 만드는 해석기가 이것들을 [abc]나 \p{Lu} 같은 표기로 바꿀 수 있어야 하기 때문입니다. satisfy에 넘긴 임의의 함수는 들여다볼 수 없지만, inClass "abc"라는 메서드 호출은 그 내용을 알 수 있습니다.

메서드: 규칙

  • rule :: String -> p a a -> p a a: 프린터-파서에 규칙 이름을 붙입니다. BNF의 비단말 기호에 해당합니다. 기본 구현 rule _ = id는 이름을 무시하고 그대로 돌려줍니다.
  • ruleRec :: String -> (p a a -> p a a) -> p a a: 자기 자신을 가리키는 재귀적인 규칙을 만듭니다. 인자는 "자기 자신을 받아 자기 자신을 정의하는 함수"입니다. 기본 구현은 rule name . fix입니다.

Data.Function의 fix는 fix f = let x = f x in x로 정의되며, "f에 자기 결과를 다시 넣는" 재귀를 만듭니다. 원문 코드가 아닌 예시입니다. 이 쪽의 예시는 모두 GHC 9.10.3에서 실행한 결과이며, 원문과 필요한 라이브러리의 정의는 최소한으로 다시 만든 코드를 썼습니다.

>>> fix (\rec n -> if n == 0 then 1 else n * rec (n - 1)) 5
120

함수가 자기 자신을 rec라는 이름으로 받아 쓰고, fix가 그 매듭을 묶어 줍니다. 문법에서도 같습니다. 괄호 안에 괄호가 들어갈 수 있는 구문은 "자기 자신을 받아 괄호로 감싸는 함수"로 쓰고, ruleRec이 매듭을 묶습니다. 이것이 동작하는 이유는 하스켈이 게으르게 평가하고 Parsor와 Printor가 함수를 감싼 newtype이기 때문입니다.

이 메서드들의 타입이 p a b가 아니라 p a a인 점도 눈여겨보십시오. 문법은 같은 타입을 읽고 쓰므로 두 자리가 같습니다.

인스턴스와 규칙 이름의 쓸모

두 인스턴스는 본문이 없습니다. 원문의 말대로 모든 메서드에 기본 구현이 있고, Printor와 Parsor는 그것을 그대로 씁니다. 다른 인스턴스는 기본 구현을 덮어쓸 수 있습니다.

원문은 스스로 묻습니다. 기본 구현이 규칙 이름을 완전히 무시한다면 이름이 왜 필요할까요. 답은 다른 해석기에 있습니다. Parsor보다 기능이 많은 파서라면 쓸모 있는 오류 메시지를 낼 수 있습니다. 예를 들어 parsec 계열 파서 라이브러리에는 <?> 또는 label 조합자(combinator)가 있어서 파싱이 실패할 때 "무엇을 기대했는지"를 이름으로 보여 줍니다. parsec 파서를 newtype으로 감싼 Grammatical 인스턴스가 rule을 이 label로 덮어쓰면, 실패 메시지에 규칙 이름이 나타납니다. 아래의 DiGrammar도 rule을 덮어써서 규칙 이름을 모으는 해석기입니다.

작은 문법 예제

원문의 큰 예제를 보기 전에, 작은 문법으로 값의 흐름을 확인하겠습니다. 다음은 원문 코드가 아닌 예시이며, 아래에서 정의할 Grammar 타입을 미리 쓰고, 그 아래 genReadS(파서로 쓰기)와 genShowS(프린터로 쓰기)도 미리 씁니다.

boolG :: Grammar Bool
boolG = rule "bool" $ only True >?< "true" <|> only False >?< "false"

natG :: Grammar Int
natG = rule "nat" $ iso show read >?< someP (inCategory DecimalNumber)

pairG :: Grammar (Bool, Int)
pairG = rule "pair" $ "(" >* boolG >*< "," >* natG *< ")"

newtype Nest = Nest [Nest]

nestG :: Grammar Nest
nestG = ruleRec "nest" $ \n -> iso (\(Nest xs) -> xs) Nest >?< "(" >* manyP n *< ")"
  • boolG: 4쪽의 only True :: Prism' Bool ()로 리터럴 "true" :: p () ()를 감싸 p Bool Bool을 만들고, False도 같은 방식으로 만들어 <|>로 합칩니다. 프린터는 True이면 첫 갈래만 맞고, 파서는 "true"를 읽으면 첫 갈래만 성공합니다.
  • natG: 6쪽의 posDecInt와 같은 생각이며, 숫자 글자를 inCategory로 다룹니다.
  • pairG: 우선순위에 따라 ("(" >* boolG) >*< (("," >* natG) *< ")")로 읽힙니다.
  • nestG: 괄호의 중첩을 나타내는 재귀 문법입니다. n이 자기 자신입니다.
>>> genReadS boolG "true!"
[(True,"!")]
>>> map ($ "") (genShowS boolG False)
["false"]
>>> genReadS pairG "(true,42)"
[((True,42),"")]
>>> map ($ "") (genShowS pairG (False,7))
["(false,7)"]
>>> fmap ($ "") (genShowS pairG (False,7) :: Maybe ShowS)
Just "(false,7)"
>>> genReadS nestG "(()())"
[(Nest [Nest [],Nest []],"")]
>>> map ($ "") (genShowS nestG (Nest [Nest []]))
["(())"]
>>> genReadS (inClass "abc") "bx"
[('b',"x")]
>>> genReadS (notInClass "abc") "bx"
[]

natG만 따로 쓰면 "42!"에서 [(4,"2!"),(42,"!")]처럼 두 결과가 나오지만, pairG 안에서는 뒤따르는 *< ")"가 4 다음의 "2"를 받아들이지 않으므로 (True,42)만 남습니다. 결과 컨테이너가 목록이면 실패한 갈래가 이렇게 자연스럽게 걸러집니다.

Grammar 타입과 생성기

type Grammar a = forall p. Grammatical p => p a a

genReadS :: Grammar a -> ReadS a
genReadS = runParsor

genShowS :: Alternative f => Grammar a -> a -> f ShowS
genShowS = runPrintor
  • type Grammar a = forall p. Grammatical p => p a a: a 타입의 문법은 "어떤 Grammatical 해석기 p에서도 동작하는 p a a"입니다. 4쪽의 Iso처럼, p를 고르는 쪽은 문법을 쓰는 쪽입니다.
  • genReadS: ReadS a는 Prelude의 type ReadS a = String -> [(a, String)]이며, 1쪽에서 본 성공 목록 파서의 함수 타입과 같습니다. Grammar a에서 p를 Parsor String []로 고르면 runParsor가 바로 이 타입을 돌려줍니다.
  • genShowS: ShowS는 2쪽에서 본 String -> String입니다. p를 Printor String f로 고르면 runPrintor는 a -> f ShowS가 됩니다. 결과 컨테이너 f는 쓰는 쪽이 고르며, 목록이면 모든 출력, Maybe이면 첫 출력입니다. Grammatical (Printor s f) 인스턴스가 Alternative f를 요구하므로 genShowS도 그것을 요구합니다.

짧은 주의. 이 두 정의는 원문에 적힌 그대로는 최근 GHC에서 컴파일되지 않습니다. GHC 9.10.3으로 확인해 보면, 랭크-2 인자를 받는 함수를 genReadS = runParsor처럼 점 없는 표기로 정의하면 타입이 맞지 않는다는 오류가 납니다. GHC 9.0부터 도입된 단순화된 포섭(simplified subsumption) 규칙 때문입니다. genReadS g = runParsor g처럼 인자를 드러내거나 DeepSubsumption 확장을 켜면 동작합니다. 위의 작은 예제는 인자를 드러낸 정의로 실행했습니다.

파이널 태그리스 인코딩

원문은 Grammar가 정규 표현식으로 확장한 BNF 문법의 파이널 태그리스 인코딩(final tagless encoding)이며, Haskell 타입 a가 그 문법의 방향을 정한다("type-directed")고 말합니다. 이 용어를 처음부터 설명하겠습니다.

작은 언어를 하스켈 안에 담는 방법은 크게 둘입니다.

  • 초기 인코딩(initial encoding): 언어의 구문을 자료형으로 만듭니다. 예를 들어 data Expr = Lit Int | Add Expr Expr처럼 쓰고, 해석기는 이 자료형을 패턴 매칭하는 함수입니다. 아래의 RegEx가 이런 자료형입니다.
  • 파이널 인코딩(final encoding): 언어의 구문을 타입 클래스의 메서드로 만듭니다. 프로그램은 그 클래스에 대해 다형적인 값이고, 해석기는 그 클래스의 인스턴스입니다. "태그리스"는 해석할 때 자료형의 생성자(태그)를 검사할 필요가 없다는 뜻입니다. Carette, Kiselyov, Shan의 논문 "Finally tagless, partially evaluated"(APLAS 2007, JFP 2009)가 이 이름을 널리 알렸습니다.

이 글에서는 Grammatical의 메서드와 그로부터 만든 조합자가 문법의 "구문"이고, Grammar a가 프로그램이며, Parsor와 Printor 인스턴스가 해석기입니다.

"조합자 대 생성기"는 거짓 이분법

원문은 파싱 도구를 비교하는 논의에서 흔히 파서 조합자(parser combinator)와 파서 생성기(parser generator)를 대립시키지만, 이것은 거짓 이분법이라고 말합니다. 원문의 논리는 이렇습니다.

  • 조합자는 타입 클래스의 메서드이거나, 메서드로 만든 함수입니다.
  • 생성기는 genReadS와 genShowS에서 보듯 그 타입 클래스의 인스턴스에서 나옵니다.
  • 그러므로 파이널 태그리스 방식은 확장 가능합니다. 예를 들어 parsec 스타일 파서를 위한 새 생성기가 필요하면, 새 타입을 만들고 Grammatical까지의 인스턴스를 정의하면 됩니다.

여기서 "생성기"는 빌드할 때 코드를 만들어 내는 yacc나 happy 같은 도구가 아니라, "문법에서 무언가를 만들어 내는 해석기"라는 뜻으로 쓰였습니다. 이것은 원문 저자의 관점입니다.

큰 예제: 정규 표현식의 추상 구문 트리

원문은 아주 낮은 수준의 조합자만으로도 추상 구문 트리(abstract syntax tree, AST)의 문법을 거의 쓸 수 있다고 말하며, 정규 표현식을 예로 고릅니다. 이유는 네 가지입니다. 독자에게 익숙하고, "산술 식 대수(arithmetic expression algebra)"의 전형이며, Grammar를 시험할 만큼 복잡하고, 내장 언어와 짝이 맞아서 더 많은 생성기를 정의할 수 있게 해 준다는 것입니다. 마지막 이유는 이 절의 끝에서 드러납니다.

data RegEx
  = Terminal String -- abc123etc\.
  | Sequence RegEx RegEx -- xy
  | Fail -- \q
  | Alternate RegEx RegEx -- x|y
  | KleeneOpt RegEx -- x?
  | KleeneStar RegEx -- x*
  | KleenePlus RegEx -- x+
  | AnyChar -- .
  | InClass String -- [abc]
  | NotInClass String -- [^abc]
  | InCategory GeneralCategory -- \p{Lu}
  | NotInCategory GeneralCategory -- \P{Ll}
  | NonTerminal String -- \q{rule-name}
  deriving stock (Eq, Ord, Show, Generic)

각 생성자 옆의 주석은 그 생성자의 구체적인 표기입니다.

생성자 뜻 표기
Terminal String 글자 그대로의 문자열. 특수 문자는 \로 이스케이프합니다. abc123etc\.
Sequence RegEx RegEx 연접 xy
Fail 항상 실패 \q
Alternate RegEx RegEx 선택 x|y
KleeneOpt, KleeneStar, KleenePlus 0~1번, 0번 이상, 1번 이상 x?, x*, x+
AnyChar 아무 글자 하나 .
InClass, NotInClass 문자 클래스와 그 여집합 [abc], [^abc]
InCategory, NotInCategory 유니코드 범주와 그 여집합 \p{Lu}, \P{Ll}
NonTerminal String 규칙 이름을 가리키는 비단말 기호 \q{rule-name}

deriving stock (Eq, Ord, Show, Generic)은 네 클래스의 인스턴스를 컴파일러의 표준 방식으로 자동 생성하라는 선언입니다. stock은 DerivingStrategies 확장의 표기로 "기본 파생 방식"을 명시합니다. Generic은 자료형의 구조를 일반적인 표현으로 다룰 수 있게 해 줍니다.

이 생성자들은 Grammatical의 능력과 하나씩 짝이 맞습니다. 단말 기호는 리터럴, 연접은 >*<, 실패는 empty, 선택은 <|>, 반복은 optionalP/manyP/someP, 문자 클래스와 범주는 정규 술어, 비단말 기호는 rule입니다. 원문은 이것을 "RegEx 타입이 Grammatical 인터페이스와 도덕적으로 같은 모양"이라고 표현합니다.

보조 조합자: SepBy, chainl1, chainl

원문은 문법을 쓰기 전에 조금 더 높은 수준의 조합자가 필요하다고 말합니다. 시작, 끝, 구분자로 둘러싸인 목록은 구문에서 아주 흔하기 때문입니다.

data SepBy p = SepBy
  { beginBy :: p () ()
  , endBy :: p () ()
  , separateBy :: p () ()
  }

sepBy :: Monoidal p => p () () -> SepBy p
sepBy = SepBy oneP oneP

noSep :: Monoidal p => SepBy p
noSep = sepBy oneP

chainl1
  :: (Choice p, Cochoice p, Distributor p)
  => APartialIso a b (a,a) (b,b) -- ^ binary constructor pattern
  -> SepBy p -> p a b -> p a b

chainl
  :: (Alternator p, Filtrator p)
  => APartialIso a b (a,a) (b,b) -- ^ binary constructor pattern
  -> APartialIso a b () () -- ^ nilary constructor pattern
  -> SepBy p -> p a b -> p a b
  • SepBy p: 목록의 시작 기호, 끝 기호, 구분자를 담는 레코드입니다. 셋 다 p () (), 즉 정보 없는 구분자입니다.
  • sepBy = SepBy oneP oneP: 생성자 SepBy에 앞의 두 필드만 주고 세 번째 필드는 인자로 남긴 부분 적용입니다. 그래서 sepBy sep은 "시작과 끝은 없음(oneP), 구분자는 sep"입니다.
  • noSep = sepBy oneP: 구분자도 없습니다.
  • chainl1 pat sep p: p로 다루는 항목이 1개 이상 sep으로 구분되어 이어진 것을 다룹니다. 원문은 본문을 보여 주지 않지만, 이름과 parsec의 같은 이름 조합자 chainl1, 그리고 "binary constructor pattern"이라는 주석으로 미루어 두 항목을 받는 생성자 패턴 pat으로 왼쪽부터 접는 것으로 보입니다. 그렇다면 a|b|c는 Alternate (Alternate a b) c처럼 왼쪽 결합(left-associative)으로 묶입니다.
  • chainl pat0 pat sep p: 항목이 0개일 수도 있습니다. 0개일 때 쓸 값을 0항 생성자 패턴(nilary constructor pattern)으로 받습니다.
  • APartialIso: 원문에 정의가 없습니다. 현재 패키지에서는 4쪽의 PartialIso에서 p를 PartialExchange로 고정한 구체 탐침 형태입니다. 4쪽의 AnIso가 Iso에 대해 하는 일을 PartialIso에 대해 하며, 패턴에서 두 부분 함수를 꺼내 쓰기 위한 타입입니다.

원문은 "이 조합자들에 정의가 있다고 가정하면" 문법을 쓸 수 있다고 말하며 본문을 생략합니다. 프린터 쪽에서 chainl1은 반대로 왼쪽으로 쌓인 Alternate 값을 패턴으로 하나씩 풀어 구분자를 끼워 출력해야 하므로, 실제 구현은 이 쪽에서 보이는 것보다 섬세합니다.

regexGrammar 읽기

원문의 문법 정의는 길어서 여러 조각으로 나누어 읽겠습니다. 조각을 이어 붙이면 원문 코드 블록 그대로입니다.

시작 규칙과 선택

regexGrammar :: Grammar RegEx
regexGrammar = ruleRec "regex" altG

makePrisms ''RegEx

altG rex = rule "alternate" $
  chainl1 _Alternate (sepBy "|") (seqG rex)
  • regexGrammar는 재귀 규칙 regex입니다. altG는 "자기 자신(rex)을 받아 문법을 만드는 함수"이고, ruleRec이 매듭을 묶습니다. 이 rex가 아래의 여러 규칙을 거쳐 괄호 규칙 parenG까지 전달되어, 괄호 안에 다시 정규 표현식 전체가 올 수 있게 합니다.
  • makePrisms ''RegEx: lens의 템플릿 하스켈(Template Haskell) 함수로, RegEx의 생성자마다 프리즘을 만듭니다. Terminal에는 _Terminal :: Prism' RegEx String, Alternate에는 _Alternate :: Prism' RegEx (RegEx, RegEx), AnyChar에는 _AnyChar :: Prism' RegEx ()처럼 생성자 이름 앞에 밑줄을 붙인 이름이 생깁니다. ''RegEx는 타입 이름 RegEx를 템플릿 하스켈에 넘기는 표기입니다.
  • altG rex: seqG rex(연접 규칙)로 다루는 항목을 "|"로 구분해 1개 이상 이어 쓰고, _Alternate 패턴으로 묶습니다. 앞의 보조 조합자 절에서 말했듯이 왼쪽부터 접는 것으로 보입니다.

원자와 아무 글자

anyG = rule "any" $ _AnyChar >?< "."

atomG rex = rule "atom" $
  nonterminalG
  <|> failG
  <|> classInG
  <|> classNotInG
  <|> categoryInG
  <|> categoryNotInG
  <|> _Terminal . _Cons >?< charG >*< pure ""
  <|> anyG
  <|> parenG rex
  • anyG: 리터럴 "."(p () ())를 프리즘 _AnyChar :: Prism' RegEx ()로 감쌉니다. 파서로는 .을 읽어 AnyChar를 만들고, 프린터로는 AnyChar이면 .을 출력합니다.
  • atomG: 원자(atom)는 반복 연산자 ?, *, +를 붙일 수 있는 가장 작은 단위입니다. 비단말 기호, 실패, 문자 클래스, 유니코드 범주, 글자 하나, 아무 글자, 괄호로 묶은 식 중 하나입니다. <|>는 infixl 3이고 >?<는 infixl 4이므로 각 갈래의 >?<가 먼저 묶입니다.
  • _Terminal . _Cons >?< charG >*< pure "": 프리즘 합성 _Terminal . _Cons는 "Terminal이고, 그 문자열이 비어 있지 않으면 (첫 글자, 나머지)"를 맞추는 프리즘입니다. 오른쪽 charG >*< pure ""는 글자 하나를 다루고, 나머지 자리에는 빈 문자열을 둡니다. 파서로는 글자 하나를 읽어 Terminal [c]를 만듭니다. 즉 원자 자리의 단말 기호는 글자 하나입니다. a*가 (a)*와 같은 뜻이 되는 이유입니다.

이 조각에는 짧은 주의가 두 가지 있습니다.

pure ""는 그대로는 컴파일되지 않습니다. 위의 Grammatical 상위 클래스에서 말한 부작용 때문입니다. 이 ""는 String이어야 하지만, GHC 9.10.3으로 확인해 보면 양화된 IsString 규칙이 먼저 적용되어 ""를 p () ()로 해석하려다 타입 오류가 납니다. pure ("" :: String)처럼 타입을 적으면 동작합니다.

프린터 쪽에서는 이 갈래가 정확한 역이 아닙니다. pure ""는 프린터로 쓰이면 입력을 무시하고 아무것도 출력하지 않습니다. 그래서 이 갈래로 Terminal "ab"를 출력하면 첫 글자 "a"만 나옵니다. 같은 모양의 작은 문법을 GHC에서 실행한 결과도 ["a"]였습니다. 단말 기호 전체는 아래 terminalG가 따로 다루므로 목록 컨테이너에서는 올바른 출력도 함께 나오지만, 원자 자리에서는 잘못된 출력이 후보에 섞입니다. 예를 들어 KleeneStar (Terminal "ab")를 Maybe 컨테이너로 출력하면 (ab)* 대신 a*가 먼저 선택될 수 있다고 추론되며, 이 부분은 직접 실행하지는 않았습니다. 원문은 곧이어 "가장 아름답지는 않지만 동작하며, 거친 부분은 다듬을 수 있다"고 말하는데, 이런 부분을 가리키는 것으로 읽을 수 있습니다.

  <|> _ClosePunctuation >?< "Pe"
  <|> _InitialQuote >?< "Pi"

  <|> _CurrencySymbol >?< "Sc"

  <|> _OtherSymbol >?< "So"
  <|> _Space >?< "Zs"
  <|> _LineSeparator >?< "Zl"

categoryInG = rule "category-in" $
  _InCategory >?< "\\p{" >* categoryG *< "}"

categoryNotInG = rule "category-not-in" $
  _NotInCategory >?< "\\P{" >* categoryG *< "}"
  • makePrisms ''GeneralCategory: Data.Char의 GeneralCategory 생성자 30개마다 프리즘을 만듭니다. 각 프리즘의 안쪽 타입은 ()입니다.
  • categoryG: 30개 갈래가 각 범주를 두 글자 약어로 다룹니다. _LowercaseLetter >?< "Ll"은 파서로는 Ll을 읽어 LowercaseLetter를 만들고, 프린터로는 LowercaseLetter이면 Ll을 출력합니다. 프린터 쪽에서는 30개 갈래 중 입력에 맞는 프리즘의 갈래만 성공합니다. 이것은 위의 작은 예제 boolG와 같은 방식입니다.
  • categoryInG: \p{, 범주 약어, }를 차례로 다루고, _InCategory 프리즘으로 InCategory 값과 연결합니다. 하스켈 문자열 "\\p{"의 \\는 역슬래시 한 글자이므로 실제 리터럴은 \p{입니다. 우선순위에 따라 _InCategory >?< (("\\p{" >* categoryG) *< "}")로 읽힙니다.
  • categoryNotInG: \P{...}를 같은 방식으로 다룹니다.

글자와 이스케이프

charG = rule "char" $ charLiteralG <|> charEscapedG

charEscapedG = rule "char-escaped" $ "\\" >* inClass charsReserved

charLiteralG = rule "char-literal" $ notInClass charsReserved

charsReserved = "$()*+.?[\\]^{|}"
  • charsReserved: 정규 표현식에서 특별한 뜻을 가진 예약 글자들입니다. 하스켈 문자열 안의 \\는 역슬래시 한 글자이므로 실제 글자는 $ ( ) * + . ? [ \ ] ^ { | }입니다. inClass와 notInClass가 String을 받으므로 이 값은 String으로 쓰입니다.
  • charLiteralG: 예약 글자가 아닌 글자 하나는 그대로 씁니다.
  • charEscapedG: 예약 글자는 앞에 역슬래시를 붙여 씁니다. 리터럴 "\\"(역슬래시 하나)를 구분자로 다루고, 이어서 예약 글자 하나를 다룹니다.
  • charG: 둘 중 하나입니다. 프린터로는 예약 글자이면 charEscapedG만, 아니면 charLiteralG만 성공하므로 출력할 때 자동으로 이스케이프가 붙습니다. 파서로는 이스케이프된 글자를 읽어 원래 글자를 돌려줍니다.

문자 클래스

classInG = rule "class-in" $
  _InClass >?< "[" >* manyP charG *< "]"

classNotInG = rule "class-not-in" $
  _NotInClass >?< "[^" >* manyP charG *< "]"

[, 글자 0개 이상, ]를 차례로 다루고 _InClass로 감쌉니다. 우선순위에 따라 _InClass >?< (("[" >* manyP charG) *< "]")입니다. classNotInG는 시작 구분자가 [^입니다. 파서로는 [abc]를 읽어 InClass "abc"를, 프린터로는 그 반대를 합니다.

식, 실패, 비단말 기호, 괄호

exprG rex = rule "expression" $
  terminalG
  <|> kleeneOptG rex
  <|> kleeneStarG rex
  <|> kleenePlusG rex
  <|> atomG rex

failG = rule "fail" $ _Fail >?< "\\q"

nonterminalG = rule "nonterminal" $
  _NonTerminal >?< "\\q{" >* manyP charG *< "}"

parenG ex = rule "parenthesized" $ "(" >* ex *< ")"
  • exprG: 연접의 한 항목인 "식"은 단말 기호, 반복이 붙은 원자, 또는 원자입니다.
  • failG: 리터럴 \q를 Fail과 연결합니다.
  • nonterminalG: \q{, 글자 0개 이상, }를 NonTerminal과 연결합니다.
  • parenG ex: 괄호 안에 ex를 둡니다. 여기서 ex가 regexGrammar 자신(rex)이므로 괄호 안에 정규 표현식 전체가 올 수 있습니다. 괄호 자체는 RegEx 값에 흔적을 남기지 않습니다. 파서는 괄호를 읽고 버리며, 프린터는 이 갈래로 출력할 때 괄호를 붙입니다.

반복 연산자

kleeneOptG rex = rule "kleene-optional" $
  _KleeneOpt >?< atomG rex *< "?"

kleeneStarG rex = rule "kleene-star" $
  _KleeneStar >?< atomG rex *< "*"

kleenePlusG rex = rule "kleene-plus" $
  _KleenePlus >?< atomG rex *< "+"

원자 하나 뒤에 ?, *, +가 붙은 것을 각 생성자와 연결합니다. 반복 연산자의 피연산자가 원자로 제한되므로 ab*는 a 다음에 b*로 읽히도록 되어 있습니다. 이것은 보통의 정규 표현식과 같은 우선순위입니다.

연접과 단말 기호

seqG rex = rule "sequence" $
  chainl _Sequence (_Terminal . _Empty) noSep (exprG rex)

terminalG = rule "terminal" $ _Terminal >?< someP charG
  • seqG: 식을 0개 이상 구분자 없이 이어 쓰고, _Sequence로 묶습니다(chainl1처럼 왼쪽부터 접는 것으로 보입니다). 식이 0개이면 _Terminal . _Empty 패턴을 씁니다. _Empty는 lens의 AsEmpty 클래스(6쪽)가 주는 "빈 값" 프리즘이므로, 이 합성은 "Terminal """을 뜻합니다. 즉 빈 정규 표현식은 빈 단말 기호입니다.
  • terminalG: 글자를 1개 이상 이어 쓴 것을 Terminal과 연결합니다. 단말 기호 전체를 한 번에 다루는 규칙입니다.

같은 입력의 여러 해석. 결과 컨테이너가 목록인 파서에서는 단말 기호 규칙 terminalG와 원자의 글자 하나짜리 갈래가 같은 글자들에 둘 다 맞을 수 있습니다. 그래서 ab 같은 입력은 Terminal "ab" 하나로도, 글자 하나짜리 단말 기호 두 개를 이은 연접으로도 읽힐 수 있습니다. terminalG의 someP가 가능한 길이를 모두 돌려주는 것도 해석의 수를 늘립니다. 같은 모양의 작은 문법(단말 기호 규칙과 글자 하나짜리 갈래를 <|>로 합쳐 manyP로 반복한 것)으로 실행해 보면, "ab" 전체를 읽는 결과로 [Terminal "ab"]와 [Terminal "a",Terminal "b"]가 함께 나오고, 뒤의 것은 여러 번 나옵니다. 원문은 이 모호성을 다루지 않습니다.

문법의 전체 구조

규칙들의 관계를 위에서 아래로 정리하면 다음과 같습니다. 원문 코드가 아닌 요약이며, chainl1과 chainl이 왼쪽부터 접는다고 보고 적었습니다.

regex       = alternate
alternate   = sequence ( "|" sequence )*          -- _Alternate 로 왼쪽부터 접기
sequence    = expression*                         -- _Sequence 로 접기, 0개면 Terminal ""
expression  = terminal | atom "?" | atom "*" | atom "+" | atom
atom        = nonterminal | fail | class | category | char | any | "(" regex ")"

선택이 가장 느슨하게, 연접이 그다음, 반복이 가장 단단하게 묶입니다. 괄호가 다시 regex로 돌아가는 곳이 재귀가 일어나는 유일한 지점입니다.

코드 배치에 관한 짧은 주의

원문 코드 블록에서 regexGrammar = ruleRec "regex" altG는 makePrisms ''RegEx보다 앞에 있고, altG는 그 뒤에 정의되어 있습니다. GHC 사용자 안내서에 따르면 최상위 템플릿 하스켈 선언은 파일을 선언 그룹(declaration group)으로 나누며, 앞의 그룹은 뒤의 그룹에 있는 선언을 볼 수 없습니다(GHC 사용자 안내서: Template Haskell). 같은 이유로 makePrisms ''GeneralCategory 앞에 있는 atomG가 그 뒤의 categoryInG를 쓰는 것도 문제가 됩니다. 이 순서로는 컴파일되지 않을 것으로 보이며, 이 판단은 문서화된 규칙에서 나온 것이고 직접 컴파일해 보지는 않았습니다. 원문은 8쪽에서 말하듯 literate Haskell이 아니므로, 설명을 위해 코드를 읽기 좋은 순서로 배치한 것으로 보면 됩니다.

더 많은 생성기: DiRegEx와 DiGrammar

원문은 "RegExp 타입이 Grammatical 인터페이스와 도덕적으로 같은 모양"이므로, Breitner의 글에서 영감을 받은 프로펑터(profunctor) 두 개를 정의해 새 생성기를 만든다고 말합니다. 여기서 RegExp는 위의 RegEx를 가리키는 오타로 보입니다. 인스턴스는 연습 문제로 남겨 둡니다.

newtype DiRegEx a b = DiRegEx RegEx

data DiGrammar a b = DiGrammar
  { grammarStart :: DiRegEx a b
  , grammarRules :: Set (String, RegEx)
  }

genRegEx :: Grammar a -> RegEx
genRegEx (DiRegEx rex) = rex

genGrammar :: Grammar a -> [(String, RegEx)]
genGrammar (DiGrammar (DiRegEx start) rules) =
  ("start", start) : toList rules
  • newtype DiRegEx a b = DiRegEx RegEx: 정규 표현식 하나를 담는 프로펑터입니다. a와 b를 둘 다 쓰지 않습니다. Breitner의 Grammar처럼 구문의 모양만 기록합니다.
  • DiGrammar a b: 시작 정규 표현식 하나와, 이름 붙은 규칙의 집합(Set (String, RegEx))을 담습니다. Set은 containers 라이브러리의 집합 타입이며, toList는 그 원소를 목록으로 꺼냅니다.
  • genRegEx (DiRegEx rex) = rex: Grammar a는 모든 Grammatical p에서 동작하므로, 인자를 DiRegEx 패턴으로 매칭하면 p가 DiRegEx로 정해집니다. 그 결과 문법 전체가 정규 표현식 하나로 해석됩니다. 같은 모양의 정의가 GHC 9.10.3에서 컴파일되는 것을 확인했습니다.
  • genGrammar: 같은 방식으로 p를 DiGrammar로 정하고, 시작 규칙 ("start", ...)과 나머지 규칙들을 목록으로 돌려줍니다.

용어에 관한 짧은 주의. 원문은 이 둘을 "invariant profunctors"라고 부릅니다. 1쪽에서 말했듯이 하스켈에서 "불변(invariant)"은 보통 양방향 함수가 모두 필요한 타입을 뜻합니다. DiRegEx와 DiGrammar는 두 매개변수를 모두 쓰지 않으므로 유령(phantom) 또는 상수 프로펑터라고 부르는 것이 정확합니다.

인스턴스가 어떻게 생겼을지. 원문은 인스턴스를 연습 문제로 남겼으므로 다음은 이 시리즈의 해석입니다. DiRegEx에서 anyToken은 AnyChar, >*<는 Sequence, <|>는 Alternate, empty는 Fail, manyP는 KleeneStar, inClass는 InClass, 리터럴은 Terminal이 되도록 인스턴스를 정의하면, 문법을 해석한 결과가 그 문법이 받아들이는 언어의 정규 표현식이 됩니다. 정규 술어가 클래스의 메서드였던 이유가 여기서 드러납니다. DiGrammar는 rule name g를 "규칙 (name, g의 정규 표현식)을 집합에 넣고 자신은 NonTerminal name이 된다"로 덮어써서, 문법을 규칙 이름별로 나누어 모읍니다. ruleRec도 덮어써서 재귀 규칙이 끝없이 펼쳐지지 않게 해야 합니다.

자기 자신을 기술하는 문법

원문은 정규 표현식 문법 regexGrammar, 문법 생성기 genGrammar, 프린터 생성기 genShowS를 합치면, 정규 표현식으로 확장한 BNF(regexBNF)로 정규 표현식 자신의 문법을 출력할 수 있다고 말합니다.

>>> printGrammar regexGrammar
start = \q{regex}
alternate = \q{sequence}(\|\q{sequence})*
any = \.
atom = \q{nonterminal}|\q{fail}|\q{class-in}|\q{class-not-in}|\q{category-in}|\q{category-not-in}|\q{char}|\q{any}|\q{parenthesized}
category = Ll|Lu|Lt|Lm|Lo|Mn|Mc|Me|Nd|Nl|No|Pc|Pd|Ps|Pe|Pi|Pf|Po|Sm|Sc|Sk|So|Zs|Zl|Zp|Cc|Cf|Cs|Co|Cn
category-in = \\p\{\q{category}\}
category-not-in = \\P\{\q{category}\}
char = \q{char-literal}|\q{char-escaped}
char-escaped = \\[\$\(\)\*\+\.\?\[\\\]\^\{\|\}]
char-literal = [^\$\(\)\*\+\.\?\[\\\]\^\{\|\}]
class-in = \[\q{char}*\]
class-not-in = \[\^\q{char}*\]
expression = \q{terminal}|\q{kleene-optional}|\q{kleene-star}|\q{kleene-plus}|\q{atom}
fail = \\q
kleene-optional = \q{atom}\?
kleene-plus = \q{atom}\+
kleene-star = \q{atom}\*
nonterminal = \\q\{\q{char}*\}
parenthesized = \(\q{regex}\)
regex = \q{alternate}
sequence = \q{expression}*
terminal = \q{char}+

printGrammar는 원문에 정의가 없습니다. genGrammar regexGrammar가 만든 (이름, RegEx) 목록의 각 RegEx를 genShowS regexGrammar로 출력해 이름 = 표기 꼴로 늘어놓는 함수로 짐작됩니다. 몇 줄을 읽어 보겠습니다.

  • start = \q{regex}: 시작 규칙은 규칙 regex를 가리킵니다. ruleRec "regex"로 만든 최상위 규칙입니다.
  • alternate = \q{sequence}(\|\q{sequence})*: 연접 하나, 그 뒤에 "(|와 연접)"이 0번 이상입니다. \|는 이스케이프된 글자 그대로의 |입니다. chainl1이 "1개 이상을 구분자로 이은 것"이므로 이런 모양이 됩니다.
  • any = \.: 글자 그대로의 마침표입니다. .은 예약 글자이므로 이스케이프되었습니다.
  • atom = ...|\q{char}|...: 원자 갈래 중 _Terminal . _Cons >?< charG >*< pure ""는 \q{char}로 나타납니다. pure ""는 아무것도 출력하지 않기 때문입니다.
  • category = Ll|Lu|...|Cn: 30개의 범주 약어가 선택으로 이어졌습니다.
  • category-in = \\p\{\q{category}\}: 글자 그대로의 역슬래시(\\), 글자 p, 글자 그대로의 {(\{), 규칙 category, 글자 그대로의 }입니다.
  • char-escaped = \\[\$\(\)\*\+\.\?\[\\\]\^\{\|\}]: 역슬래시 하나 다음에 예약 글자 중 하나입니다. 문자 클래스 안의 글자도 모두 이스케이프되어 출력되었습니다. charG로 출력했기 때문입니다.
  • char-literal = [^...]: 예약 글자가 아닌 글자 하나입니다.
  • sequence = \q{expression}*, terminal = \q{char}+: 연접은 식 0개 이상, 단말 기호는 글자 1개 이상입니다.

이 출력은 그것이 기술하는 바로 그 표기법(regexBNF)으로 적혀 있습니다. 문서 전체는 여러 줄의 이름 = 식 목록이므로 그 자체가 RegEx 값은 아니지만, 각 규칙의 오른쪽(= 뒤의 식)은 regexGrammar로 다시 파싱할 수 있는 같은 표기법입니다. 하나의 정의 regexGrammar에서 파서(genReadS), 프린터(genShowS), 그리고 문법 문서(genGrammar)가 모두 나왔습니다. 부제의 세 단어 "Parsers, Printers & Grammars"가 하나로 묶인 장면입니다.

이 쪽이 글의 목표에 기여하는 바

이 절은 글의 목표를 완성합니다. Grammatical은 지금까지의 모든 능력을 묶은 인터페이스이고, Grammar a는 그 인터페이스로 쓴 해석기 독립적인 기술입니다. 같은 기술을 Parsor로 해석하면 파서, Printor로 해석하면 프린터, DiRegEx나 DiGrammar로 해석하면 정규 표현식이나 문법 문서가 됩니다. 새 해석기가 필요하면 새 인스턴스를 쓰면 됩니다. 원문은 마지막 절에서 이 생각을 어디까지 넓힐 수 있을지 묻습니다.

정리

  • Grammatical은 부분 디스트리뷰터이면서 Char 토큰을 다루고 문자열 리터럴을 p () ()로 받아들이는 인터페이스이며, 정규 술어(inClass 등)와 규칙(rule, ruleRec)을 메서드로 가집니다. 기본 구현은 이름을 무시하지만, 다른 해석기는 이름을 오류 메시지나 문법 문서에 씁니다.
  • 양화 제약 forall t. t ~ p () () => IsString t는 구분자 자리의 리터럴 타입을 p () ()로 정해 주는 대신, 진짜 String 리터럴에는 타입 표시가 필요할 수 있다는 부작용이 있습니다.
  • Grammar a = forall p. Grammatical p => p a a는 파이널 태그리스 인코딩이며, 생성기는 인스턴스를 고르는 일입니다. genReadS는 파서, genShowS는 프린터입니다.
  • regexGrammar는 정규 표현식의 AST RegEx를 프리즘(makePrisms)과 조합자로 기술하며, 선택, 연접, 반복, 원자의 우선순위를 규칙의 층으로 표현합니다. 원문 코드에는 컴파일 순서, pure "", 원자 단말 기호의 출력 같은 거친 부분이 있습니다.
  • DiRegEx와 DiGrammar라는 유령 프로펑터로 같은 정의를 해석하면, 정규 표현식 문법이 자기 자신의 표기법으로 출력됩니다. 하나의 정의에서 파서, 프린터, 문법이 모두 나옵니다.
