자바/스프링으로 개발된 시스템을 NodeJS로 마이그레이션 해볼까 하는 생각을 전부터 하고 있었는데 이번에 진행을 해봤다. AI를 사용해서 스프링 백엔드로 개발했던 내 새로운 블로그/위키 서비스가 대상이었다. 개인 프로젝트로 만들어서 혼자, 혹은 지인들과만 쓰는 서비스는 여럿 있지만 그 중에서 공개적으로 가장 많은 방문자를 가진 서비스이고, 틈날 때마다 이런 저런 기능을 붙여나가며 다양한 실험을 하는 코드라 이 정도라면 해볼만 하겠다 싶었다.

AI 개발 시대가 되었는데 굳이 스프링을 계속 쓸 필요가 있을까, 스프링에서도 표현력과 가독성이 좋다는 코틀린을 고집할 필요가 있을까, 심지어 무거운 JVM 기반 기술을 계속 사용할 필요가 있을까하는 질문을 작년 말부터 가지고 있었다. 점점 똑똑하게, 언제부턴가는 내가 굳이 코드를 열어볼 필요도 없다고 느껴지는 결과를 내는 AI라면 인간 개발자가 더 일을 잘 하도록 만들어진 기술과 언어를 꼭 고집하지 않아도 되는 것 아닌가 하는 생각이 들었기 때문이기도 하고, 얼마전 만난 한 유명 개발자가 노드로 바꾸면 JVM용 서버 하나에 노드 인스턴스 30개는 돌릴 수 있다고 한 이야기를 들었던 기억도 있고 해서 확인을 해보고 싶기도 했다.

AI가 코드를 뽑긴했지만, 나름 스프링에서 잘 쓰이는 기술과 아키텍처, 패턴 등을 잘 적용해서 개발하도록 면밀히 조율해서 만들었던 거라, 이걸 기술 마이그레이션을 할 때 얼마나 정확하게 전환이 될 수 있을지, 대응되는 기술 조합은 어떻게 될지가 궁금했다.

그래서 첫 단계는 마이그레이션 의도를 AI에게 던져주고 가능한 노드 기반 기술을 살펴보고 장단점을 비교해서 알려달라고 했다. 단지 노드 계열에서 많이 쓰이는 기술이기 때문만이 아니라, 스프링으로 작성된 코드를 마이그레이션 할 때 가능하면 1:1에 가깝게 구현 코드의 의도와 기능이 최대한 반영되기 좋은 구성을 찾도록 했고, 결과적으로 NestJS + MikroORM을 기본 구성으로 선택했다. 이 구조가 스프링으로 된 코드와 최대한 유사한 방식으로 코드를 구성할 수 있는 방식이라는 설명을 받아들였다.

그리고 계획을 세웠다. 전환 방식, 배포 토폴로지, 스키마 관리, 토큰 암호화, 테스트, 그리고 각종 검증까지.

10개 이상의 마이그레이션 계획 문서가 작성됐고, 며칠 전 잠에 들기 전에 goal을 설정하고 운영 서버 배포만 제외하고 모든 작업을 진행하라고 해서 아침에 최종 결과를 확인했다.

그리고 몇 턴의 테스트와 놓친 부분을 다시 고치는 과정을 거쳐 운영서버 배포와 롤백 리허설을 진행하고, 그리고 오늘 최종 전환 완료. 잘 동작한다.

그 동안 진행했던 작업 내용을 블로그 글로 써보자고 했다. 어떤 검증을 해야할지 고민하고, 적용하면서 문제를 찾아나가는 과정이 흥미롭다. 이 재밌는 걸 대부분 AI가 스스로 즐긴 것 같아서 그게 얄미울 뿐이다.

9시간이 사라질 뻔했다 — Spring Boot 백엔드를 NestJS로 옮긴 이야기

메모리 절약과 언어 통일을 위해 Spring Boot에서 NestJS로 마이그레이션한 경험

옮기기로 한 이유

Toby's Codex의 백엔드는 Spring Boot로 시작했다. Java 25, JPA, Flyway. 잘 돌아갔다. 문제는 이 블로그가 도는 서버가 메모리 1.8GB짜리 작은 EC2 인스턴스라는 점이었다.

JVM 하나가 600MB 가까이 쓰고 있었다. free -m을 쳐보면 남은 메모리가 82MB일 때도 있었다. 언젠가 터질 것 같은 숫자였다.

프론트엔드는 이미 Next.js와 TypeScript다. 백엔드도 Node로 옮기면 언어가 하나로 통일되고 메모리도 줄어든다. 그래서 NestJS로 옮기기로 했다.

계획을 세우고 보니 규모가 만만치 않았다.

항목 수량
Java 프로덕션 코드 약 9,000줄
컨트롤러 26개 (엔드포인트 99개)
JPA 엔티티 17개
Flyway 마이그레이션 27개

혼자 운영하는 블로그치고는 꽤 자란 상태였다.

가장 무서웠던 것

포팅을 시작하기 전에 코드를 훑다가 등골이 서늘해진 지점이 있었다.

java

@Transactional
public PostDetailResponse publishPost(Long id) {
    Post post = postRepository.findById(id).orElseThrow(...);
    post.publish();                    // 상태만 바꾸고 끝
    return PostDetailResponse.from(post);
}                                      // save()가 없다

save()를 부르지 않는다. 그런데도 DB에 저장된다. Hibernate가 "이 객체 아까랑 달라졌네?" 하고 알아서 UPDATE를 날려주기 때문이다. 이걸 dirty checking이라고 한다.

이런 코드가 23곳 있었다.

무서운 건 이게 잘못 옮겨졌을 때의 증상이다. 에러가 안 난다. 응답은 200이고 본문도 멀쩡하다. 화면에는 "발행 완료"라고 뜬다. 그런데 DB에는 아무것도 안 쓰였다. 새로고침하면 원래대로 돌아와 있다.

조용히 실패한다. 이게 제일 무섭다.

그래서 검증을 먼저 설계했다

코드를 짜기 전에 "어떻게 틀렸다는 걸 알아낼 것인가"부터 정했다. 두 가지를 준비했다.

1. 골든 파일 — Java가 살아 있을 때만 뽑을 수 있는 것

슬러그 생성, 마크다운 처리, 읽는 시간 계산 같은 순수 함수들이 있다. 입력을 넣으면 출력이 나오는, DB도 네트워크도 필요 없는 함수들.

Java 쪽에 덤퍼를 하나 만들어서 입출력 쌍 1,289건을 JSON으로 뽑아뒀다. 그리고 TypeScript로 옮긴 함수에 같은 입력을 넣어 바이트 단위로 비교했다.

이 작업은 Java를 지우기 전에 해야 한다. 지우고 나면 정답지가 사라진다.

덕분에 미묘한 함정들을 잡았다. Java의 정규식 \s와 자바스크립트의 \s가 매칭하는 문자 집합이 다르다든가, 문자열 자르기가 이모지를 반쪽만 남긴다든가 하는 것들. 알고 보면 별거 아니지만, 모르고 지나가면 어느 날 슬러그가 이상하게 생성된다.

2. 섀도우 diff — 두 백엔드를 나란히 세우기

이게 핵심이었다.

        같은 요청을 양쪽에 보낸다
              ↓              ↓
      Spring :8080      NestJS :8081
              ↓              ↓
        MySQL codex_a   MySQL codex_b
        (운영 DB 복제본) (운영 DB 복제본)

운영 DB를 덤프해서 익명화하고, 복제본 두 개를 만들었다. 각 백엔드에 하나씩 물렸다. 그리고 같은 요청을 양쪽에 쏴서 응답을 비교했다.

여기서 중요한 게 DB를 분리했다는 점이다. 응답만 비교하면 아까 말한 flush 누락을 못 잡는다. 응답은 200이고 본문도 같으니까. 요청을 보낸 뒤 DB 테이블 상태까지 비교해야 "얘는 진짜로 저장했고 쟤는 안 했다"가 드러난다.

읽기 요청 70건, 쓰기 요청 26건짜리 코퍼스를 만들어 돌렸다.

첫 실행: 58건 중 58건이 달랐다

100%였다.

당황했지만, 뜯어보니 대부분은 같은 원인 몇 개에서 나온 것이었다. 그리고 그중 하나가 이 마이그레이션에서 가장 아찔했던 발견이었다.

9시간

모든 날짜가 어긋나 있었다.

DB에 저장된 값        2026-08-09 08:59:25
운영 Spring이 응답    2026-08-08 23:59:25   ← 9시간 전
새로 만든 NestJS      2026-08-09 08:59:25   ← DB 값 그대로

원인은 이랬다. JDBC 접속 URL에 serverTimezone=Asia/Seoul이 붙어 있는데, Docker 컨테이너에는 타임존 설정이 없어서 JVM은 UTC로 돌고 있었다. MySQL 드라이버가 이 둘 사이에서 서울 → UTC 변환을 하고 있었던 것이다. 9시간.

즉 원래 운영 서비스가 DB 값을 9시간 밀어서 보여주고 있었고, 새로 만든 NestJS는 DB 값을 정직하게 그대로 보여주고 있었다.

정직한 쪽이 문제였다. 그대로 배포했으면 어떻게 됐을까? 어제 쓴 글의 작성 시각이 갑자기 9시간 뒤로 점프한다. RSS 발행일이 바뀐다. 구독자에게 나가는 알림 메일의 날짜가 틀어진다.

그런데 테스트는 전부 통과했다. 234개가 전부 초록불이었다. NestJS는 자기 기준으로 완벽하게 일관적이었으니까. 기준이 되는 Spring을 옆에 세워놓고 같은 요청을 쏴봐야만 보이는 종류의 버그였다.

이 하나 때문에 섀도우 diff를 만든 값을 다 했다고 생각한다.

비슷한 결의 문제가 6개 더 나왔다.

  • 읽을 때는 변환하는데 쓸 때는 변환하지 않는 비대칭 (새로 쓴 글만 9시간 과거로)
  • 검색 API만 유독 변환을 안 타는 문제 — 알고 보니 원래 서비스가 그랬다. 같은 글인데 목록에서 보는 시각과 검색 결과에서 보는 시각이 9시간 달랐다. 이건 고치지 않고 그대로 재현했다. 버그까지 똑같이 옮기고, 컷오버가 끝난 뒤에 고치기로 미리 정해뒀기 때문이다
  • Express가 자동으로 붙이는 헤더 3종. 그중 ETag는 브라우저에 304를 내보내서 상태 코드 계약을 깬다
  • 헬스체크 응답 본문이 문서에 적힌 것과 달랐다
  • 댓글 검증 실패 메시지가 엉뚱한 걸 안내했다. 닉네임을 안 썼는데 "100자 이내로 써주세요"라고 나왔다

수정을 마치고 다시 돌리니 96건 중 4건으로 줄었다. DB 상태 차이는 1밀리초짜리 시계 오차 하나뿐이었다. dirty checking 23곳이 전부 제대로 저장하고 있다는 뜻이었다.

문서를 믿지 말 것

이번에 크게 배운 게 하나 더 있다.

마이그레이션 계획 문서를 꽤 공들여 썼다. 결정 사항, 아키텍처, API 계약, 검증 전략, 컷오버 절차까지 6천 줄 넘게. 그런데 막상 운영 서버에서 하나씩 재보니 틀린 게 계속 나왔다.

  • "마지막 마이그레이션은 V26" → 실제로는 V27
  • "이메일은 Resend" → 실제로는 Brevo로 바뀌어 있었다
  • "컷오버 후 소셜 토큰 3개를 다시 입력해야 한다" → 그 토큰이 애초에 없었다. 운영 설정 테이블 8줄이 전부 평문이었고, 암호화된 토큰은 존재한 적이 없었다
  • "타임존은 영향 없다" → 위에서 본 그 9시간

마지막 것이 제일 뼈아팠다. 문서에 "이건 영향 없음"이라고 단정적으로 적어놨는데, 실측이 정반대였다. 확신을 가지고 틀린 것이다.

curl 한 번, SELECT 한 번이면 확인되는 것들이었다. 추론으로 채운 칸은 결국 다시 재봐야 한다.

리허설에서 배운 것

배포 전날, 롤백 연습을 해봤다. 실제로 NestJS를 운영에 올렸다가 다시 Spring으로 되돌리는 것이다.

스테이징 환경이 따로 없어서 운영에서 했다. 마음이 편하진 않았지만, 롤백 절차를 문서로 읽는 것과 실제로 해보는 건 다르다고 판단했다.

잘한 선택이었다. 배포 스크립트에서 두 가지가 깨졌다.

준비 작업 중에 서버의 환경변수 파일 권한이 666으로 되어 있는 걸 발견했다. 비밀번호와 API 키가 들어 있는 파일인데 누구나 읽고 쓸 수 있는 상태였다. 조였다. 그랬더니

  1. 마이그레이션 스크립트가 그 파일을 못 읽게 됐다. sudo를 붙였더니 이번엔 ECR 접근 권한을 잃었다. 권한이 사용자 계정에 붙어 있었는데 sudo로 넘어가면서 서버 역할로 떨어진 것이다
  2. Docker Compose도 그 파일을 못 읽었다

두 번째는 다행히 아무것도 하지 않고 멈췄다. 기존 컨테이너가 그대로 떠 있어서 서비스는 멀쩡했다. 안전하게 실패한 셈이다.

이걸 배포 당일에 처음 만났다면 새벽에 식은땀 흘리며 디버깅했을 것이다.

전환에 18초, 롤백에 26초가 걸렸다. 숫자를 손에 쥐고 나니 마음이 훨씬 편해졌다.

결과

컷오버는 18초 만에 끝났다. 헬스체크 첫 시도에 통과했다.

이전 (Spring) 이후 (NestJS)
Docker 이미지 947MB 723MB
컨테이너 메모리 595MB 220MB
서버 여유 메모리 396MB 1,146MB

여유 메모리가 1.1GB로 늘었다. 82MB까지 떨어지던 서버가 이제 한숨 돌린다.

그리고 배포 직후 제일 먼저 확인한 것.

컷오버 전   2026-08-08T23:59:25
컷오버 후   2026-08-08T23:59:25

날짜가 그대로였다. 이 한 줄 보려고 그 고생을 했다.

남은 이야기

아직 하루밖에 안 됐다. 재시작 0회, 에러 로그 0건이지만 일주일은 지켜봐야 한다고 생각한다. 롤백 경로도 그대로 열어뒀다. 이전 이미지에 태그를 박아뒀고, DB 스냅샷도 떠뒀고, Java 소스도 아직 지우지 않았다.

돌아보면 이번 작업에서 제일 잘한 건 코드를 잘 옮긴 게 아니라 틀렸다는 걸 알아낼 방법을 먼저 만든 것이었다.

테스트 234개가 전부 통과했을 때 솔직히 다 됐다고 생각했다. 그런데 진짜 문제는 그다음에 나왔다. 테스트는 "내가 예상한 게 맞는지"를 확인한다. 예상하지 못한 건 확인해주지 않는다.

옛 시스템이 아직 살아 있을 때, 그 옆에 새 시스템을 세워놓고 같은 질문을 던져보는 것. 그게 유일하게 "예상하지 못한 것"을 잡아주는 방법이었다.

혹시 비슷한 마이그레이션을 앞두고 있다면, 옛 시스템을 지우기 전에 이것만은 꼭 하시길. 정답지는 원본이 살아 있을 때만 뽑을 수 있다.
