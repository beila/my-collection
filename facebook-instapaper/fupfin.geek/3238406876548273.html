📘 Claude Code에서 한글이 "잡모", "로까잉"처럼 깨져 나오는 문제의 원인을 찾아 Anthropic에 공식 보고했습니다. 일주일간 1,200여 런의 통제 실험으로 확인한 내용을 정리해 공유합니다. 증상은 이렇습니다. AskUserQuestion/TodoWrite에서 "로그인"이 "로까잉"으로, "잘못"이 "잡모"로, "완료"가 "완릷"으로 바뀌어 출력됩니다. 에러도, 깨진 기호(�)도 없이 유효한 글자로 바뀐다는 게 특징입니다. Sonnet 5에서는 매우 빈번하고, Opus 5에서도 종종 등장합니다. 1/ 원인은 의외로 인프라가 아니라 모델의 출력 습관이었습니다. 모델이 툴 호출 JSON의 한글을 글자 그대로 쓰지 않고 \uXXXX 유니코드 번호로 "받아쓰기"할 때가 있는데, 이때 번호 한 자리를 틀리는 것입니다. 한글 11,172자는 번호가 빈틈없이 연속 배치되어 있어서 한 자리 오기가 에러가 아니라 옆의 멀쩡한 글자가 됩니다. "잘못"(\uc798\ubabb)을 쓰려다 \uc7a1\ubaa8로 틀리면 그대로 "잡모"가 되는 식입니다. 2/ 재현 시험으로 이슈를 확증했습니다. 같은 과제를 두 그룹으로 나눠 한쪽은 번호 표기를 유도하고 다른 쪽은 글자 그대로 쓰게 했더니, 번호 표기를 실제로 쓴 응답은 45건 중 45건(100%)이 손상됐고 글자 그대로 쓴 응답은 60건 중 1건(1.7%)에 그쳤습니다. 서로 다른 AWS 계정 두 개에서 Claude Enterprise , Claude code on Bedrock으로 동일하게 재현되어 특정 인프라의 문제가 아님도 확인했습니다. 조사 초기의 두 가설, 즉 "대화가 길어지면 깨진다"(컨텍스트 사용률 0~70,80%)와 "Bedrock에서만 깨진다"(1P/3P 유의차 없음)는 모두 아니었습니다. 3/ 해결은 지시문 한 줄입니다. CLAUDE.md 또는 Claude 메모리에 "툴 호출 파라미터(JSON)의 한글 등 비ASCII 문자열은 항상 리터럴 UTF-8로 작성하고, \uXXXX 유니코드 이스케이프로 표기하지 않는다"를 추가하면 됩니다. 번호 받아쓰기 자체를 차단해 오기 기회를 없애는 원리이고, 적용 후 빈번한 증상이 완전히 사라졌습니다. 솔직히 한마디 보태면, 이해하기 어려운 대목이 있습니다. 한국은 여러 지표에서 Claude Code 의 전 세계 최상위권으로 꼽히는 유료 사용자 시장입니다. 그런데 툴 호출에 한글을 넣으면 사실상 매번 깨지는 수준의 결함이, Sonnet 5에 이어 Opus 5까지 연달아 출시되는 동안 걸러지지 않았습니다. 영어 벤치마크 점수는 소수점까지 경쟁하면서, 최상위 과금 시장의 문자 체계가 제품 출시에서 부터 지금까지 깨지는 건 릴리스 QA 항목에 없었다는 뜻입니다.
