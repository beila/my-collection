For context, OpenAI's 4 new papers resolve 8 problems of the Top 500 Open Problems in Math list (LLM ranked, proofatlas.ai/open-problems/).

They include: #25 — Matrix-multiplication exponent equals two. The paper gives the exact exponent 9/4 over every field, refuting the conjecture.

#89 — Strongly polynomial linear programming (Smale’s ninth problem). The same paper also gives polynomial-time algorithms for #64 — Mean-payoff games, #65 — Parity games, #340 — Condon’s simple stochastic games.

#183 — Polynomial diameter bound for polytopes, #130 — Polynomial pivot rule for the simplex method, both refuted. Some pairs of vertices are superpolynomially far apart.

#137 — Erdős–Rado sunflower conjecture. For every fixed number of petals r, the paper proves the conjectured Cᵣᵏ bound.

(rankings post Riemann (#2) and VP vs VNP (#31)).

I can help explain big O, it's a super weird concept:

Let's say you want to know the speed of an algorithm. That's a hard thing to do. First, there's the problem that it's different speeds on different computers. Then there's the problem that speed will be relative to the size of the thing you are processing. Then, there's the issue that what you really want is easy ways to compare algorithms, so you don't really want the exact speed of an algorithm but a quick estimate. Finally, you want to make it mathematically provable.

Big O is so weird because of the last two. If you want a quick estimate, you probably want it to be handwavy. But if you want it mathematically provable, then you don't. It feels like these two should be impossible to fit together. But Big O makes it work by putting algorithms into different buckets. If two algorithms are in the same bucket, you handwave minor differences in speed. But which bucket that it's in is mathematically provable.

The way Big O works is that you build an equation of how long it takes given some input with size n, then you take the largest term and you ignore any constant multipliers and smaller terms, with precise mathematical terminology that lets you do so. So the run time of some algorithm is 3 * n^2 + n, then it would be O(n^2), as that is the largest term.

The perfect place to see this in action is in sorting algorithms. They tend to fall into three main buckets - O(n^2) for slow algorithms that are easy to create, O(n lg n) for fast algorithms that are optimal, and O(n) for super fast algorithms that only work if the data you are sorting has particular properties. So simply by knowing which of these three buckets your sorting algorithm is in, I can tell if you are using a bad algorithm, using a good one, or making assumptions about your data that may or may not be true.

2026-11-25 · comment
While "Θ(n^2.25)" is better, imho it's still misleading. Matrix multiplication is a problem that can be solved by algorithms whose running times (under various conditions) are functions. "Being Θ(n^2.25)" is a property of a function, not an algorithm, and not a problem. There are matrix multiplication algorithms commonly used whose worst-case running times are most certainly not Θ(n^2.25) (namely, all of them known before last month). One could precisely say that "an optimal algorithm for matrix multiplication has worst-case running time Θ(n^2.25)" or "optimal matrix multiplication takes time Θ(n^2.25)", though personally I think that the paper's formulation is cleanest: the matrix multiplication constant is ω = 2.25.

This may seem pedantic, but misconceptions about the meanings of big-O/Theta/Omega notation are very common (e.g., conflating them with "best/average/worst case" or other such nonsense) and they muddy the waters.
