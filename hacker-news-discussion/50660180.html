2026-11-26 · comment
In some ways it's better, in some ways it's worse.

It's certainly easier than ever to spin up a VPS/cloudflare proxy and deploy. Agents can pretty much do that end to end.

The bigger issue is you're then accountable for keeping up with security. Previously that meant using fail2ban and running a system update every few months. Now it means patching within 24hrs of a CVE9+ dropping, which is happening at an accelerated rate.

It got so bad during October I made firefighter.sh as a joke (a root-permissioned agent that continuously monitors for CVEs and patches your system live as soon as they drop - it's a security nightmare given the nondeterministic aspect of AI), but I'm actually starting to come around to the idea for my non-critical servers.

What worked for me is to almost never let an agent edit my working copy of a project, however, to regularly prompt it for review, or to implement something I want in a scratch copy that I then use as a reference.

It's almost like working pre-AI, except I always have very relevant documentation available.

I know if what I want to do is possible or not while retaining control because when implementing the feature (by hand) I understand what I'm typing and make edits if it doesn't make sense for me.

The rule is, if I don't understand it I'm skipping it, and I'll see what breaks and maybe re-prompt to ask, but never let the AI do the edits. Always prompt for explanation and never action.

To me, it's the best way to upgrade your workflow without losing ownership of your projects.

For my VPS infrastructure, I’ve also started building my own Debian-based bootc image (after thinking about it for some time).

I still remember what updating a service used to look like: bumping the version and adjusting the Docker Compose file on my laptop, pushing the changes to the Git remote, SSHing into the server, pulling the changes, and finally deploying them. Now, a single Git push is enough. If a push is even necessary.

Both of these cases are a great fit for Ansible or the alternatives. Given how much the author leans towards the idea of storing configuration in repos, it's a bit odd I haven't seen a single mention of configuration management tools.

Generate Ansible playbooks, set up a simple CI/CD workflow and you don't need an agent to do the same manual labor every time - it just needs to bump the versions and make a PR/push. Saves a great deal of tokens.

I have a feeling that AI prices are only going to go up and such 'frivolous' usage when agents repeat a lot of unnecessary actions is going to become an anti-pattern (unless you have unlimited funds).

It's not a perfect flow. Certain actions require you to use the Synology webui, which is painful and slow at times, but I haven't found a way to give agents access to that, while being able to monitor what they do.

I've also been having luck with agents configuring things related to kubernetes. I'll spin up a cluster in the cloud with something like digitalocean, and then the agent can deploy apps to it and monitor things. Kubernetes is much easier to give better scope access to certain resources, so I'm slowly trying to migrate things from Synology over to kubernetes.

Anything I don't feel like managing myself, I just use pikapods for hosting. If I need more control over it, I migrate it over to either my NAS or to kubernetes.
