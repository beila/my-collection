2026-11-17 · comment — Super impressive work by Calif as usual.

The exploit conditions are very specific but there are still going to be a lot of hosts impacted. We at Semgrep published some free detection scripts here: github.com/semgrep/detection-scripts/tree/main/CVE-2...

They look for these five conditions:

  * HotSpot VM: any OpenJDK build, Oracle JDK, or GraalVM JDK. Only HotSpot generates the stub. OpenJ9 and GCJ are OK. Azul Prime (Zing), which replaces C2 with its own JIT, and any VM name not recognized as HotSpot are [?], never [!].
  * x86-64 JVM on an x86-64 host.
  * Version 17.0.6 or later, not at or above a version listed in FIXED_IN, and no newer than the newest releases checked (see below). Newer versions are [?]: they may carry the fix.
  * The JVM reports avx512_vbmi and avx512bw, and UseAVX >= 3.
  * Base64 intrinsics are on and C2/JVMCI can compile. These turn it off: -XX:-UseBASE64Intrinsics, -XX:DisableIntrinsic=_base64_decodeBlock, -Xint, -XX:TieredStopAtLevel below 4.

2026-11-18 · comment — For anyone who cares, I have a solution "for now":
github.com/Qbix/proxy/blob/main/java4shell.md

When PHP2shell was announced, before the patches were available, I wrote a proxy to sanitize input. You should have an input-sanitizing proxy in front of your app servers anyway instead of waiting for patches for as-yet-undiscovered CVEs.

PHP < 8 doesn't have patches coming. It's either the proxy or be pwned. Some our honeypot machines running PHP 5 got infiltrated with full chained kernel-level exploits. The ones with the proxy didn't. Which one do you want to be?

github.com/Qbix/proxy -- now updated to help mitigate java4shell

Having said that, my proxy approach wouldn't fully protect ALL Java apps in this case, because:

A Java program that opens a TLS connection to a malicious server can be compromised, even if it exposes no service of its own.

The problem is that you can't intercept and "heal" TLS connections with a proxy, unless you also spoof the TLS certificates. However, since most Java apps don't pin certs, a workaround is using /etc/hosts and a CA cert added in cacerts. Then the proxy approach works even on outbound traffic. And you don't have to wait for the patches.

  1. Add maliciousserver.com -> 127.0.0.1 (or proxy IP) in /etc/hosts
  2. Java app resolves the hostname, connects to your proxy on 443
  3. Proxy presents a cert for maliciousserver.com signed by your local CA
  4. JVM checks: right hostname, trusted CA? handshake succeeds
  5. Proxy connects to the real server (using its own resolver that bypasses /etc/hosts, or the real IP directly)
  6. Normalizes Base64 in the response (assuming Calif relies on a wacky base64)
  7. Relays to Java client (safe)
so what you'd do is:

  1. Generate proxy CA cert
  2. Install in JVM truststore (keytool)
  3. /etc/hosts entries for known hostnames
  4. forward_proxy config block (port, ca_cert, ca_key)
  5. You have three options for routing: 
    HTTPS_PROXY env, 
    JVM flags (-Dhttps.proxyHost), 
    or iptables REDIRECT (covers code that ignores proxy vars)
  6. Start qbixproxy
  7. Verify with curl
The usual disclaimers... lock down the executable, removing any ability to read or write files, only pass traffic through like a proxy. Investigate the repo yourself, with your own Claude or ChatGPT etc. The repo even has links to pre-fill the prompts to do just that.
