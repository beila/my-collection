jitl · 2025-04-12 · comment — My favorite move is to use a typed scripting language like TypeScript or Lua to generate static JSON or YAML. This approach is orders of magnitude better than using a templating system like Jinja2 or Go templates to add power, it tends to be very well understood by machines and humans, have good tooling (since you’re using a normal programming language), you can write tests if things are getting complicated.

The important bit is to commit the outputs, and enforce the outputs are up-to-date in CI. This eliminates chicken-and-egg problem of “oh I need some config to boot up my scripting language, but my scripting language produces that config” but more importantly it makes the concrete config also easily reviewable and access to it is instant and always available. Plus it proves the config compiles and prevents drift where the config may be different between developer’s machines and CI.

jitl · 2025-04-12 · comment — Yeah probably the biggest downside is that documentation and examples for the output config format are harder to understand & apply to the source scripting language.

It’s hard for me to imagine an automatic backflow option from config file to source script that doesn’t require a baroque/complicated build system.

I can imagine it if you have three components: input data, transform in script language, output data — write your transform as prolog (losing points for strangeness) or using invertable function composition in a normal language (also losing points for forcing big brain thinking when you just wanna config). But either way you end up being able to run the transform in inverse, tada.

But if you want to only have two components: script language & output, actually flowing changes to output back into script language source requires both an inverse compiler to manipulate the source AST, and an inverse interpreter to rewind the program from its output.

I’ve also considered implementing sourcemaps, which automates go-to-definition for spans of text in the output but doesn’t actually flow the data back there. But again the issue w/ sourcemap is your scripting language input needs to know the precise origin location of each AST node. In Python there’s sys.settrace but we also need to tag data as it leaves its declaration scope with the origin file location… it’s just tricky to do without stuff starting to get nutty.

I think Rust, lisps, Swift - languages with macros - probably would support that the best, but I’m still not sure if it would end up being helpful enough to outweigh the complexity of manual annotation and such.

inactive-user · 2025-04-12 · comment — I would split the last level into two:

5 - Turing-complete but sandboxed. Your configuration file might be written in Lua, but it's still limited to the primitives defined by the host application. The main difference from (4) is that it's more difficult to statically analyze, but that might not be a fatal problem, and the advantage over a less-common language like Starlark is access to a deeper developer tooling ecosystem.

6 - Turing-complete and unconstrained. Your configuration file can access the filesystem (e.g. inspecting /etc/lsb-release) and the network (e.g. querying its own DNS hostname to figure out the local IP address). Popular implementations are Bourne shell, Ruby, and Perl. Depending on who you ask this is either the best possible way to configure a complex system (such as the Unix boot process) or a newly-invented layer of hell.

fanf · 2025-04-12 · comment — There’s another level 3.5 which is a roughly hierarcial structure with a scattering of environmental awareness: often includes, maybe variable interpolation, maybe conditionals.

These level 3.5 languages tend to be quite ad-hoc, eg configs for Apache httpd, nginx, OpenSSH. UCL was intended to fit in this category and to try to help it converge on something sensible.

Levels 3 and 4 are often adopted as reactions against level 3.5. There’s a cycle of reincarnation, where a program starts out with a simple config, but it gets more and more ad-hoc programming features; a successor goes for full programmatic config, but that proves hard to debug, resistant to static analysis, and/or difficult for simple cases; another successor replaces unified programmatic configuration with a separation between scripted config generation and simple config descriptions; the scripting layer is left out for simple situations, but the simple config proves to be too simple in lots of cases, so it grows ad-hoc programming features.

There’s another pressure that can drive this cycle: the need to adjust complicated run-time behaviour – separate from the need to assemble a config in a complicated manner at or before startup. The run-time behaviour can start as a few knobs but it easily turns into an ad-hoc rules engine. This happens in mail server address rewriting, web server virtual host matching, openssh, and many other places. You can solve both static config complexity and runtime behaviour complexity with an embedded scripting language such as Tcl or Lua. Or even completely invert control and make your program into a scripting framework like Emacs or XUL. The reaction against scripting is often something much simpler with a tasteful selection of useful features. Which then grows, maybe using a plugin architecture to accommodate weird requirements.

andyc · 2025-04-12 · comment — Hm I also made a taxonomy of 5 categories of config languages, which is a bit different - https://github.com/oils-for-unix/oils/wiki/Survey-of-Config-Languages

  1. Languages for String Data
  2. Languages for Typed Data
  3. Programmable String-ish Languages
  4. Programmable Typed Data
  5. Internal DSLs in General Purpose Languages

Their taxonomy is:

  1. String in a File
  2. A List
  3. Nested Data Structures
  4. Total Programming Languages
  5. Full Programming Language

So the last category (#5) is the same, the first one is different (they start with plain files), and the middle is a bit different.

FWIW I don't think "Total" is useful -- for example, take Starlark ... The more salient things about Starlark are that it is restricted to evaluate very fast in parallel, and it has no I/O to the external world. IMO it has nothing to do with Turing completeness.
